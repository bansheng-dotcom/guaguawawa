# 段落标签驱动审查协议

## 原则

不要让每个段落遍历所有文风问题。每段先判定功能标签，再按标签触发对应审查项。全文层面再检查链路是否完整。

目标是保留文章节奏：不是把每段都改成“问题-证据-动作-边界”的小报告。

## 段落标签

| 标签 | 段落职责 | 重点审查 | 不该强求 |
|---|---|---|---|
| `problem_entry` | 提出真实问题、现象、困惑、业务背景 | 是否从真实问题进入；是否避免百科定义；读者是否知道为什么要看 | 不强求动作建议和完整证据 |
| `misconception` | 指出常见误区、模板拆法、AI 式理解 | 是否明确指出常规理解为什么不够；是否服务后文判断 | 不强求完整解决方案 |
| `judgment` | 给出作者判断、取舍、阶段结论 | 判断是否明确；是否有生成路径；是否区分事实和推断 | 不强求长解释和案例 |
| `evidence` | 提供数据、案例、事实、观察 | 是否支撑判断；是否避免堆数据；是否能转成业务含义 | 不强求结尾升华 |
| `mechanism` | 解释因果、业务机制、系统关系 | 是否说明“为什么”；是否把指标和场景串起来 | 不强求清单化 |
| `transition` | 从上一层问题推进到下一层 | 是否推动下一层分析；是否不是空泛过渡 | 不强求高信息密度 |
| `action` | 落到策略、看板、专项、复盘、资源配置 | 是否可干预；对象、动作、指标、节奏是否具体 | 不强求重新论证 |
| `boundary` | 限制外推、说明未验证点、承认不可解问题 | 是否说明适用范围；是否避免万能结论 | 不强求新结论 |
| `summary` | 阶段性收束、回扣主线 | 是否总结当前阶段；是否引出下一步 | 不强求覆盖所有问题 |

## 局部审查输出

审查 agent 对每段只输出与标签相关的问题：

```json
{
  "paragraph_id": "p03",
  "label": "judgment",
  "secondary_labels": ["mechanism"],
  "expected_function": "给出作者阶段性判断，并说明判断来自哪一层拆解",
  "checks_applied": ["judgment_has_path", "fact_inference_action_boundary"],
  "issues": [
    {
      "issue": "判断出现得太突然，缺少从业务现象到作者取舍的生成路径",
      "severity": "medium",
      "repair_hint": "补一句这个判断来自哪个指标变化或业务场景，而不是直接下结论"
    }
  ]
}
```

## 全文链路审查

全文不要求每段都具备所有元素，但整篇文章要尽量具备：

```text
真实问题
-> 常见误区
-> 作者判断
-> 指标/概念拆解
-> 业务场景翻译
-> 阶段性结论
-> 可干预动作
-> 边界或下一步
```

缺口要作为跨段问题输出，例如：

```json
{
  "issue": "全文有判断和证据，但缺少可干预动作段",
  "scope": "cross_paragraph",
  "repair_node_hint": "style-harmonizer",
  "repair_hint": "在结尾补出下一步看什么、谁做什么、用什么指标复盘"
}
```

## 修改原则

修改 agent 必须遵守：

- 只修该段标签职责内的问题。
- 不把每段都补齐所有元素。
- 不新增未经证实的事实、数据、案例。
- 如果缺口属于全文链路，优先交给全文 style-harmonizer 或人工确认。
- 如果一个段落标签不明确，先调整段落功能，再谈文风润色。

## 渭河文风特例

使用渭河文风时，段落标签的优先级是：

1. 真实问题和误区要尽早出现。
2. 判断段必须体现作者取舍，不能只是中性总结。
3. 证据段必须翻译成业务场景，不能停留在指标之间。
4. 动作段必须区分可解释和可干预。
5. 边界可以短，但不能完全没有。
