## 7.1 状态上报（s07/status）





**RAG 映射**（对齐 status-report 语义层）：


`on_track → G（绿） / at_risk → A（黄） / behind → R（红） /


missed → R（红）`。missed 不是「黄偏红」，是**当场拦下**


（已验证负例）——错过的里程碑没有「观察中」状态。





- **attention 排序**：黄红项目按影响度排关注清单；


- **跨角色依赖识别**：`\br\d{2}\b` 正则扫依赖描述，


  句中出现的 r06/r07 依赖被识别（已验证：正则不能锚定 `^$`，


  否则匹配不到句子中间的角色号）。





## 7.2 分波编排（s07/plan）





1. **Kahn 分波**：按依赖层分波次，同波内可并行；


2. **人工审批门**：`p0_change / funding / redline` 三类任务


  **未获审批不许进波**（已验证负例：红线未获批被拦）；


3. **波负载预警**：每波负载 ≤24h，超了说明波次切分有问题；


4. **依赖环**：成环即拦并报环。





已验证算例：三波编排，红线人工门识别，wave_2 负载 16h 达标。





## 7.3 依赖图诚实门禁（s07/graph）





对齐 graphify 的诚实规则：


- **引用完整性**：边引用的节点必须存在——**无中生有检测**，


  声明了不存在节点的边当场拦（已验证负例）；


- **置信三态**：`EXTRACTED（原文可证）=1.0 / INFERRED（推断）


  0.4-0.9 / AMBIGUOUS（存疑）0.1-0.3`，置信分越界即拦


  （已验证负例）——每条边标注「这关系是从哪来的」；


- **god 节点**：度 > 20%×节点数的节点标记为 god——


  什么都依赖它 = 改一处崩全局，拆解候选；


- **深度上限**：BFS 3 / DFS 6，实测可达深度超限报警；


  5000 节点以上语料建议先分区再建图。





已验证算例：6 节点 5 边、可达深度 5 ≤ DFS 上限。





## 7.4 与 R01 编排器的分工





R01 是**公司级**编排（意图→任务卡→20 角色路由）；


R02 的 plan 是**项目群级**编排（已派任务→分波→审批→负载）。


R02 不做角色路由，只做执行排序与门槛——「怎么排」不越权到「拆给谁」。





## 7.5 实战踩坑





- 置信三态的意义是**防止模型幻觉出依赖关系**——


  图里的每条 INFERENCE 都要能答「凭什么推断的」，答不出降 AMBIGUOUS。


- god 节点是**拆解信号**不是缺陷本身：先看它承担的是否单一职责，


  再决定拆或豁免（有些 hub 节点如「部署」天然高连接度）。


- 审批门只拦**进波**，不拦已在波内的执行——审批状态变更


  应在波次重排时生效，而不是中途抽任务。


- RAG 阈值、审批门类别、god 节点比例、深度上限以


  `experience/thresholds.json → portfolio` 为准。
