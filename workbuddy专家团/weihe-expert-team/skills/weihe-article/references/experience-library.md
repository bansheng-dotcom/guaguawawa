# Article Experience Library

## 2026-05-22 - `supervisor-mode` 小白开场逻辑修正

### 问题

`supervisor-mode` 的前几版开场直接进入：

- `Supervisor 是什么`
- `它和 Router 的区别`

这条写法对熟悉多 Agent 术语的人可读，但对小白不成立。读者还不知道：

- 为什么会突然提 `Supervisor`
- 多 Agent 系统到底出了什么问题
- 解决这个问题是不是只有一种办法
- `Router / Pipeline / Swarm / Supervisor` 这些词属于什么层面的概念

结果是：

- 名词解释本身是对的
- 章节顺序却不对
- 读者会觉得作者在回答一个自己还没提出的问题

### 修正后的正确顺序

面向小白写这类“架构模式解释文”时，前 `3-4` 节优先采用下面的叙事顺序：

1. 先讲问题  
   说明系统为什么会乱。不要先抛模式名词，先让读者理解真实痛点：交接点变多、状态容易丢、误差会放大、返工成本会上升。

2. 再讲常见解法  
   告诉读者，解决这种混乱不是只有一种办法。先引出 `Router / Pipeline / Swarm / Supervisor`，把它们解释成几种不同的组织方式，而不是几颗零散术语。

3. 再讲差别和知识图谱位置  
   说明这几种模式分别解决什么层的问题：入口分配、顺序执行、分散协作、全局控制。让读者知道它们在同一张多 Agent 架构地图里，但职责不同。

4. 最后才聚焦本文主角  
   在读者已经知道“有好几种解法”的前提下，再讲为什么这篇文章重点讨论 `Supervisor`，以及它和 `Router` 的边界。

### 可复用判断

如果一篇知识科普文章同时满足下面两个条件，就优先套用这条经验：

- 主题里出现多个陌生架构名词
- 目标读者是第一次接触该主题的小白

### 失败信号

只要出现以下任一情况，就说明前几节顺序大概率写反了：

- 读者会问“为什么突然开始解释这个词”
- 第二节已经在比较两个术语，但第一节还没解释整体问题
- 文章在回答“模式差别”，但读者还不知道“为什么需要这些模式”
- 名词解释正确，阅读阻力仍然很大

### 执行动作

- 不要上来定义术语
- 先把“问题 -> 常见解法 -> 差别 -> 为什么重点讲这个”走完
- `Router vs Supervisor` 这种边界解释，放在“模式地图”之后，不放在开头
- 如果前几节仍然难读，优先检查是不是顺序问题，而不是先改文风
