# 批注经验库

## 抽象工程概念要从业务案例进入

更新时间：2026-06-12

适用场景：BaseAgent、模板方法、工作流、Agent 架构、输出约束、校验机制等抽象工程概念。

### 经验

读者第一次接触抽象工程概念时，不应该从概念定义、类继承、模式名称进入。应该先从读者熟悉的业务产物进入，再用一个可操作案例把问题讲出来。

例如讲 BaseAgent，不要先写：

> BaseAgent 是一个抽象父类，用模板方法约束子类执行流程。

更好的进入方式是：

> 假设团队要写一份新功能埋点文档。一个人临时写一次，用提示词就够了；如果多个产品、分析师、研发长期都要写同类文档，事件名、属性、触发时机、验收方式就需要统一底座。

### 本次 2-06 批注沉淀

1. 必须先简单介绍埋点文档是什么、长什么样、一个页面新功能埋点例子是什么。
2. 不需要再提周报，主案例聚焦埋点文档。
3. 内容不要过长，能合并的章节要合并。
4. 不要从陌生概念切入，要先讲“用提示词建立 BaseAgent 的案例”，再解释案例细节和知识点。
5. 标准输出字段、子 Agent 差异、提示词构造、代码骨架应融合进一个连续案例，而不是拆成太多独立章节。
6. 代码部分不要只解释代码含义，读者更想看到怎么使用代码。
7. 管理和可视化不要写太长，用几段话和一两个纲领即可。
8. 常见错误也不要过长，给几个总结性纲领即可。

### 后续写作规则

- 先案例，后概念。
- 先使用，后实现。
- 先解释读者为什么需要，再讲怎么做。
- 对小白读者，减少“模式”“父类”“抽象”等概念堆叠。
- 工程文章中的代码样例要展示“怎么用”，不是只展示“怎么理解”。

## 先让用户傻瓜式用上，再解释背后含义

更新时间：2026-06-12

适用场景：BaseAgent、Agent 工作流、提示词工程、数据分析自动化、工具教程、工程方法论。

### 经验

文章必须从用户视角组织。读者最先关心的不是概念定义，也不是系统为什么高级，而是：

1. 我怎么用？
2. 我照着做要输入什么？
3. 它会输出什么？
4. 我怎么判断它做对了？
5. 出错或不确定时怎么办？

所以写这类文章时，要先给傻瓜式使用路径：完整提示词、最小输入、预期输出、检查方式。等读者已经能照着操作，再解释背后的 BaseAgent、模板方法、工作流、校验门禁、扩展点。

### 本次 2-06 返工沉淀

- 原稿过多解释“为什么需要 BaseAgent”，但最应该先说的是“如何用提示词建立 BaseAgent”。
- 只写“固定流程”还不够，要说明提示词只是软约束，可能出现跳步、幻觉、校验不到位。
- 稳定 BaseAgent 应该把流程拆成阶段输出和校验门禁，例如 `requirement_parse -> event_candidates -> tracking_spec -> validation -> confirm_questions`。
- 案例要贯穿全文：先用商品详情页收藏按钮跑一遍，再基于这个案例解释工作流、扩展和维护。

### 审稿检查项

- 开头三段内是否给出用户可执行的使用路径或最小案例。
- 是否先展示输入、提示词、输出，再解释概念含义。
- 是否把“能用”和“为什么这么设计”分开讲。
- 是否说明提示词的边界，尤其是幻觉、跳步、校验不到位。
- 是否给出验证方式或失败时的处理方式。

## 作者视角不等于显性第一人称

更新时间：2026-06-14

适用场景：系列文章、知识科普文章、工作流复盘文章，尤其是作者希望文章有个人判断但不希望出现聊天式“我”的时候。

### 经验

文章可以有作者视角，但不一定要显性写“我”。作者视角应该体现在取舍、判断和讲解顺序里，而不是靠第一人称来证明“这是我在说”。

例如不要写：

> 我一开始看 2-07 到 2-10 的时候，发现它们可以合并。

更好的写法是：

> 接下来本来应该分别写几个主题：请求失败后的重试、任务卡住时的超时、数据拿不到时的降级、连续失败后的暂停。放到数据分析 Agent 里，它们更适合合并成一章。

### 审稿检查项

- 开头是否写给真实读者，而不是写给看过内部大纲的人。
- 是否出现“看第几章”“2-07 到 2-10”这类内部生产痕迹。
- 是否用客观判断句承载作者取舍，而不是频繁使用“我觉得”“我认为”“我的判断”。
- 如果删掉“我”，文章是否仍然保留清楚的观点和取舍。
