# 轻量 Intake 与数据门禁

## 1. 目标

在进入完整需求分析报告前，先用一层轻量判断回答：

- 我先按什么理解推进？
- 现在有没有数据或证据？
- 需求细节是否足够？
- 没有数据时，本轮还能不能分析？
- 应该输出完整报告、假设版报告、补数据计划，还是只问一个关键问题？

这层不是完整 `pm-grill`，也不是重度研究流程。它只服务 `requirement-report` 的入口判断。

## 2. 30 秒入口判断

每次先给出四项判断，能直接继续就继续，不要把用户拦在问题列表前。

| 判断项 | 写法 |
| --- | --- |
| 我先按这个理解推进 | 用一句话复述用户要判断的需求 |
| 数据状态 | 有数据 / 部分有 / 没有 / 不确定 |
| 细节状态 | 足够 / 缺 1 个关键点 / 不足 |
| 本轮路径 | 完整需求分析报告 / 假设版需求分析报告 / 先补数据 / 只问 1 个问题 |

## 3. 数据状态

| 状态 | 判断标准 | 允许输出 |
| --- | --- | --- |
| Data-ready | 有用户来源、行为数据、业务指标、访谈、工单、销售反馈或项目证据 | 证据版需求分析报告 |
| Data-partial | 有少量证据，但样本、口径、基线或分组不完整 | 报告可以继续，但结论要标证据等级和缺口 |
| Data-missing but feasible | 没有数据，但需求处于早期探索、低成本、低风险，或用户只要先想清楚 | 假设版需求分析报告 + 证据更新计划 |
| Data-missing and not feasible | 没有数据，且会影响高成本开发、战略取舍、重大资源投入或确定性结论 | 先输出补数据/证据计划，不写“需求成立”的确定结论 |

## 4. 需求细节检查

优先检查这些细节，不要求一次性全齐：

| 细节 | 作用 |
| --- | --- |
| 来源/用户 | 判断这是谁的问题，是用户反馈还是内部假设 |
| 场景 | 判断问题发生在什么时候、哪里、什么任务中 |
| 行动 | 判断用户现在怎么解决、是否有替代方案或付费/流失信号 |
| 痛点/成本 | 判断损失的是时间、钱、效率、信任、转化还是体验 |
| 期望结果 | 判断用户想完成的结果，不等于照做用户给的功能 |
| 约束 | 判断技术、合规、资源、时间或商业边界 |
| 决策目标 | 判断这份报告要支持“做/不做/先验证/写 PRD”的哪类决策 |

## 5. 只问一个问题规则

只有缺口会改变方向时才问。每次最多问 1 个问题，并说明为什么问、如果用户不答默认怎么处理。

推荐格式：

```md
我需要先确认一个点：这个需求来自真实用户反馈，还是我们内部假设？
为什么问：这决定报告是证据版，还是假设版。
如果你不补充，我会先按“内部假设，需验证”处理。
```

不要连续追问 5 个问题。能用项目文件或已给材料补的，不问用户。

## 6. 无数据时是否可行

| 场景 | 处理 |
| --- | --- |
| 早期想法、低成本探索、只要先判断方向 | 可以做假设版，但所有结论标“假设/待补证据” |
| 需要进入开发、预算、资源排期或战略承诺 | 不写确定结论，先补证据层 |
| 缺少一个会改变方向的事实 | 只问 1 个关键问题 |
| 细节缺失但可从本地文件获取 | 先读文件，不把问题丢给用户 |
| 用户明确要“先帮我想” | 可以继续，但输出“假设版需求分析报告” |

## 7. 路由结果

| 路由 | 含义 |
| --- | --- |
| `full_requirement_report` | 数据和细节足够，进入完整需求分析报告 |
| `hypothesis_requirement_report` | 无数据或证据弱，但可以先做假设版 |
| `data_needed_before_report` | 数据缺失会导致错误决策，先补证据层 |
| `one_question_before_report` | 只差一个方向性关键点，先问一个问题 |
| `not_requirement_report` | 任务本质不是需求分析，应转 PRD、技术翻译、项目状态或其他 workflow |

## 8. 禁止项

- 不一次性抛出多个追问。
- 不伪造数据、频次、样本、基线或用户来源。
- 没有数据时不写“需求已成立”的确定结论。
- 不把数据补充写成自动触发其他 agent；只能作为可选审查或补证据提醒。
