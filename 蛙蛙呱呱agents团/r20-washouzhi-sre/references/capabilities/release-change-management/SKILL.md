# 发布与变更管理（release-change-management）

> **事故里最常见的一句话是「就改了个配置」。** 变更本身不可怕，可怕的是**没有回滚预案的变更**——它把「可恢复」变成了「只能修」。

## §1 何时用 / 何时不用

**该用（用户真实会这么说）**

- 「这次能不能发」
- 「要不要灰度」
- 「怎么回滚」
- 「改配置要不要走流程」

**不该用，转给谁**

| 用户其实想要 | 转给 | 理由 |
|---|---|---|
| 故障发生后的处理 | r20 的 `incident-response` | 那是响应 |
| 代码评审 | r09 的 `tdd-review-pair` | 那是评审 |
| 监控告警设计 | r20（后续补） | 那是可观测 |
| 备份与恢复演练 | r20 的 `incident-response` | 那是演练 |

**最小可开工输入**：**一次具体变更 + 影响面**。

## §2 前置输入与最省追问

| 输入 | 是否必需 |
|---|---|
| 变更内容（代码/配置/数据/依赖） | 必需 |
| 影响面（影响哪些功能与客户） | 必需 |
| 回滚方式与耗时 | 必需 |
| 灰度方案（比例/观察指标/放量节奏） | 必需 |
| 发布窗口与冻结期 | 建议 |

**追问纪律**：最多一轮，只问**回滚要多久**。答不出回滚时间，就不该发。

## §3 执行流水线（Workflow）

### Step 1 · 变更分级（按不可逆性，不按代码量）
**一级（可逆）**：代码/配置，能分钟级回滚；**二级（半可逆）**：数据迁移、schema 变更，回滚需脚本；**三级（不可逆）**：删除数据、对外承诺、合同变更。

**判据**：每级有对应审批层级；三级必须创始人签字

### Step 2 · 写清影响面（谁、哪个功能、多严重）
影响面 = **功能清单 + 客户范围 + 最坏后果**。「影响所有用户」不是影响面，要说清哪个功能会怎样。

**判据**：影响面含功能/客户范围/最坏后果三项

### Step 3 · 回滚预案（必须给时间，不给「应该能回」）
回滚预案 = **触发条件 + 步骤 + 预计耗时 + 验证方式**。**耗时超过 15 分钟的一级变更，要重新设计**。

**判据**：回滚预案四项齐备，且耗时写明

### Step 4 · 灰度与观察（先小后大，有放量条件）
灰度阶梯：**1% → 10% → 50% → 100%**，每档观察 ≥30 分钟。放量条件写死（错误率、延迟、关键业务指标）。

**判据**：灰度有阶梯与放量条件，每档有观察时长

### Step 5 · 发布窗口与冻结期
**避开**：周五下午、节假日前一天、大促期间、关键人不在。冻结期内的变更需额外审批，且要有 on-call。

**判据**：发布窗口写明；冻结期内变更需升级审批

### Step 6 · 留发布单（事后可追溯）
发布单含：变更内容、影响面、回滚预案、灰度结果、执行人、时间、审批人。

**判据**：发布单六项齐备

### Step 7 · 事后回看（24 小时内）
看三件：**是否按灰度放量**、**有无意外影响**、**回滚预案是否可用**（哪怕没用到也验证一遍思路）。

**判据**：24 小时内回看三项并记录

## §5 质量门（一票否决）

1. 变更按不可逆性分级（一级可逆/二级半可逆/三级不可逆），三级须创始人签字；
2. 影响面含功能清单、客户范围、最坏后果三项；
3. 回滚预案含触发条件/步骤/预计耗时/验证方式；一级变更回滚 ≤15 分钟；
4. 灰度有阶梯（1/10/50/100%）与放量条件，每档观察 ≥30 分钟；
5. 发布窗口避开周五下午、节假日前、大促期；冻结期变更需升级审批；
6. 发布单六项齐备；24 小时内完成事后回看三项；

> 本卡无自动门禁。可配合 `python agent.py dr rollback --input <预案.json>` 校验回滚预案结构（间接）。

## §6 交付前自检清单

- [ ] 我给变更分了级，三级我确认过需要创始人签字
- [ ] 我写清影响哪个功能、影响哪些客户、最坏会怎样
- [ ] 我的回滚预案有触发条件、步骤、耗时、验证方式
- [ ] 一级变更回滚 ≤15 分钟，超过的我重设计了
- [ ] 灰度是 1%→10%→50%→100%，每档观察 ≥30 分钟
- [ ] 放量条件写死了（错误率/延迟/业务指标）
- [ ] 我没在周五下午或节假日前发
- [ ] 发布单六项我都填了
- [ ] 24 小时内我回看过灰度、意外影响、回滚可用性

## §7 易犯错误对照表

| # | 易犯错法 | 正确做法 |
|---|---|---|
| EX-01 | 按代码量分级 | 按不可逆性分级 |
| EX-02 | 影响面写「所有用户」 | 写清哪个功能、哪些客户、最坏后果 |
| EX-03 | 回滚只说「应该能回」 | 给触发/步骤/耗时/验证 |
| EX-04 | 一级变更回滚要 1 小时 | 重新设计，≤15 分钟 |
| EX-05 | 直接全量发布 | 1/10/50/100 灰度 |
| EX-06 | 周五下午发 | 避开周五下午与节假日前 |
| EX-07 | 冻结期偷偷发 | 冻结期需升级审批 + on-call |
| EX-08 | 无发布单 | 六项齐备留档 |
| EX-09 | 不回看 | 24 小时内看三项 |
| EX-10 | 改配置不走流程 | 配置也是变更，同样分级 |

## §8 降级与边界

| 触发情况 | 处置 |
|---|---|
| 无灰度能力 | 改为分时段发布 + 快速回滚，标注「无灰度」 |
| 无监控 | 发布后人工观察 30 分钟关键路径，标注「无可观测」 |
| 紧急修复（hotfix） | 允许简化流程，但回滚预案与发布单不可省 |
| 数据迁移不可回滚 | 先备份 + 演练，按三级变更审批 |
| 第三方依赖变更 | 提前确认对方发布时间，避免叠加 |
| 多人同时发布 | 串行排队，禁止同时发 |

**明确不做**：不做故障响应、不做代码评审、不做容量规划、不签合同。
