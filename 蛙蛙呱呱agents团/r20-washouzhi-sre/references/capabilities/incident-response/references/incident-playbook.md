# 故障响应手册（incident-playbook）

> 被 §3、§5、§7 按需引用。版本：v2.0.0（项目自建，v1）

---

## 一、分级判据

| 级别 | 判据 | 响应时限 | 谁参与 |
|---|---|---|---|
| **P0** | 全站不可用 / 数据丢失 / 安全事件 | 立即 | 全员 + 创始人 |
| **P1** | 核心功能不可用或大面积降级 | 15 分钟 | 值守 + 相关工程 |
| **P2** | 非核心功能异常 / 部分用户 | 1 小时 | 值守 |
| **P3** | 体验问题 / 单用户 | 次工作日 | 值守 |

**安全类直接 P0**：数据泄露、越权访问、密钥外泄——跳过分级讨论，直接叫创始人 + `r03`。

**影响面不明时按高一级定**，恢复后修正并记录修正原因。

## 二、时间线规范

```json
{"events": [
  {"ts": "2026-11-11T09:12:00", "actor": "监控", "action": "告警触发：5xx 率 18%", "impact": "全站"},
  {"ts": "2026-11-11T09:14:00", "actor": "r20", "action": "确认 P0，开事件", "impact": "全站"},
  {"ts": "2026-11-11T09:31:00", "actor": "r09", "action": "回滚 v7.3 → v7.2", "impact": "部分恢复"},
  {"ts": "2026-11-11T09:38:00", "actor": "r20", "action": "5xx 回落至基线，确认恢复", "impact": "无"}
]}
```

| 规则 | 说明 |
|---|---|
| `ts` 单调递增 | 门禁强制；倒序即 FAIL |
| 补记只追加 | 标 `"backfilled": true`，**绝不改原 `ts`** |
| 只写动作 | 不写"手忙脚乱""沟通不畅"这类评价 |
| 记两个时间 | `started_at`（故障开始）与 `detected_at`（被发现）——间隔就是发现延迟 |

**发现延迟是最该改进的指标**：故障 3 分钟修好但 40 分钟才发现，比故障 10 分钟但 1 分钟发现更糟。

## 三、升级路径

```json
{
  "trigger": "5xx 率 > 10% 持续 5 分钟",
  "escalate_to": "创始人",
  "deadline_minutes": 15,
  "actual_minutes": 9,
  "events": [{"ts": "...", "actor": "r20", "action": "升级创始人"}]
}
```

| 要素 | 缺了会怎样 |
|---|---|
| `trigger` | 靠感觉叫人：要么太早（钝化通道）要么太晚（错过窗口） |
| `deadline_minutes` | 没有时限就没有"迟到"的概念 |
| `actual_minutes` | 无法评估升级是否及时 |

## 四、恢复验证（restored 的三种含义）

| 说法 | 实际含义 | 够不够 |
|---|---|---|
| "服务起来了" | 进程活着 | ❌ 不够 |
| "接口返回 200" | 表面可用 | ❌ 不够 |
| "数据行数/校验和与备份点一致" | **真的恢复了** | ✅ 够 |

```json
{
  "backup_point": "2026-11-11T08:00:00",
  "restored_at": "2026-11-11T10:20:00",
  "verification": {
    "row_count_match": true,
    "checksum_match": true,
    "orphan_rows": 0
  },
  "rpo_minutes": 72,
  "rto_minutes": 68,
  "restored": true
}
```

| 术语 | 定义 | 怎么测 |
|---|---|---|
| **RPO** | 最多丢多少数据（按时间） | 恢复点与故障点的时间差 |
| **RTO** | 多久能恢复服务 | 故障开始到服务可用的时长 |

**必须是实测值**。写"RPO 5 分钟"而从未演练过，等于没有 RPO。

## 五、三层根因法（把"人为失误"拆开）

```
表层：某人执行了错误命令
  ↓ 为什么他会执行？
中层：流程缺了一步确认 / 工具没有 dry-run
  ↓ 为什么这个错没被拦住？
深层：无灰度、无回滚预案、告警阈值过松
```

| 层 | 问题 | 典型改进 |
|---|---|---|
| 表层 | 谁做了什么 | 培训（最弱，通常不解决问题） |
| 中层 | 为什么允许这么做 | 加确认步骤、加 dry-run、加权限 |
| 深层 | 为什么没被拦住 | 灰度、回滚、告警、自动化校验 |

**规则**：根因必须至少到**中层**，只写表层＝没找到根因。

## 六、复盘六章（缺一不可）

```markdown
1. 影响：影响用户数 / 时长 / 业务损失 / 是否泄数据
2. 时间线：开始 → 发现 → 处置 → 恢复（含发现延迟）
3. 根因：三层分析结论（表层/中层/深层）
4. 处置：当时做了什么、哪些有效、哪些无效
5. 改进项：每条带 owner + 到期日 + 验证方式
6. 未解决项：哪些还没修、为什么、何时修
```

**第 6 章最常被删，也最重要**：把没修的东西写下来，下一次才不会假装已经解决了。

## 七、与门禁的对应关系

| 门禁 | 覆盖哪一节 | 判不了什么 |
|---|---|---|
| `harness.py incident` | §二 时间线单调 | 判不了发现延迟是否可接受 |
| `harness.py escalation` | §三 时限与单调 | 判不了触发条件定得合不合理 |
| `harness.py drill` | §四 恢复验证（restored） | 判不了数据是否**业务上**完整 |
| `harness.py postmortem` | §六 严重度与章节、根因非空 | 判不了根因是否真到深层 |

> 门禁保证"事实链完整、恢复被验证、复盘有结构"，
> **保证不了"根因找对了"**。后者靠评审与后续是否复发来检验。
