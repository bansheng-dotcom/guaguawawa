# 故障响应与恢复演练（Incident Response）

> 一句话定位：**这个技能存在的意义，是防止"故障处理完了，但说不清什么时候发生了什么、为什么"**。
> 事故最贵的失败不是宕机，而是**不可复盘**：
> 时间线顺序乱（事后补记）、根因写成"人为失误"（等于没找到根因）、
> 备份"演练过"但没人验证数据真的回来了。
> 没有事实链的事故，下一次一定会以同样的方式再来一遍。

## §1 何时用 / 何时不用

**该用（用户真实会这么说）**
- 「线上挂了，先怎么处理」「帮我记事故时间线」
- 「写个故障复盘」「根因是什么」
- 「备份能恢复吗」「做一次恢复演练」

**不该用，转给谁**

| 用户其实想要 | 转给 | 理由 |
|---|---|---|
| 修代码 / 改架构 | `r09` 工程 | 本技能只做响应、记录与复盘 |
| 判断要不要发公告 | `r01` + 业务方 | 对外沟通需决策层确认 |
| 定 SLO 目标 | `r01` + 业务方 | 目标由业务定，本技能给实测值 |
| 法务 / 监管报告 | `r03` 合规 | 本技能产出内部复盘，不是法定报告 |

**最小可开工输入**：**一个事件（发生时间 + 影响面）**。缺影响面就无法分级。

---

## §2 前置输入与最省追问

| 输入 | 是否必需 | 缺失时怎么办 |
|---|---|---|
| 事件开始时间 | 必需 | 时间线无法排序，必须问 |
| 影响面（用户数/功能/地域） | 必需 | 无法分级，必须问 |
| 时间线事件（时间/主体/动作） | 必需 | 无事件可复盘 |
| 恢复时间点 | 恢复后必需 | 无法算 RTO |
| 数据丢失量 | 恢复后必需 | 无法算 RPO/判是否真恢复 |

**追问纪律**：故障中**先处理再问**——只问"影响多大、现在什么状态"，细节事后补。

## §3 执行流水线（Workflow）

### Step 1 · 分级与开线（先定级，再动作）
| 级别 | 判据 | 响应 |
|---|---|---|
| P0 | 全站不可用 / 数据丢失 / 安全事件 | 立即全员 + 创始人 |
| P1 | 核心功能不可用或大面积降级 | 15 分钟内响应 |
| P2 | 非核心功能异常 / 部分用户受影响 | 1 小时内响应 |
| P3 | 体验问题 / 单用户 | 次工作日处理 |

**安全类（数据泄露、越权）直接 P0，跳过分级讨论。**

- **产出**：级别 + 影响面
- **过关条件**：级别与影响面一致（P0 不能只影响 1 个用户）

### Step 2 · 时间线（必须单调，禁止美化）
```bash
python harness.py incident --input <事件时间线.json>
```
每条事件记 `ts / actor / action / impact`。**必须按时间递增**。
门禁实测：时间倒序即 FAIL（`incident.monotonic`）。

**纪律**：
- 事后补记只能**追加**并标 `backfilled`，不改原 `ts`；
- 写"发现时间"和"开始时间"两个字段——两者间隔就是**发现延迟**，是最该改进的指标；
- 不写"某人手忙脚乱"这类评价，只写动作。

- **产出**：时间线
- **过关条件**：`harness.py incident` 退出码 0

### Step 3 · 升级路径（写死触发条件与时限）
```bash
python harness.py escalation --input <升级记录.json>
```
必须含：触发条件 / 升级目标 / 响应时限 / 实际升级时间。时间同样必须单调（`escalation.monotonic`）。

**常见失效**：升级靠"感觉严重就叫人"，没有触发条件。结果是有人叫得太早（钝化通道），有人叫得太晚（错过窗口）。

- **产出**：升级记录
- **过关条件**：`harness.py escalation` 退出码 0

### Step 4 · 恢复验证（restored 不是"重启成功"）
```bash
python harness.py drill --input <恢复演练.json>
```
"恢复"必须验证三件事：
| 验证 | 判据 |
|---|---|
| 数据回来了 | 行数/校验和与备份点一致（`drill.restored`） |
| 服务可用 | 关键接口返回正常 |
| 一致性 | 关联数据无孤儿行 |

**重启成功 ≠ 数据恢复**。门禁实测：未验证恢复即 FAIL。

- **产出**：恢复演练记录 + RPO/RTO 实测值
- **过关条件**：`harness.py drill` 退出码 0

### Step 5 · 复盘（根因不能是"人为失误"）
```bash
python harness.py postmortem --input <复盘.json>
```
必须是：`severity`（与 Step 1 一致）+ 必备章节 + `root_cause`。
门禁实测：缺严重度/章节/根因即 FAIL（`postmortem.severity/sections/root_cause`）。

**必备章节**：影响 / 时间线 / 根因 / 处置 / 改进项（含 owner 与到期） / 未解决项。

**"人为失误"不是根因**，它是根因的起点。继续问三层：
1. 为什么这个人会犯这个错？（流程缺步骤 / 工具没防护）
2. 为什么这个错没被拦住？（无校验 / 告警缺失）
3. 为什么拦住的成本这么高？（无灰度 / 无回滚）

- **产出**：复盘报告
- **过关条件**：`harness.py postmortem` 退出码 0

## §5 质量门（一票否决，不过不给交付）

1. **级别与影响面一致**，安全类直接 P0；
2. **时间线单调递增**（`incident.monotonic`），补记标 `backfilled`；
3. **记录发现延迟**（开始时间与发现时间都有）；
4. **升级有触发条件 + 时限 + 实际时间**（`escalation.monotonic`）；
5. **恢复经数据验证**（`drill.restored`），不只"重启成功"；
6. **有 RPO/RTO 实测值**，不是估算；
7. **复盘含严重度 + 六章 + 根因**（`postmortem.*`），且根因不是"人为失误"。

> 验收命令：`python harness.py incident|escalation|drill|postmortem --input <json>`
> 命中任一项不过 → 回 §3 对应 Step，**不允许改时间戳让时间线变单调**。

## §6 交付前自检清单

- [ ] 级别有判据支撑，不是"感觉挺严重"
- [ ] 时间线按时间递增，没有回跳
- [ ] 事后补记的条目都标了 `backfilled`，没改原始时间
- [ ] 同时记了"开始时间"和"发现时间"，发现延迟算出来了
- [ ] 每条事件含主体与具体动作，没有"手忙脚乱"这类评价
- [ ] 升级写了触发条件、时限与实际时间
- [ ] 恢复后验证了数据行数/校验和，不只是"服务起来了"
- [ ] RPO/RTO 是实测值，标了测量方式
- [ ] 复盘六章齐全（影响/时间线/根因/处置/改进/未解决）
- [ ] 根因追到了流程或工具层，不是止步于"人为失误"
- [ ] 每个改进项都有 owner 与到期日
- [ ] 四道门禁均退出码 0

## §7 易犯错误对照表

| # | 易犯错法 | 正确做法 |
|---|---|---|
| EX-01 | 事后把时间线顺序改成"看起来合理" | 补记只能追加并标 `backfilled`，**改时间是最严重的失信** |
| EX-02 | 只记"开始时间"，不记"发现时间" | 两者都要；间隔＝发现延迟，是最该改进的指标 |
| EX-03 | 根因写"人为失误" | 继续问三层：流程缺什么、为什么没拦住、为什么代价高 |
| EX-04 | 升级靠感觉叫人 | 写死触发条件 + 时限；否则要么迟到要么钝化通道 |
| EX-05 | "重启成功"就宣布恢复 | 必须验证数据行数/校验和一致（`drill.restored`） |
| EX-06 | RPO/RTO 写估算值 | 必须实测并标测量方式；估算是自欺 |
| EX-07 | 复盘没有"未解决项"章节 | 必须写：哪些还没修、为什么、什么时候修 |
| EX-08 | 改进项没有 owner 与到期 | 无 owner 的改进项等于没提 |
| EX-09 | 时间线写"某人手忙脚乱" | 只写动作与事实，不写评价 |
| EX-10 | 安全事件按 P1 处理 | 数据泄露/越权直接 P0，跳过分级讨论 |
| EX-11 | 复盘只写自己团队的问题 | 跨团队问题要写清依赖方，否则改了也不生效 |
| EX-12 | 一份复盘覆盖多次事故 | 一次事故一份复盘；混在一起无法归因 |

## §8 降级与边界

| 触发情况 | 处置 |
|---|---|
| `harness.py` 跑不了 | 按 §6 人工逐项核对，标注「未跑门禁」；**不得标记"已恢复"** |
| 故障仍在进行 | 只出"当前状态 + 已采取措施"，不出复盘；复盘等恢复后 |
| 时间戳缺失（原始日志无时间） | 标注"时间不可考"，用相对顺序（T+0, T+15min），不改造成绝对时间 |
| 无备份可演练 | 标注"无备份，RPO 不可知"，并把"建立备份"列为 P0 改进项 |
| 影响面未知 | 按最坏情况定级（宁可高一级），恢复后修正并记录修正原因 |
| 涉及客户数据泄露 | 直接 P0 + 通知 `r03` 合规 + 创始人；本技能不出对外措辞 |
| 用户要求"别写那么细，快点结" | 拒绝；可缩短**描述**，不可删章节与根因 |

**明确不做**
- 不修业务代码与架构（归 `r09`）；
- 不决定对外公告口径（归 `r01` + `r03`）；
- 不产法定/监管报告（归 `r03`）；
- 不替业务定 SLO 目标（只给实测值）。
