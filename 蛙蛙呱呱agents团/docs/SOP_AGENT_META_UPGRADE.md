# 一人公司 · 智能体能力升级标准 SOP (Meta-Upgrade SOP · 全角色推行版)

> **文档编号**：DSH-SOP-META-001  
> **适用范围**：一人公司全量 20 个角色智能体（R01~R20）及未来新增角色  
> **核心使命**：将「创始人 × AI 架构师」之间临时、随机的对话式改造，固化为**可复现、可度量、可传承的六阶段升级方法论**。任何角色都能依此从"脚本执行器"进化为"具备商业闭环能力的数字员工"。

---

## 第一部分 · 升级方法论（六阶段跃迁模型）

### 全景跃迁图

```text
① 现状体检  →  ② 差距对标  →  ③ 底座硬化  →  ④ 认知注入
                                                      ↓
                    ⑥ 标准沉淀  ←  ⑤ 闭环验证（能力实测）
```

---

### Stage 1 · 现状体检（As-Is Audit）

**目标**：不预设结论，先让角色真实跑起来，暴露它"能做什么 / 不能做什么"。

| 动作 | 具体执行 | 产出证据 |
| :--- | :--- | :--- |
| 1.1 结构扫描 | 遍历角色目录：`agent.py` / `skills/` / `configs/` / `cases/` / `references/` | 目录资产清单 |
| 1.2 真实试跑 | 执行 `manifest` / `demo` / 核心 skill 子命令，**必须真跑不能空谈** | 终端原始输出（含报错） |
| 1.3 故障复现 | 遇到 `ModuleNotFoundError` / 编码乱码 / 路径错误，逐一贴出堆栈 | 最小复现步骤 |
| 1.4 能力盘点 | 列出「已真实可跑」「半成品」「纯模拟」三类能力 | 能力三色台账 |

> **纪律**：本阶段严禁给出任何升级建议。**先看见，再判断**。  
> **反模式**：只读 README 就宣称"已了解能力"，导致后续方案全部悬空。

---

### Stage 2 · 差距对标（Gap Analysis）

**目标**：用**外部高标准**丈量角色差距，而非自我感觉。

| 对标来源 | 用途 |
| :--- | :--- |
| 用户提供的学习体系 / 方法论仓库（如 `python_xuexi` 的 32 周工程化计划） | 校准"高阶分析师应具备什么" |
| 用户提供的同类标杆实现（如 `补充技能/data-analysis-report-agent`） | 校准"交付物应该长什么样" |
| GitHub 高星开源项目（通过 API 检索 Metric Layer / RCA / Headless BI） | 校准"工业界主流架构是什么" |
| 行业 JD / 能力矩阵 | 校准"市场真实付费点在哪" |

**输出物**：**三维差距表**

```markdown
| 维度 | 行业基线 | 当前实现 | 差距性质（缺失/薄弱/错误） | 优先级 |
|---|---|---|---|---|
| 工程化测试 | pytest + CI 门禁 | 无自动化测试 | 缺失 | P0 |
| 数据链路 | 自动 ETL / 数仓连接 | 仅手工投喂 CSV | 缺失 | P0 |
| 报告能力 | 多 Agent 对抗审查 + 高密度排版 | 字符串拼接 Markdown | 薄弱 | P0 |
| 商业归因 | Metric Store + 三级 RCA | 单点统计 | 薄弱 | P1 |
```

> **纪律**：差距必须**可度量、可排序**。模糊的"能力不够"不构成差距。  
> **反模式**：把所有差距都标 P0，导致无从下手。

---

### Stage 3 · 底座硬化（Engineering Hardening）

**目标**：先让角色**不崩、可验证、可观测**，再谈聪明。

| 硬化项 | 落地方式 | 验收标准 |
| :--- | :--- | :--- |
| 自动化测试 | 建 `tests/`，用 pytest 覆盖核心计算函数 | `python agent.py test` 全绿 |
| 可观测性 | `print` → `logging`，按 run/task 分文件落盘 | 有结构化日志可回溯 |
| 契约校验 | 每个 action 产出走 JSON Schema 门禁 | 不符即 fail |
| 编码治理 | 全链路强制 UTF-8（文件读写 + 子进程环境变量） | 报告无乱码 |
| 配置外置 | 阈值/维度/数据源移入 `configs/`，不硬编码 | 改规则不改代码 |

**关键教训（来自 R06 实战）**：
1. `pytest` 必须用**绝对路径**定位 `tests/`，否则在异构 cwd 下收集 0 项。
2. Windows 下子进程捕获中文必须同时设置 `PYTHONIOENCODING=utf-8` 与 `subprocess(..., encoding='utf-8')`。
3. PowerShell `Out-File` 默认可能带 BOM，JSON 读取需 `encoding='utf-8-sig'`。
4. 报告类 HTML 必须用 `write` 工具直写 UTF-8，**不可**经由 shell 字符串拼接中转。

---

### Stage 4 · 认知注入（Cognitive Injection）

**目标**：把"专家怎么想"写成角色能执行的 SOP 与资产。

| 注入物 | 存放位置 | 内容要求 |
| :--- | :--- | :--- |
| 业务诊断 SOP | `cases/<case_id>.md` | 含逻辑导图 + 分步诊断动作 + 归因路径 |
| 指标语义层 | `configs/metric_store.json` | 公式 / 维度 / 告警阈值 / 口径边界 |
| 数据源治理 | `configs/data_sources.json` | 类型 / 权限 / ETL 标准 / 巡检周期 |
| 决策案例库 | `cases/experience/` | 阈值、优先级规则、优质范例文本 |
| 分析框架 | `references/` | 框架图 + 反例 + 禁用词表 |

**三级归因引擎（L1-L3）是本阶段的标准范式**：
- **L1 数据层**：先排除"假异动"（脏数据 / 断流 / 重复）。
- **L2 经营层**：多维交叉下钻，锁定贡献度 ≥70% 的核心因子。
- **L3 商业层**：外部情报对齐，区分"内部失误"与"大盘周期"。

> **纪律**：SOP 必须写成**机器可执行的分支**，而非给人读的散文。

---

### Stage 5 · 闭环验证（Closed-Loop Verification）

**目标**：证明角色能**从发现问题一路走到给出可执行决策**，而不是停在半路。

**标准闭环五步（以 R06 为原型）**：

```text
① 主动巡检 (daily_check.py)
   → 读 metric_store 阈值，发现指标越界
② 自动触发诊断 (agent.py diagnose --case ...)
   → 加载对应 SOP，启动下钻
③ 三级归因 (analysis_bridge.py)
   → L1 质量门禁 → L2 维度下钻 → L3 外部对齐
④ 自动发起验证实验 (run_ab_fast.py)
   → 真跑 Z 检验，输出 lift / p-value / 决策
⑤ 双格式报告出具 (report_generator.py)
   → HTML 决策报告 + Markdown 快读版
```

**验证方式**：必须**真实执行并贴出终端输出**，禁止用"已完成"三个字代替。

> **反模式**：只写脚本不运行；用模拟数据却不标注"这是模拟"。

---

### Stage 6 · 标准沉淀（Standard Codification）

**目标**：把一次性成果升级为**全角色可复用资产**，否则等于没做。

| 沉淀物 | 目标路径 | 复用方式 |
| :--- | :--- | :--- |
| 通用报告引擎 | `agents/shared/report_generator.py` | 全角色 `import` 即用 |
| 全角色报告 SOP | `agents/docs/SOP_BUSINESS_ANALYSIS_AND_REPORTING.md` | 20 角色统一遵循 |
| 升级方法论 SOP | `agents/docs/SOP_AGENT_META_UPGRADE.md`（本文） | 任何新角色按图施工 |
| 自动化验证脚本 | `agents/scripts/test_multi_agent_reporting.py` | 回归测试冒烟 |
| 清理归档 | 删除 `.bak` / `tmp_*` / `__pycache__` / 废弃样板 | 保持目录生产级整洁 |

> **纪律**：沉淀必须**可执行、可导入、可回归**。写成 PPT 不算沉淀。

## 第二部分 · 交互协作协议（创始人 × AI 架构师）

### 2.1 双方职责边界

| 环节 | 创始人（您）负责 | AI 架构师（我）负责 |
| :--- | :--- | :--- |
| 目标 | 提出业务痛点与验收标准 | 拆解为可执行技术方案 |
| 标准 | 提供标杆实现 / 方法论源（如 `python_xuexi`、`data-analysis-report-agent`） | 完成对标分析与差距定位 |
| 决策 | 拍板优先级（A/B/C 选项） | 给出选项的代价与收益评估 |
| 验收 | 实际打开产物、指出"看不了/不够好" | 立即定位根因并修复重发 |
| 沉淀 | 要求"变成 SOP、全角色推行" | 固化为共享模块 + 文档 + 测试 |

### 2.2 交互节奏（高效对话的四条铁律）

1. **先跑通再优化**：任何能力先用真实命令跑出输出，再谈设计。  
2. **失败即黄金**：报错堆栈是最有价值的输入，必须完整呈现并逐条归因。  
3. **产物必须可打开**：交付前自检"用户双击能不能看见内容"，杜绝乱码/路径失效。  
4. **不做无证据承诺**：不说"已支持"，只说"已执行，输出如下"。

### 2.3 典型对话推进范式（本项目的真实路径）

```text
Q1 你都有什么能力？          → 跑 manifest + demo，暴露真实边界
Q2 全量展开商业分析          → 输出三层认知矩阵 + 差距表
Q3 这些在 SOP 里有吗？        → 做 SOP 映射审计，指出空白
Q4 做吧（逐项落地）           → 建 tests/ configs/ cases/，真跑验证
Q5 我的报告呢？               → 先给内容，再补 HTML 载体
Q6 报告太弱，对标标杆         → 引入多 Agent 对抗 + 模板化
Q7 看不了                    → 定位编码乱码，直写 UTF-8 重发
Q8 变成 SOP，全角色推行       → 下沉 shared/ + 写双 SOP + 冒烟测试
```

**规律**：每一轮都是「**暴露问题 → 定位根因 → 立即修复 → 沉淀资产**」的微闭环。**升级不是一次大爆炸，而是连续的小闭环累积**。

## 第三部分 · 全角色推行落地清单

### 3.1 每个角色升级的 Checklist

```markdown
- [ ] 1. 结构审计：agent.py / skills / configs / cases / references 是否齐备
- [ ] 2. 真实试跑：manifest + demo + 至少一个核心 skill 通过
- [ ] 3. 工程硬化：tests/ 可跑、logging 可查、UTF-8 无乱码
- [ ] 4. 认知注入：本角色专属 SOP（cases/）+ 指标定义（configs/）
- [ ] 5. 闭环验证：能从"发现异常"走到"给出可执行决策"
- [ ] 6. 报告接入：调用 generate_professional_report 输出 HTML + MD
- [ ] 7. 冒烟回归：scripts/test_multi_agent_reporting.py 全绿
- [ ] 8. 目录清理：无 .bak / tmp_* / __pycache__ 残留
```

### 3.2 推进排期建议（分批推进，避免一次性返工）

| 批次 | 角色 | 理由 |
| :--- | :--- | :--- |
| **第一批（P0）** | R01 CEO、R03 CFO、R06 分析师、R14 电商 | 直接决定经营决策质量，收益最高 |
| **第二批（P1）** | R02 COO、R07 PM、R12 增长、R13 CSM | 运营与增长核心链路 |
| **第三批（P2）** | R04 评审、R18 数仓、R19 ML、R20 SRE | 质量与稳定性保障 |
| **第四批（P3）** | R05/R08/R09/R10/R11/R15/R16/R17 | 支撑型角色，按需推进 |

### 3.3 验收标准（Definition of Done）

一个角色才算"升级完成"，必须同时满足：

1. **可跑**：`python agent.py test` 与核心子命令真实执行成功。  
2. **可查**：有结构化日志与运行记录，失败可回溯。  
3. **可归因**：能完成 L1→L2→L3 三级归因，而非只报数字。  
4. **可闭环**：能自动发起验证实验并给出决策建议。  
5. **可汇报**：能一键产出商业级 HTML + Markdown 双格式报告。  
6. **可复用**：调用的全部是共享模块，无私有重复实现。  
7. **可清单**：目录干净，无临时代码与备份残留。

## 第四部分 · 反模式清单（踩过的坑，全角色禁止再踩）

| # | 反模式 | 真实后果 | 正确做法 |
| :--- | :--- | :--- | :--- |
| 1 | 只读文档就宣称已了解能力 | 方案悬空，全盘返工 | 必须真实执行命令并贴输出 |
| 2 | 用 `print` 当日志 | 线上问题无法定位 | 统一 `logging` + 分文件落盘 |
| 3 | 报告用字符串拼 HTML | 编码乱码、样式崩坏 | 用 `write` 直写 UTF-8 或模板引擎 |
| 4 | 子进程不设编码 | Windows 下中文全乱 | `PYTHONIOENCODING=utf-8` + `encoding='utf-8'` |
| 5 | pytest 用相对路径 | 收集 0 项，假绿 | 用 `__file__` 推导绝对路径 |
| 6 | 只给"建议加强宣传"式空话 | 业务无法落地 | 必须带灰度计划 + 熔断红线 |
| 7 | 一键 100% 全量上线 | 线上事故 | 5% → 20% → 50% → 100% 阶梯灰度 |
| 8 | 升级成果只留在单角色目录 | 其他 19 个角色重复造轮子 | 立即下沉到 `agents/shared/` |
| 9 | 沉淀写成 PPT / 散文 | 无法执行 | 写成可 import 的模块 + 可跑的测试 |
| 10 | 交付前不自检可打开性 | 用户回一句"看不了" | 交付前亲自验证文件可读、无乱码 |

## 第五部分 · 一页速查（贴在每个角色的 README 顶部）

```text
【升级六步】体检 → 对标 → 硬化 → 注入 → 闭环 → 沉淀
【报告五段】决策指令 / KPI 格栅 / 归因分析 / 护栏熔断 / 灰度+下一步

【清理三删】.bak 备份 / tmp_* 临时 / __pycache__ 缓存
```
