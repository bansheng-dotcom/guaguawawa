## 2. 五条结论（对五个问题的修正回答）

### 结论 1：卡片不该只有"评分"，要先过"就绪清单"（DoR）

DoR 的本质是**二值门禁**：8 项不全，就不进 sprint；对应我们：**不齐就不发卡**。
评分卡（0–20）只用于**排序与抽检**，不能替代"就绪"。

→ 改造：**DoR 8 项硬门禁 + 10 项评分排序**，两者并存。

### 结论 2：R01/R02 弱，不是缺 SOP，是缺两个"关口"

- **R01 的关口**：brief 必须**用户确认**（OpenAI Deep Research 的做法：先给计划，用户可改，再开跑）；
- **R02 的关口**：卡必须**就绪**（DoR）才发，且有红队记录。

现在的 SOP 写了流程，但这两道关口**没有产物、没有签字、没有记录**，所以形同虚设。

→ 改造：brief 签字 + 就绪签字，两者进 `manifest`，没签字不许进入下一阶段。

### 结论 3：正文由 R01 写，但要按 SCQA/金字塔，不是按"五块模板"硬填

金字塔原理要求：**每节先给答案，再给支撑**；节与节之间是同层并列或上下推导。
五块（结论/证据/机理/反例/动作）是**内容清单**，SCQA 是**叙述顺序**，两者要合起来：

```
节 = SCQA（背景一句 → 冲突/问题 → 答案 → 支撑）
支撑 = 证据（图）+ 机理 + 反例 + 动作
```

→ 改造：写作契约从"五块"升级为"SCQA + 五块"；节 = 论点，一问可多节。

### 结论 4：图表接线是"三段式"，不是"一个接口"

Vega-Lite 与 Evidence 都说明：**图是查询结果的编码**，不是文本的装饰。

```
query(raw) → encoding(mark+channel) → charts_pro
```

→ 改造：图表 owner 只接 `query`；图的数据点必须等于查询行数；图覆盖率进 manifest。

### 结论 5：R01 必须交互，且交互要"两段式"

- **第一段：≥10 问**（DBA 的三组问题：问题/上下文/交付）；
- **第二段：计划草案**（OpenAI 式：把问题树 + 拟采数据 + 交付形态写成计划，让用户改）。

只问不确认计划，用户改了意图还得重来；只给计划不问，计划是空中楼阁。

→ 改造：`intake`（≥10 问）→ `brief`（用户签字）→ 才允许拆卡。

## 3. 本轮新增的关键判断（之前没有的）

1. **"就绪"是二值，"评分"是排序**——混在一起会既不可执行也不可排序；
2. **brief 要用户签字**，不是 R01 自己写完就拆；
3. **报告结构要 SCQA**，否则五块会变成另一种模板；
4. **验证要分层**（行/指标/论点），MAST 的 FC3 占 21%，我们目前只有单层字段校验；
5. **计划可改**是流程的一部分，不是返工。

## 4. 建议写进 SOP 的条目（待你确认）

| # | 条目 | 依据 |
|---|---|---|
| 1 | R01 接活：≥10 问 + 计划草案 + 用户签字，未签不拆卡 | DBA + OpenAI |
| 2 | 卡片就绪：DoR 8 项硬门禁（价值/细节/依赖/人手/可估/验收可测/演示/口径） | Ken Rubin |
| 3 | 卡片评分：10 项 0–20，仅用于排序与抽检，不替代 DoR | 本轮结论 1 |
| 4 | 角色交行 + 一句判断；未注册 metric 拒收 | 语义层 + Data Contract |
| 5 | R01 综合出 theses；正文按 SCQA + 五块写；节=论点 | 金字塔/SCQA |
| 6 | 图表只接 query(raw)；图覆盖 100% 或写理由 | Vega-Lite/Evidence |
| 7 | 三层验证：行级/指标级/论点级 | MAST FC3 |
| 8 | 两个签字（brief、就绪）+ 两个回流（数据、论点）进 manifest | OpenAI + 本轮结论 2 |
