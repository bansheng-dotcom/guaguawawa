## 1. 八个组件

### 1.1 能力目录 Agent Card

每个角色一张卡：能答什么、有什么工具、SLA、不可用条件、交付格式。

```yaml
role: r06
name: 蛙得清
capabilities: [数据分析, 指标口径, 覆盖测算]
tools: [csv, sql, chart_spec]
entitlements: [公开数据, 平台报表]      # 能不能拿付费/一手数据
sla: {response: 2h, capacity: 3 卡/轮}
unavailable_when: [需要一手 POS, 需要签约授权]
deliverable: claims.json + cells[]
```

来源：`core/registry.py` 的能力/技能/动作字段，**不另写一份**，由 R02 生成。
对标 A2A 的 Agent Card（能力发现）：[A2A 周年](https://opensource.googleblog.com/2026/04/a-year-of-open-collaboration-celebrating-the-anniversary-of-a2a.html)。

### 1.2 任务契约 Task Contract

一张卡的完整契约，**由 R02 签发**，R01 只提供内容（问题 + 格子）：

```yaml
task_id: T-2026-11-21-003
owner: r06
deliverable: cells[]  (Q3 空间维 6 格)
acceptance: G1/G3/G7/G13
depends_on: [T-002  (r05 品类定义)]
deadline: 2026-11-21T18:00
escalate_to: r02
escalate_after: 2h
```

### 1.3 缺口路由 Gap Routing（这次的核心）

执行者填不了格时，**不再写 `missing` 了事**，而是判类型、发请求：

| 缺口类型 | 判断 | 路由 | 升级 |
|---|---|---|---|
| **能力缺口** | 这问题不在我能力目录里 | 查能力目录 → 最匹配的角色 | 无匹配 → R02 |
| **数据缺口** | 有分析能力，但没有这个数 | R02 → 采购 / 一手 / 平台账号 | 拿不到 → 缩范围或标未答 |
| **授权缺口** | 需要签字/账号/合同 | R02 → 创始人 | 不可逆动作必须签字 |

请求单（结构化，不是自由文本）：

```yaml
request_id: RQ-018
from: r06
type: data_gap            # capability | data | authority
cell: Q3.结构.品类×渠道
need: 品牌×渠道 份额，2025，平台口径
why: G14 要求构成加总 100%，现只有 37.4%
deadline: 2h
acceptance: 有 source + grade ≥ C + period
```

路由规则（对标合同网 contract net）：**一个请求可以同时投给 2–3 个候选角色**，谁先 accept 谁做；全部 decline 或超时 → 回 R02 升级。

### 1.4 依赖 DAG 与并行

由格子自动生成依赖：

- 同一 `measure + entity + period` → **同一事实**，只采一次（证据指纹）；
- 派生指标依赖其 `input_metrics` → 先采输入；
- 空间下钻依赖上级总量 → 先省后市。

R02 输出 `dag.json`：节点=格子，边=依赖，标注**关键路径**与可并行波次。
对标 CrewAI 的 Flows（事件驱动 + 依赖）与 R02 自己的"关键路径与浮动时间"。

### 1.5 交接签收 Handoff

生产者交、消费者**必须签收**（像 PR review）：

```yaml
handoff_id: H-031
from: r06        # 交
to: r01          # 收（写报告）
artifact: cells[] for Q3
accept: false
reasons: ["空间维只到盟市，缺旗县", "机制格无 L3"]
action: backfill
```

**默认不通过**。没有签收记录 = 交接没发生。
对标 CrewAI hierarchical 的"经理验证"与 MetaGPT 的共享消息池。

### 1.6 冲突仲裁 Arbitration

同一 `scope + period + measure` 出现两个值：

| 情形 | 裁决人 | 规则 |
|---|---|---|
| 来源等级不同 | R02 按规则自动 | 高等级胜 |
| 等级相同、口径不同 | **R02 裁口径** | 写清差异，报告并列 |
| 等级相同、口径相同 | **R04 裁证据** | 回抓原文，取可复现者 |
| 涉及不可逆动作 | **创始人** | 不自动裁 |

裁决必须落 `arbitration.json`：谁裁、依据、结论、是否未决。

### 1.7 SLA 与降级

| 事件 | 时限 | 超时处理 |
|---|---|---|
| 请求被接 | 30 min | 转下一候选 |
| 交格 | 2h | 回 R02，进 backfill |
| 签收 | 1h | 视为 reject，回 backfill |
| 升级到创始人 | 24h | 报告标"未决" |

超时不是失败，**是必须留痕的事件**。

### 1.8 协作账本 Ledger

四类事件全记：`request / handoff / arbitration / backfill`，每条带 id、时间、参与人、证据引用。
作用：复盘"哪一步卡住、哪个角色缺口、下次怎么改"，直接喂给经验卡（product-manager 的 RAG Gate 模式）。

## 4. 四条反模式（谁碰谁错）

1. **R01 派活给自己** —— 作者兼调度，等于没人调度（现在就是这样）。
2. **R02 改内容** —— 调度只排期、只路由，不改结论。
3. **R04 补格** —— 验收只记录，不生产。
4. **执行者写 `missing` 就结束** —— 缺口必须走路由，否则等于静默丢弃。
