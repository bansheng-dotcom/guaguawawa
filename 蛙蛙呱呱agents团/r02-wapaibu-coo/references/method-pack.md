# R02 蛙排布 · 方法包（Method Pack v1）

## 1. 决策问题

- 典型决策：瓶颈在哪 / 先改哪一步 / 要加多少人/多少产能 / 这件事谁接、什么时候交。
- 决策者：业务负责人；最怕「局部优化、整体更慢」。
- 成功标准：找到约束 + 给出改动 + 定义吞吐指标 + 交接不出错。
- 非目标：不替专业角色做判断；不排不可执行的「完美计划」。

## 2. 问题树（MECE）

| 分支 | 要回答 | 数据 | 方法 | 产出 |
|---|---|---|---|---|
| 需求 | 来多少、波动多大 | 订单/工单量 | 到达率、峰值 | 负荷 |
| 产能 | 每步能做多少 | 工时/设备/人员 | 产能表、OEE | 瓶颈 |
| 流动 | 卡在哪、等多久 | 各环节时长 | 利特尔法则、排队 | 在制品 |
| 交接 | 谁交给谁、丢什么 | 交接单/返工 | 交接审计 | 接口 |
| 质量 | 返工从哪来 | 缺陷/返工 | 帕累托 | 改进点 |

**critical branch**：`流动`——瓶颈通常不在最忙的人，而在等待最长的那一步。

## 3. 假设与证伪

- 假设例：「分拣是瓶颈，增加 1 人可把日处理量从 8 吨提到 10 吨」。
- 三件套：支持（排队时长）/ 反对（上游到货不足）/ 杀死标准（加人后 2 周吞吐 <9 吨）。
- 竞争解释（至少 2 个）：① 不是产能问题，是到货节奏不均衡；② 不是人不够，是订单结构（SKU 太多）导致换线损失。逐个用时间戳数据排除。

## 4. 证据分级

| 级别 | 来源 | 用途 |
|---|---|---|
| A | 系统时间戳、工单、打卡 | 可定瓶颈 |
| B | 访谈、估算工时 | 方向 |
| C | 经验值 | 标注 + 敏感性 |

规则：没有时间戳的流程只能给「疑似瓶颈」，不能给「就是瓶颈」。

## 5. 方法与陷阱

**可执行**：`python scripts/methods.py little --arrival ... --cycle ...`。

- **约束理论（TOC）**：识别→利用→ subordinate→提升→回到识别；只改瓶颈。
- **利特尔法则**：在制品 = 到达率 × 周期；用来验证瓶颈判断。
- **关键路径**：WBS + 依赖，找最长路径而不是最忙的人。
- **SOP 控制点**：每步写判据、超限处理、责任人；关键步骤必须有 control_point。
- **前后对照**：改动前后各测 2 周，同一口径对比吞吐/周期，不做「感觉快了」。
- **敏感性**：需求 ±20%、人员缺勤 10% 两种情形下，方案是否仍成立。
- 陷阱：优化非瓶颈；用局部效率当整体吞吐；交接无单据；SOP 只写步骤不写判据。

## 6. 输出契约

```
claim        一句话结论（瓶颈在哪 + 依据）
evidence     时间戳/工单 + 观测窗口（A/B/C 级别）
confidence   区间或「点估计，未验证」
falsifier    什么数据会推翻「这是瓶颈」
constraint   瓶颈（步骤 + 证据 + 时长）
change       改动（做什么 + 投入 + 预期吞吐）
throughput   指标（当前 → 目标 + 观察窗口）
handoff      交接单（谁→谁 + 字段 + 超时处理）
owner        唯一负责人
```

缺吞吐指标或交接单 → 不通过。
