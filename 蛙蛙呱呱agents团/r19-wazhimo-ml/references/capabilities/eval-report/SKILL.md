# 模型评测与发布门禁（Eval Report）

> 一句话定位：**这个技能存在的意义，是防止"这次感觉比上次好，发吧"**。
> 模型发布最贵的失败不是效果差，而是**无法判断是不是变差了**：
> 评测集没期望输出、评分器没有判据、回归只跑新用例不跑老的绿集。
> 结果是：上了线才发现某个原本能过的场景悄悄挂了，而且没人知道是这次改的。

## §1 何时用 / 何时不用

**该用（用户真实会这么说）**
- 「这个模型能不能上」「这次改动有没有变差」
- 「帮我设计评测集和评分器」「评测报告怎么写」
- 「为什么回归挂了」

**不该用，转给谁**

| 用户其实想要 | 转给 | 理由 |
|---|---|---|
| 训练 / 微调模型 | 训练侧（不在本角色范围） | 本技能只做评测与门禁 |
| 数据标注与清洗 | `r18` / `r06` | 那是数据侧 |
| 业务是否接受这个效果 | `r01` + 业务方 | 本技能给数字，不替业务拍板 |
| 线上监控告警配置 | `r20` 值守 | 本技能只定义监控指标，不配告警 |

**最小可开工输入**：**一个待评模型或版本 + 一组带期望输出的用例**。

---

## §2 前置输入与最省追问

| 输入 | 是否必需 | 缺失时怎么办 |
|---|---|---|
| 被测模型/版本 | 必需 | 无版本无法做回归对比 |
| 评测集（`inputs` + `expectations`） | 必需 | 缺期望输出则只能人工看，不出口径 |
| 评分器定义（type/target/criteria） | 必需 | 缺则无法判"过没过" |
| 上版基线结果 | 回归时必需 | 缺则无法判"有没有变差" |
| 业务可接受阈值 | 建议 | 缺则按同类默认并标注"阈值待业务确认" |

**追问纪律**：最多一轮，只问**跟谁比、怎么算过**。

## §3 执行流水线（Workflow）

### Step 1 · 评测集（输入与期望必须成对）
```bash
python harness.py evaluation_dataset --input <评测集.json>
```
每条用例必须含 `inputs` 与 `expectations`（期望输出或判定标准）。
门禁实测：缺任一即 FAIL（`dataset.inputs` / `dataset.expectations`）。

**四条纪律**
1. **用例来自真实场景**，不是自己编的"应该能过"的例子；
2. **包含 3–5 条难例**（上一版做错的），否则测不出进步；
3. **包含 3–5 条近邻负例**（看起来像但答案不同），防止过拟合；
4. 用例**版本化**，改用例要记版本，否则跨版本对比无效。

- **产出**：评测集 + 版本号
- **过关条件**：`harness.py evaluation_dataset` 退出码 0

### Step 2 · 评分器（先定判据，再看结果）
```bash
python harness.py evaluation_scorer --input <评分器.json>
```
每个评分器必须有：`type`（精确匹配/包含/LLM 判定/规则）/ `target`（评什么）/ `criteria`（什么算过）。
门禁实测：任一缺失即 FAIL（`scorer.type/target/criteria`）。

| 评分器类型 | 适合 | 风险 |
|---|---|---|
| 精确匹配 | 有唯一答案 | 对同义表达过于严格 |
| 包含/正则 | 关键信息存在 | 可能"包含即过"放过错答 |
| 规则（结构化校验） | JSON/字段类输出 | 只判格式不判语义 |
| LLM 判定 | 开放生成 | **必须给判据**，否则不可复核 |

> **LLM 判定不是免死金牌**：没有 `criteria` 的 LLM 判定等同拍脑袋。
> 判据要写成"满足哪几条算过"，并附 2–3 个正反例校准。

- **产出**：评分器定义
- **过关条件**：`harness.py evaluation_scorer` 退出码 0

### Step 3 · 跑评测并出报告（数字 + 分布 + 失败样本）
报告必须含四块，缺一块不可交付：

| 块 | 内容 |
|---|---|
| 总体 | 通过率 / 主指标 / 样本量 |
| 分布 | 按场景/难度的分层通过率（防止"整体好看但某类全挂"） |
| 失败样本 | 至少列 5 条，含输入与错误输出 |
| 局限 | 评测集覆盖不到什么 |

**禁止只报总体分**：一个 90% 通过率下面，可能某一类场景 0%。

### Step 4 · 发布回归（新旧绿集都要跑）
```bash
python harness.py release_regression --input <回归.json>
```
三项必填：
| 字段 | 含义 | 漏了会怎样 |
|---|---|---|
| `existing_green` | 上一版已通过、本次仍需通过 | 悄悄变差没人发现 |
| `pass_after` | 本次通过项 | 无法对比 |
| `diagnosis_layer` | 失败归因层次（数据/提示/模型/评测） | 挂了不知道怎么查 |

门禁实测：三项缺任一即 FAIL，且同时命中多个 `regression.*` 维度。

**核心规则**：**只在新增用例上变好、却在旧绿集上变差，判定为回归失败**。
这是发布门禁里最容易被绕过、也最常导致线上事故的一条。

- **产出**：回归对比结论
- **过关条件**：`harness.py release_regression` 退出码 0

### Step 5 · 模型卡与监控指标（让别人敢用）
- **模型卡**：用途/不适用场景/训练数据来源/已知偏差/评测结论；
- **监控指标**：线上用哪些指标判"效果漂移"，阈值多少。

```bash
python harness.py modelcard_card --input <模型卡.json>
python harness.py monitor_metrics --input <监控.json>
```

## §5 质量门（一票否决，不过不给交付）

1. **每条用例都有 `inputs` 与 `expectations`**（`dataset.*`）；
2. **评分器三件齐全**（`scorer.type/target/criteria`）；
3. **报告含分布 + ≥5 条失败样本 + 局限说明**；
4. **回归跑过旧绿集**（`regression.existing_green`）；
5. **回归写明归因层次**（`regression.diagnosis_layer`）；
6. **旧绿集变差即判回归失败**，不得只用新增用例变好来抵；
7. **模型卡写明不适用场景与已知偏差**。

> 验收命令：三道 harness 门禁 + 回归门禁
> 命中任一项不过 → 回 §3 对应 Step，**不允许删掉旧绿集让回归变绿**。

## §6 交付前自检清单

- [ ] 每条评测用例都有期望输出，不是"人工看看"
- [ ] 用例里有 3–5 条上一版做错的难例
- [ ] 用例里有 3–5 条近邻负例
- [ ] 评测集有版本号，且本次与基线用同一版本
- [ ] 每个评分器都写了 `criteria`，LLM 判定附了正反例
- [ ] 报告有分层分布，不只有总体通过率
- [ ] 报告列了 ≥5 条失败样本（含输入与错误输出）
- [ ] 报告写了"这个评测集覆盖不到什么"
- [ ] 回归跑了旧绿集，且逐一交代变差项
- [ ] 失败项写了归因层次（数据/提示/模型/评测）
- [ ] 模型卡写了不适用场景与已知偏差
- [ ] 四道门禁均退出码 0

## §7 易犯错误对照表

| # | 易犯错法 | 正确做法 |
|---|---|---|
| EX-01 | 评测用例只有输入没有期望输出 | 必须成对；没有期望就只能人工看，不出口径 |
| EX-02 | 用例全是自己编的"应该能过" | 用例来自真实场景，并含上一版做错的难例 |
| EX-03 | 只跑新增用例，不跑旧绿集 | 旧绿集必须跑；只在新用例上变好＝回归失败 |
| EX-04 | LLM 判定不给判据 | `criteria` 必填，并附 2–3 个正反例校准 |
| EX-05 | 只报总体通过率 | 必须给分层分布；90% 下面可能有某类 0% |
| EX-06 | 报告不列失败样本 | 至少 5 条，含输入与错误输出，否则无法改进 |
| EX-07 | 回归失败只写"效果不好" | 必须写归因层次：数据 / 提示 / 模型 / 评测 |
| EX-08 | 改评测集后与旧基线对比 | 用例版本变了就不能跨版本比；要么冻结版本，要么重跑基线 |
| EX-09 | 用"平均分提升"掩盖单项暴跌 | 逐项看；主指标提升但关键场景崩了，不能发布 |
| EX-10 | 模型卡只写优点 | 必须写不适用场景、已知偏差、覆盖不到的情况 |
| EX-11 | 一次改动同时改模型和评测集 | 无法归因；一次只改一个变量 |
| EX-12 | 没有监控指标就上线 | 上线前定好漂移判据，否则出问题靠用户投诉发现 |

## §8 降级与边界

| 触发情况 | 处置 |
|---|---|
| `harness.py` 跑不了 | 按 §6 人工逐项核对，标注「未跑门禁」；**不得标记"可发布"** |
| 无基线结果 | 只能做"首次评测"，不得判"没有变差" |
| 评测集太小（<20 条） | 标注"样本不足，结论仅供参考"，不出发布结论 |
| 无业务阈值 | 按同类默认，标注"阈值待业务确认"，不擅自定 |
| 用例与基线版本不一致 | 重跑基线同一版本，或声明"跨版本不可比" |
| 只有失败样本没有成功样本 | 无法判分布，补抽样成功样本 |
| 用户要求"先发再评" | 拒绝；可给"灰度 + 监控阈值"，但不取消评测门禁 |

**明确不做**
- 不训练、不微调模型；
- 不做数据标注与清洗（归 `r18` / `r06`）；
- 不替业务判断"效果够不够"（归 `r01` + 业务方）；
- 不配置告警（归 `r20`）。
