# 评测纪律与回归判定（eval-discipline）

> 被 §3、§5、§7 按需引用。版本：v2.0.0（项目自建，v1）

---

## 一、评测集设计四纪律

| # | 纪律 | 反例 | 后果 |
|---|---|---|---|
| 1 | 用例来自真实场景 | 自己编"应该能过"的例子 | 评测分虚高，上线就打脸 |
| 2 | 含 3–5 条上一版做错的难例 | 只放简单用例 | 测不出任何改进 |
| 3 | 含 3–5 条近邻负例 | 只有正例 | 过拟合到关键词，边界全错 |
| 4 | 用例版本化 | 边改边比 | 跨版本对比无效 |

**版本纪律**：改用例后必须重跑基线，否则"变好了"可能是用例变简单了。

## 二、评分器设计（判据优先）

```json
{
  "type": "llm_judge",
  "target": "回答是否覆盖了全部三个要点",
  "criteria": [
    "必须提到退款时限（7 天）",
    "必须提到需原包装",
    "不得承诺额外补偿",
    "三个要点缺一即不过"
  ],
  "calibration": {
    "pass_examples": 2,
    "fail_examples": 2
  }
}
```

| 类型 | 何时用 | 必须给 |
|---|---|---|
| `exact` | 唯一答案 | 允许的同义表 |
| `contains` / `regex` | 关键信息 | 必须命中的片段 |
| `rule` | 结构化输出 | 字段与取值规则 |
| `llm_judge` | 开放生成 | **criteria + 正反例校准** |

**反模式**：`type` 写了 `llm_judge` 但 `criteria` 为空 —— 等于把判定完全交给模型，
既不可复核也无法复现。

### 一条常被忽略的判据有效性检查

拿 2 条**明显错误**的输出去跑评分器：如果它们也能通过，说明这个评分器只测格式不测语义。
这比没有评分器更危险——它给了你一个假的绿灯。

## 三、评测报告四块（缺一不可交付）

```markdown
## 1. 总体
- 通过率：82%（41/50）
- 主指标：回答要点覆盖率 0.78
- 样本量：50

## 2. 分布（按场景）
| 场景 | n | 通过率 |
|---|---|---|
| 退换货 | 12 | 92% |
| 账务争议 | 10 | **40%** |   ← 总体 82% 掩盖了这里
| 产品咨询 | 28 | 93% |

## 3. 失败样本（≥5 条）
| # | 输入 | 期望 | 实际 | 失败原因 |
|---|---|---|---|---|

## 4. 局限
- 未覆盖多轮对话；未覆盖非中文输入；账务场景样本仅 10 条
```

**为什么必须给分布**：总分是平均值，平均值天然掩盖极端值。
发布决策看的是**最差的那一类**，不是平均。

## 四、回归判定（发布门禁的核心）

```json
{
  "model_version": "v7",
  "baseline_version": "v6",
  "existing_green": {"total": 40, "still_green": 38, "now_red": 2},
  "pass_after": {"total": 50, "passed": 41, "delta": "+3"},
  "diagnosis_layer": {
    "data": 0, "prompt": 1, "model": 1, "eval": 0
  }
}
```

### 判定规则

| 情况 | 判定 |
|---|---|
| 旧绿集全绿 + 新用例提升 | ✅ 可发布 |
| 旧绿集有变红 + 新用例提升 | ❌ **回归失败**（这是最重要的一条） |
| 旧绿集全绿 + 新用例持平 | ✅ 可发布（无退化） |
| 旧绿集变红 + 新用例也降 | ❌ 回归失败 |

> **"新用例变好"永远不能抵消"旧绿集变红"**。
> 因为旧绿集代表"我们已经承诺能做到的事"，退化就是失信。

### 四个归因层次

| 层 | 典型原因 | 先查什么 |
|---|---|---|
| `data` | 数据分布变了 / 用例错了 | 抽样对比新旧输入 |
| `prompt` | 提示词改动引入副作用 | diff 提示词，逐句回滚 |
| `model` | 模型版本本身能力变化 | 同一提示词跑两版模型 |
| `eval` | 评分器或期望写错了 | 人工复核失败样本 |

**不许写"效果不好"** —— 无法归因就无法修复。

## 五、模型卡要素

| 要素 | 内容 |
|---|---|
| 用途 | 这个模型用来做什么 |
| **不适用场景** | 明确列出不该用的地方（最常被漏掉） |
| 训练数据 | 来源、时间范围、已知偏差 |
| 评测结论 | 通过率 + 分布 + 已知失败模式 |
| 版本与日期 | 可追溯 |
| 监控指标 | 线上用什么判漂移 |

> 没有"不适用场景"的模型卡，等于告诉使用者"什么都能干"。

## 六、与门禁的对应关系

| 门禁 | 覆盖哪一节 | 判不了什么 |
|---|---|---|
| `harness.py evaluation_dataset` | §一 输入与期望成对 | 判不了用例质量 |
| `harness.py evaluation_scorer` | §二 三件齐全 | **判不了判据是否有效**（需人工用错误样本校准） |
| `harness.py release_regression` | §四 旧绿集与归因层次 | 判不了归因对不对 |

> 门禁保证"该有的都有"，保证不了"评测是真的在测能力"。
> 判据有效性只能靠"喂错误答案看它会不会挂"来验证。
