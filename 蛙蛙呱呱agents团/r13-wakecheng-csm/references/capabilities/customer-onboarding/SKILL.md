# 客户上手与激活（customer-onboarding）

> **续费率低，八成不是价格问题，是客户从没到达过「啊，有用」的那一刻。** 而这个时刻通常不在第 30 天，在第 1 天——如果我们没设计它的话，它就不会发生。

## §1 何时用 / 何时不用

**该用（用户真实会这么说）**

- 「客户签了但不怎么用」
- 「新客户怎么引导」
- 「为什么激活率低」
- 「首价值要几天」

**不该用，转给谁**

| 用户其实想要 | 转给 | 理由 |
|---|---|---|
| 健康分与 QBR | r13 的 `qbr-health` | 那是存量经营 |
| 续约与增购 | r13 的 `renewal-expansion` | 那是续费 |
| 客服与 SLA | r13 的 `customer-support-sla` | 那是支持 |
| 产品需求 | r07 的 `prd-authoring` | 那是需求 |

**最小可开工输入**：**一个客户角色 + 一个「用了就有用」的具体成果**。

## §2 前置输入与最省追问

| 输入 | 是否必需 |
|---|---|
| 客户角色与规模 | 必需 |
| 首个价值时刻（客户得到什么算「有用」） | 必需 |
| 当前上手步骤（有几步） | 必需 |
| 激活度量口径（事件 + 阈值） | 必需 |
| 常见卡点（来自支持工单） | 建议 |

**追问纪律**：最多一轮，只问**客户在什么时候会说「这玩意儿有用」**。这个时刻定不下来，整条路径都是瞎设计。

## §3 执行流水线（Workflow）

### Step 1 · 定首个价值时刻（TTV）
一句话：**客户在第 N 天，通过做 X，得到了 Y**。Y 必须是客户能感知的成果（不是「完成配置」）。

**判据**：TTV 写成「第 N 天 + 做 X + 得到 Y」，且 Y 可被客户自己确认

### Step 2 · 定义激活（可度量，一个事件 + 阈值）
激活 = **一个事件 + 一个阈值**，如「创建首个任务并运行成功 ≥1 次」。**不许**用「登录了」「注册了」当激活——那是到访，不是价值。

**判据**：激活定义是一个事件 + 数值阈值

### Step 3 · 压到 ≤3 步最短路径
从签约到激活，**步骤 ≤3**。每多一步，流失率约翻倍。把可以代做的（配置、导入）由我们代做，别让客户做。

**判据**：路径步骤 ≤3，且列出哪些由我们代做

### Step 4 · 每步配失败兜底与责任人
每一步写：**失败现象 / 兜底动作 / 责任人 / 时限**。如「第 2 步导入失败 → 发模板 + 人工代导 → 实施 → 24h 内」。

**判据**：每步都有兜底、责任人与时限

### Step 5 · 定度量与回看（激活率 + TTV）
两个数：**激活率**（30 天内达激活的占比）、**TTV 中位数**（不是均值）。按客户规模或渠道分组看，找差异。

**判据**：激活率与 TTV 中位数都定义并采集

### Step 6 · 把卡点回灌产品与支持
同一卡点出现 ≥3 次 → 不是客户问题，是产品问题，提单给 `r07`；出现 1–2 次 → 进支持话术库（`customer-support-sla`）。

**判据**：卡点有归口：产品 bug 与话术缺口分开

## §5 质量门（一票否决）

1. TTV 写成「第 N 天 + 做 X + 得到 Y」，且 Y 是客户可感知成果；
2. 激活定义 = 一个事件 + 一个数值阈值（禁用登录/注册当激活）；
3. 上手路径 ≤3 步，且列出由我们代做的步骤；
4. 每一步都有失败兜底、责任人与时限；
5. 激活率与 TTV 中位数都有定义并在采集；
6. 卡点已归口：产品问题 vs 话术缺口；

> 本卡无自动门禁。激活率与 TTV 可用现有数据算出，这是本卡最硬的自我验证。

## §6 交付前自检清单

- [ ] 我能说出客户在第几天、做什么、得到什么会觉得有用
- [ ] 激活是一个事件加一个阈值，不是「登录了」
- [ ] 上手步骤 ≤3 步，且我标了哪些是我们代做
- [ ] 每一步失败了我都写了谁在多久内做什么
- [ ] 我算过激活率和 TTV 中位数，不是只看平均值
- [ ] 我按客户规模或渠道分过组，看过差异
- [ ] 同一个卡点出现 3 次时，我把它提成了产品问题
- [ ] 不支持的功能我没有在引导里承诺

## §7 易犯错误对照表

| # | 易犯错法 | 正确做法 |
|---|---|---|
| EX-01 | 把注册/登录当激活 | 激活=一个事件+阈值（如首次运行成功） |
| EX-02 | 上手步骤 8 步 | ≤3 步，其余代做 |
| EX-03 | TTV 写成「完成配置」 | 写成客户可感知的成果 |
| EX-04 | 不写失败兜底 | 每步配现象/动作/责任人/时限 |
| EX-05 | 只看平均 TTV | 看中位数与分位 |
| EX-06 | 卡点不归口 | 产品问题提单，话术缺口进支持库 |
| EX-07 | 引导承诺未上线功能 | 只承诺当前可用的 |
| EX-08 | 全客户一套引导 | 按规模/角色分路径 |
| EX-09 | 不度量 | 激活率 + TTV 必须采集 |
| EX-10 | 把客户不用当客户问题 | 同一卡点 ≥3 次视为产品问题 |

## §8 降级与边界

| 触发情况 | 处置 |
|---|---|
| 无产品埋点 | 用登录+核心动作反推，标注「近似激活」 |
| 客户拒绝提供数据 | 用访谈确认 TTV，标注「非全量」 |
| 大客户定制交付 | 走人工实施，单独定义 TTV |
| 产品功能未就绪 | 明确不做该路径，标注「待功能上线」 |
| 多角色采购 | 按决策者/使用者分别定激活 |
| 自助产品无人力 | 只做产品内引导，标注「无人工兜底」 |

**明确不做**：不做健康分与 QBR、不做续约谈判、不做客服 SLA、不做产品功能。
