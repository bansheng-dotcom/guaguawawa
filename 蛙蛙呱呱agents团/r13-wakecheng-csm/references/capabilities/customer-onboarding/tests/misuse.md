# 负向测试集（misuse cases）

> **本卡是 knowledge 卡**（`entry: null`），本表是**人工评审清单**，逐条判真假。
> 版本：v2.0.0

## 一、硬门（§5，任一不过即不得交付）

| # | 判据 | 出处 |
|---|---|---|
| MU-01 | TTV 写成「第 N 天 + 做 X + 得到 Y」，且 Y 是客户可感知成果 | §5 第 1 条 |
| MU-02 | 激活定义 = 一个事件 + 一个数值阈值（禁用登录/注册当激活） | §5 第 2 条 |
| MU-03 | 上手路径 ≤3 步，且列出由我们代做的步骤 | §5 第 3 条 |
| MU-04 | 每一步都有失败兜底、责任人与时限 | §5 第 4 条 |
| MU-05 | 激活率与 TTV 中位数都有定义并在采集 | §5 第 5 条 |
| MU-06 | 卡点已归口：产品问题 vs 话术缺口 | §5 第 6 条 |

## 二、软门（§6 自检，靠人抓）

| # | 常见错法 |
|---|---|
| MU-06 | 我能说出客户在第几天、做什么、得到什么会觉得有用 |
| MU-07 | 激活是一个事件加一个阈值，不是「登录了」 |
| MU-08 | 上手步骤 ≤3 步，且我标了哪些是我们代做 |
| MU-09 | 每一步失败了我都写了谁在多久内做什么 |
| MU-10 | 我算过激活率和 TTV 中位数，不是只看平均值 |
| MU-11 | 我按客户规模或渠道分过组，看过差异 |
| MU-12 | 同一个卡点出现 3 次时，我把它提成了产品问题 |
| MU-13 | 不支持的功能我没有在引导里承诺 |

## 三、诚实说明

本卡没有可自动断言的门禁：上手路径的好坏取决于客户是否真的到达价值，只能由激活率与 TTV 事后验证。

## 四、怎么验（没门禁时的替代验证）

1. **双评**：两人独立按 §5 逐条判，一致率 ≥80%；
2. **抽样反查**：随机抽 3 条要求指出具体位置/数字；
3. **对照抽检**：与 `references/onboarding-path.md` 里的 BAD/GOOD 并列看。

> **纪律**：上手的目标不是「让客户完成流程」，是「**让客户在第 2 天就觉得这东西有用**」。
