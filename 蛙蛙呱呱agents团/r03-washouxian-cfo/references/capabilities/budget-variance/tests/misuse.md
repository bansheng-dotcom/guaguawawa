# 负向测试集（misuse cases）

> **本卡是 knowledge 卡**（`entry: null`），本表是**人工评审清单**，逐条判真假。
> 版本：v2.0.0

## 一、硬门（§5，任一不过即不得交付）

| # | 判据 | 出处 |
|---|---|---|
| MU-01 | 科目 / 期间 / 币种三项口径已对齐并声明 | §5 第 1 条 |
| MU-02 | 逐科目算差异，不只给总额 | §5 第 2 条 |
| MU-03 | 每个重大差异做了价格/数量/结构三段拆解，且三段可加总回总额 | §5 第 3 条 |
| MU-04 | 重大差异归入「可解释」或「需追责」两类之一 | §5 第 4 条 |
| MU-05 | 每条整改动作都有验证指标与回看日期 | §5 第 5 条 |
| MU-06 | 判断了差异性质：执行偏差 vs 预算假设错误 | §5 第 6 条 |

## 二、软门（§6 自检，靠人抓）

| # | 常见错法 |
|---|---|
| MU-06 | 科目/期间/币种我确认过一致，不一致的地方我修了口径 |
| MU-07 | 我逐科目算了差异，并用金额降序排 |
| MU-08 | 最大的三项差异我都做了三段拆解 |
| MU-09 | 三段加起来等于总额差（我复算过） |
| MU-10 | 每个重大差异我都归了类（可解释/需追责） |
| MU-11 | 整改动作有验证指标，不是「加强管控」 |
| MU-12 | 我判断过：这是执行问题还是预算本身定错了 |
| MU-13 | 我没有把「业务增长带来的增长」当成超支 |

## 三、诚实说明

本卡没有可自动断言的门禁：差异归因依赖业务量指标与台账，不是固定 schema。唯一的自我验证是三段加总——人工必须复算一次。

## 四、怎么验（没门禁时的替代验证）

1. **双评**：两人独立按 §5 逐条判，一致率 ≥80%；
2. **抽样反查**：随机抽 3 条要求指出具体位置/数字；
3. **对照抽检**：与 `references/variance-bridge.md` 里的 BAD/GOOD 并列看。

> **纪律**：差异分析的目标不是「解释超支」，是「**判断这个月该改动作还是改预算**」。
