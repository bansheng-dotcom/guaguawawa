# 负向测试集（misuse cases）

> **本卡是 knowledge 卡**（`entry: null`），本表是**人工评审清单**，逐条判真假。
> 版本：v2.0.0

## 一、硬门（§5，任一不过即不得交付）

| # | 判据 | 出处 |
|---|---|---|
| MU-01 | 每个事件对应一个明确的度量问题（含主体/场景/动作/指标） | §5 第 1 条 |
| MU-02 | 事件名遵循 `<对象>_<动作>`，无缩写与数字编号 | §5 第 2 条 |
| MU-03 | 必填属性 ≥3 个，且含 `user_id` 与 `occurred_at` | §5 第 3 条 |
| MU-04 | 触发时机写明，且「发起」与「成功」分为两个事件 | §5 第 4 条 |
| MU-05 | 漏斗逐步显式声明，每步有时间窗 | §5 第 5 条 |
| MU-06 | 数据字典齐全，属性变更走版本升级（不原地改） | §5 第 6 条 |
| MU-07 | 上线 7 天内做过回看（量级/缺失率/漏斗异常） | §5 第 7 条 |

## 二、软门（§6 自检，靠人抓）

| # | 常见错法 |
|---|---|
| MU-07 | 每个事件我都能说出它回答哪个问题 |
| MU-08 | 事件名是「对象_动作」，不是 click1/btn2 |
| MU-09 | 必填属性里有 user_id 和 occurred_at |
| MU-10 | 触发时机写清了，且「点击」和「成功」是两个事件 |
| MU-11 | 漏斗我逐步列了，每步有时间窗 |
| MU-12 | 我没有用「A 之后有 B」推导漏斗 |
| MU-13 | 字典里每个事件有负责人和上线日期 |
| MU-14 | 改过属性的都升了版本，没有原地改 |
| MU-15 | 上线 7 天内我回看过量级、缺失率、漏斗 |

## 三、诚实说明

本卡没有可自动断言的门禁：埋点设计是契约设计，质量取决于「埋的东西能不能回答业务问题」，而这只能靠回看数据验证。结构校验（`quality check`）只能验字段齐不齐。

## 四、怎么验（没门禁时的替代验证）

1. **双评**：两人独立按 §5 逐条判，一致率 ≥80%；
2. **抽样反查**：随机抽 3 条要求指出具体位置/数字；
3. **对照抽检**：与 `references/event-schema.md` 里的 BAD/GOOD 并列看。

> **纪律**：埋点的目标不是「多采点数据」，是「**每个数都能追溯到为什么采它**」。
