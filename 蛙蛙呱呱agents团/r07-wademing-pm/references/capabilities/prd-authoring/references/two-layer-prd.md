# 两层 PRD · AC/DoD · RICE（two-layer-prd）

> 被 §3、§5、§7 按需引用。版本：v2.0.0（项目自建，v1）

---

## 一、为什么是两层

一份 PRD 同时要服务两类读者，而他们的需求相反：

| 层 | 读者 | 要回答 | 载体 | 门禁 |
|---|---|---|---|---|
| **战略层** | 创始人 / 产品 / 数据 | 为什么做、给谁做、做到什么算赢 | `examples/prd.json` 形状 | `python harness.py prd` |
| **执行层** | 设计 / 工程 / 测试 | 具体行为是什么、边界在哪 | `prdguard` 规范 | `python agent.py prdguard check` |

**两层 schema 不通用**，这是本项目最容易踩的坑：

- 战略层字段：`problem_statement` / `users[]` / `value_proposition{}` / `scope{p0,p1,p2,non_goals}` / `metrics{}` / `acceptance_criteria[]` / `risks[]` / `executive_summary`
- 执行层字段：`title` / `product_contract{user,trigger,job,completion}` / `p0_features[{name,trigger,rule,result,state,source}]` / `non_goals[]` / `edge_cases[]` / `assumptions[]` / `open_questions[]` / `summary`

> 用战略层 JSON 去跑 `prdguard` 会报"标题非空 / 契约四要素缺失"——不是门禁坏了，是喂错了层。

## 二、AC 与 DoD 的区别（最常被混为一谈）

| | AC（Acceptance Criteria） | DoD（Definition of Done） |
|---|---|---|
| 归属 | **这一条需求** | **整个团队** |
| 回答 | 这个需求怎样算做完了 | 我们默认什么标准才算交付 |
| 示例 | "取消后 7 天内可原价恢复，且恢复后数据不丢" | "通过代码评审、有单测、有监控、文档已更新" |
| 写在哪 | PRD 的 `acceptance_criteria` | 团队规范 / 工程 SOP |
| 变化频率 | 每条需求都不同 | 长期稳定 |

**混用的后果**：把 DoD 写进 AC，会让每条需求都"看起来完成"却没人验证业务行为；
把 AC 写进 DoD，会让团队标准变成业务细节的堆砌。

**写法**：AC 用 `{given, when, then}` 三件套，每条都能判真假。

```json
{"given": "用户已完成订阅", "when": "在账单页点取消", "then": "7 天内可原价恢复且数据不丢"}
```

## 三、RICE 优先级（>3 个候选时才用）

```
RICE = (Reach × Impact × Confidence) / Effort
```

| 因子 | 含义 | 取值口径 |
|---|---|---|
| `Reach` | 影响多少用户（一段时间内） | 用真实活跃数，不用注册数 |
| `Impact` | 对单个用户影响多大 | 3=巨大 / 2=高 / 1=中 / 0.5=低 / 0.25=极小 |
| `Confidence` | 对以上估计的信心 | 100% 有数据 / 80% 有访谈 / 50% 有判断 / 20% 纯猜 |
| `Effort` | 人月 | 含设计+开发+测试+上线 |

**算例（必须带算式，不许只给分数）**

```
功能 A：（8000 用户 × 2 × 0.75） / 4 人月 = 3000
功能 B：（2000 用户 × 3 × 0.5）  / 1 人月 = 3000
```

> A 与 B 同分 → 说明纯算分不足以决策，需引入**战略权重**或**依赖关系**再判。
> 出现这种情况时，把判断理由写进 `open_questions`，而不是偷偷改分数。

**三条纪律**：
1. `Confidence` 必须能说出依据；纯猜就写 20%，不要写 80%；
2. `Effort` 不许只算开发，必须含设计与测试；
3. **算完不复核**＝白算。RICE 排完必须人工过一遍"这条是不是真该先做"。

## 四、PRD 十二项审批清单（交付前逐条打勾）

- [ ] 1. 问题一句话能说清，且不是"我们要做 X 功能"
- [ ] 2. 目标用户有场景，不只是人群标签
- [ ] 3. 写清了用户现在怎么凑合、代价多大
- [ ] 4. 价值主张 `after` 是可观察状态
- [ ] 5. P0/P1/P2 分层明确
- [ ] 6. `non_goals` ≥ 2 且各有理由
- [ ] 7. 每个 P0 四段齐全（触发/规则/结果/状态）
- [ ] 8. 每个 P0 的 `source` 在枚举内且真实
- [ ] 9. 假设与待验证问题成对
- [ ] 10. AC 全是 `{given, when, then}`
- [ ] 11. 边界覆盖空/错/取消/重试至少一项
- [ ] 12. 指标有 baseline + target + data_source + 护栏

> 12 条全过才可标记"可进入开发"。**缺任意一条就标"待补齐"，不要用"基本齐了"糊过去。**

## 五、与下游的交接

| 交给谁 | 给什么 | 不给什么 |
|---|---|---|
| `r08` MVP | 执行层 JSON（`p0_features` 四段） | 战略层讨论过程、未被采纳的方案 |
| `r09` 工程 | 执行层 JSON + `open_questions` 里的技术疑问 | 实现方案（由 r09 出） |
| `r10` 设计 | `product_contract` + `edge_cases` | 视觉偏好（由 r10 提方案） |
| `r04` 评审 | 两份 JSON + AC 清单 | 你自己的评价（自评不算数） |

**交接铁律**：只交 JSON，不交"我们讨论下来大概是……"。
讨论过程无法被门禁校验，也无法被下游复现。
