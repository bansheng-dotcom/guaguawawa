# 评审分级（Review Tiering）

> 一句话定位：**评审漏东西，往往不是不认真，是"把该收口判的项当成逐项项，或者反过来"。**
>
> 举个真实类型的错：把「所有测试都通过」这种**只有全部做完才能判**的项，
> 要求每提交一次就勾一次——评审者只能撒谎或流于形式。
> 反过来，把「改了哪三个文件」这种**可以逐项核对**的项留到最后一次性看，
> 就失去了发现漏改的机会。
>
> 这张卡就是分清这两类，并给出证据回溯的方法。

## §1 何时用 / 何时不用

**该用（用户真实会这么说）**
- 「评审要做多细」「哪些必须逐项看」
- 「这个 checklist 怎么勾」
- 「为什么每次评审都走过场」「怎么发现漏做」

**不该用，转给谁**

| 用户其实想要 | 转给 | 理由 |
|---|---|---|
| 直接出 pass/fail 结论 | `r04` 的 `review-anti-collusion` | 那是评审本体 |
| 判断产物好不好看 | `r10` 的 `visual-hierarchy` | 那是品味判据 |
| 写规范的结构 | `r04` 的 `bad-good-contrast` | 那是写法 |
| rubric 打分与校准 | `r04` 的 `rubric-calibration` | 那管评分 |

**最小可开工输入**：**一份 checklist 或评审要求**。

## §2 前置输入与最省追问

| 输入 | 是否必需 | 缺失时怎么办 |
|---|---|---|
| checklist 或评审项清单 | 必需 | 无清单无法分级 |
| 提交历史 / 交付记录 | 建议 | 缺则只能判「项该怎么分」，判不了节奏 |
| 产物本身 | 必需（做结论时） | 无产物不做评价 |

**追问纪律**：最多一轮，只问**这次评审要判的是哪些项、有没有提交记录**。

## §3 执行流水线（Workflow）

### Step 1 · 给每个评审项打 Tier（一句话判据）
**判据**：这个项**能不能在单个提交里被验证**？

| Tier | 判据 | 典型项 |
|---|---|---|
| **A（逐项）** | 描述的是**一个具体可指认的产物**（某文件、某函数、某章节、某表格） | 改了哪几处、加了哪个测试、补了哪张图 |
| **B（收口）** | 描述的是一个**只有全部完成后才能观测的条件** | 全部测试通过、无遗留 TODO、整体一致性、最终验收 |

**分类口诀**：**项里点了具体东西 → A；项里说的是"整体/全部/最终" → B。**

### Step 2 · 校验节奏（A 必须交错，B 必须收口）
| Tier | 正确节奏 | 错的节奏 | 后果 |
|---|---|---|---|
| A | 与提交**交错**（改一个验一个） | 攒到最后一次全勾 | 漏改无法发现 |
| B | **全部完成后**一次判 | 每提交一次就勾一次 | 只能撒谎或形式化 |

**阈值**：A 项的勾选顺序与提交顺序的**一致性 ≥80%**；B 项在中期被勾选的**数量 = 0**。

### Step 3 · 证据回溯（这是评审最硬的一招）
对每条「已完成 / 已修复 / 已通过 / 已验证」的声称：

1. **回看同一轮**：这一轮里有没有工具输出、diff、日志能证明它？
2. **找不到 → 记为「无证据声称」**，不管声称者多可信。
3. **有证据但证据过期**（针对旧版本）→ 记为「证据失效」。

**判据**：无证据声称**数量为 0** 才可给 pass。

### Step 4 · 抽样反查（防"逐项勾了但没看"）
从 A 项里**随机抽 3 项**，要求指出「在哪一行 / 哪个文件 / 哪一页」。
- 指不出来 → 该批评审走过场，整份 checklist 作废重做；
- 指得出来 → 通过。

**阈值**：抽样 **3 项**，成功率须 **3/3**。

### Step 5 · 出分级结论（不做"总体还行"）
| 结论 | 条件 |
|---|---|
| **pass** | A 全核 + B 全收口 + 无证据声称 0 + 抽样 3/3 |
| **conditional** | 仅 B 类条件未完全满足，且已写明何时补 |
| **fail** | A 有漏、或无证据声称 >0、或抽样失败 |

## §5 质量门（一票否决）

1. 每个评审项都标了 **A 或 B**，且附一句话判据；
2. **A 项与提交交错**（一致率 ≥80%），**B 项中期勾选数为 0**；
3. **无证据声称数为 0**（每条完成声称都有同轮证据）；
4. **抽样反查 3/3** 成功（能指出具体位置）；
5. 结论是 **pass / conditional / fail** 三选一，不是「总体还行」。

> 本卡无自动门禁。可配合 `python agent.py artifact verify --input <产物.json>` 做结论侧校验（间接）。

## §6 交付前自检清单

- [ ] 每个项都能一句话说清是 A 还是 B
- [ ] A 项的勾选节奏和提交节奏对得上
- [ ] B 项里没有一条在中期被勾选
- [ ] 每条「已完成」我都回看了同一轮的证据
- [ ] 我列出了所有无证据声称（包括听起来很合理的）
- [ ] 我随机抽了 3 个 A 项，都能指出具体位置
- [ ] 结论是三选一，且写了理由
- [ ] 我没有因为「对方资深」就跳过证据检查

## §7 易犯错误对照表

| # | 易犯错法 | 正确做法 |
|---|---|---|
| EX-01 | 把「全部测试通过」当逐项项 | 那是 B 类，收口判 |
| EX-02 | 把「改了哪些文件」留到最后看 | 那是 A 类，必须交错 |
| EX-03 | 一口气勾完所有项 | A 项必须与提交交错 |
| EX-04 | 中期就把 B 类勾了 | B 类只能整体完成时判 |
| EX-05 | 只听说"已完成"就记通过 | 回看同轮证据 |
| EX-06 | 证据针对旧版本 | 记「证据失效」 |
| EX-07 | 勾了但指不出位置 | 抽样 3 项反查 |
| EX-08 | 结论写「总体还行」 | pass / conditional / fail |
| EX-09 | 因对方资深而放宽证据 | 证据面前无资历 |
| EX-10 | 抽样只抽最简单的 3 项 | 随机抽，不许挑 |
| EX-11 | 把 A 项拆得过细（100+ 项） | A 项控制在可核对范围（≤20） |
| EX-12 | 评审完不改 checklist | 每次评审后校准分级表 |

## §8 降级与边界

| 触发情况 | 处置 |
|---|---|
| 无提交历史可查节奏 | 只做 A/B 分级与证据回溯，标注「未核节奏」 |
| 项数过多（>50） | 先按 Tier 分组，只抽 A 组核 |
| 无法取得工具输出 | 标注「无证据可核」，结论最高只能 conditional |
| 评审对象是文档 | A = 具体章节/表格，B = 整体一致性 |
| 时间极紧 | 可只核 A 类 + 抽样，B 类延后但必须写明 |
| 被要求"快速过一下" | 明说「快速过 = 只核 A + 抽样，不给 pass」 |

**明确不做**
- 不生产、不改稿、不替他人质量背书、不与他人协商出结论。
