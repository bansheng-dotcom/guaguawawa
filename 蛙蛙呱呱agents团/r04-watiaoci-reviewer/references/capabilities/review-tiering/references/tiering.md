# 评审分级细则（tiering）

> Tier A/B 判据 · 节奏校验 · 证据回溯 · 抽样反查。版本：v1（P1 起步）

---

## 一、A/B 分级：一句话判据

> **项里点了具体东西 → A；项里说的是"整体/全部/最终/一致" → B。**

| 项（真实样式） | Tier | 为什么 |
|---|---|---|
| 已完成登录页的表单校验 | **A** | 点了具体产物（登录页表单） |
| 已新增 `test_refund_ratio.py` 三个用例 | **A** | 点了具体文件与数量 |
| 报告第 3 章补了对照表 | **A** | 点了具体章节 |
| 全部单元测试通过 | **B** | 只有全部做完才能观测 |
| 无遗留 TODO | **B** | 全仓扫描才成立 |
| 文档与实现一致 | **B** | 整体比对 |
| 已通过最终验收 | **B** | 终态条件 |
| 代码风格统一 | **B** | 整体属性 |

**边界情形**：
- 「重构了支付模块」→ **A**（可指出哪个文件哪几处）
- 「重构没有引入回归」→ **B**（要全量回归跑完才能说）

## 二、节奏校验（这是最容易被忽略的）

### A 类：必须与提交交错

```
✅ 正确
提交1: 改 login.py  → 勾「登录页表单校验」(A1)
提交2: 加 test_*.py → 勾「新增三个用例」(A2)
提交3: 改 report.md → 勾「第3章补对照表」(A3)

❌ 错误（batching）
提交1..3 都没勾
提交4: 一次性勾 A1 A2 A3
```

**为什么错**：攒着勾的时候，人只能凭记忆勾；凭记忆就会漏，且事后无法查证。

**量化**：A 项勾选顺序与提交顺序的一致性 **≥80%**。

### B 类：必须收口

```
✅ 正确
中途不勾；全部提交完成后，跑到全量测试 → 勾「全部测试通过」

❌ 错误（提前勾）
提交2 就勾「全部测试通过」——此时还有 60% 的代码没写
```

**为什么错**：提前勾 B 类只有两条路——撒谎，或把勾选当成形式。两者都让 checklist 失效。

**量化**：B 项在**中期**（进度 <80%）被勾选的数量 **= 0**。

## 三、证据回溯（评审最硬的一招）

对每条声称（已完成 / 已修复 / 已通过 / 已验证 / 已上线）：

| 步骤 | 问法 | 结论 |
|---|---|---|
| 1 | 这一轮里有没有工具输出/diff/日志？ | 没有 → **无证据声称** |
| 2 | 证据是否针对**当前版本**？ | 针对旧版 → **证据失效** |
| 3 | 证据是否直接支持这条声称？ | 只能间接推测 → **证据不足** |

**示例**

```
声称：「退款比例校验已修复」
同轮证据：「pytest test_refund.py 输出 3 passed」
判定：✅ 有效（直接支持）

声称：「已修复退款 bug」
同轮证据：只有文件 diff，没有测试运行
判定：⚠ 证据不足（改了 ≠ 修好了）

声称：「全部测试通过」
同轮证据：上一版的测试输出
判定：❌ 证据失效
```

**阈值**：**无证据声称数 = 0** 才可给 pass。有一条就只能 conditional。

## 四、抽样反查（防"勾了没看"）

**做法**：从 A 项里**随机**抽 3 项，逐个问：
「这一项具体在哪？第几行 / 哪个文件 / 哪一页？」

| 结果 | 判定 |
|---|---|
| 3/3 指得出来 | 通过 |
| 2/3 | 该批评审不完整，重核剩余项 |
| ≤1/3 | **整份 checklist 作废重做**（走过场） |

**为什么要抽样**：全部复核成本高，但不抽就无法区分「认真核过」和「全勾了但没看」。
3 项是个平衡点——低于 3 抓不住，高于 3 太贵。

**禁止**：抽自己最熟的那 3 项。抽样要随机（可用编号抽签）。

## 五、分级结论表

| 结论 | 条件（全部满足） |
|---|---|
| **pass** | A 项全核 + B 项全收口 + 无证据声称 0 + 抽样 3/3 |
| **conditional** | 有 ≤2 条 B 类未满足，且写明何时补、谁补 |
| **fail** | A 项有漏 / 无证据声称 >0 / 抽样失败 / 有越权行为 |

**禁止**的结论写法：「总体还行」「基本通过」「问题不大」——都不是判据。

## 六、checklist 本身的健康度

评审完顺手看一眼 checklist 有没有病：

| 病 | 表现 | 处方 |
|---|---|---|
| A/B 错置 | B 类项被要求每次勾 | 移到收口区 |
| A 项过细 | 100+ 项，无法逐项核 | 合并到 ≤20 项 |
| 不可判 | 「代码质量良好」 | 换成可指认项（见 `bad-good-contrast`） |
| 无证据要求 | 只写"完成后勾选" | 补「须附证据」 |
| 从不校准 | 三个月没改 | 每次评审后收集"哪项最难勾" |
