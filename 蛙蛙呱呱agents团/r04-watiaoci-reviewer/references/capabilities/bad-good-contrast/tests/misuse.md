# 负向测试集（misuse cases）

> **本卡是 knowledge 卡**（`entry: null`），因此本表是**写规范时的常见错法清单**，
> 由评审者逐条判真假。版本：v2.0.0

## 一、硬门（§5，任一不过即不得作为规范发布）

| # | 错法 | 判据 | 怎么验 |
|---|---|---|---|
| MU-01 | 某条原则只有文字没有对照 | 每条原则 ≥1 组同场景错/对例 | 逐条数 |
| MU-02 | 错例是编的，错得太明显 | 错例为真实样本且有出处 | 问「什么时候在哪出的问题」 |
| MU-03 | 错对例不是同一场景 | 同场景同内容，只改判据点 | 把两例并排看内容是否一致 |
| MU-04 | 差异点写「感觉更好」 | 差异点可指认（位置/字号/词/顺序） | 让对方照着差异点指出位置 |
| MU-05 | 通篇无数字阈值 | 每条原则 ≥1 个数字 | 数阈值个数 |
| MU-06 | 抽象句占比过高 | 抽象句 ≤20% | 抽样 10 句数抽象句 |

## 二、软门（§6 自检，靠人抓）

| # | 错法 | 问题 |
|---|---|---|
| MU-07 | 场景句没有「人 + 动作 + 条件」 | 无法复现，判据无从落地 |
| MU-08 | 阈值定得离谱（≥10×） | 做不到 → 团队直接放弃整条规范 |
| MU-09 | 一条原则配 10 组对照 | 太长没人看完，等于没写 |
| MU-10 | 直接搬英文 tech demo | 中文长度/标点/行业习惯不同，水土不服 |
| MU-11 | 做完不双评就发布 | 无法确认「别人能判出同样结论」 |
| MU-12 | 把审美偏好写成规范 | 偏好不可判，会引发无休止争论 |
| MU-13 | 判据依赖颜色/装饰 | 灰化后判据消失，说明判的是装饰不是结构 |

## 三、双评怎么做（这是本卡唯一的"验收"）

1. 找两人独立按 §5 六条打分（通过/不通过），**不互相看**；
2. 计算一致率 = 一致条目 / 总条目；
3. **一致率 <80% → 先改规范（多半是差异点写得不具体），不要怪评审人**；
4. 改完重评，直到 ≥80%。

## 四、诚实说明

本卡没有可自动断言的门禁：它判的是「一份规范写得好不好」，输入是文档而不是固定 schema。
写一个「永远 exit 0」的脚本只会制造假绿——比没有门禁更糟。

> **纪律**：规范的唯一标准是「别人拿它能判出同样的结论」。
> 达不到这一点，写得再漂亮也只是感想。
