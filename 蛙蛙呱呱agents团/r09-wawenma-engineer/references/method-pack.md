# R09 蛙文码 · 工程师 · 方法包（Method Pack v1）

## 1. 决策问题

- 典型决策：这个方案能不能上线、架构怎么选。
- 决策者：技术负责人；成功标准：可维护、可回滚、有测试与监控。
- 非目标：不做无测试的重构、不做一次性脚本冒充系统。

## 2. 问题树（MECE）

| 分支 | 要回答 | 假设 | 数据 | 方法 |
|---|---|---|---|---|
| 需求 | 要解决什么、边界在哪 | 需求稳定且可验收 | 需求文档/接口 | 用例 + 约束清单 |
| 方案 | 有哪几种做法、取舍 | 选型可辩护 | 技术调研 | ADR + 权衡表 |
| 风险 | 会怎么坏 | 故障可发现可回滚 | 故障树 | FMEA + 演练 |
| 交付 | 怎么上、怎么退 | 灰度 + 回滚 | 发布计划 | 发布检查单 |

**critical branch**：`风险`——资源优先给它。

## 3. 假设与证伪

- H1：该方案在峰值负载下 P95 延迟 ≤ 目标。
- H2：故障时可 5 分钟内回滚到上一版本。
- 竞争解释（至少 2 个）：问题在代码，还是在数据/依赖？；是容量不足，还是查询写错？
- 每条假设必须有**杀死标准**：指标 + 阈值 + 观察窗口。

## 4. 证据分级

| 级别 | 来源 | 允许用法 |
|---|---|---|
| A | 系统记录、合同、官方数据、可复算台账 | 可进结论与决策 |
| B | 行业报告、供应商报价、抽样数据 | 方向 + 区间 |
| C | 访谈、估算、单点经验 | 标注 + 敏感性 |

**规则**：每个结论挂来源；同名不同口径单列；缺什么、影响什么、怎么补，必须写清；C 级超过 3 条时结论降级为「条件成立」。

## 5. 方法与陷阱

- ADR：记录背景、选项、决定、后果，一次一页。
- 权衡表：性能/成本/复杂度/可维护性四项打分。
- 故障注入/演练：上线前验证回滚与降级。
**陷阱清单**：
- 过度设计
- 忽略运维与告警
- 无测试就重构
- 把「能跑」当「能上线」
工程结论必须给「怎么坏、怎么退」，否则不算完成。

## 6. 输出契约

```
claim        一句话结论（方向 + 幅度 + 范围/时间）
evidence     来源 + 观测/记录 + 口径
confidence   A/B/C + 区间（无区间写「点估计，未验证」）
falsifier    什么新证据会推翻它
```

缺任一项 → 不得进首页；建议缺负责人/阈值 → 行动性不通过。

2. 问题树 MECE 吗？critical branch 对吗？

4. 竞争解释排除了几个？
5. 每个数字能回指来源吗？
6. 有对照/基线吗？匹配了吗？
7. 结论带区间吗？
8. 最可能错在哪？
9. 建议有负责人/阈值/时间吗？
