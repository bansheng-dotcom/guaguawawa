# ADR 与架构取舍：把「为什么」写进代码仓

> 适用角色：R09 工程官；对应工程链第 1 段 `adr`。
> 本文只讲可执行做法，不讨论组织政治。

## 1. 来源

- Michael Nygard, *Documenting Architecture Decisions*（2011）：提出用短文档记录
  Context / Decision / Consequences，ADR 一词由此普及。
- MADR（Markdown Any Decision Records）3.0：给出可复用的 Markdown 模板与
  「考虑过的方案」章节，强调备选方案必须留痕。
- ISO/IEC/IEEE 42010:2022：架构描述需要说明关注点（concern）、视角（viewpoint）
  与决策理由，ADR 是其中一种轻量载体。
- Martin Fowler, *Architecture TradeOffs*（2019）：架构没有免费选项，记录收益时必须
  同时记录代价与缓解手段。

以上来源均为公开资料；本文只做工程化裁剪，不替代原文档。

## 2. 适用边界

适合：

- 存在两个以上真实可选方案，且选择会影响模块边界、数据归属、部署形态或运维成本；
- 决定一旦落地，回退成本高于半天；
- 需要让后来者在不打扰原作者的情况下理解「为什么不是另一个方案」。

不适合：

- 既定事实（公司只允许某云、语言由平台决定），写 ADR 只是复述约束；
- 纯实现细节（变量命名、单个函数是否抽取），应进提交信息或代码注释；
- 可逆的小改动（换一个日志库且可在一天内回滚），用 PR 描述即可；
- 把 ADR 当设计文档写：ADR 记录决策与后果，不展开接口字段和表结构。

## 3. 方法：五件套

1. **背景（Context）**：一段话写清问题、触发事件与硬约束。约束至少两条，且必须是
   可验证的事实，例如「只允许标准库」「必须离线运行」「数据不能出境」。
2. **候选（Options）**：至少两个，每个都写优点与代价。只有一个候选时，ADR 退化为
   通知，评审应拒绝。
3. **决定（Decision）**：从候选中选一个，写一句可被反对的理由。理由要指向约束，
   而不是「团队熟悉」这类无法验证的偏好。
4. **后果（Consequences）**：分正向、负向、风险三类。负向后果必须能对应到一条缓解
   措施或一个有负责人的行动项。
5. **边界（Boundaries）**：每个模块写 `owns` 与 `does_not_own`。不写「不负责」的
   边界等于没写边界，后续一定扯皮。

## 4. 仓内落点

`eng_chain/adr.py` 把上述五件套变成可校验结构，门禁如下：

| 门禁 | 检查内容 | 失败级别 |
|---|---|---|
| `adr:context` | 背景问题非空，约束 ≥2 条 | CRITICAL |
| `adr:options` | 候选 ≥2，且每个都有优点与代价 | CRITICAL |
| `adr:decision` | 决定必须来自候选项，且有理由 | CRITICAL |
| `adr:boundaries` | 模块 ≥2，逐个写 owns / does_not_own | CRITICAL |
| `adr:tradeoffs` | 取舍 ≥2，逐条写收益与代价 | CRITICAL |

`adr.json` 与 `adr.md` 会随 `eng_manifest.json` 一起落盘，manifest 记录 sha256，
便于事后审计「当时到底比较了哪几个方案」。

## 5. 误用反例

| 反例 | 后果 | 拦截门禁 |
|---|---|---|
| 只写「采用 A」，没有候选 B/C | 无法判断是否被锁定供应商 | `adr:options` |
| 把「因为时间紧」当决策理由 | 下次同样会因时间紧做出相反决定 | `adr:decision` |
| 模块只写负责什么，不写不负责什么 | 边界重叠，故障归属不清 | `adr:boundaries` |
| 只写收益不写代价 | 上线后才发现并发/运维代价 | `adr:tradeoffs` |
| 用 ADR 代替接口文档 | 字段与错误码无契约，联调靠猜 | `api:contract_refs` |
| 决定后不写复审触发条件 | 环境变化后仍沿用旧决策 | 工程评审（人工） |

## 6. 检查清单

- [ ] 背景里每条约束都能被一条命令或一份制度验证；
- [ ] 每个候选都写了「在什么条件下它会赢」；
- [ ] 决定的理由引用了至少一条约束；
- [ ] 每个负向后果都有缓解措施或行动项；
- [ ] 每个模块的 `does_not_own` 指向另一个明确模块；
- [ ] ADR 编号、状态（proposed / accepted / superseded）可追踪；
- [ ] 与 `api`、`release` 段无冲突：迁移、回滚、版本策略能对上。
