## 1. 外部研究给了什么

### 1.1 MAST：多智能体为什么失败

[Why Do Multi-Agent LLM Systems Fail?](https://arxiv.org/abs/2503.13657) 用 7 个框架、200+ 轨迹归纳出
**3 类 14 种失败模式**：

| 类别 | 占比 | 典型失败模式 |
|---|---|---|
| **FC1 规格问题** | 41.77% | 不遵守任务要求 10.98%、步骤重复 17.14%、上下文丢失 3.33%、不识别任务完成 9.82% |
| **FC2 智能体间错位** | 36.94% | 带着错误假设推进 11.65%、任务跑偏 7.15%、隐瞒关键信息 1.66%、无视他人输入 0.17%、推理与行动不一致 13.98% |
| **FC3 任务校验** | 21.30% | 过早终止 7.82%、验证不完整 6.82%、验证错误 6.66% |

它的结论很硬：**多数失败来自组织设计，不是模型能力**；简单补丁不够，要做结构性重设计。

### 1.2 语义层：指标一处定义、多端消费

[语义层实践](https://github.com/wangyong9999/lakehouse-wiki/blob/main/docs/bi-workloads/semantic-layer.md) 的核心抽象：
**entities · measures · dimensions · time_spine**；一个指标只定义一次，
BI/报表/API/LLM 都消费同一份定义；指标要有 owner、版本与 lineage。

对我们的意义：**角色各写各的指标名，就是缺这一层**。

## 2. 用 MAST 对照我们的系统

| MAST 失败模式 | 我们的具体表现 | 机制对策 |
|---|---|---|
| 不遵守任务要求（FC1） | 角色交长文、不交行；卡片要求被忽略 | 行级契约 + 未注册指标拒收 |
| 步骤重复（FC1） | 多个角色把同一指标各查一遍 | 度量注册表 + 任务去重 |
| 不识别完成（FC1） | 交上来就算完，没人判“是否够” | 交接签收 + 覆盖门禁 |
| 带错误假设推进（FC2） | 把“全国”当“北京”用 | 强制 entity/scope 字段 |
| 任务跑偏（FC2） | 问品牌份额，交来行业规模 | 子问题绑 metric_id |
| 隐瞒关键信息（FC2） | 口径写在段落里，别人看不到 | 口径进 scope 字段，不进正文 |
| 推理与行动不一致（FC2） | 文字说 A，图上是 B | 图/文共享 slice_id，图数据点=行数 |
| 过早终止（FC3） | 答不了写 missing 就结束 | 缺口走路由（接棒/采购/缩范围） |
| 验证不完整（FC3） | 只验字段齐不齐，不验数能否互算 | 三层校验：行→指标→论点 |
| 验证错误（FC3） | 图从段落反推，验不出对错 | 图只许 query(raw) |

**结论**：我们踩的坑，MAST 全有编号。对策不该是加提示词，而是加**契约与校验层次**。

## 3. 目标形态：数据房（Data Room）

一次跑批产出四件东西，人只做“审论点、改口径、批动作”：

```
out/raw.xlsx        01 原始数据 / 02 度量注册 / 03 冲突 / 04 覆盖 / 05 来源
out/metrics.json    语义层：entities / measures / dimensions / metric types
out/theses.md       3–7 条论点：claim + support_rows + 反例 + 决策含义
out/report.html     章节 = 论点；图 = query(raw)
out/manifest.json   行数/指标数/冲突数/论点覆盖/门禁
```

**报告是数据房的视图，不是数据的替代品。**

## 3.5 数据房在产线中的位置（接入点）

数据房不是第五个孤立产物，它是**产线的中枢**：角色往里交行，R01 从里面取论点，图表 owner 从里面查数，R04 从里面验。

```
用户指令
  │
  ▼
[R01] 澄清 + 拆卡：clarify → issue_tree → grid
  │  产物：clarify.json / issue_tree.json / grid.json
  │  关键：每个子问题绑 metric_id + entity + period（拆卡五测）
  ▼
[R02] 契约与派工：能力匹配 / 任务卡 / DAG / 期限 / 缺口路由
  │  产物：plan.json / cards/*/TASK.md / dispatch.json
  │  关键：卡片里直接写“你要交哪几个 metric 的哪些行”
  ▼
[执行角色] 交行：rows + 一句判断
  │  产物：cards/*/rows.json
  │  约束：未注册 metric 拒收；不写长文、不画图
  ▼
[collect + 数据层] 行级校验 → 归一/去重/冲突 → raw.xlsx + metrics.json
  │  ├─ 冲突 → R02 路由 → metric owner 裁决 → 回写 raw
  │  └─ 缺口 → R02 路由 → 补采 / 缩范围 / 标未答
  ▼
[R01 综合] 跨题聚类 / 矛盾检测 / 按决策影响排序 → theses.md
  │  每条论点挂 support_rows；支撑不足 → 退回补行
  ▼
[图表 owner R06/R09] query(raw) + encoding → 图/表
  ▼
[装配] report.html：章节 = 论点；图 = 查询结果
  ▼
[R04] 三层校验（行 / 指标 / 论点）+ flow 门禁 → manifest
  ▼
交付：数据房 + 报告
```

### 3.5.1 各阶段谁做什么（RACI）

| 阶段 | R（做） | A（拍板） | C（被咨询） | I（被告知） | 代码入口 |
|---|---|---|---|---|---|
| 澄清/拆卡 | R01 | R01 | R05/R06（领域） | R02 | `report clarify` → `card_upgrade.build_grid` |
| 派工/契约 | R02 | R02 | 执行角色 | R01 | `report_dispatch.issue` + `grid_attach` |
| 交行 | 数据角色 | R02（收卡） | R18（口径） | R01 | `cards/*/rows.json` |
| 归一/冲突 | 产线（确定性） | R18（口径裁决） | 提交者 | R02 | `dispatch.collect` → `data_model` |
| 论点 | R01 | R01 | R02/R04 | 全体 | `theses`（待建） |
| 图表 | R06/R09 | R01 | 数据角色 | R04 | `query(raw)`（待建） |
| 验收 | R04 | R04 | R01/R02 | 全体 | 24 条卡门禁 + flow 门禁 |

### 3.5.2 卡片里多出来的东西（角色怎么接）

拆卡后，每张卡不再只说“回答 Q3”，而是：

```
## 你负责的指标（已注册，口径见 metrics.json）
- breakeven.monthly（万元/月，grain=store×month，owner=r03）
- gross_margin.pet_supply（%，grain=category×channel）

## 你必须交的行
| 指标 | entity | period | 说明 |
|---|---|---|---|
| breakeven.monthly | 社区自雇店 | 2026 | 单店模型 |
| breakeven.monthly | 前置仓 | 2026 | 对照 |

## 交付格式
rows.json（每行带 metric_id/entity/period/value/unit/scope/source）
+ 一句判断（≤80 字，含数字）
```

角色拿到卡就知道：**交哪几个指标、哪些主体、哪一期、交给谁验**——这就是“协同”的具体形态。

### 3.5.3 两个回流环

1. **数据回流**：冲突/缺口 → R02 路由 → owner 裁决或补采 → raw 更新 → 覆盖表刷新；
2. **论点回流**：thesis 支撑不足（<3 行）→ 退回 collect/角色补行 → 论点重排。

没有这两个环，数据房就是一次性快照；有了环，它才是活的。

## 4. 四层契约

### 4.1 角色契约（谁交什么）

| 角色类型 | 交什么 | 不交什么 |
|---|---|---|
| 数据角色（r05/r06/r07/r12/r14/r15/r18） | 行：metric_id/entity/period/value/unit/scope/source | 不写长文、不画图 |
| 语义层 owner（r18） | metrics.json（含 owner/version/lineage） | 不生产业务结论 |
| 综合（R01/r02） | theses.json：聚类/矛盾/排序 | 不编数 |
| 图表 owner（r09/r06） | 图/表（query(raw)） | 不改口径 |
| 验收（r04） | 三层校验结论 | 不改稿、不补数 |

### 4.2 行契约

`role / question_id / metric_id / entity_type / entity / value / unit / period / scope / source_id / grade`

### 4.3 语义层契约

```yaml
metric_id: breakeven.monthly
name: 月盈亏平衡点
type: derived            # simple/cumulative/ratio/derived/conversion
unit: 万元/月
grain: [store, month]
additivity: flow
formula: fixed_cost / (gross_margin - variable_cost_rate)
non_additive_dimension: [month]
owner: r03
version: 1
```

规则：**未注册 metric_id 拒收**；同名不同义拆 id；改定义升版本。

### 4.4 论点契约

```yaml
thesis:
  id: T1
  claim: "10 万预算只有社区自雇店能打平"
  support_rows: [R001, R004, R009]
  contradiction: "连锁单店营收更高，但固定成本是 3 倍"
  decision: "先做自雇店；前置仓不进"
  evidence_gaps: ["缺 3 家门店实测"]
  covered_questions: [Q7]
```

## 5. 拆卡到专家水准

### 5.1 五道测试

| 测试 | 判据 |
|---|---|
| MECE | 子问题互斥穷尽；构成类加总 100% |
| 可测 | 能被 `metric_id + entity + period` 回答 |
| 有反例 | 判断带可观测作废条件 |
| 可行动 | 落到人/钱/时间 |
| 决策相关 | 不知道这条会不会改变决定 |

### 5.2 流程

```
问题 → 问题树（≤3 层） → 视角枚举（消费者/门店/经销商/竞品/监管/供应链）
     → 每视角出子问题（STORM 式） → 绑 metric/entity/period
     → 红队质询（另一个角色问“不知道会怎样”）
     → 五测通过才发卡
```

### 5.3 行业问题库（以宠物为例）

| 视角 | 专家会问 | 需要的 metric |
|---|---|---|
| 消费者 | 单只年消费、品类偏好、复购 | `spend.per_pet` / `pref.category` / `repurchase.cycle` |
| 门店 | 单店月销、坪效、洗美占比 | `sales.per_store` / `sales.per_sqm` / `mix.grooming` |
| 经销商 | 库存周转、账期、退换 | `inventory.weeks` / `dso.days` / `return.rate` |
| 竞品 | 份额、价格带、上新 | `share.brand` / `price.band` / `new_sku.count` |
| 监管 | 备案周期、宣称限制 | `reg.lead_time` |
| 供应链 | 到岸成本、时效 | `landed.cost` / `lead_time.days` |

新增业务线先补问题库，再拆卡。

## 7. 路线（P1–P4）

| 阶段 | 动作 | 验收 |
|---|---|---|
| **P1 语义层接产线** | 把 `metrics.json` 升级为 entities/measures/dimensions + 版本 + owner；collect 校验未注册指标 | 未注册拒收率 100%；指标归并率 ≥80% |
| **P2 综合层** | 跨题聚类、矛盾检测、按决策影响排序，产出 theses | must Q 覆盖 100%；每论点 ≥3 行支撑 |
| **P3 图表 owner** | 图只许 query(raw)；关掉段落反推；表 = pivot(raw) | 图覆盖 100%；图数据点=查询行数 |
| **P4 卡片 v5** | 角色交行 + 一句判断；r02/r04 移出执行池 | 每行进 raw；越权拒收 |

**P0（数据层）已完成**，是上面四步的地基。

## 8. 三层校验（对应 MAST FC3）

| 层 | 验什么 | 失败处理 |
|---|---|---|
| 行级 | metric_id 已注册、entity/period/source 齐、单位可换算 | 拒收该行 |
| 指标级 | 同键唯一、冲突已裁决、口径与 grain 一致 | 进 conflicts，owner 裁决 |
| 论点级 | 每条论点 ≥3 行支撑、有反例、覆盖 must Q | 退回综合层 |

## 9. 验收指标

| 指标 | 目标 |
|---|---|
| 行可溯源率 | 100% |
| 指标归并率 | ≥80% |
| 冲突显式率 | 100% |
| 图覆盖率 | 100% 或写明不可画 |
| 论点覆盖率 | must Q 100% |
| 支撑密度 | 每论点 ≥3 行 |
| 正文节数 | = 论点数 |

---

## 10. 不做什么

1. 不用字数验收；
2. 不让角色交文章或图；
3. 不从段落反推数字；
4. 不按问题数决定节数；
5. 不让调度/验收角色进执行池；
6. 不在没有 raw 的情况下做综合。
