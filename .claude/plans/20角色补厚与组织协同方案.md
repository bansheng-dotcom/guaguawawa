# 20 角色 Agent · 补厚与组织协同方案

## 现状诊断（实测数据）

**基础设施是好的**：`agents/core/`（protocol/registry/runner/workspace）已实现端口契约、任务卡、事件流、单写者文件锁、子进程隔离调用。20 个角色的 `agent.py / skills / harness / contracts / review / cases` 骨架**全部已生成**，是真实可跑的代码，不是空壳。

**三个真问题（实测得出，非猜测）**：

1. **参考层厚度极不均**（T14 标准要求每份 reference 四层：方法论→可执行口径→已验证算例→实战踩坑）
   - R03 蛙守线：8 份参考中 **7 份 < 2KB**（1.3–1.9KB），是全域最薄，低于 SOP 红线。
   - R04 有 1 份 < 2KB；R06 有 2 份 < 2KB。
   - 其余角色参考层已达标（19–49KB）。
   - SKILL.md 厚度也不齐：R12 仅 3.5KB、R03 4.2KB，而 R06 8.9KB。

2. **报告产出是「JSON 裸转」不是「交付物」**。实测 `workspace/artifacts/111b876e/ceo_report.md` 内容是 `## ok / ## intent / ## 门禁` 加 JSON 代码块——**只是把 agent 返回的 JSON 拍成 markdown**，没有叙事、没有结论、没有排版。而 SOP 第十节已确立 qiuqiu 编辑级报告为**最低产出线**（设计系统+信息架构+内嵌 SVG+确定性渲染+可追溯），R06 已建 `report_renderer.py` 但**只有 R06 用上了**，其余 19 个角色仍吐裸 JSON。

3. **组织协同停留在「能跑」而非「可运营」**。`TEAM.md` 只有 1.6KB、单一「停车场营收」案例；R01 编排器有路由矩阵和波次/环检测，但**缺少**：单角色被直接调用时的任务展开协议、失败/越界时的升级移交协议（T7 有 failure_category 但没定义「移交给谁」）、以及统一的汇报格式规范。

**结论**：功能域基本齐全，缺的是**厚度（reference 深度）**、**产出形态（报告文笔/排版）**、**组织协议（展开/移交/汇报）**三件事——正是用户判断的方向。

## 任务一：文档补厚 + 文献化

### 1.1 参考层补厚（对齐 T14 四层标准）
对未达标角色逐份补写 reference，四层结构固定：

```
## 方法论（来源与主张）
## 可执行口径（公式/枚举/白名单/阈值引用，指向 thresholds.json 真源）
## 已验证算例（真实数字对拍，可复现）
## 实战踩坑（从该角色已有经验/案例反推）
```

优先级：
- **P0** R03（7 份薄壳）——合规风险最高，文档薄=专业度存疑。
- **P1** R04（1 份）、R06（2 份）。
- **P2** SKILL.md < 5KB 的角色：R12、R03、R04、R13、R20。

### 1.2 建立「角色能力说明书」标准（新增文档类型）
现状 SKILL.md 是**工程说明书**（子命令表），用户要的「专业度/准确性/厚度」需要另一层——面向使用者的**能力说明书**。拟定统一模板落到 `references/00-capability-charter.md`（每角色一份）：

- 角色定位一句话 + 与相邻角色的边界（谁不做什么）
- 能力域清单：每域 → 能回答什么业务问题 → 交付物 → 精度/口径约束
- 专业术语表（该角色领域术语 + 本 agent 的判定口径）
- 典型交付样例（一段真实的产出节选，展示文笔与深度）
- 能力边界与降级声明（什么情况下会 blocked）

### 1.3 全景文档合并
`我是大老板-12角色能力全景.md` 与 `-20角色能力全景.md` 行数同为 617，需确认是否重复/演进关系，合并为单一权威版（`我是大老板-角色能力全景.md`），消除歧义。

## 任务二：组织架构与协同协议

### 2.1 组织架构图（升级 TEAM.md → 组织手册）
用实测的 `registry.py` 六能力层，在 `agents/ORG.md` 建立**公司组织章程**：

- **治理层**：R01 CEO（总负责/编排）、R04 评审（独立否决权，向「创始人」即用户直接汇报）
- **六事业群**：决策治理 / 战略数据智能 / 产品技术 / 市场客户 / 交易组织运营 / 自动化可靠性
- **汇报线**：执行角色 → R01 汇总 → 用户；R04 独立通道（不经 R01，保证评审独立性）
- **编制表**：角色 / 汇报对象 / 输入来自 / 输出交付 / 验收方 / 升级路径

### 2.2 三种协同模式（覆盖用户全部提问）

**模式 A —— 单角色直接调用（用户只点一个角色）**
定义「任务展开协议」：角色收到模糊意图时的标准动作流
1. **澄清**（R01 六问裁剪版：目标/交付物/边界/口径/时限/验收）
2. **能力自查**（我的哪个技能域能覆盖？契约是否齐全？）
3. **展开**（选定 skill/action → 拉取所需输入 → 执行 → harness 门禁）
4. **自评**（对照交付标准；不达标进模式 B）
5. **汇报**（按 2.4 报告规范产出）

**模式 B —— 失败/越界移交（任务进行不下去时）**
定义移交协议 `HANDOFF`，分类后路由：
| 触发 | 移交对象 | 载体 |
|---|---|---|
| 输入不足/口径不明 | 回上游或 R01 澄清 | `note` 端口 |
| 超出本角色边界（如数据分析要正式财务结论） | 边界表指定的邻角色 | 任务卡 + handoff 事件 |
| 需独立评审 | R04 | `artifact` 端口 |
| 需跨域编排（2+ 角色） | R01 重拆 | `task_cards` |
| 不可逆操作/资金/合同 | 升级到用户 | `escalate` 事件 |

落地：`core/protocol.py` 已有 `handoff` 事件类型，补一份 `references/00-handoff-protocol.md` 统一定义字段（from/to/reason/artifacts/acceptance）。

**模式 C —— 多角色编排（跨域方案）**
把 TEAM.md 的单一案例抽象成**通用编排模板**：意图拆解 → 任务卡(DRI单一主责) → 依赖图/波次 → 并行执行 → 汇合 → R04 复核 → R01 收口。Pipeline 式协作（如 R06→R07→R08→R04）写成可复用 pattern。

### 2.3 任务下发与传递规范
- **下发**：R01 → `task_cards`，每卡六字段（目标/拥有物/需求/接口契约/验收/明确不做），已在 R01 reference B2。
- **传递**：通过 `workspace` 共享状态 + 端口（inputs/outputs），子进程隔离，`__AGENT_RESULT__` 单行 JSON 回收。
- 统一 `core/protocol.py` 的 Port.kind 语义（data/artifact/decision/report）到组织手册。

### 2.4 汇报规范（用户要看的「报告」）
这是重点，需产出 `agents/REPORT-STANDARD.md`，规定**谁给用户写报告、什么格式、什么文笔、什么排版**：

- **分层报告**：
  - **一线执行汇报**（单角色）：`执行摘要 → 结论 → 证据 → 边界 → 下一步`，1 页内。
  - **跨域汇总汇报**（R01）：`背景 → 各角色结论 → 综合判断 → 决策建议 → 风险与边界 → 附录`。
  - **评审报告**（R04）：独立 `pass/fail + 缺陷定位`，不得与执行角色同稿。
- **文笔标准**：结论先行、每个数字可复算、以事实说话（禁「需要关注/有待进一步分析」类空话，对齐 T7 禁用词）。
- **排版标准**：对齐第十节 qiuqiu 编辑级五件套，**推广到全部 20 角色**——把 R06 的 `report_renderer.py` 抽成 `core/report_renderer.py` 共享库，各角色产出 report contract JSON → 统一渲染 HTML（设计令牌+SVG+证据边界块）。
- **默认双格式**：`.md`（快读）+ `.html`（正式交付）。
