# 模块1 · 工作拆解与排期





>








> 整合自 anthropics__knowledge-work-plugins 的 operations/task-management。


> 核心主张：**排期不是拍脑袋，是日历实算**——WBS 先过白名单门禁，


> 冲刺逐日填充容量，关键路径用拓扑+正反传算出来。





## 1.1 WBS 八类任务白名单（s01/wbs）





任务 `kind` 必须命中八类之一：`feature / bug / refactor / research /


sop / ops / meeting / review`。命中不了的「杂活」说明任务卡本身没想清楚，


先回 R01 补任务卡，而不是塞进排期。





估算口径（人日）：每项 0.05-3.0 人日。>3.0 人日 = 拆得还不够细，


当场退回；<0.05 = 琐碎到不值得单独排，并进相邻任务。





## 1.2 冲刺日历（s01/sprint）





确定性填充规则：


1. 起始日按 `start` 锚定，周末（周六/日）不排，自动顺延；


2. 每个工作日容量 = `capacity`（人日），按 WBS 顺序逐日填；


3. 塞不下的任务顺延到下一工作日，禁止「预支」未来容量；


4. 每日例会（standup）作为节奏锚：15 分钟盒，三问（昨天/今天/阻塞）。





已验证算例：4 人日任务 ÷ 2 人日/日容量 → **2 个工作日**排完，


`end=2026-11-05`（2026-11-03 周二起），利用率 `[1.0, 1.0]` 满载无预支。


排期结果里 `utilization` 逐日给出，任何一天 >1.0 即爆容量。





## 1.3 关键路径（s01/critpath）





纯 CPM 实算，四步：


1. **DFS 环检测**——依赖成环先报环，不进排期（报 `cycle` 字段）；


2. **Kahn 拓扑排序**——按依赖层进序；


3. **正传**：ES（最早开始）= 前驱 EF 最大值，EF = ES + 工期；


4. **反传**：LF（最晚完成）= 后继 LS 最小值，LS = LF − 工期；


   **浮动 = LS − ES**，浮动 = 0 的任务即关键路径。





已验证算例：t1(2d)‖t2(3d)→t3(4d)→t4(1d)，总工期 = **8 天**


（关键路径 t2→t3→t4，3+4+1），t1 浮动 = 8−(2+2) … 实算


`slack_t1 = 1.0`。总工期取所有任务 EF 最大值，不是路径枚举。





## 1.4 与 R01 的边界





R01 的 wave（波次编排）管「谁先谁后能开工」；R02 的 sprint/critpath 管


「按日历哪天做、哪条链不能拖」。拿到 R01 的 task_cards 后，


每张卡先过 `wbs` 门禁再进排期，禁止跳过白名单直接排。





## 1.5 实战踩坑





- 估算单位统一**人日**（1 人日=8h），与 capacity 的**小时**口径区分，


  两个动作输入别混用单位。


- `critpath` 的工期字段与 `wbs` 的估算字段独立——排期前先跑 wbs，


  把越界估算拦在门外。


- 周末判定用 Python `weekday()>=5`，与本地时区无关；若跨节假日，


  当前版本不识别法定假日，需在 capacity 里手工预留。


- 白名单、估算上下限以 `experience/thresholds.json → schedule` 为准，


  本文不手抄数值。
