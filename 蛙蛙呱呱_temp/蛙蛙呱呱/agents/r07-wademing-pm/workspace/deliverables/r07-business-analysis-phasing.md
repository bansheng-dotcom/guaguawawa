# R07 蛙得明 · 商业分析分期的方法论框架

> 角色：R07 蛙得明（产品经理，产品与技术层）
> 主题：从产品经理视角讲清「商业分析分期」是什么、怎么切、每期怎么验收
> 术语口径来源：`SKILL.md`、`references/00-capability-charter.md` 及 `references/01`–`08`
> 配套文档：R06《商业分析分期的数据与口径规范》（数据侧的 7 阶段）
> 适用对象：需要发起或评审一次商业分析的业务方、产品方与协作角色（R06 / R03 / R04 / R09）

---

## 一、什么是商业分期

**商业分期（phasing）= 把一次商业分析拆成若干个有顺序、有产物、有门禁的阶段，每期交出可验收的东西才允许进入下一期。**

它不是「把报告分成几章来写」，也不是「把事情拖长」。它回答的是三个工程问题：

| 问题 | 不分期的后果 | 分期的做法 |
|---|---|---|
| 先干什么、后干什么 | 一边找数据一边定结论，返工 | 每期有明确入口条件，前一期产物是后一期输入 |
| 干到什么程度算完 | 「感觉差不多了」就汇报 | 每期有可判定的门禁，过不了就停 |
| 错了怎么退 | 结论已对外，只能硬撑 | 阶段可回退：口径歧义退回口径期，假设被推翻回改假设 |

**关键认知：分期 ≠ 瀑布。** 分期是「阶段可回退、结论可推翻」的切割方式。分期唯一锁死的是**证据顺序**——不许先出结论再补数据；锁不住的也不该锁的是**假设本身**：假设被数据推翻，就回改假设，不硬凑结论。

---

## 二、为什么要分期

1. **认知负荷**：一次商业分析同时要处理「用户要什么」「数据说了什么」「先做哪个」「怎么算赢」四类问题，混在一起做必然含糊。
2. **决策节奏**：不是所有阶段都要等数据。问题定义、机会判断可以当天做；统计验证要等样本。分期让该快的快、该等的等。
3. **可回退**：最大的浪费不是做得慢，是**用三个月把错的假设做扎实**。分期让错误在便宜的阶段暴露。
4. **可验收**：每期产物都是可评审对象（Job story、假设清单、PRD、排序表），能被 R04 对抗评审挑刺，而不是最后交一份「不可反驳的漂亮报告」。

---

## 三、七个阶段总览

| 阶段 | 阶段名 | 核心要回答的问题 | 对应能力域 | 主责 |
|---|---|---|---|---|
| P1 | 问题定义与发现 | 用户到底想完成什么「活儿」？ | S01 产品发现与 JTBD | R07 |
| P2 | 机会与假设 | 最大的机会藏在哪里？先验什么假设？ | S02 机会树用户研究 | R07 |
| P3 | 方案与需求成形 | 做出来的东西验收标准是什么？ | S03 用户故事与 PRD | R07 |
| P4 | 优先级排序 | 先做哪个？为什么？ | S04 优先级 Backlog | R07 |
| P5 | 数据验证（交接期） | 承重假设成立吗？ | 交 R06 执行 | R06 验证 / R07 回改 |
| P6 | 路线图与发布 | 下个周期交付什么成果？ | S05 路线图发布 | R07 |
| P7 | 目标与决策汇报 | 怎么知道我们赢了？上次是怎么处理的？ | S06 愿景指标 + S08 决策汇报 | R07 |

**分期三条纪律：**

1. **产物即契约**：每一期必须有落盘产物，口头共识不算过门禁。
2. **阶段可回退**：P5 推翻 P2 的假设，就退回 P2 重排假设，不许在 P5 就地改结论。
3. **不越界下结论**：R07 出的是**需求假设**，不是数据结论。

## 四、逐阶段规范

### P1 问题定义与发现（S01）

**目标**：把模糊诉求转成可验证的「活儿」，而不是先想功能。

| 项目 | 内容 |
|---|---|
| 输入 | 业务诉求、用户声音（VOC）、现有数据现象描述 |
| 产出 | Job story（三段式）、发现计划（问题/分群/假设/验证方式）、访谈脚本 |
| 门禁（FAIL） | ① Job story 缺段即不合格——必须是「当（情境）／我要（动机）／以便（期望结果）」三段齐全；② 发现计划四项（问题、分群、假设、验证）缺一即 FAIL；③ 访谈脚本不符合 Mom Test 四段即 FAIL；④ 通篇「提升体验/优化功能」无口径 → FAIL |
| 主责 | R07 |

**要点**：这一期的产物是**待验证假设**，不是结论。写下「我们相信……但还没验证」。

---

### P2 机会与假设（S02）

**目标**：把机会排序，把假设分级，避免「先做最容易做的」。

| 项目 | 内容 |
|---|---|
| 输入 | P1 的 Job story 与发现计划 |
| 产出 | 机会解树（OST 四层）、POC 打分与推荐、假设 Impact×Risk 四象限、访谈笔记 |
| 门禁（FAIL） | ① OST 四层结构不完整即 FAIL；② POC 缺 Feasibility / Impact / MarketFit 任一项即 FAIL；③ 假设未做 Impact×Risk 定位即 FAIL；④ 高影响×低信心的假设若未安排小流量实验（experiment）即 FAIL |
| 主责 | R07 |

**案例规则（来自 `cases/saas-activation/experience/priority_rules.md`）**：高影响 × 低信心 → 先小流量实验，不要直接全量。

---

### P3 方案与需求成形（S03）

**目标**：把选定机会写成别人能照着做、能验收的需求。

| 项目 | 内容 |
|---|---|
| 输入 | P2 的机会与假设清单 |
| 产出 | PRD、用户故事 / Job story、验收准则（Given/When/Then） |
| 门禁（FAIL） | ① **PRD 八门禁**：背景 / 目标 / 非目标 / 用户 / 需求 / 验收 / 指标 / 风险，**缺任一即 FAIL**——尤其是「不在范围（非目标）」缺失时直接 FAIL；② 用户故事 AC 条数须在 **4–8** 条，超出或不足即 FAIL；③ 每条 AC 必须 Given/When/Then 完整，缺段即 FAIL；④ **承重假设 ≥ 3 条**，不足即 FAIL |
| 主责 | R07 |

**样例（引自 `cases/saas-activation`）**：

```
PRD · 激活率提升（节选）
目标：新用户 7 日激活率 32% → 45%
非目标：不优化付费转化（另立项）
验收准则（AC）：
  Given 新用户完成注册
  When  首次进入工作台
  Then  30 秒内看到 3 个引导任务，完成 1 个即计激活
假设清单：
  H1 引导任务降低「不知道第一步干啥」的流失（Impact=高，Risk=中）
  H2 邮件新手序列提升召回（Impact=中，Risk=低）
```

---

### P4 优先级排序（S04）

**目标**：用可复算的算术决定顺序，而不是「感觉重要」。

| 项目 | 内容 |
|---|---|
| 输入 | P3 的 PRD、候选方案/需求池 |
| 产出 | RICE / ICE / Opportunity Score 实算排序、结构化 Backlog |
| 门禁（FAIL） | ① 排序必须**可复算**：RICE/ICE/Opportunity Score 是确定性算术，换个人代入同样输入必须得同样排序，排序不可复现即 FAIL；② Backlog 结构校验不通过即 FAIL；③ 用主观「重要性」替代打分即 FAIL |
| 主责 | R07 |

---

### P5 数据验证（交接期，S05 相关纪律）——**全程唯一的跨角色硬交接**

**目标**：让数据来判假设的生死。这是分期存在的核心理由。

| 项目 | 内容 |
|---|---|
| 输入 | P2 的假设清单 + P3 的承重假设（≥3 条）+ 埋点/实验设计 |
| 产出 | 由 **R06** 出具：证伪/证实的假设清单、效应量与置信区间、贡献度占比 |
| 门禁（FAIL） | ① 承重假设未被验证就进入路线图即 FAIL；② 用过程指标冒充结果指标即 FAIL（见下方案例规则第 4 条）；③ R07 自行给统计显著性结论即越界 FAIL |
| 主责 | **R06 验证假设，R07 只出假设** |

**交接语义（关键，不可混淆）：**

> **R07 出「假设」，R06 只「验证假设」。** PRD 是需求假设，非数据结论；需 R06 验证、R04 评审。

**回退规则**：假设被数据推翻 → **回改假设，不硬凑结论**（移交协议见 `PROTOCOL.md` 模式 B），退回 P2 重排假设。

---

### P6 路线图与发布（S05）

**目标**：说清下个周期交付什么**成果**（不是交付什么功能）。

| 项目 | 内容 |
|---|---|
| 输入 | P5 验证通过的假设与优先级排序 |
| 产出 | 成果路线图、发布说明、事前尸检（pre-mortem） |
| 门禁（FAIL） | ① 路线图必须用**成果句式**，写成「交付某功能」即 FAIL；② 发布说明五分类不完整即 FAIL；③ 未做事前尸检即 FAIL |
| 主责 | R07 |

**事前尸检**：假设产品发布即失败，倒推死因，提前埋缓解措施。

---

### P7 目标与决策汇报（S06 + S08）

**目标**：定义「赢了」长什么样，并把整件事汇报到能决策。

| 项目 | 内容 |
|---|---|
| 输入 | P6 的路线图与全流程产物 |
| 产出 | 北极星指标、指标分层、OKR 3×3、决策汇报三层、需求卡、经验卡 |
| 门禁（FAIL） | ① **北极星 7 标准**：一个指标须满足七条（可衡量 / 可影响 / 前置与滞后平衡等）才配当北极星，不过即 FAIL；② 拿过程指标充数当北极星即 FAIL；③ OKR 不足 3×3 即 FAIL；④ 决策汇报三层不完整即 FAIL；⑤ 经验卡五要素不全即 FAIL；⑥ 声明「已验证」但无来源可信度即 FAIL |
| 主责 | R07 |

**案例规则（来自 saas-activation 第 4 条）**：输入指标是「牵引」而非「结果」——首日完成率上升但北极星不动 = **指标选错或护栏破了**。

## 五、案例走查：SaaS 激活提升（全流程）

| 阶段 | 本期实际产物 |
|---|---|
| P1 | Job story：当新用户刚注册完，我要知道第一步该干什么，以便尽快拿到价值 |
| P2 | OST 四层 → 机会落在「首次关键动作成本高」；H1（High×Med）、H2（Med×Low）；高影响低信心项安排小流量实验 |
| P3 | PRD：目标 7 日激活率 32%→45%；**非目标**：不优化付费转化（另立项）；AC 用 Given/When/Then 写；承重假设 ≥3 |
| P4 | RICE 排序：优先做「降低首次关键动作成本」而非「加更多引导内容」 |
| P5 | 交 R06 验证 H1/H2：看首日完成率与 7 日激活率，同时报效应量与置信区间 |
| P6 | 成果路线图：不是「上线引导任务」，而是「7 日激活率提升到 45%」；事前尸检埋护栏 |
| P7 | 北极星：7 日激活率（过 7 标准）；护栏绑定：**缩短路径的改动必须同时验证「引导放弃率」不升反降** |

**本期最贵的一课**：如果 P5 显示首日完成率上升但北极星不动，那不是成功，是指标选错或护栏破了——这正是分期要拦下的东西。

## 六、与 R06 的分工对照

| | R07 负责 | R06 负责 |
|---|---|---|
| 出什么 | 假设、需求、优先级、路线图、指标定义 | 口径定义、数据质量、探索、根因、统计验证 |
| P1–P4 | 主责 | 提供数据现象与可行性输入 |
| P5 | 出假设、回改假设 | **主责验证**：效应量 + 置信区间 + 证伪清单 |
| P6–P7 | 主责 | P7 提供可审计报告与置信度声明 |

**一句话**：R07 说「我认为这里有机会，值得做」，R06 说「数据支不支持这个我认为」。两边都不越界，分期才成立。

## 七、边界声明

| 事项 | 归属 |
|---|---|
| 产品取舍、优先级、路线图、北极星定义 | **R07** |
| 统计显著性、口径、数据质量与验证结论 | **R06** |
| 正式财务 / 合规结论 | **R03** |
| 工程实现、生产代码 | **R09** |
| 品牌 / 视觉 | **R10** |
| 对抗评审与验收挑刺 | **R04** |

**底线**：PRD 是需求假设，非数据结论；需 R06 验证、R04 评审。写代码不归 R07；假设被数据推翻就回改假设，不硬凑结论。

## 八、验收清单：怎么算这套分期用对了

- [ ] 七个阶段的产物都在，且有落盘文件而非口头共识
- [ ] Job story 三段齐全，PRD 八门禁齐全（尤其「不在范围」）
- [ ] 每条用户故事带 4–8 条 AC，且 Given/When/Then 完整
- [ ] 承重假设 ≥ 3 条，且每条都能被 R06 验证
- [ ] 优先级是 RICE/ICE/Opportunity 实算，排序可复现
- [ ] P5 由 R06 出具效应量与置信区间，R07 未越界下统计结论
- [ ] 路线图是成果句式，事前尸检已做
- [ ] 北极星过 7 标准，未拿过程指标充数
- [ ] 被推翻的假设**已回改**，而不是被写进报告当没看见
