# 商业分析本身怎么做

> 角色：R07 蛙得明（产品经理，产品与技术层，汇报对象 R01 蛙全局）
> 主题：从业务问题走到决策——商业分析是什么、分析什么、用什么方法、怎么保证结论靠得住、怎么交到决策桌上
> 术语与阈值来源：`SKILL.md`、`references/00-capability-charter.md` 与 `references/01`–`08`、`experience/thresholds.json`、案例 `cases/saas-activation/`
> 适用对象：需要发起、执行或评审一次商业分析的业务方、产品方与协作角色（R03 / R04 / R06 / R09 / R10）

---

## 一、商业分析的定义与它要回答的业务问题

**商业分析是把一个模糊的业务问题，转成一条可复算的证据链，并落成一个能被评审、能被推翻、能被执行的决策。**

它交付的不是「一份报告」，而是「一个决策包」：结论、支撑结论的证据、承重假设、停止条件。报告只是决策包的载体。

对外可讲的一句话口径：

> 商业分析 = 把「我觉得」变成「有口径、有基线、有数据源、有验收标准」。

### 1.1 四类业务问题

商业分析回答的问题只有四类，混淆它们是最常见的翻车起点：诊断类问题要的是**归因**，识别类问题要的是**排序**，评估类问题要的是**取舍**，验证类问题要的是**判定**——用错方法，结论再漂亮也是答非所问。

| 问题类型 | 典型提问 | 要交付的答案形态 | 主要方法（R07 能力域） |
|---|---|---|---|
| 现状诊断 | 激活率为什么低？卡在哪儿？ | 归因结论 + 量化缺口 | JTBD 发现、Mom Test 访谈、漏斗/分群证据 |
| 机会识别 | 最大的机会藏在哪个用户任务里？ | 机会清单 + 优先级 | OST 四层、POC 打分、假设四象限 |
| 方案评估 | 先做哪个方案？值不值得做？ | 排序表 + 取舍理由 | POC、RICE / ICE / Opportunity Score |
| 效果验证 | 做了之后到底有没有用？ | 判定 + 停止/继续/回改假设 | 承重假设对拍、护栏指标、A/B 验证（交 R06 判显著性） |

### 1.2 商业分析不是什么

界定反面，比堆砌正面定义更能保证结论质量：

| 反模式 | 典型表现 | 为什么不算商业分析 |
|---|---|---|
| 报表罗列 | 把数据表、看板、涨跌曲线贴满，不给结论 | 只有现象没有判断，读者拿不到可执行的下一步 |
| 拍脑袋建议 | 「建议优化体验、加强引导、提升留存」 | 无口径、无基线、无数据源、无法验收 |
| 结论先行再补数据 | 先定「要做 X」，再找证据支撑 | 证据被用来辩护而非检验，假设永远推不翻 |
| 单点数据当规律 | 一次访谈/一周数据就下全局结论 | 不区分候选经验与已验证规则，样本与边界未声明 |
| 越界结论 | 直接给财务预测、统计显著性、工程方案 | 越出产品取舍的职责范围，专业结论必须回到对口角色 |

「提升用户体验/优化功能/增加留存/提升效率」这类空泛措辞在本角色内是**硬性拦截项**：指标门禁与对抗评审都会直接判 FAIL。它们必须被改写成可衡量的说法，例如「提升用户体验」→「首日完成首个项目率从 8% 到 15%」（案例 `cases/saas-activation/experience/good_summaries.md`）。

## 二、商业分析的分析框架：从业务问题到可执行结论

框架就是那条**证据顺序被锁死的路径**。商业分析允许结论被推翻，不允许顺序被颠倒——不允许先出结论再补数据。

### 2.1 主路径（六步）

| 步 | 动作 | 进入下一步的条件 | 产物 | 对应方法 |
|---|---|---|---|---|
| ① 问题定义 | 把「用户想要 X」拆成症状与根因 | 能写成 Job story 三段句 | Job story、发现计划 | JTBD、Mom Test |
| ② 机会拆解 | 把模糊机会拆成可验证假设 | 机会 3–7 条、聚焦 ≤3 | OST 四层 | OST、POC 打分 |
| ③ 假设排序 | 排出「先验哪条假设」 | 每条假设落到四象限之一 | 假设四象限表 | Risk=(1−Confidence)×Effort |
| ④ 需求成形 | 定验收标准与不在范围 | PRD 八门禁全过 | PRD、用户故事、AC | PRD 八门禁、Given/When/Then |
| ⑤ 优先级实算 | 排「先做哪个」 | 排序可复算、可对拍 | 排序表、Backlog | RICE / ICE / Opportunity Score |
| ⑥ 目标与决策 | 定义赢的判据、交决策 | 决策三层俱全，含停止条件 | 北极星指标、决策汇报 | 北极星 7 标准、决策三层 |

### 2.2 这条路径的三条纪律

1. **句式即契约**：Job story 必须三段俱全（`When [情境], I want [动机], so I can [结果]`），user story 必须 `As a / I want / so that`。句式不符即 FAIL——不是文风要求，是防止「我要一个导出按钮」这类无情境的功能请求混进分析。
2. **可复算**：RICE / ICE / Opportunity Score 是确定性算术，同样的输入永远得出同样的排序，可被任何人复算、质疑、对拍。排序不允许引入随机 tiebreak。
3. **止血优先于证明**：分析的目标不是把结论做扎实，而是**让错误的假设在便宜的地方暴露**。用三个月把错假设做扎实，是商业分析最大的浪费。

### 2.3 方法清单（R07 产品侧全量）

| 方法 | 判定口径（本角色真实阈值） | 用途 |
|---|---|---|
| JTBD / Job story | 三段键 `situation` / `motivation` / `outcome`，缺一即不合格；接受字段或文本两种形态 | 把功能请求还原成任务 |
| 发现计划 | 必填 problem / segment / why_now；假设 ≥1 条且落在 8 类风险枚举 | 立项前的假设登记 |
| 8 类风险假设 | `value` / `usability` / `viability` / `feasibility` / `ethics` / `gtm` / `strategy` / `team`，封闭枚举 | 假设分类，写中文或缩写即判非法 |
| Mom Test 访谈 | 四段时长 opening 2–3 / warmup 5 / core 15–20 / wrapup 3–5 分钟；规则 no_pitching / listen_ratio_80_20 / ask_why_deep | 只问过去行为，不问「你会不会用」 |
| OST 四层 | 机会 3–7 条；聚焦 ≤3；每个聚焦机会方案 ≥3；至少 1 个方案含 hypothesis+method | 从期望结果拆到可跑实验 |
| POC 打分 | Feasibility / Impact / Market Fit 三项各 1–5，clamp 到 1–5，**总分 ≥12 推荐** | 方案过筛，避免「想做的都做」 |
| 假设优先级 | `Risk = (1 − Confidence) × Effort`，Effort 下限 0.1 | 定位先验哪条假设 |
| 假设四象限 | impact≥0.5 且 risk≥0.5→**experiment**；impact≥0.5→**proceed**；risk≥0.5→**reject**；否则→**defer** | 决定「做实验 / 直接做 / 先否掉 / 先搁置」 |
| PRD 八门禁 | problem / user / value / scope / metric / acceptance / risk / read，**八项全过才 ok** | 需求能否进开发 |
| 承重假设 | `prd.risk_hypotheses_min` = **≥3 条**，每条带最小验证 | 防「方案没有风险」的假自信 |
| 用户故事 AC | user story **4–6 条**；job story **6–8 条** | AC 太少说明拆得不够 |
| RICE | `(Reach × Impact × Confidence) / Effort`；Effort 下限 **0.1**（防除零/防放大），Confidence clamp 0–100 | 把「影响多少人」纳入排序 |
| ICE | `Impact × Confidence × Ease`，各项 clamp 1–10 | 快速粗排 |
| Opportunity Score | `Importance × (1 − Satisfaction)`；价值增量 = `Importance × (S2 − S1)` | 衡量未被满足的重要程度 |
| 北极星 7 标准 | 表达价值 / 可衡量 / 有输入指标 / 有护栏 / 可行动 / 有时窗 / 非虚荣，`nsm_criteria` = **7** | 定「怎么知道我们赢了」 |
| 指标分层 | 四层枚举 `north_star` / `input` / `guardrail` / `business`；至少 1 北极星 + 1 护栏，每指标带 definition + data_source；输入指标 **3–5 个** | 防过程指标充数 |
| OKR | **3 套 × 3 KR**，信心 **60–70%** | 目标对齐 |
| 路线图与发布 | 成果句式 `Enable [分群] to [期望结果] so that [业务影响]`；发布说明五分类 New Features / Improvements / Bug Fixes / Breaking Changes / Deprecations | 交付对外表达 |
| 事前尸检 | 假设已发布，倒推失败原因，Tiger ≥1，行动表含 risk/mitigation/owner/due_date | 发布前埋缓解 |
| 决策三层 | product_judgment / execution_spec / decision_gate 俱全；门禁含 success / non_goals / **stop_condition** | 把判断变成可评审决策包 |
| 经验卡 | 五要素 trigger / scope / rule / boundary / source_credibility；verified=true 必须带来源可信度 | 把踩过的坑变成可检索规则 |

### 2.4 PRD 八门禁逐条口径

八门禁的价值在于每道门禁对应一个真实翻车点：

| 门禁 | 判读口径 | 最容易漏的坑 |
|---|---|---|
| problem | 非空，且不能是「支持/优化/增强/完善」类短句（长度 <20 判 vague） | 只写「优化某功能」必然 FAIL |
| user | 有分群与场景，含替代方案与行动成本 | 写成「所有用户」 |
| value | before / how / after / alternatives 或 experience_gain / cost_reduction 之一 | 只讲方案不讲改变前后 |
| scope | **p0 非空 且 non_goals 非空**（双非空） | 只给 p0 不给「不在范围」，八门禁里最易漏 |
| metric | 有口径/数据源/基线之一，且无空泛指标 | 「提升用户体验」直接 FAIL |
| acceptance | acceptance_criteria 非空，Given/When/Then 可观察可复现，须覆盖失败态 | 只写成功路径 |
| risk | 承重假设 **≥3** 条，每条带最小验证 | 假设与承重假设是别名，两种写法都认 |
| read | executive_summary / conclusion 非空，结论先行 | 把结论藏在最后一段 |

## 三、结论如何被验证与推翻

商业分析的可靠性不来自「分析得多细」，而来自**结论里哪些部分是可被推翻的、由谁推翻、推翻了怎么办**。

### 3.1 承重假设：把结论挂在明面上

每条 PRD 必须写清 **≥3 条承重假设**，且每条带最小验证方式。承重假设就是「如果这条不成立，整个结论塌掉」的那几条——把它们写在明面上，等于提前告诉评审者往哪里打。

一个合格的承重假设长这样：`{"hypothesis": "引导能提升激活率", "validation": "A/B 实验"}`。不合格的写法是「用户会喜欢新功能」——无从验证，也不算假设。

### 3.2 分工：R07 出假设，R06 验证假设

| 环节 | 归属 | 做什么 | 不做什么 |
|---|---|---|---|
| 出假设 | **R07** | 把假设写成可验证形态（对象、量、方向、时窗），指定验证方法 | 不自己判统计显著性 |
| 验证假设 | **R06** | 数据侧检验：口径、样本、显著性、效应量、SRM | 不替 R07 改产品取舍 |
| 推翻后处置 | **R07** | 回改假设、重排四象限、调整 PRD 与指标 | 不硬凑结论、不做事后辩护 |

R06 的验证前置条件是：数据不足时不制造确定性；统计检验是探索前哨；因果结论只对**已调整的观测混杂**成立，未观测混杂不可消除，必须在结果中如实声明。

### 3.3 假设被推翻就回改假设

这是本角色一条不可协商的纪律，也是 `SKILL.md` 边界里写死的行为：**假设被数据推翻时回改假设，不硬凑结论。**

处置动作是确定的四步：

1. **判定推翻范围**：是假设本身错了，还是指标口径错了，还是护栏破了；
2. **回改假设**：把旧假设标为「已被推翻」并记录反证，不删除、不美化；
3. **重排四象限**：更新 Confidence，重算 Risk，重新落象限；
4. **回改需求与指标**：更新 PRD 承重假设、Backlog 顺序与指标定义；若护栏被破（例如「首日完成率上升但北极星不动 = 指标选错或护栏破了」），先修指标而不是继续冲量。

### 3.4 四种典型「结论不成立」的信号

| 信号 | 含义 | 处置 |
|---|---|---|
| 输入指标涨、北极星不动 | 指标选错，或护栏破了 | 回到指标定义层重修口径 |
| 假设靠「大概率有效」措辞支撑 | 证据链缺失 | 补证据重算，评审 `verdict=PASS` 必须有 evidence |
| 同一个人既出结论又评审结论 | 身份红线被破 | 换独立评审者重做（评审者≠生产者） |
| 结论只有成功判据、没有停止条件 | 决策包不完整 | 补 stop_condition，否则不得进决策 |

## 四、方法与案例串联：SaaS 新用户激活（cases/saas-activation）

以下全部沿用案例 `cases/saas-activation` 的真实口径与数字，不另造数据。

**案例背景**：新用户注册后不知道如何创建首个项目，导致 7 日激活率偏低。
**北极星**：7 日激活率（注册后 7 天内完成首个关键动作的用户占比）。
**护栏**：引导放弃率。
**默认问题**：如何提升 SaaS 新用户 7 日激活率？

### 4.1 第一步：问题定义（JTBD）

把「想提升激活」翻译成任务句式：

> **When** 新用户首次登录，**I want** 快速上手，**so I can** 在 10 分钟内创建第一个项目。

三段俱全，通过校验。反面例子是「我要一个引导弹窗」——没有情境、没有期望结果，无法判断做出来是否解决了问题。

### 4.2 第二步：机会拆解（OST 四层）

| 层 | 本案内容 |
|---|---|
| Desired Outcome | 更快完成首个项目 |
| Opportunities | 3 条机会，聚焦前 2 条（`focus` 长度 ≤3） |
| Solutions | 每个聚焦机会配 ≥3 个方案 |
| Experiments | 至少 1 个方案带 hypothesis + method（本例 `A/B`） |

结构门禁：机会数须落在 3–7 之间；聚焦机会按 `focus` 长度逐条校验方案数——夹具必须按 focus 长度配足方案，只给 `selected: true` 的那一个会判「方案数 0」。

### 4.3 第三步：方案过筛（POC 打分）

对候选方案按 Feasibility / Impact / Market Fit 三项各打 1–5 分：

| 方案 | Feasibility | Impact | Market Fit | 判定（总分 ≥12 推荐） |
|---|---|---|---|---|
| A | 5 | 5 | 5 | **推荐** |
| B | 2 | 2 | 2 | 不推荐 |

判定口径以 `ost.poc_recommend_min` = **12** 为准，分数 clamp 到 1–5。注意两点：分数写 99 或负数不会报错，会被 clamp 后再参与判读，别被「看起来超高」误导；POC 三项的口径是可行性与市场匹配，**不等于**假设四象限里那个 `impact` 字段——两者是不同字段，不可互相套用。

### 4.4 第四步：假设排序（Risk 与四象限）

本案 H1（引导任务降低「不知道第一步干啥」的流失）取 impact=0.9、confidence=0.2、effort=1.0：

```
Risk = (1 − Confidence) × Effort = (1 − 0.2) × 1.0 = 0.8
impact = 0.9 ≥ 0.5 且 risk = 0.8 ≥ 0.5 → quadrant = experiment
```

结论：H1 进 **experiment**，走小流量实验，不直接全量。这正是案例 `experience/priority_rules.md` 的第 3 条规则（高影响 × 低信心 → 先小流量实验）。对照 H2（邮件新手序列）Impact=中、Risk=低，方向是直接做而非先实验。

方向性提醒：`confidence` 语义是「置信度」，**越高风险越低**。写反会把高置信误判成高风险，四象限结果全错。

### 4.5 第五步：需求成形（PRD 八门禁）

| 门禁 | 本案内容 |
|---|---|
| problem | 新用户注册后 7 天内不知道如何创建第一个项目，导致激活率偏低 |
| user | SaaS 试用新用户，注册后首次登录；替代方案=手动翻帮助文档（行动成本高） |
| value | before 无引导靠自己摸索 → how 分步新手引导 → after 10 分钟完成首个项目；替代=帮助中心/视频教程 |
| scope | P0 分步引导流程；P1 跳过并稍后继续；**non_goals：不做自动创建项目、不做个性化推荐** |
| metric | 7 日激活率，基线 12% → 目标 20%，数据源=行为埋点 |
| acceptance | Given 新用户完成注册 / When 首次进入工作台 / Then 出现分步引导 |
| risk | 3 条承重假设，分别配小流量实验、可用性测试、A/B 实验 |
| read | 结论先行：给新用户分步引导，让其 10 分钟完成首个项目，7 日激活率从 12% 提升到 20% |

八项全过，`passed_gates=8`。任何一项抽掉都会 FAIL——例如把 `scope.p0` 置空，范围门禁立刻拦下。

### 4.6 第六步：优先级与排序

- **RICE 实算**：reach=100, impact=0.8, confidence=70, effort=2 → `(100 × 0.8 × 70) / 2 = 28.0`。
- **Opportunity Score**：importance=8, satisfaction=0.3 → `8 × (1 − 0.3) = 5.6`。
- **Backlog 实排**：分步新手引导（score 5）→ 跳过引导按钮（score 3，依赖前项）→ 引导完成打点（score 2），按 score 降序稳定排序。

案例侧取舍规则：优先做「降低首次关键动作成本」的改动，而不是「加更多引导内容」。

### 4.7 第七步：指标与决策汇报

- **北极星**：7 日激活率；**输入指标**：首日完成首个项目率、模板使用率、邀请完成率（3 个，落在 3–5 区间）；**护栏**：引导中途放弃率、错误率（≥1 个）；数据源=行为埋点；基线 12% → 目标 20%。
- **决策三层**：产品判断（做分步引导）＋ 执行说明（P0/P1 范围与依赖）＋ 决策门禁（成功判据=7 日激活率到 20%；不在范围=不做自动创建项目与个性化推荐；**停止条件**=护栏「引导放弃率」上升即停）。

### 4.8 案例自检：结论怎么被推翻

假设 R06 验证后出现「首日完成率上升、7 日激活率不动」——按案例规则，这**不等于**方案失败，而是**指标选错或护栏破了**。处置回到 §3.3 的四步：判定范围 → 回改假设 → 重排四象限 → 回改需求与指标。硬说「数据有延迟」是把假设当结论辩护，属于禁止行为。

## 五、交付物形态：分析结论如何交到决策桌上

商业分析的产物必须**可评审、可执行、可验收**。本角色固定五类交付物，对应 `contracts.py` 的输出契约：

| 交付物 | 内容 | 落盘口径 / 契约字段 | 谁消费 |
|---|---|---|---|
| **PRD** | 背景、目标、非目标、用户、需求、验收、指标、风险 | 八门禁全过；输出 `gates` / `gate_ok` / `passed_gates` | R08 立 MVP、R09 实现 |
| **Job story** | `When / I want / so I can` 三段句 + AC | job story AC **6–8 条**；输出 `kind` / `ac_count` / `ac_band` | 设计、开发、验收 |
| **Backlog** | 结构化待办：title + 验收标准 + score + 依赖 | 结构校验 + 按 score 降序；输出 `item_count` / `ordered` | 排期与迭代 |
| **指标定义** | 北极星 + 输入 + 护栏 + 商业四层，每项带 definition + data_source | 北极星 7 标准；输入 3–5；≥1 护栏；输出 `nsm_criteria` / `layers` / `metric_count` | R06 验证、R12 增长 |
| **决策汇报** | 三层：产品判断 / 执行说明 / 决策门禁 | 门禁含 success / non_goals / **stop_condition**；输出 `layers` | R01 决策、R04 评审 |

### 5.1 决策汇报三层的实质

| 层 | 回答什么 | 缺了会怎样 |
|---|---|---|
| 产品判断 | 为什么做这个、为什么不做别的 | 决策者无法复现取舍逻辑，只能凭信任签字 |
| 执行说明 | 具体做什么、范围与依赖、谁做 | 结论无法变成行动 |
| 决策门禁 | 成功判据 / 不在范围 / **停止条件** | 做成「只有成功标准、没有退出条件」的单向承诺 |

三层里最稀缺、也最容易漏的是**停止条件**——说清「什么情况放弃」比说清「什么情况成功」更难，但它是决策包能不能被追责的基础。写决策时最常见的错误就是只写 success，漏掉 stop_condition。

### 5.2 需求卡与经验卡

- **需求卡**必填 7 字段：编号 / 问题 / 范围 / 不在范围 / 成功指标 / 验收 / 复核状态。复核状态未通过时只能标「草稿」，**草稿不得作为正式开发输入**（`submittable=true` + 草稿状态会被直接拦截）。复核状态是中文枚举，写英文 `reviewed` 不会被认成「已复核」。
- **经验卡**必填五要素：触发 / 范围 / 规则 / 边界 / 来源可信度。**候选经验 ≠ 已验证规则**：声明 verified=true 必须带来源可信度；经验卡要写「可复用的规则」，不是「这次做了什么」。

### 5.3 交到决策桌前的对抗评审

结论在进入决策前必须过独立评审（R04），评审是**对抗性**的，且有三条硬红线：

1. **评审者 ≠ 生产者**：实现者不得自评，违反即 BLOCKER 并回退重做；
2. **PASS 必须有证据链**：判 PASS 却没有任何 evidence 字段，BLOCKER 回补证据重算；
3. **评审只记录不修复**：评审输出不得含修复后内容声明（`applied_fixes` / `modified` 等），违反即 BLOCKER。

另有两类处置：评审报告使用推测措辞（should / probably / seems to / I believe / 应该 / 大概 / 似乎 / 我认为）回 writer 改写；keep 项被降级为 FAIL 却没有理由，补理由或撤销降级。评审结论只取三个值：**PASS / FAIL / BLOCKED**。

因此，「交到决策桌上」的正确姿势是：**一份带证据链的决策包 + 一份独立评审记录**，而不是一份自说自话的漂亮报告。

## 六、边界声明

本角色只做产品取舍；以下事项不由 R07 下结论，必须移交对口角色：

| 事项 | 归属 | 说明 |
|---|---|---|
| 产品取舍与优先级判断 | **R07**（本角色） | 做什么、不做什么、先做哪个；PRD、Job story、Backlog、指标定义、决策汇报 |
| 统计显著性与数据结论 | **R06 蛙得清** | 口径、样本、显著性、效应量、SRM、因果识别；本角色的统计检验只是探索前哨 |
| 财务与合规结论 | **R03 蛙守先** | 收入/成本/预算测算与合规判定不由本角色出具 |
| 工程实现 | **R09 蛙文码** | R07 出 PRD，R09 出生产代码；写代码不归 R07 |
| 视觉与品牌 | **R10 蛙成美** | 品牌/视觉诉求直接移交 R10，本角色不代决 |
| 独立评审 | **R04 蛙挑刺** | 评审者≠生产者；R07 不得自评自证 |
| 客户反馈持续收集 | **R13 蛙客成** | R07 只把反馈转成产品取舍，不替代持续收集机制 |

**降级与停止行为**（不可协商）：

1. **假设被数据推翻 → 回改假设**，不硬凑结论、不做事后辩护；
2. **需求边界不清 → 退回澄清**，不写含糊 PRD；
3. **数据不足 → 不制造确定性**，如实声明证据边界；
4. **要求写生产代码 → 移交 R09**；**品牌/视觉诉求 → 移交 R10**；
5. **空泛措辞 → 一律改写为可衡量口径**（口径 + 基线 + 目标 + 数据源），否则不得进入交付物。

**本文件的性质**：这是一份方法说明文档，说明 R07 视角下商业分析怎么做；文中的阈值均引自 `experience/thresholds.json` 与 `references/`，案例数字均来自 `cases/saas-activation/`。文中不包含任何未验证的业务结论，也不替代任何一次具体分析所需的证据链。
