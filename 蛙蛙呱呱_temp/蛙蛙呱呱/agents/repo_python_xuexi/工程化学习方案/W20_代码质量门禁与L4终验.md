你打开了新同事的 Pull Request。你看了 10 分钟——你知道有些地方不对，但你说不出来"哪里不对"和"应该怎么改"。你最后写了"LGTM, 一个小建议: 变量名可以再清晰一点"——这是一次无效的 code review。

### 📖 核心原理

**数据分析代码审查 checklist——15 项：**

**可读性（5 项）**
- [ ] 文件有模块 docstring？（一句话说清这个文件是干什么的）
- [ ] 每个对外函数有 docstring（至少 Args + Returns）？
- [ ] 变量名能表达"是什么"？（不是 `x`/`d`/`tmp`/`df1`）
- [ ] 函数名能表达"做什么"？（不是 `process()`/`handle()`/`do_stuff()`）
- [ ] 魔法数字是否被提取为命名常量？（不是 `if len(df) > 1000`——而是 `MIN_ORDERS_FOR_ANALYSIS = 1000`）

**正确性（5 项）**
- [ ] 有 Type Hints？（参数 + 返回值）
- [ ] try/except 捕获的是具体异常类型？（没有裸 `except:`）
- [ ] 浮点数比较用的是 `np.isclose()` 而不是 `==`？
- [ ] 数据加载后有验证？（至少检查了必需列存在）
- [ ] 关键逻辑有测试？（pytest 测试覆盖了"可能出错的地方"）

**可维护性（5 项）**
- [ ] 没有重复代码？（同一段逻辑出现在 ≥3 处——提取成函数）
- [ ] 函数体 ≤ 30 行？（不是硬规定——但 > 30 行就值得问"这个函数是否在做多件事"）
- [ ] 没有硬编码路径/参数？（用 pathlib + 配置文件）
- [ ] import 顺序正确？（标准库 → 第三方 → 本地，按字母序）
- [ ] 没有注释掉的代码？（注释掉的代码 = "我不敢删"——要么删了等 git 恢复，要么恢复并写清楚为什么保留）

### dbt 的数据质量测试——在 pandas 中实现同样的哲学

```python
# src/data/validate.py —— 数据分析版 dbt test
def validate_input(df, required_columns, table_name="unknown"):
    """验证输入数据质量——dbt test 的 pandas 版本。
    检查: 必需列存在？主键唯一？关键列无 NULL？数值列无负值？行数合理？
    """
    issues = []
    missing = [c for c in required_columns if c not in df.columns]
    if missing: issues.append(f"[{table_name}] 缺失必需列: {missing}")
    if "order_id" in df.columns:
        dupes = df["order_id"].duplicated().sum()
        if dupes > 0: issues.append(f"[{table_name}] order_id 重复: {dupes} 行")
    for col in required_columns:
        if col in df.columns:
            nulls = df[col].isna().sum()
            if nulls > 0: issues.append(f"[{table_name}] {col} 含 {nulls} 个 NULL")
    if "amount" in df.columns:
        neg = (df["amount"] < 0).sum()
        if neg > 0: issues.append(f"[{table_name}] amount 含 {neg} 个负值")
    if len(df) == 0: issues.append(f"[{table_name}] 空 DataFrame")
    return {"passed": len(issues)==0, "issues": issues, "n_rows": len(df)}
```

### 📖 核心原理

**dbt 的 `test` 和 pytest 的 `test`——同一个哲学：用代码验证假设。**

dbt test 的两个核心：
- `unique` test：验证某列无重复值（如 `order_id`——如果重复说明数据有 bug）
- `not_null` test：验证某列无空值（如 `amount`——如果有空值说明 ETL 出了问题）

这些不是"可选的好习惯"——它们是数据管道在**生产环境中唯一的自动验证机制**。没有它们——你永远不知道数据在某一层静默地损坏了。

**在你的 pandas 代码中实现同样的哲学**——每个数据加载函数之后、分析函数之前，调 `validate_input()`（W3D1）。这不只是"检查数据"——它是你的 dbt test 的 pandas 版本。

### Airflow DAG——把 main.py 翻译成 DAG

```python
# main.py 现在是线性执行
def main():
    orders = load_orders()
    users = load_users()
    clean = clean_data(orders)
    validate_data(clean)
    metrics = compute_metrics(clean)
    export_report(metrics)
```

**翻译成 Airflow DAG：**

```python
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime, timedelta

default_args = {"owner":"data-team","retries":2,"retry_delay":timedelta(minutes=5)}

with DAG("xianguoduo_daily",start_date=datetime(2026,12,1),
         schedule_interval="0 8 * * *",catchup=False,default_args=default_args) as dag:
    t1 = PythonOperator(task_id="load_orders",python_callable=load_orders)
    t2 = PythonOperator(task_id="load_users",python_callable=load_users)
    t3 = PythonOperator(task_id="clean",python_callable=clean_data)
    t4 = PythonOperator(task_id="validate",python_callable=validate_data)
    t5 = PythonOperator(task_id="metrics",python_callable=compute_metrics)
    t1 >> t3 >> t4 >> t5  # 拓扑排序——支持并行
    t2 >> t4
```

| Python | Airflow | 差异 |
|--------|---------|------|
| def main(): | DAG | 声明 Task 依赖——自动处理执行顺序 |
| def load_orders(): | Operator | 包装函数——加重试/超时/告警 |
| python main.py | cron schedule | Scheduler 自动触发 |

### Airflow DAG 的工程化理解——不是"学 Airflow 语法"——是"把你的 main.py 翻译成 DAG"

**你的 main.py 已经是一个 DAG——只是缺少三个东西：调度、重试、可视化。**

```python
# 你现在的 main.py——所有步骤线性执行
def main():
    orders = load_orders()
    users = load_users()
    clean_orders = clean_data(orders)
    validate_data(clean_orders)
    metrics = compute_metrics(clean_orders)
    create_charts(metrics)
    export_report(metrics)
```

**翻译成 Airflow DAG：**

```python
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime, timedelta

default_args = {
    'owner': 'data-team',
    'retries': 2,                    # 失败自动重试 2 次
    'retry_delay': timedelta(minutes=5),  # 重试间隔 5 分钟
    'email_on_failure': True,        # 失败发邮件告警
}

with DAG(
    'xianguoduo_daily_report',
    start_date=datetime(2026, 12, 1),
    schedule_interval='0 8 * * *',   # 每天 8:00 AM
    catchup=False,
    default_args=default_args,
) as dag:

    t1 = PythonOperator(task_id='load_orders', python_callable=load_orders)
    t2 = PythonOperator(task_id='load_users', python_callable=load_users)
    t3 = PythonOperator(task_id='clean_data', python_callable=clean_data)
    t4 = PythonOperator(task_id='validate', python_callable=validate_data)
    t5 = PythonOperator(task_id='compute_metrics', python_callable=compute_metrics)

    # 定义依赖——Airflow 自动按拓扑顺序执行——支持并行
    t1 >> t3  # load_orders 完成后 -> clean_data
    t2 >> t4  # load_users 完成后 -> validate
    t3 >> t4  # clean_data 完成后 -> validate
    t4 >> t5  # validate 完成后 -> compute_metrics
```

**核心概念——三个对应——把你的 Python 知识迁移到 Airflow：**

| Python 概念 | Airflow 概念 | 差异 |
|------------|-------------|------|
| `def main():` 函数体 | DAG（有向无环图） | DAG 声明了 Task 之间的依赖——Airflow 自动处理"先跑哪个、并行哪个" |
| `def load_orders():` 函数 | Task / Operator | Operator 包装了你的 Python 函数——加了重试/超时/告警 |
| `if __name__ == '__main__': main()` | `schedule_interval='0 8 * * *'` | 不是手动运行——是 Airflow Scheduler 按 cron 自动触发 |

**面试时——面试官问"你用过 Airflow 吗"——即使你没在生产环境部署过——你回答"我理解 Airflow 的核心概念——DAG = 声明 Task 依赖关系——Operator = 包装函数加容错——Scheduler = 按 cron 自动触发。我的鲜果多项目 main.py 已经有了清晰的 DAG 结构——我在 README 中画了 ASCII DAG 图——迁移到 Airflow 时——每个 Python 函数包装成 PythonOperator——DAG 图直接映射。"**

### L4 命名标准——L4 vs L3

| 场景 | L3 | L4 | 差异 |
|------|----|----|------|
| 加载 | orders = load_orders() | orders_raw = load_orders() | _raw 明确这是原始数据 |
| 清洗 | orders = clean_amounts(orders) | orders_clean = clean_amounts(orders_raw) | 保留两个——可追溯差异 |
| 聚合 | result = compute_gmv(orders) | daily_gmv = compute_gmv(orders_clean) | daily_gmv 自描述 |
| 中间 | tmp = orders.groupby(...) | orders_by_city = orders_clean.groupby(...) | 不需要"临时"概念 |

**L4 核心原则——变量名 = 数据内容 + 数据状态。** orders_raw（原始）、orders_clean（清洗后）、orders_by_city（按城市聚合）、daily_gmv（每日 GMV）。

### L4 六项门禁——本地一键检查脚本

```bash
#!/bin/bash
# scripts/l4_gate.sh
set -e

echo "[5/6] naming audit..."
BAD=$(grep -rnE "\b(x|y|z|d|d1|d2|tmp|df1)\b" src/ --include="*.py" | wc -l)

echo "[6/6] pyproject.toml..."

echo "  PASS"
echo "=== ALL PASSED ==="
```

### L4 代码质量门禁终局——六项自动化检查的完整脚本

```bash
#!/bin/bash
# scripts/l4_gate.sh —— L4 质量门禁——本地一键检查——全部通过才允许 push

set -e  # 任何命令失败 -> 立即退出

echo "=== L4 Quality Gate ==="

echo "[1/6] ruff check..."
ruff check src/ || { echo "FAIL: ruff check 未通过"; exit 1; }
echo "  PASS"

echo "[2/6] mypy check..."
mypy src/ --strict 2>&1 | tail -1
WARNINGS=$(mypy src/ 2>&1 | grep -c "error:" || true)
if [ "$WARNINGS" -gt 5 ]; then
    echo "  FAIL: mypy 警告数 $WARNINGS > 5"
    exit 1
fi
echo "  PASS ($WARNINGS warnings)"

echo "[3/6] pytest..."
pytest tests/ -v --tb=short || { echo "FAIL: pytest 未通过"; exit 1; }
echo "  PASS"

echo "[4/6] pre-commit..."
pre-commit run --all-files || { echo "FAIL: pre-commit 未通过"; exit 1; }
echo "  PASS"

echo "[5/6] naming audit..."
BAD_VARS=$(grep -rnE '(x|y|z|d|d1|d2|tmp|df1|df2|df3)' src/ --include="*.py" | wc -l)
if [ "$BAD_VARS" -gt 0 ]; then
    echo "  FAIL: $BAD_VARS bad variable names found"
    grep -rnE '(x|y|z|d|d1|d2|tmp|df1|df2|df3)' src/ --include="*.py"
    exit 1
fi
echo "  PASS"

echo "[6/6] pyproject.toml config check..."
test -f pyproject.toml || { echo "FAIL: pyproject.toml not found"; exit 1; }
echo "  PASS"

echo ""
echo "=== L4 Quality Gate: ALL PASSED ==="
```

**把这个脚本放在 `scripts/l4_gate.sh`——在 Makefile 中加 `gate` target——每次 push 前跑 `make gate`——六项全绿才 push。不是"应该检查"——是"不通过就 push 不了"。**

**L4 六项门禁的"为什么"——不只是"通过"——是理解每项防什么：**

| 门禁 | 防什么 |
|------|--------|
| ruff check | 防低级错误（未使用变量/语法错误/不安全代码）进入仓库 |
| mypy | 防类型错误——传了 str 给需要 int 的函数——运行时才崩溃 |
| pytest | 防行为回归——改了 A 函数——B 函数的行为静默改变 |
| pre-commit | 防"忘了跑检查"——在 commit 之前自动跑——不给人犯错的机会 |
| naming audit | 防代码腐烂——`x`/`tmp`/`df1` 随时间累积——直到没人能读懂 |
| pyproject.toml | 防配置漂移——工具配置散落在不同文件中——版本不一致 |

### L4 终验的故障排查手册——6 步中每步的常见失败和修复

**步骤 1——ruff check 不通过：** 通常是 F401（未使用的 import）或 F841（未使用的变量）。修复——删掉未使用的 import/变量——或加 `# noqa: F401` 并写注释解释为什么保留（如 __init__.py 的 re-export）。

**步骤 2——mypy 报 > 5 个警告：** 最常见的——`arg-type`（传错类型）和 `union-attr`（Optional 未检查 None）。修复——优先修"你的分析函数"中的警告——第三方库的 type stub 不完整导致的警告可以暂时忽略（`# type: ignore[arg-type]`——但必须写注释解释为什么）。

**步骤 3——pytest 不通过：** 通常是因为数据文件缺失——test 依赖的 sample_data 不在 CI 环境中。修复——确认 sample_data/ 在 git 中——没有被 gitignore——CI checkout 后能访问。

**步骤 4——pre-commit 不通过：** 通常是 hook 版本和本地安装的工具版本不一致。修复——pre-commit 会自己管理 hook 的环境——确认 `.pre-commit-config.yaml` 中的 `rev` 是最新稳定版本——不是 `main`。

**步骤 5——naming audit 不通过：** 最重要的检查。`x`/`tmp`/`df1` 在 2000+ 行代码中可能藏在某处。修复——逐项改名——每次改名后跑 pytest——确认没改坏。

**步骤 6——clone 后六步跑通：** 这是 L4 的核心标准——比 L3 多了一步——"ruff + mypy + pytest 全部零报错"。如果在全新环境中 ruff/mypy 报错——说明你的 pyproject.toml 配置和代码不一致——在你的开发环境中"碰巧能跑"——但在标准 CI 环境中暴露了问题。
