## D1（周一 8/4）：模块化的深层设计——不是"拆文件"，是"定接口"

> 📓 今日主课：DataFrame 核心思维——六板斧/loc/iloc/布尔索引

---

### 🔴 认知冲突

W1 你建了 `io.py`、`clean.py`、`analyze.py` 三个文件。然后你的 `clean.py` 越来越胖——从 30 行变成 200 行。里面有清洗日期的、有清洗金额的、有去异常值的、有填缺失的。你觉得应该再拆——但拆成什么？`clean_dates.py`？`clean_amounts.py`？`clean_outliers.py`？拆太细了 import 满天飞，拆太粗了一个文件 500 行。

然后是 `analyze.py`。你写了一个 `compute_monthly_gmv()` 函数，内部调用了 `clean.py` 里的 `fix_amount_types()`。你改了 `fix_amount_types()` 的实现——原来返回 DataFrame 现在返回 Tuple——然后 `analyze.py` 崩了，因为调用方还在按旧接口解包。

**问题**：模块化不是"把长文件切碎"。那它到底是什么？为什么有的代码拆成一堆文件反而更难维护了？"接口"和"实现"这两个词到底是什么意思？

---

### 📖 核心原理

**模块化 = 隐藏实现，暴露接口。**

用大白话说：你有一个做蛋糕的机器。外面的人只需要知道"从这个口倒面粉进去，从那个口出蛋糕"。他们不需要知道机器内部面粉是怎么搅拌的、烤箱是多少度。那个"进面粉的口"和"出蛋糕的口"就是**接口**。机器内部的齿轮和烤箱就是**实现**。

在代码里：
- **接口** = 函数名 + 参数 + 返回值。`def load_orders(filepath: str) -> pd.DataFrame`——外面的人看到这行就够用了，他们不需要知道里面是用 `pd.read_csv` 还是用 `openpyxl`。
- **实现** = 函数体内部的代码。你怎么读文件、怎么处理缺失值——外面的人不关心，也不应该依赖这些细节。

**为什么要隐藏实现？**

因为实现会变。鲜果多的订单数据现在从 CSV 来，三个月后可能从数据库来。如果 `analyze.py` 里的函数直接调了 `pd.read_csv()`——改数据库的时候 `analyze.py` 也得改。但如果 `analyze.py` 只调 `load_orders()`——改数据库只需改 `io.py` 这一个文件。

**耦合与内聚——判断代码拆得对不的两个标准**

- **低耦合（Loose Coupling）**：改一个模块时，其他模块不受影响。理想状态：改 `io.py` 时 `analyze.py` 不用动。
- **高内聚（High Cohesion）**：一个模块内部的代码全部围绕同一个职责。`io.py` 里的所有函数都是"数据的进和出"——不应该出现一个数据清洗函数。

用这两个标准检查你的项目：
- `clean.py` 里的 `fix_amount_types()`——它是清洗逻辑（改数据类型），属于 `clean.py`。✔ 高内聚。
- `analyze.py` 里调用了 `pd.read_csv()`——分析模块直接做了 IO 的事。✗ 低内聚，高耦合。把它换成 `from src.io import load_orders`。

**拆文件的判断标准——不是"太长就拆"，是"职责变了就拆"**

一个文件 500 行但不是"太长"就拆——看看它内部是不是做了两类不同的事。`clean.py` 里有 10 个函数，8 个是"改数据值"（去空、去异常、修类型），2 个是"检查数据质量"（验证列存在、验证值范围）。后两个职责不同——应该拆到 `validate.py`。

但不要过度拆分——5 个文件每个只有 30 行，import 关系像蜘蛛网，比一个 200 行的文件更难维护。

**接口稳定的价值——用鲜果多举例**

`load_orders()` 的接口是 `(str) -> pd.DataFrame`。只要你保证这个签名不变——输入一个文件路径，返回一个 DataFrame——里面怎么改都没关系：
- V1：`pd.read_csv(filepath)`
- V2：加了 `encoding='gbk'` 的 fallback 逻辑
- V3：从数据库读而不是读文件

外部调用方——`main.py`、`analyze.py`——完全不用改。这就是"隐藏实现，暴露接口"的价值。

## D2（周二 8/5）：Python 异常模型——异常不是"错误"，是"通信机制"

> 📓 今日主课：groupby/agg/transform——核心区别 + cumsum/rolling

---

### 🔴 认知冲突

你的 `load_orders()` 函数用了 `pd.read_csv()`。如果文件不存在——程序直接炸了，终端打印一大段红色的 traceback，末尾是 `FileNotFoundError`。

你不想让程序炸。于是你：
```python
def load_orders(filepath):
    try:
        return pd.read_csv(filepath)
    except:
        return pd.DataFrame()
```
现在文件不存在时——程序不炸了，返回一个空的 DataFrame。后面代码继续跑——然后因为数据为空，在 `groupby` 那里崩了。traceback 变得更长、更难定位——报错位置离真正的根因（文件不存在）差了几十行。

**问题**：异常到底该不该 catch？try/except 写了反而更难排查——那我为什么要写？`except` 和 `except Exception` 和裸 `except:` 有什么区别？

---

### 📖 核心原理

**异常不是错误——它是"这里发生了意料之外的情况，当前代码不知道该怎么处理，请上级调用方决定"。**

用大白话说：你（`load_orders`）去仓库拿货，发现仓库门锁了（文件不存在）。你自己能做决定吗？不能——你不知道这个货重要不重要。你应该告诉上级（调你的 `main.py`）："仓库门锁了，我拿不到货。"上级决定：是换一个仓库（换文件路径），还是今天不送货了（退出程序），还是找人撬锁（创建文件）。

**`try/except/else/finally` 的完整语义**

```python
try:
    # "尝试做这件事"
    df = pd.read_csv(filepath)
except FileNotFoundError:
    # "如果这件事因为'文件不存在'而失败，用这个方案补救"
    logger.error("数据文件不存在: %s", filepath)
    raise  # 重新抛出——让上级知道，我没搞定
except pd.errors.EmptyDataError:
    # "如果是'文件为空'而失败，用另一个方案"
    logger.warning("文件为空: %s，返回空 DataFrame", filepath)
    return pd.DataFrame()
else:
    # "如果 try 里没有任何异常，执行这里"
    logger.info("数据加载成功: %d 行", len(df))
    return df
finally:
    # "不管有没有异常，这一块一定会执行"
    # 用于关闭文件、释放连接等清理工作
    pass
```

**`except` vs `except Exception` vs 裸 `except:` 的区别**

这是 Python 里最容易踩的坑之一：

```python
# ❌ 裸 except——会捕获 KeyboardInterrupt（Ctrl+C）和 SystemExit
try:
    ...
except:
    ...

# ⚠️ except Exception——捕获所有标准异常，但不捕获 KeyboardInterrupt
try:
    ...
except Exception:
    ...

# ✅ except 具体异常类型——只捕获你预期可能发生的异常
try:
    df = pd.read_csv(filepath)
except FileNotFoundError:
    ...
```

为什么要这么讲究？因为有些异常你**不应该**捕获。比如用户按了 Ctrl+C 想中止程序——裸 `except:` 会把它吞掉，程序继续跑，用户只能强制关闭终端。再比如 `SystemExit`——你的程序想正常退出（`sys.exit(0)`），被裸 `except:` 吞了。

**经验法则：**
- 如果你不知道要 catch 什么具体异常——先别 catch。让它炸。炸出的 traceback 告诉你应该 catch 什么。
- 如果你知道文件可能不存在——catch `FileNotFoundError`。在你不知道"上级希望怎么处理"时——`raise` 重新抛出去。
- **永远不要用裸 `except:`。** 如果必须兜底，用 `except Exception as e:`，然后 `logger.exception(e)` 记录完整 traceback。

**为什么"catch 所有异常然后 return 空值"是陷阱？**

因为你把错误的根因隐藏了。`load_orders()` 因为文件不存在返回了空 DataFrame → `clean_orders(df)` 因为 `df.empty` 把后续逻辑跳过了 → `compute_gmv(df)` 返回 0 → 运营总监看到"上月 GMV = 0"。你以为程序跑通了——实际上数据根本没加载进去。

**正确做法**：让你的函数在它无法完成任务时**大声失败（fail fast）**。炸在离根因最近的地方，traceback 最短，排查起来最快。

---

### 🏢 鲜果多案例

鲜果多的 `orders.csv` 有时候会被 ERP 系统锁住（别的程序正在写入）。这时 `pd.read_csv()` 会抛 `PermissionError`。

你不处理这个异常——程序炸了，traceback 显示 `PermissionError`。你一眼就知道：ERP 在写文件，等 30 秒再跑。

如果你静默 catch 了所有异常，返回空 DataFrame——程序跑完了但 GMV 是 0。你用了一下午排查为什么 GMV 是 0，最后发现是文件被锁了。fail fast 的价值就在这 4 个小时里。

### ✅ 自检反馈

**✅ 参考答案**

- `FileNotFoundError` 被 catch 后 `raise` 重新抛出——`main.py` 会收到这个异常，程序终止。
- `EmptyDataError` 被 catch 后返回空 DataFrame——程序继续跑，但后续 `validate_input` 应该检测到并报错。

**❓ 常见偏差**

| 偏差 | 原因 | 🔧 补救 |
|------|------|---------|
| "catch 了 `Exception` 而不是具体异常" | `except Exception` 太宽，`FileNotFoundError`、`PermissionError`、`ValueError` 都被同一种方式处理 | 思考每种异常应该怎么处理——文件不存在（raise）、权限不足（raise）、空文件（返回空值）。不同异常，不同处理 |
| "catch 之后 print 一下就完了" | 你没有 `raise`，异常被吞了。上层代码不知道这里出了错，继续跑——产生错误的结果 | 如果不能处理，就 `raise` 让上层决定。print 不是处理方式 |
| "觉得 try/except 很麻烦" | 你现在写的是 3 个函数。等你写 30 个函数的时候，你会发现不处理异常的代码排查 bug 的时间是处理了的 10 倍 | — |

## D3（周三 8/6）：logging 架构——为什么大厂代码里从来没有 print

> 📓 今日主课：merge/concat/join + 行数膨胀检测

---

### 🔴 认知冲突

W1 你写代码用 `print` 看中间结果——`print('清洗完成')`、`print(f'订单数: {len(df)}')`。能跑。但三个问题慢慢浮现：

1. **你不知道是谁输出的。** 终端里有 20 条消息，你分不清哪条来自 `io.py`、哪条来自 `clean.py`、哪条来自 `analyze.py`。
2. **你不知道什么时候输出的。** 代码跑了两分钟，你回来看到打印了一大堆——但每条消息是第 1 秒输出的还是第 119 秒输出的？你无法判断哪一步是瓶颈。
3. **你只能输出到屏幕。** 想保存到文件永久记录？得改代码。想把重要的错误和普通的进度分开？`print` 做不到——所有消息在 `print` 看来都是一样的。

**问题**：`logging` 和 `print` 的区别，难道只是"多了个时间戳"？为什么整个 Python 社区都说"不要用 print"？

---

### 📖 核心原理

**print 是"对人喊话"。logging 是"程序的自我叙述"。**

print 的逻辑：现在，把这句话显示在屏幕上。说完就没了。没法回溯、没法分类、没法控制开关。

logging 的逻辑：程序在持续记录自己的运行状态。每一条记录有**时间、来源、重要程度**。这些记录可以同时输出到屏幕和文件——文件里的记录在程序跑完后仍然可以搜索。

**logging 的三层架构**

```
Logger（记录器）     —— "谁"在记录     —— 每个模块一个 logger
  ↓
Handler（处理器）    —— 记录"去哪"    —— 屏幕 / 文件 / 邮件 / 远程服务器
  ↓
Formatter（格式化器）—— 记录"长什么样" —— 时间格式 / 是否含文件名 / 是否含行号
```

你可以对同一个 logger 加多个 handler：
- StreamHandler → 输出到终端（实时看）
- FileHandler → 输出到文件（跑完查）

**五级日志——不是什么消息都平等**

| 级别 | 用途 | 生产环境默认是否显示 | 示例 |
|------|------|-------------------|------|
| **DEBUG** | 排查问题时才需要看的细节 | 不显示 | `logger.debug('第 %d 行处理中, 值=%s', i, val)` |
| **INFO** | 正常的流程节点——"做到了哪一步" | 显示 | `logger.info('数据加载完成: %d 行', len(df))` |
| **WARNING** | 不太对但还能继续——"可能需要关注" | 显示 | `logger.warning('%s 缺失率 %.1f%%', col, rate)` |
| **ERROR** | 某个步骤失败了 | 显示 | `logger.error('文件不存在: %s', filepath)` |
| **CRITICAL** | 整个程序不能继续了 | 显示 | `logger.critical('数据为空，无法继续')` |

你可以通过设置 level 来控制哪些级别的消息被显示：
```python
logging.basicConfig(level=logging.INFO)   # DEBUG 不显示，INFO 及以上显示
logging.basicConfig(level=logging.DEBUG)  # 全显示（排查问题时开）
logging.basicConfig(level=logging.ERROR)  # 只看错误（生产环境精简输出）
```

**为什么 `%s` 占位符的写法比 f-string 好？**

```python
# 方式一：f-string
logger.info(f'数据加载完成: {len(df)} 行')  # f-string 在 logger 判断级别之前就执行了格式化

# 方式二：占位符
logger.info('数据加载完成: %d 行', len(df))  # logger 先判断级别，不够级别就不格式化——省了开销
```

对于几十万行的数据处理，方式二在高频调用时能省下可观的格式化开销。但更重要的是——logging 框架可以自动把 `%s` 格式的消息和参数分开存储，方便后续搜索和分析。

## D4（周四 8/7）：类型系统——Python 的类型标注不是给 Python 看的

> 📓 今日主课：apply/map/str/dt + 向量化性能（for vs apply vs 向量化）

---

### 🔴 认知冲突

你写了一个函数 `def filter_orders(df, min_amount)`。三个月后回来看——`df` 是 DataFrame 还是 Series？`min_amount` 是 int 还是 float？`filter_orders` 返回什么？你看了 5 行函数体才推导出来——"哦，这返回的是过滤后的 DataFrame"。

然后你给 `filter_orders` 传了一个 Series——程序没报错，但结果不是你要的。因为 Python 不在乎你传什么——**它只在你运行到不兼容的操作时才报错**（比如传了 Series 后调 `.groupby()` 会炸，但传 Series 本身不报错）。

**问题**：Type Hints 不是"给 Python 看的"——Python 运行时根本不检查它们。那它写在代码里到底有什么用？为什么大厂代码里 Type Hints 覆盖率是代码审查的硬指标？

---

### 📖 核心原理

**Type Hints 的读者是人（你和你的同事），不是 Python。**

Python 是动态类型语言——变量没有固定类型，同一个变量可以先是 `int` 后来变成 `str`。Python 运行时完全忽略 Type Hints。这个事实很多教程没讲清楚——导致你以为"写了 Type Hints Python 就会检查"。

检查 Type Hints 的是另一个工具——**mypy**（W19 你会学）。它在你跑代码之前，**静态地**检查函数调用时传的参数类型是否匹配。

但即使没有 mypy，Type Hints 本身就有巨大的价值——在你读代码时：

```python
# 没有 Type Hints
def filter_orders(df, min_amount):
    return df[df['amount'] >= min_amount]

# 有 Type Hints
def filter_orders(df: pd.DataFrame, min_amount: float) -> pd.DataFrame:
    return df[df['amount'] >= min_amount]
```

第一个版本：你需要 5 秒去理解参数和返回值。
第二个版本：你扫一眼就知道了——输入是一个 DataFrame 和一个 float，返回一个 DataFrame。**Type Hints 降低了代码的阅读理解成本。**

**数据分析常用的 Type Hints**

```python
from typing import List, Dict, Optional, Tuple, Union, Any
import pandas as pd
import numpy as np

# 最常用的三个
def load_csv(path: str) -> pd.DataFrame: ...
def clean_amounts(df: pd.DataFrame) -> pd.DataFrame: ...
def compute_gmv(orders: pd.DataFrame) -> float: ...

# Optional：参数可以不传，默认为 None
def filter_by_city(df: pd.DataFrame, city: Optional[str] = None) -> pd.DataFrame: ...

# List/Dict/Tuple：容器类型
def get_top_cities(df: pd.DataFrame, n: int = 10) -> List[str]: ...
def run_ab_test(control: pd.Series, treatment: pd.Series) -> Dict[str, float]: ...
def split_date(df: pd.DataFrame, date_col: str) -> Tuple[int, int, int]: ...

# Union：多种类型之一
def load_data(source: Union[str, pd.DataFrame]) -> pd.DataFrame: ...
```

**Duck Typing——Python 的"如果你走起来像鸭子、叫起来像鸭子，我就当你是鸭子"**

这是 Python 类型系统最难理解的地方。静态类型语言（如 Java）检查的是"你是不是鸭子"——即你是不是 Duck 类的子类。Python 不检查——它看你有没有 `quack()` 方法。有，就让你过。这叫"鸭子类型"（Duck Typing）。

但这不意味着 Type Hints 没用。恰恰相反——在动态语言中，Type Hints 是**人的锚点**。它告诉读代码的人："这个函数期望的输入是什么形状"。程序不在乎，但三个月后的你在乎。

---

### 🏢 鲜果多案例

你三个月后回来维护鲜果多项目。打开 `analyze.py`，看到这个函数签名：

```python
def compute(data, group, metric, method='sum'):
    ...
```

你花了 10 分钟看函数体才理解：`data` 是 DataFrame，`group` 是列名字符串，`metric` 也是列名字符串，`method` 是聚合方式。你重构了这个函数，改成：

```python
def aggregate_by_group(
    df: pd.DataFrame,
    group_col: str,
    value_col: str,
    agg_method: str = 'sum'
) -> pd.Series:
    """按指定维度聚合指标。

    Args:
        df: 含 {group_col} 和 {value_col} 的 DataFrame
        group_col: 分组维度列名（如 'city'）
        value_col: 聚合指标列名（如 'amount'）
        agg_method: 聚合方式，默认 'sum'，支持 'mean'/'count'/'max'/'min'

    Returns:
        以 group_col 唯一值为 index、聚合结果为 values 的 Series
    """
    return df.groupby(group_col)[value_col].agg(agg_method)
```

新的函数名和类型标注告诉你：读函数签名就能理解 80%——不再需要翻函数体。

## D5（周五 8/8）：docstring 哲学——你不是在写文档，你是在和三个月后的自己对话

### 🔴 认知冲突

你写了一个 `compute_rfm()` 函数。一个月后回来改——你看着这行代码，不知道"R 分"是什么打分逻辑：
```python
r_score = pd.qcut(r, q=4, labels=[4,3,2,1])
```
为什么 `labels=[4,3,2,1]` 是倒序的？为什么用 4 分位而不是 5 分位？切割点在哪？

你只好打开 Stack Overflow 翻你当时查过的帖子，拼凑出当时的思路。20 分钟过去了。

隔壁同事的 `compute_rfm()` 长这样：
```python
def compute_rfm(orders, reference_date, user_col='user_id', ...):
    """计算 RFM 三维分群。

    打分逻辑（分位数法）:
    R: 最近一次购买距参考日期的天数。天越少→分越高。
       因为越近越活跃，所以 qcut labels 用倒序 [4,3,2,1]。
    F: 购买次数。次越多→分越高。
    M: 总消费金额。金越高→分越高。

    切割点: 4 分位（0, 0.25, 0.5, 0.75, 1.0）。选 4 分位而非 5 分位
    是因为 RFM 三段式（高/中/低）每维需要 4 分位才能产生 4³=64 种组合，
    再合并为常见的 8 类用户。

    注意: 此函数不会原地修改输入 DataFrame——返回的是一个新 DataFrame。
    """
```

你读这段 docstring——不需要看函数体就知道了打分逻辑、参数选择原因、使用注意事项。这不是"给函数写说明书"——**这是在和未来的自己对话。**

---

### 📖 核心原理

**docstring 的读者，首先是三个月后的你，其次才是别人。**

所以 docstring 应该写什么？不是"这个函数做了什么"——函数名和类型标注已经说了 50%。docstring 应该补充那 50% 无法从函数签名读出的信息：**为什么要这样设计？有什么陷阱？参数的决定过程是什么？**

**docstring 应该写的三件事**

1. **设计决策**：为什么选这个方法而不是那个方法？为什么切割点是 4 分位？
2. **边界行为**：传空 DataFrame 会怎样？传缺失值会怎样？
3. **使用注意**：这个函数会修改原数据吗？返回的 DataFrame 和输入的是同一个吗？

**docstring 不应该写的三件事**

1. **代码的逐行翻译**：`"""用 pd.qcut 进行分位数切割，labels 是 [4,3,2,1]，然后..."""`——这是废话。会看代码的人不需要你翻译。
2. **显而易见的类型信息**：参数 `df: pd.DataFrame` 已经说了是 DataFrame——docstring 里不用重复"df 是 DataFrame"。
3. **"这个函数用于..."**：这是 filler（填充词）。直接说干什么，不要说我准备说干什么。

**Args + Returns 是底线，但不是全部**

```python
def clean_amount_column(df: pd.DataFrame, col: str = 'amount') -> pd.DataFrame:
    """清洗金额列：去除负数、将类型统一为 float64、将 0 值标记为可疑。

    金额 = 0 的记录不会被删除（可能是赠品订单），但会被标记在
    is_zero_amount 列中。如果 0 值占比超过 20%，函数会发出 WARNING 日志。

    Args:
        df: 含 {col} 列的订单 DataFrame
        col: 要清洗的金额列名，默认 'amount'

    Returns:
        清洗后的 DataFrame，新增 is_zero_amount 布尔列，行数不变

    Raises:
        ValueError: 如果 {col} 列不存在于 df 中
    """
```

这个 docstring 回答了三个问题：
- 0 值怎么处理？（不删，标记）
- 什么情况会警告？（0 值占比 > 20%）
- 返回和输入的关系是什么？（行数不变，新增一列）

**Google Style vs NumPy Style**

两种主流风格。区别不大。选 Google Style 是因为它在纯文本下可读性更好，适合 GitHub README 和 Jupyter notebook：
```python
# Google Style（推荐）
def func(arg1: str, arg2: int = 0) -> bool:
    """一句话描述。

    Args:
        arg1: 第一个参数的说明
        arg2: 第二个参数的说明

    Returns:
        返回值的说明
    """

# NumPy Style
def func(arg1: str, arg2: int = 0) -> bool:
    """一句话描述。

    Parameters
    ----------
    arg1 : str
        第一个参数的说明
    arg2 : int, optional
        第二个参数的说明, default 0

    Returns
    -------
    bool
        返回值的说明
    """
```

### 📝 10 道概念自测题

**Q1**："接口"和"实现"的区别是什么？为什么改 IO 模块的内部实现（比如从 CSV 改成数据库）时，analyze 模块不应该需要改动？

**Q2**：`try/except/else/finally` 四个块各自什么时候执行？如果 `try` 中的代码抛出异常，`else` 还会执行吗？

**Q3**：裸 `except:` 和 `except Exception:` 和 `except FileNotFoundError:` 的区别是什么？为什么永远不要用裸 `except:`？

**Q4**：logging 的 Logger / Handler / Formatter 三层各自负责什么？如果我想让日志同时输出到终端和文件，应该怎么做？

**Q5**：五级日志（DEBUG/INFO/WARNING/ERROR/CRITICAL）各自的使用场景。为什么 DEBUG 在生产环境默认不显示？

**Q6**：Python 运行时检查 Type Hints 吗？如果 Python 不检查，为什么还要写？

**Q7**：`Optional[str]` 和 `str` 在 Type Hints 中的区别是什么？

**Q8**：docstring 应该写什么、不应该写什么？

**Q9**：一个函数已经能跑了，Type Hints 不会让它跑得更快，docstring 也不会让它跑得更正确。为什么我们还要花时间写这些东西？

**Q10**：你写了一个函数处理了数据异常，返回了空 DataFrame。后面的分析函数因为空 DataFrame 报了错。为什么"静默处理异常然后返回空值"比"让异常直接炸出来"更难排查？

### ✅ 参考答案 + 偏差诊断

**Q1**：接口 = 函数名 + 参数 + 返回值。实现 = 函数体内部逻辑。改实现不改接口 = 外部不受影响。偏差：把接口理解为"函数的代码"——接口是签名，不是实现。

**Q2**：try 抛出异常 → except 执行 → else **不**执行。try 无异常 → except 跳过 → else 执行。finally 永远执行。偏差：以为 else 和 finally 是同一回事——不是。else 只在 try 无异常时执行（和 except 互斥）。

**Q3**：裸 `except:` 捕获一切（包括 Ctrl+C 的 KeyboardInterrupt 和 SystemExit）。`except Exception:` 捕获所有标准异常但不捕获系统信号。`except FileNotFoundError:` 只捕获文件不存在。偏差：说不出来裸 except 到底多捕获了什么——它会吞掉 Ctrl+C，导致程序无法被用户终止。

**Q4**：Logger = "谁"在记录。Handler = 记录"去哪"（屏幕/文件/邮件）。Formatter = 记录"长什么样"（时间格式等）。同时输出到终端和文件：给 logger 加两个 handler（StreamHandler + FileHandler）。偏差：把 Formatter 理解成"日志的样式"——对，更准确地说它决定了每条日志消息的字符串格式。

**Q5**：DEBUG = 排查细节，生产环境不开（太多噪音）。INFO = 流程节点，生产环境开。WARNING = 不太对但能继续。ERROR = 步骤失败。CRITICAL = 程序停止。偏差：不知道 DEBUG 和 INFO 的区别——DEBUG 是给开发者看的细节（如变量值），INFO 是给使用者看的流程（如"加载完成"）。

**Q6**：不检查。但 Type Hints 的读者是人——降低阅读理解成本。mypy 工具可以静态检查（W19）。偏差：以为 Python 运行时会检查类型标注——不会。Python 是动态类型语言，类型标注是"注释"而非"约束"。

**Q7**：`Optional[str]` = `str | None`——这个参数可以是字符串也可以是 None。`str`——只接受字符串，传 None 会被 mypy 标记。偏差：以为 `Optional[str]` 表示"可以不传这个参数"——不是，它表示"传了的话可以是 str 也可以是 None"。默认值和 Optional 是独立的概念。

**Q8**：应该写：设计决策（为什么选这个方法）、边界行为（空数据/缺失值怎么处理）、使用注意（是否会修改原数据）。不应该写：代码逐行翻译、类型信息重复、filler。偏差：docstring 写了一堆"这个函数用于..."——这是 filler，直接说干什么。

**Q9**：Type Hints 和 docstring 不是写给计算机的——是写给人的。代码被读的次数远多于被写的次数。你花 30 秒写 Type Hints，为三个月后的自己（或同事）节省 5-20 分钟的理解时间。偏差：说"不需要"——说明你还没经历过维护六个月前的代码。

**Q10**：异常在离根因最远的地方炸出来——traceback 指向分析函数，但根本原因是"文件没加载进去"。中间隔了好几层函数调用，排查链路被拉长。而"让异常在 IO 函数就直接炸"——traceback 指向根因，排查时间缩短。偏差：说"反正都会报错"——不是都会报错。静默处理的话程序可能继续跑出错误结果（如 GMV=0），比直接炸更危险。
