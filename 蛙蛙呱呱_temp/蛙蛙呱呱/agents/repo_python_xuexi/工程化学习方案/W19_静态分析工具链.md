### mypy 的 5 种最常见错误类型与修复

| 错误代码 | 含义 | 示例 | 修复 |

### 🔴 认知冲突

W2D4 你学了 Type Hints——"Python 运行时完全不检查它们"。现在你写了 4 个月的 Type Hints——但你不知道它们是否真的是对的。有人传了 `Optional[int]` 但你的代码没有处理 None——mypy 是在跑代码**之前**发现这个问题的。

---

### 📖 核心原理

**mypy 是静态类型检查器——它在不运行代码的情况下分析代码的类型一致性。**

```python
# Python 运行时: 不报错（直到实际调用才可能报错）
def add_one(x: int) -> int:
    return x + 1

add_one("hello")  # Python: 运行到这里才报错 TypeError

# mypy: 在不运行的情况下就检测到类型不匹配
# error: Argument 1 to "add_one" has incompatible type "str"; expected "int"
```

**mypy 的渐进式采用——不是"全项目零报错"，而是"重点文件零报错"。**

```ini
# pyproject.toml 或 mypy.ini
[mypy]
python_version = "3.10"
strict = false                    # 不要求所有检查全开
warn_return_any = true            # 返回 Any 时警告
warn_unused_ignores = true        # 检测冗余的 type: ignore
disallow_untyped_defs = true      # 禁止无 Type Hints 的函数定义
```

**先从 `disallow_untyped_defs = true` 开始——要求所有函数有 Type Hints。** 这是 Type Hints 工程的"第一道门"——没有类型标注的函数会被 mypy 标记。这是 L4 的硬指标。

### mypy 进阶配置与实战——不只是"跑一下"——是"渐进式严格化"

**mypy 的配置策略——不是一次性开启 strict=true——而是逐步收紧：**

```ini
# pyproject.toml [tool.mypy] —— 渐进式严格化路径
[tool.mypy]
python_version = "3.10"

# 阶段 1（本周）: 基础检查——不允许无类型标注的函数
disallow_untyped_defs = true
warn_return_any = true
warn_unused_ignores = true

# 阶段 2（下周 W20）: 更严格——不允许隐式 Optional
strict_optional = true
no_implicit_optional = true

# 阶段 3（项目阶段 W21-W24）: 全严格
strict = true
```

**mypy 最常见的 5 种错误类型——提前知道——修复不慌：**

| 错误代码 | 含义 | 示例 | 修复 |
|---------|------|------|------|
| `arg-type` | 传入参数类型不匹配 | `add_one("hello")` | 检查调用方——是传错了还是类型标注错了 |
| `return-value` | 返回值类型不匹配 | `def f() -> int: return None` | 如果可能返回 None——改标注为 `Optional[int]` |
| `attr-defined` | 访问了不存在的属性 | `df.amounts`（应该是 amount） | 拼写错误——改属性名 |
| `union-attr` | 对 Optional 类型未做 None 检查 | `x.startswith(...)` 但 x 可能是 None | 加 `if x is not None:` 或 `assert x is not None` |
| `call-overload` | 函数调用时参数类型匹配了错误的 overload | `pd.read_csv(123)` | 检查参数类型 |

**鲜果多项目 mypy 上线——第一周的经验：** 5 个人的团队——首次跑 mypy 报 200+ 个错误。不是一次性修完——而是"每次 commit 修复 <= 5 个"——两周内归零。关键策略——先修"分析函数"（你的核心代码）——再修"工具函数"（别人写的/第三方库的封装）——最后修"main.py"（入口——影响最小）。

**面试时——面试官问"你怎么推广 mypy 到团队"——你讲这个"渐进式严格化"的故事——不是强制执行——而是逐步收紧——每次只修最关键的 5 个——两周内平滑过渡。**

### ruff 完整配置与规则选择

鲜果多最有价值的 5 条 ruff 规则——每条对应一次真实 bug：

| 规则 | 检测什么 | 鲜果多真实案例 |

### 🔴 认知冲突

你以前听说过 flake8、isort、black、pyupgrade、pylint——一堆工具，每个检查不同的东西。现在社区统一到了 ruff——一个 Rust 写的工具，速度 10-100 倍于 Python 实现。

---

### 📖 核心原理

**ruff 检查什么？三类规则：**

**1. 代码风格（F/E/W 规则）**：未使用的 import、未定义的变量、语法错误、缩进问题。
**2. 代码质量（I/N/UP 规则）**：import 排序（isort）、PEP 8 命名规范（N 规则）、升级到新 Python 语法（UP 规则——如 `Optional[X]` → `X | None`）。
**3. 安全（S 规则）**：检测 `eval()`/`exec()`/硬编码密码/弱加密。

```toml
# pyproject.toml
[tool.ruff]
line-length = 100
target-version = "py310"

[tool.ruff.lint]
select = ["E", "F", "I", "N", "UP", "B", "SIM"]
ignore = ["E501"]  # 行长度由 formatter 处理
```

**你的项目中 ruff 最有价值的规则：**
- `F401`：import 了但没使用的模块——删掉
- `F841`：赋值了但没使用的变量——删掉
- `I001`：import 顺序不规范——自动排序
- `B006`：可变默认参数（`def f(x=[])`）——这是经典 Python 坑

---

### ✍️ 动手练习

1. 安装 ruff：`pip install ruff`。
2. 配置 `pyproject.toml`——启用 E/F/I/N/UP/B 规则。
3. 跑 `ruff check src/`——修掉所有自动可修复的（`ruff check --fix src/`）。
4. 在 CI 里加 `ruff check src/` 步骤。
5. `git add . && git commit -m "add ruff linter to project and CI" && git push`

---

### ruff 完整配置与规则选择——不只是"复制粘贴"——是"理解每条规则的业务价值"

```toml
# pyproject.toml [tool.ruff] —— 数据分析项目的推荐配置
[tool.ruff]
line-length = 100
target-version = "py310"

[tool.ruff.lint]
select = [
    "E",     # pycodestyle errors——语法错误/缩进
    "F",     # pyflakes——未使用的 import/变量
    "I",     # isort——import 排序
    "N",     # pep8-naming——命名规范
    "UP",    # pyupgrade——升级到新 Python 语法
    "B",     # flake8-bugbear——常见 bug 检测
    "SIM",   # flake8-simplify——代码简化建议
    "C4",    # flake8-comprehensions——推荐 list comprehension
]
ignore = [
    "E501",  # 行长度——由 formatter 处理
    "B008",  # 函数参数默认值——在某些场景合理
]

[tool.ruff.lint.per-file-ignores]
"__init__.py" = ["F401"]  # __init__.py 中 import 可能就是为了 re-export
"tests/*.py" = ["S101"]   # 测试中允许使用 assert

[tool.ruff.format]
quote-style = "double"
indent-style = "space"
```

**鲜果多项目中最有价值的 5 条 ruff 规则——每条对应一次真实 bug：**

| 规则 | 检测什么 | 鲜果多真实案例 |
|------|---------|-------------|
| F401 | import 了但未使用 | 有人 import 了 requests 但从未使用——增加了无意义的依赖 |
| F841 | 赋值了但未使用 | `result = compute_gmv(df)` 然后 `return gm`（拼错了变量名——返回了旧值） |
| B006 | 可变默认参数 | `def f(cities=[])`——第二次调用时 cities 还残留第一次的数据 |
| SIM108 | 用 if-else 代替三元表达式 | `if x: y = 1 else: y = 2` -> `y = 1 if x else 2` |
| UP006 | 用新版类型语法 | `Optional[int]` -> `int | None`（Python 3.10+） |

**ruff 和 ruff format 的分工——ruff check 检查逻辑问题——ruff format 统一格式。** 你的团队不再争论"单引号还是双引号"——pyproject.toml 里写了 `quote-style = "double"`——ruff format 自动统一——争论结束。

## D3（周三 12/3）：pre-commit——在 git commit 之前自动检查


---

### pre-commit 完整配置与故障排查

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.0
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
  - repo: https://github.com/pre-commit/mirrors-mypy
    rev: v1.11.0
    hooks:
      - id: mypy
        args: [--strict, --ignore-missing-imports]
        additional_dependencies: [pandas-stubs]
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: check-yaml
      - id: check-toml
      - id: check-added-large-files
        args: [--maxkb=1000]
      - id: detect-private-key
      - id: end-of-file-fixer
      - id: trailing-whitespace
```

| 故障 | 原因 | 修复 |
|------|------|------|
| pre-commit 不触发 | 忘记 pre-commit install | 重新跑确认输出 installed |
| mypy 报 library stubs not installed | 需要类型 stub 包 | additional_dependencies: [pandas-stubs] |
| ruff 报 unknown rule | 本地版本和 pre-commit 版本不一致 | rev: v0.6.0 固定版本 |
| mypy 太慢（30s+） | 每次全量检查 | pre-commit 只跑 ruff——mypy 放在 CI 中 |

> 📓 今日主课：设计模式在大项目中的应用

---

### 📖 核心原理

**pre-commit = 一个 git hook——在每次 `git commit` 之前自动跑你指定的检查。**

如果检查不通过——commit 被阻止。这意味着"忘记跑 mypy"或"忘了跑 ruff"变得不可能。

配置 `.pre-commit-config.yaml`——每次 commit 前自动跑 ruff + mypy + 检查是否有大数据文件被提交。

---

### ✍️ 动手练习

1. 安装 pre-commit：`pip install pre-commit`。
2. 创建 `.pre-commit-config.yaml`——含 ruff + mypy + check-yaml + check-toml + forbid-large-files。
3. `pre-commit install`——激活 hook。
4. 故意引入一个 ruff 会报错的代码，尝试 `git commit`——确认被阻止。
5. `git add .pre-commit-config.yaml && git commit -m "add pre-commit hooks: ruff + mypy + file checks" && git push`

### pre-commit 完整配置与故障排查——不只是"能跑"——是"团队里每个人都跑同一条规则"

```yaml
# .pre-commit-config.yaml —— 数据分析项目的标准配置
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.0  # 固定版本——不是 main——确保团队一致性
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format

  - repo: https://github.com/pre-commit/mirrors-mypy
    rev: v1.11.0
    hooks:
      - id: mypy
        args: [--strict, --ignore-missing-imports]
        additional_dependencies:
          - pandas-stubs
          - types-requests

  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: check-yaml          # YAML 语法检查
      - id: check-toml          # TOML 语法检查
      - id: check-json          # JSON 语法检查
      - id: check-added-large-files  # 防止提交大文件（> 1MB）
        args: ['--maxkb=1000']
      - id: detect-private-key  # 防止提交私钥文件
      - id: end-of-file-fixer   # 文件末尾加换行
      - id: trailing-whitespace # 删除行尾空格
```

**pre-commit 的常见故障与修复：**

| 故障 | 原因 | 修复 |
|------|------|------|
| pre-commit 不触发——git commit 直接通过了 | 忘记 `pre-commit install` | 重新跑——确认输出 "pre-commit installed at .git/hooks/pre-commit" |
| mypy hook 报 "library stubs not installed" | mypy 需要类型 stub 包 | `additional_dependencies: [pandas-stubs]`——告诉 pre-commit 自动安装 |
| ruff hook 报 "unknown rule" | 本地 ruff 版本和 pre-commit 的版本不一致 | `rev: v0.6.0` 固定版本——不是 `rev: main` |
| 每次 commit 都跑 mypy 太慢（30s+） | mypy 每次全量检查 | 改用 `args: [--strict, --follow-imports=skip]` 跳过第三方库——或只在 CI 中跑 mypy——pre-commit 只跑 ruff |

**pre-commit 不是替代 CI——是和 CI 分工：** pre-commit 跑快的检查（ruff 1-2s）——CI 跑全量检查（mypy 30s + pytest 60s）。pre-commit 让你在 commit 时就发现 80% 的问题——CI 发现剩下的 20%。

### pyproject.toml 统一配置——从"散落各处的 .cfg/.ini"到"一个文件管理全部"

**迁移对照表——每个旧配置文件的内容应该放在 pyproject.toml 的哪个位置：**

| 旧文件 | 对应 pyproject.toml section | 迁移注意事项 |
|--------|--------------------------|------------|
| mypy.ini / .mypy.ini | [tool.mypy] | 格式从 INI 变成 TOML——`strict = true` 不变——但 `[mypy-*.py]` 变成 `[[tool.mypy.overrides]]` |

| setup.cfg（pytest 部分） | [tool.pytest.ini_options] | filterwarnings / testpaths / addopts 迁移——格式从 INI 变成 TOML |
| setup.cfg（项目元数据） | [project] | name / version / requires-python / dependencies——全部迁移 |

### W19 闭卷自测

**Q1:** mypy 和 Python 运行时的类型检查区别？
> **A:** mypy 是静态类型检查——不运行代码——分析类型一致性。Python 运行时只在执行到那行代码时才检查类型。mypy 能发现"传了 str 给需要 int 的函数"——即使这行代码在当前测试中没有被执行到。

**Q2:** ruff --fix 能/不能修复什么？
> **A:** 能——未使用的 import（删除）、import 排序、行尾空格、废弃语法（Optional[X]->X|None）。不能——类型错误、未使用变量（需判断"该删还是忘了用"）、逻辑错误。

**Q3:** pre-commit 和 CI 的分工？
> **A:** pre-commit 跑快的检查（ruff 1-2s）——commit 前拦截 80% 低级错误。CI 跑全量（mypy 30s + pytest 60s）——push 后验证剩余 20%。两个都需要——只用 CI 会因低级错误浪费等待时间——只用 pre-commit mypy 太慢影响 commit 体验。

**Q4:** 面试官问"你怎么保证团队代码质量一致"？
> **A:** "我用工具而非人来保证。ruff 统一代码风格——pyproject.toml 定义规则——所有人共享。mypy 统一类型标注——disallow_untyped_defs=true。pre-commit 每次 commit 前自动跑 ruff。CI 三重门每次 push 自动跑 ruff+mypy+pytest——任何一项不通过不允许合并。工具铁面无私——不会因为赶时间就放行。"
