### L3 代码可读性评审的实战走查——不只是"检查清单"——是逐文件的具体审查示例

**走查示例 1：模块 docstring——从"废话"到"有用的索引"**

修改前：
```python
# src/data/io.py
"""IO module for data loading."""
```

修改后：
```python
# src/data/io.py
"""数据加载与导出模块——从 CSV/Parquet/PostgreSQL 加载原始数据，将处理后的数据导出为 CSV/Parquet/Excel。

数据源优先级: DWD 层 Parquet > ODS 层 CSV > 原始数据库查询
导出格式选择: 分析师使用 Parquet（快，列式存储）; 业务方使用 Excel（格式化后）
依赖: src/utils/paths.py（路径常量）, src/utils/logger.py（日志）
"""
```

**为什么改后是 L3 标准？** (1) 一句话说清了"这个文件做什么" (2) 说明了"什么时候选什么格式"（决策逻辑）(3) 标注了依赖（新同事不需要从 import 语句反向推导）

**走查示例 2：函数签名——从"需要读函数体"到"看签名就知道怎么用"**

修改前：
```python
def compute_gmv(orders, include_tax=True, exclude_refund=True, use_payment_time=False):
```

修改后：
```python
def compute_gmv(
    orders: pd.DataFrame,
    include_tax: bool = True,
    exclude_refunded: bool = True,
    use_payment_time: bool = False
) -> float:
```

**为什么改后是 L3 标准？** (1) Type Hints 告诉调用方"传入 DataFrame——返回 float" (2) 参数名自描述——`exclude_refunded` 比 `exclude_refund` 更精确（"已退款的"不是"退款行为"）(3) 调用方不需要打开函数体就能写代码。

**走查示例 3：docstring 中的"为什么"——从"做了什么"到"为什么这么做"**

修改前："去除 amount 为负值的行。"
修改后："去除 amount 为负值的行——负值来源于退款单（退款另表处理——不在订单表中混合）。如果 amount 列不存在——raise ValueError——因为上层 analyze.py 依赖此列。如果所有行都被过滤了——返回空 DataFrame（不报错）——调用方需检查 len(result)==0。"

**为什么改后是 L3 标准？** 前两句话解释了"为什么过滤负值"和"为什么 raise"。第三句话声明了边界行为——如果调用方不检查空 DataFrame——会在下游报错——这个声明等于告诉调用方"你应该检查"。

### Type Hints 覆盖率审计的完整脚本——CI 自动执行

```python
#!/usr/bin/env python
import ast, sys
from pathlib import Path

def audit_coverage(root_dir="src"):
    total, with_return_type, with_docstring = 0, 0, 0
    external_total, external_ok = 0, 0
    issues = []

    for py_file in Path(root_dir).rglob("*.py"):
        tree = ast.parse(py_file.read_text(encoding="utf-8"))
        for node in ast.walk(tree):
            if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef)):
                total += 1
                if node.returns:
                    with_return_type += 1
                if ast.get_docstring(node):
                    with_docstring += 1

                if not node.name.startswith("_"):
                    external_total += 1
                    if node.returns and ast.get_docstring(node):
                        external_ok += 1
                    else:
                        issues.append(f"{py_file}:{node.lineno}: {node.name}")

    ret_pct = with_return_type / total * 100 if total else 0
    doc_pct = with_docstring / total * 100 if total else 0
    ext_pct = external_ok / external_total * 100 if external_total else 100

    print(f"Total functions: {total}")
    print(f"Type Hints coverage: {ret_pct:.0f}% ({with_return_type}/{total})")
    print(f"docstring coverage: {doc_pct:.0f}% ({with_docstring}/{total})")
    print(f"External function coverage: {ext_pct:.0f}% ({external_ok}/{external_total})")

    if issues:
        print(f"L3 violations ({len(issues)}):")
        for issue in issues:
            print(f"  {issue}")
    if external_ok < external_total:
        sys.exit(1)

if __name__ == "__main__":
    audit_coverage()
```

**把这个脚本放在 scripts/audit_coverage.py——在 Makefile 中加 coverage-audit target——CI 中每次 push 自动跑。对外函数覆盖率 < 100% -> CI 标红——不允许合并。**

**因果推断函数的特殊要求——W14D4 的四段式 docstring 不是建议——是 L3 硬标准。** 审计脚本额外检查——如果函数名含 did/psm/rdd/iv/causal——docstring 必须含"假设清单"/"不适用场景"/"面试常见追问"三个关键词中至少两个——否则警告。

---

### 📖 核心原理

**覆盖率审计不是追求 100%——是追求"被外部调用的函数 100% 覆盖"。**

- **对外函数**（被其他模块 import 的）——必须有 Type Hints + docstring——**目标 100%**
- **内部辅助函数**（`_` 开头——只在当前文件内部用）——可以有选择地省略——**目标 ≥ 50%**
- **画图函数**（`plot_*`）——返回值是 `(fig, ax)` 元组——Type Hints 必须写 `Tuple[plt.Figure, plt.Axes]`

```bash
# 快速统计——总函数数 / 有返回类型标注的 / 有 docstring 的
grep -rn "^def " src/ --include="*.py" | wc -l
grep -rn "^def.*->.*:" src/ --include="*.py" | wc -l
grep -rn '^def ' src/ --include="*.py" -A1 | grep '"""' | wc -l
```

**因果推断函数（W14-W15）还需要四段式 docstring（核心逻辑+假设清单+不适用场景+面试追问）——这是 L3 的特有要求。**

### Type Hints 覆盖率自动化统计——不只是手跑 grep——是写进 CI 的脚本

```python
#!/usr/bin/env python
"""自动统计 Type Hints 和 docstring 覆盖率——CI 中每次 push 自动跑。"""
import ast
import sys
from pathlib import Path

def audit_coverage(root_dir='src'):
    total, with_return_type, with_docstring = 0, 0, 0
    issues = []

    for py_file in Path(root_dir).rglob('*.py'):
        tree = ast.parse(py_file.read_text(encoding='utf-8'))
        for node in ast.walk(tree):
            if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef)):
                total += 1
                # 检查返回类型标注
                if node.returns:
                    with_return_type += 1
                # 检查 docstring
                if (ast.get_docstring(node)):
                    with_docstring += 1

                # 对外函数（不以 _ 开头）必须有 Type Hints + docstring
                if not node.name.startswith('_'):
                    if not node.returns:
                        issues.append(f'{py_file}:{node.lineno}: {node.name} 缺少返回类型标注')
                    if not ast.get_docstring(node):
                        issues.append(f'{py_file}:{node.lineno}: {node.name} 缺少 docstring')

    ret_pct = with_return_type / total * 100 if total else 0
    doc_pct = with_docstring / total * 100 if total else 0

    print(f'总函数数: {total}')
    print(f'Type Hints 覆盖率: {ret_pct:.0f}% ({with_return_type}/{total})')
    print(f'docstring 覆盖率: {doc_pct:.0f}% ({with_docstring}/{total})')

    if issues:
        print(f'\nL3 违规——对外函数缺少标注或文档 ({len(issues)} 个):')
        for issue in issues:
            print(f'  {issue}')

    # 对外函数覆盖率 < 100% -> CI 标红
    external_total = sum(1 for i in issues if '缺少' in i)
    if external_total > 0:
        sys.exit(1)

if __name__ == '__main__':
    audit_coverage()
```

**把这个脚本放在 `scripts/audit_coverage.py`——在 Makefile 中加 `coverage-audit` target——CI 中每次 push 自动跑。覆盖率 < 100%（对外函数）-> CI 标红——不允许合并。**

**因果推断函数的特殊要求——W14D4 的四段式 docstring 不是"建议"——是"L3 硬标准"。** 审计脚本中额外检查——如果函数名含 `did`/`psm`/`rdd`/`iv`/`causal`/`parallel_trend`/`propensity`——docstring 必须含"假设清单"/"不适用场景"/"面试常见追问"三个关键词中至少两个——否则警告。

### GUIIDE 六标准的鲜果多实战走查——每项标准的修改前 vs 修改后

### L3 终验实验的故障排查指南——每个失败步骤的根因和修复

**步骤 1 失败——git clone 超时/失败：** 根因——仓库太大（含数据文件？）或网络问题。修复——检查 .gitignore——确认 data/ 和 output/ 目录被忽略——只有 sample_data/ 被提交。如果仓库仍 > 100MB——检查是否不小心提交了 .pkl/.parquet 大文件——`git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectsize) %(rest)' | sort -nr -k2 | head -20`。

**月 3（W9-W12）：L2 -> L3——从"数据可信"到"代码自解释"**

核心突破：SQL 不再只是"查出结果"——CTE 分层注释让 SQL 自带文档——双源验证让结果自带信任。数仓不只是"建四张表"——四层 = 四种信任级别。指标不只是"一个数"——有分子/分母/时间窗口三要素——口径差异表让"为什么同一个 GMV 算出来不一样"在 10 秒内解决。归因不只是"看了一下哪里变了"——MECE 拆解 + log 分解——贡献度量化让"直觉"变成"可以复现的逻辑"。

关键残留：W12 的归因报告——你可能还停留在"描述数据"阶段——结论先行的习惯需要持续练习。W9 的 SQL 工程规范——需要在新写的每一条 SQL 上刻意应用——不是"学完就完了"。

### L3 毕业面试模拟——面试官看到你的 GitHub 仓库——会问什么

**Q1：** "你的项目有多少行代码？测试覆盖率多少？怎么统计的？"

> **A：** "我的项目约 2000 行 Python 代码——分布在 data/analysis/viz/utils 四个子目录中。测试覆盖率我关注的是'危险区域覆盖率'——即所有数据变换函数的测试覆盖率——≥ 80%。我用自己写的 audit_coverage.py 脚本自动统计——每次 CI push 自动跑——对外函数的 Type Hints 和 docstring 覆盖率必须 100%。我不追求 100% 代码行覆盖——因为画图函数和日志配置不需要单元测试——在那上面花时间是浪费。"
