## D1（周一 10/13）：指标口径三要素——为什么同一个"GMV"在不同部门算出不同的数

> 📓 今日主课：北极星指标+OSM——NSM 五标准/虚假 NSM/OSM 三层因果链

---

### 🔴 认知冲突

周一的早会。运营总监说"上月 GMV 环比涨了 5%——我们的运营策略有效果"。财务总监立刻打断："不对——环比跌了 2%——成本控制要收紧。"同一个词——"GMV"——一个说涨了 5%，一个说跌了 2%。会议室陷入争执——两位总监各持己见——因为他们各自的下属给了他们不同的数据——而这背后的根因是**同一个指标名对应了两种不同的计算口径**。

你被叫去解释。你打开两位下属的代码——两个函数都叫 `compute_gmv()`——函数名一模一样。但运营版的口径：按订单**创建时间**、含税、不含退款——GMV=523 万。财务版的口径：按支付**完成时间**、不含税、含退款——GMV=518 万。差异 5 万 = 税 ~2 万 + 退款 ~1 万 + 跨天订单的时间窗差异 ~2 万。

两位总监争论了 20 分钟。而这 20 分钟的根因是——**两个函数的口径没有在任何地方显式声明**。如果 `compute_gmv()` 的 docstring 写了"口径: 分子=已支付金额+税-退款，时间窗口=订单创建时间（运营）/支付完成时间（财务），差异=5万（税2万+退款1万+时间窗2万）"——这场争论在开始之前就能结束。

**这不是"应该写文档"——这是"代码本身就应该携带口径信息"。**

---

### 📖 核心原理

**指标口径三要素——缺一个就不叫"定义完整"：**

1. **分子**：被计数的东西是什么？含什么、不含什么？为什么含/不含？——不只是"列出过滤条件"——是**解释业务原因**
2. **分母**：被除的东西是什么？（比率类指标必须有——绝对量指标如 GMV 本身无分母）。如果分母为 0——应该返回什么？（None？0？报错？）——**必须声明**
3. **时间窗口**：数据的时间范围。用的是哪个时间戳——创建时间/支付完成时间/更新时间？为什么选这个？

**每个指标函数的 docstring 必须携口径——和代码放在一起——改代码必须改 docstring——口径永远和代码同步：**

```python
def compute_gmv(
    orders: pd.DataFrame,
    include_tax: bool = True,
    exclude_refunded: bool = True,
    use_payment_time: bool = False
) -> float:
    """计算 GMV（总成交额）。

    📐 口径:
        分子 = SUM(amount)
              条件: status = 'paid'（已支付——资金实际到账的标志）
              + 税额（若 include_tax=True——运营口径含税——因为运营关心"用户付了多少"）
              - 退款金额（若 exclude_refunded=True——运营口径不含退款——因为退款不属于成交）
        分母 = 不适用——GMV 是绝对量指标
        时间窗口 = 自然月 00:00:00-23:59:59
                  若 use_payment_time=False: 以 order_date（创建时间）为准——运营口径
                  若 use_payment_time=True:  以 payment_date（支付时间）为准——财务口径
                  为什么选创建时间？运营关注"什么时候产生了这笔交易"——和流量来源对齐
                  为什么选支付时间？财务关注"什么时候到账"——和现金流对齐

    ⚠️ 与其他口径的差异:
        | 口径   | include_tax | exclude_refunded | use_payment_time | 上月值  | 环比  |
        |--------|-------------|------------------|------------------|---------|-------|
        | 运营   | True        | True             | False            | 523 万  | +5%   |
        | 财务   | False       | False            | True             | 518 万  | -2%   |
        | 差异   | —           | —                | —                | 5 万    | —     |
        差异分解: 税 ~2万 + 退款 ~1万 + 时间窗(跨天订单) ~2万

    🔄 更新频率: 每天 8:00 AM——处理昨天全天数据
    📊 数据源: dws_order_daily (DWS 层——每日预聚合表)

    Example:
        >>> gmv_ops = compute_gmv(orders)                    # 运营口径: 523万
        >>> gmv_fin = compute_gmv(orders, include_tax=False, # 财务口径: 518万
        ...                       exclude_refunded=False, use_payment_time=True)
    """
```

**这个 docstring 的价值在于——当"为什么 GMV 不一样"的问题被问到——你不需要排查代码——你打开 docstring——指给提问者看"口径差异表"——10 秒结束问题。**

### 🏢 鲜果多案例

鲜果多 GMV 口径不一致问题发生后——你在 `compute_gmv()` 的 docstring 中加了口径差异表。下次两位总监再起争执——你打开代码——指着表——"运营口径含税不含退款——这是 523 万（+5%）。财务口径不含税含退款——这是 518 万（-2%）。差异 5 万 = 税 2 万 + 退款 1 万 + 时间窗 2 万。两位的数据都对——只是口径不同。"10 秒——结束了。不是因为你的记忆力好——是因为**代码替所有人记住了口径差异**。

## D2（周二 10/14）：MECE 拆解 + 贡献度量化——不只是"哪个变了"，是"每个因子贡献了总变化的百分之几"

> 📓 今日主课：CMOP+指标治理——枚举/剪枝/绑定责任人/生命周期

---

### 🔴 认知冲突

GMV 跌了 8%。你说"新用户 UV 下降了 12%"。运营总监追问三连："①新用户少了——贡献了总跌幅的百分之几？②老用户表现怎么样？转化率有变化吗？③哪个城市的新用户下降最明显——它占 GMV 的百分之几？"

你的"新用户少了"不是一个完整的归因——是归因的**起点**。你缺少两个东西：①一个**MECE 拆解树**——确保你考虑了所有可能的原因，而不是只看到了第一个跳出来的原因 ②**贡献度量化**——每个因子贡献了总变化的 X%——所有因子加总 = 100%。

更致命的是——你一直在"下钻"——但从来没有**量化过每个下钻因子的贡献度**。"北京新用户下降了 15%"——但如果北京只占 GMV 的 3%——那它的 15% 下降只贡献了总 GMV 变化的 0.45%。而上海的 5% 下降占 GMV 的 30%——贡献了 1.5%——上海的贡献是北京的 3.3 倍。不做贡献度量化——你的注意力会被"变化幅度大但体量小"的因子吸引——错过"变化幅度小但体量大"的真正驱动因素。

**面试场景**：面试官给你一个开放题——"GMV 跌了 10%——你怎么分析？"——你的回答从"我先做 MECE 拆解——GMV = UV × 转化率 × 客单价——然后用 log 分解量化每个因子的贡献度——"开始。面试官知道你不是在"描述数据"——你在"系统化归因"。

---

### 📖 核心原理

**归因两步法——第一步 MECE 拆解，第二步贡献度量化。**

**第一步：MECE 拆解——把"GMV -8%"拆成互斥穷尽的因子树。** ASCII art 直接画在代码注释中：

```
GMV = UV × 转化率(CVR) × 客单价(ASP)  ← 第一层：乘法拆解

UV 拆解:
  ├── 新用户 UV: 自然增长 / 付费投放 / 社交流量 / 地推
  └── 老用户 UV: 日活回流 / Push 唤醒 / 活动召回

CVR 拆解:
  ├── 设备: iOS vs Android
  ├── 城市: 一线 / 新一线 / 二线 / 其他
  ├── 品类: 水果 / 蔬菜 / 肉禽 / 乳品
  └── 时段: 早(6-10) / 中(10-14) / 晚(14-20) / 夜(20-24)

ASP 拆解:
  ├── 件单价: 涨价 / 促销拉低
  ├── 连带率: 凑单满减 / 跨品类推荐
  └── 品类结构: 高价品占比变化

每个叶子标注: [数据来源表] + [贡献度计算公式]
```

**第二步：贡献度量化——log 分解（乘法模型 Y = A × B × C）。**

公式：因子 i 的贡献度 = log(i_new / i_old) / log(Y_new / Y_old)。性质：所有因子贡献度之和 = 1.0。

```python
import numpy as np

def log_decompose(old_vals: dict, new_vals: dict) -> dict:
    """对数分解——量化乘法模型中各因子的贡献度。
    
    公式: 贡献度(i) = log(i_new/i_old) / log(Y_new/Y_old)
    性质: Σ贡献度 = 1.0（因为 log(abc) = log a + log b + log c）
    
    适用: Y = A × B × C 等乘法模型
    不适用: Y = A + B + C 等加法模型（直接用 ΔA/ΔY）
    
    Example:
        GMV: 100→92 (-8%)
        UV:  1000→880 (-12%)  → 贡献度 = log(880/1000)/log(92/100) = 1.51
        CVR: 0.05→0.048 (-4%) → 贡献度 = log(0.048/0.05)/log(92/100) = 0.49
        ASP: 2.0→2.18 (+9%)   → 贡献度 = log(2.18/2.0)/log(92/100) = -1.00
        检验: 1.51 + 0.49 + (-1.00) = 1.00 ✓
        
        解读: UV 下降贡献 151%（主因——完全解释 GMV 下降且 ASP 上升抵消了一部分）
              CVR 下降贡献 49%（次要因子）
              ASP 上升贡献 -100%（抵消因子——如果没有 ASP 上升——GMV 会跌约 16%）
    """
    log_change_y = np.log(new_vals['Y'] / old_vals['Y'])
    contributions = {}
    for factor in ['A', 'B', 'C']:
        log_change_factor = np.log(new_vals[factor] / old_vals[factor])
        contributions[factor] = log_change_factor / log_change_y
    
    # 验证贡献度之和 = 1.0
    total = sum(contributions.values())
    assert abs(total - 1.0) < 0.001, f"贡献度之和 {total:.4f} ≠ 1.0"
    return contributions
```

**为什么 log 分解的贡献度可能 > 100% 或 < 0%？** 因为某些因子可能**抵消**了其他因子的影响。上面的例子——UV 下降贡献 151%——超过 100% 是因为 ASP 上升抵消了一部分——使得总跌幅不是 12% 而是 8%。151% 的意思是"如果没有 ASP 的上升——GMV 跌幅会是 UV 单独造成的跌幅——即 12% 而不是 8%"。贡献度 > 100% 不是"算错了"——是"这个因子单独造成的跌幅比总跌幅更大——因为其他因子反向变化抵消了部分"。

### 📖 指标治理的工程化实践——不只是"定义清晰"——是"每个指标有自己的生命周期"

**指标治理的三个阶段——对应代码中的三种状态：**

**阶段 1——定义期（Draft）：** 分析需求和业务方一起定义指标——产出物 = docstring 中的口径段 + 业务方签署确认。在这个阶段——指标函数可以还没写——但 docstring 必须先写——因为 docstring 是"和业务方对齐口径的界面"——业务方不会看代码——但他们能看 docstring 中的"分子/分母/时间窗口"并用业务语言确认是否正确。

**阶段 2——使用期（Active）：** 指标函数被至少一个下游依赖——变更需要 review。在这个阶段——任何口径变更必须同步更新 docstring——且 docstring 里的"口径差异表"必须更新为"旧口径 vs 新口径"的差异分解。如果只是修 bug（如修复了一个 NULL 处理错误）——不算口径变更——但必须在 commit message 中标注"bugfix——口径不变——修复了 XX 场景的 NULL 处理"。

**阶段 3——废弃期（Deprecated）：** 当业务变化导致旧口径不再适用——不删除旧函数——在 docstring 第一行标注"DEPRECATED——替代口径见 compute_xxx_v2"——保留旧代码——确保历史分析可复现（任何人想复现 2026 年 9 月的 GMV 报告——仍然能找到当时使用的口径）。

**鲜果多指标治理的落地实例：** compute_gmv() 从 V1（运营口径——含税不含退款）演进到 V2（支持两种口径——通过参数切换）。V1 没有删除——标注了 deprecated——历史报告引用的 V1 仍然可以复现。V2 的 docstring 里有一张"V1 vs V2 差异表"——解释了为什么新增了 use_payment_time 参数和改动对下游的影响。

## D3（周三 10/15）：异动归因——五个分析视角 + 自动化扫描脚本

> 📓 今日主课：异动归因——5 步归因法/MECE/驱动树/量化

---

### 🔴 认知冲突

GMV 跌了 8%。你做了 MECE 拆解 + log 分解——UV 下降贡献 151%——主因找到了。然后呢？

你的归因停在了"UV 下降"——但 UV 为什么下降？是季节性的（每年 9 月开学季后都有回落）？是竞品动作（竞争对手 App 在 9 月上线了新功能——抢了你的用户）？是数据质量问题（埋点 SDK 新版本有 bug——少上报了一部分 UV）？还是你刚改的获客策略起了反效果？

你缺的不是"拆解深度"——是**分析视角的广度**。五个视角全部过一遍——不是"选一个"——是"五个全部扫一遍——排除不相关的——锁定最可能的"。漏掉任何一个——你的归因结论可能完全错误。比如你把"季节性回落"归因成"运营策略失效"——团队会错误调整策略——损失更大。

**问题**：怎么保证每次归因都系统地扫过五个视角——不会因为"直觉上觉得是 X"就跳过了 Y？

---

### 📖 核心原理

**异动归因五个视角——每个视角回答一个不同的问题——代码自动化检查四个——第五个需要人工介入：**

**视角 1：时间维度——"这个变化是异常的——还是正常的？"**

同比：去年同期也跌了吗？如果是→季节性——不需要干预。环比：跌了多久了？单月异常 vs 连续 3 个月趋势——前者可能是偶发事件——后者是结构性变化。

```python
def _check_time_pattern(df, metric_col, date_col):
    """时间维度检查——对比同比和环比趋势。"""
    current = df[df[date_col] == '2026-09'][metric_col].sum()
    last_month = df[df[date_col] == '2026-08'][metric_col].sum()
    last_year = df[df[date_col] == '2025-09'][metric_col].sum()
    
    mom = (current - last_month) / last_month  # 环比
    yoy = (current - last_year) / last_year     # 同比
    
    if abs(yoy) < 0.05:
        return f"同比仅变化 {yoy:.1%}——可能是季节性波动——去年同期也有类似变化"
    else:
        return f"同比变化 {yoy:.1%}——远超季节性范围——需要进一步排查"
```

**视角 2：结构维度——"谁在跌？哪个 Segment 贡献了最大的变化？"**

按城市/品类/渠道/用户类型拆——计算每个 Segment 的贡献度——排序——锁定贡献最大的 2-3 个 Segment。**注意区分"变化幅度大"和"贡献度大"——北京 -15% 体量小——贡献小。上海 -5% 体量大——贡献大。**

**视角 3：因子维度——"哪个因子驱动了总变化？"** D2 的 log_decompose——UV/CVR/ASP 各贡献多少。

**视角 4：外部维度——"有没有内部数据不能解释的因素？"** 节假日、竞品动作、天气、政策变化。代码里输出人工排查清单——不假装自动化。

**视角 5：数据质量维度——"数据本身有没有问题？"** W3D1 的验证金字塔——数据量异常？新增 NULL 列？编码变了？

**代码实现——`run_anomaly_analysis()` 自动输出五个视角的检查结果：**

```python
def run_anomaly_analysis(df, metric_col, dim_cols, date_col):
    """异动归因——五个视角自动扫描。
    
    四个视角自动化——第五个（外部）需要人工介入。
    返回结构化 Dict——每个视角含"发现"和"置信度"。
    """
    results = {
        'time': _check_time_pattern(df, metric_col, date_col),
        'structure': _check_segment_contribution(df, metric_col, dim_cols),
        'factor': log_decompose(old_vals, new_vals),  # D2
        'external': {
            'status': '需要人工排查',
            'checklist': ['节假日?', '竞品动作?', '天气/政策?', '内部运营变更?'],
            'confidence': 'low'  # 人工判断——置信度低
        },
        'data_quality': _check_data_quality(df)  # W3D1
    }
    # 汇总: 五个视角中哪些指向同一结论？哪些互相矛盾？
    return results
```

### 📖 三版本翻译的工程化实现——不只是"三个不同长度的文字"——是"三个不同信息层级的结构化输出"

**三版本的代码生成逻辑——从同一份结构化分析结果中提取不同层级：**

```python
def generate_report(analysis_result, audience):
    """统一报告生成器——根据受众提取不同信息层级。

    三个受众对应三种"信息密度"——不是"长度不同"——是"提取的信息字段不同"。
    """
    if audience == 'ceo':
        # CEO 只需要: 结论 + 1 个关键数字 + 建议 + 下一步
        return {
            'sections': ['conclusion', 'key_number', 'recommendation', 'next_step'],
            'max_words': 100,
            'format': 'bullet_points'  # 不是段落——是 3 个 bullet
        }
    elif audience == 'pm':
        # PM 需要: 结论 + 分维度拆解 + 可执行建议 + 优先级
        return {
            'sections': ['conclusion', 'dimension_breakdown', 'actionable_recs'],
            'max_words': 500,
            'format': 'structured_paragraph'  # 结构化段落
        }
    elif audience == 'engineer':
        # Engineer 需要: 全部——含口径/数据源/SQL/代码路径/复现步骤/局限
        return {
            'sections': ['all'],
            'max_words': None,  # 不限制
            'format': 'full_report'
        }
```

| 维度 | CEO 版 | PM 版 | Engineer 版 |
|------|--------|-------|------------|

| 字数 | <= 150 字 | <= 800 字 | 不限 |
| 格式 | 3 个 bullet | 结构化段落 | 完整报告 |
| 含口径说明？ | 否——CEO 默认口径已统一 | 简要提及 | 完整口径文档 |
| 含 SQL/代码？ | 否 | 否（除非 PM 要求） | 是——含路径 |
| 含局限讨论？ | 否——CEO 只需要知道"多大把握" | 简要——"主要局限是 X" | 完整——每个假设 + 敏感性分析 |
| 决策者拿到后 | 30 秒内说"同意/不同意" | 10 分钟内说"做 A 还是做 B" | 1 小时内能完整复现分析 |

## D7（周日 10/19）：W12 审计——闭卷指标口径 + 归因量化 + 模拟 Case 面试

### 📝 闭卷自测（5 题——每题都需要能闭卷回答）

**Q1**：指标口径三要素——如果你公司两个部门的 GMV 不一样——你怎么排查？你的代码里哪个部分能 10 秒给出答案？

> **A**：三要素=分子/分母/时间窗口。排查步骤——不是翻代码——是打开 `compute_gmv()` 的 docstring——看"口径差异表"——直接对比两个口径的差异值和差异分解。如果 docstring 里没有这张表——补上——这是"知识固化"。偏差：说"排查代码逻辑"——代码逻辑一样——参数不一样——排查参数。

**Q2**：log 分解公式——为什么贡献度可能 > 100%？举一个鲜果多的具体例子。什么时候用加法分解？

> **A**：公式=log(i_new/i_old)/log(Y_new/Y_old)。贡献度>100%=某个因子的单独影响大于总影响——因为其他因子反向变化抵消了部分。鲜果多例子：UV -12% 贡献 151%——因为 ASP +9% 贡献 -100%——抵消了 UV 下降的部分影响——总跌幅不是 12% 而是 8%。加法分解用于 Y=A+B+C 模型——直接用 ΔA/ΔY。

**Q3**：五个归因视角是哪五个？为什么"外部维度"不能自动化？面试中最可能被追问的是哪个视角？

> **A**：时间/结构/因子/外部/数据质量。外部维度=节假日/竞品/天气/政策——不在内部数据库——需要人工排查。最可能被追问——"你怎么排除数据质量不是根因？"——回答：先跑 W3D1 验证金字塔——确认数据量/格式/编码没有异常——然后才开始归因。数据质量问题不先排除——所有后续归因都是无效的。

**Q4**："结论先行"和传统"数据→分析→结论"的本质区别？如果报告太长——运营总监只看前 3 段——这 3 段应该包含什么？

> **A**：传统结构=以写作者为中心（我的推导过程）。结论先行=以读者为中心（读者的决策时间）。前 3 段：①核心结论（GMV -8%——UV 主因——北京最明显）②关键数字（UV -12% 贡献 151%——ASP +9% 部分抵消）③建议方向（北京专项拉新——下周汇报进展）。偏差：把"结论"写成"GMV 环比 -8%"——这是数据描述不是结论——结论需要含"为什么"和"怎么办"。

**Q5**：三版本翻译——CEO 版和 PM 版的本质区别不是"长短"——是什么？

> **A**：CEO 版=决策导向（"我该做什么决定"）——结论+关键数字+建议+下一步。PM 版=执行导向（"我该怎么执行"）——分维度拆解+可执行建议+优先级。CEO 不需要知道"北京新用户 UV 降 20%"——他需要知道"北京市场需要加大投放"。PM 需要知道"北京新用户 UV 降 20%——竞品新功能——建议北京专项拉新"。



**Q6**（OSM 框架）：什么是 OSM？北极星指标（NSM）的五个选择标准是什么？鲜果多的 NSM 应该是什么？为什么不是 GMV？

> **A**：OSM = Objective（业务目标）+ Strategy（达成策略）+ Measurement（衡量指标）。不是"选一个指标"——是"从目标倒推策略——从策略倒推指标"——三层因果链。
>
> NSM 五标准：(1) 反映用户从产品中获得的核心价值——不是"公司赚了多少"——是"用户得到了什么价值" (2) 是 leading indicator——先于收入变化 (3) 可被产品/运营团队直接影响 (4) 简单到公司每个人都能记住和复述 (5) 随时间可追踪——可以画趋势图。
>
> 鲜果多的 NSM 应该是"周活跃购买用户数"而不是"GMV"。因为：(1) 用户核心价值是"方便地买到新鲜食材"——活跃购买 = 用户在定期获得这个价值 (2) 活跃用户下降会先于 GMV 下降——是 leading indicator (3) 团队可以影响（通过改善配送/品质/推荐）(4) 简单——"每周有多少人买菜"——每个人都能理解 (5) 可追踪——每周一个数字——画 52 周趋势图。GMV 是 lagging indicator——GMV 跌了才反应——但活跃用户在 4 周前就已经开始跌了——NSM 应该在 4 周前就发出预警。

**Q7**（指标生命周期管理）：一个指标从"被定义"到"被废弃"会经历哪些阶段？鲜果多的"GMV"现在处于哪个阶段？

> **A**：三个阶段——(1) 定义期（和业务方共同签署口径文档——含分子/分母/时间窗口/business reason/更新频率/数据源）(2) 使用期（每次使用前确认口径——docstring 是唯一真相来源——不允许口头口径）(3) 废弃/替换期（当业务变化导致旧口径不再适用——不是直接改——是创建新口径 V2——旧口径保留——标注 deprecated——确保历史分析可复现）。鲜果多 GMV 目前处于"使用期但多口径共存"——运营口径和财务口径都在使用——需要显式管理——不是消灭一个——是让两个口径都在 docstring 中透明共存。

**Q8**（面试 Case 模拟）：面试官给你 Data——"电商 GMV 月环比 -10%——请归因"。你不能开始写 SQL——你需要先讲你的分析框架。60 秒回答。

> **A**："我会分五步。第一步——确认 GMV 的口径——分子含不含退款、时间用创建时间还是支付时间——口径不一样归因结论可能完全相反。第二步——MECE 拆解——GMV = UV x CVR x ASP——用 log 分解量化每个因子的贡献度。第三步——五个视角扫描——时间维度排除季节性、结构维度下钻到城市x品类x渠道——找贡献度最大的 2-3 个 Segment、数据质量维度排除数据问题。第四步——外部因素排查——竞品动作、节假日、内部运营变更——和业务方确认。第五步——给结论——不是"UV 下降了"——是"UV 下降贡献了 X%——主要来自 Y Segment——原因是 Z——建议 A"。整个分析过程约 2 小时——最终输出是三版本——CEO 3 句话、PM 1 段、Engineer 全篇。"
