# 模块 5：FastAPI——把分析结果变成一个 API

## 🔴 认知冲突

你做了一份"各城市 GMV 趋势"分析。运营总监在 Slack 上问"今天的 GMV 多少？能不能给个链接让我自己查？"你每次跑脚本发 CSV——你是人形数据接口。

**问题**：你的分析结果应该在浏览器里能直接访问——不是下载 CSV。FastAPI 让 Python 函数变成 URL。

---

## 📖 核心原理

**FastAPI = 给 Python 函数绑定一个 URL。同事不需要知道 Python——打开浏览器就有数据。**

```python
# api.py
from fastapi import FastAPI, Query
from datetime import date
import pandas as pd

app = FastAPI(title="鲜果多数据 API", version="1.0")

@app.get("/api/gmv")
def get_gmv(city: str = Query(None), start_date: date = Query(None)):
    """查询 GMV——可按城市和日期过滤。"""
    df = pd.read_parquet('output/daily_kpi.parquet')

    if city:
        df = df[df['city'] == city]
    if start_date:
        df = df[df['date'] >= start_date]

    return {
        "gmv": float(df['gmv'].sum()),
        "n_orders": int(df['orders'].sum()),
        "city": city or "全部",
        "start_date": str(start_date) if start_date else None
    }

# 启动:
# pip install fastapi uvicorn
# uvicorn api:app --reload
```

然后任何人打开浏览器访问：
- `http://localhost:8000/api/gmv` → 今天全部城市的 GMV
- `http://localhost:8000/api/gmv?city=北京&start_date=2026-09-01` → 北京 9/1 起的 GMV
- `http://localhost:8000/docs` → **自动生成的交互式 API 文档**（Swagger）——在网页上直接测试

**核心价值——Swagger 文档：** 你的 `Query()` 参数自动变成网页表单。同事在 `http://localhost:8000/docs` 里填参数、点"Execute"——直接看到结果。你不需要写任何文档——FastAPI 自动生成。

### 📖 四个模块的面试追问与标准回答

**FastAPI 追问：** "FastAPI 和 Flask 有什么区别——为什么选 FastAPI？"
> A: "三个原因。(1) 自动生成的 Swagger 文档——Flask 需要额外插件——FastAPI 自带。(2) 类型提示——FastAPI 用 Python 的类型 hint 自动做参数验证——age: int = Query(ge=0)——自动拒绝负数年龄——Flask 需要手动验证。(3) 异步支持——FastAPI 原生 async——高并发场景下性能更好。对于数据分析师——前两点最实用——我不需要写额外的文档和验证代码。"

**S3 追问：** "S3 和 HDFS 有什么区别——为什么数据分析项目用 S3？"
> A: "HDFS 是为 Hadoop 生态设计的——需要 NameNode+DataNode——需要专门的集群。S3 是云服务——不需要管理基础设施——按存储量+请求次数付费。对于数据分析项目——数据量在 TB 级以下——S3 的运维成本远低于 HDFS。但如果你的数据量在 PB 级——且主要在 Hive/Spark 上做计算——HDFS 可能更合适（数据本地性——计算和存储在同一节点——减少网络 IO）。"

**DVC 追问：** "DVC 和 Git LFS 有什么区别？"
> A: "Git LFS 是 Git 的扩展——把大文件存在 Git 服务器上（如 GitHub LFS 存储）。DVC 把数据存在任何地方（S3/GCS/本地磁盘/SSH）——Git 里只存元数据指针。核心区别——Git LFS 和 Git 绑定（换 Git 服务器=LFS 数据也要迁移）——DVC 的数据存储可以独立于 Git——更灵活。且 DVC 有 Pipeline 功能——Git LFS 没有。"

**Sphinx 追问：** "文档写了但没人看——怎么办？"
> A: "文档没人看通常有三个原因——(1) 找不到——解决方法——GitHub Pages 部署——一个公开 URL——书签即可。(2) 过期了——解决方法——Sphinx doctest 扩展——自动跑 docstring 中的 Example 代码——CI 中跑——文档和代码不一致就告警。(3) 太长——解决方法——Sphinx 自动生成索引和搜索——不是让人从头读到尾——是按需搜索——'clean_amounts 怎么用？'——搜索框输入——直接定位。"

### 📖 FastAPI 进阶——依赖注入 + 缓存 + 测试

**依赖注入——API endpoint 的公共逻辑（如数据库连接、用户认证）不重复写在每个函数里——用 FastAPI 的 Depends 自动注入：**

```python
from fastapi import Depends

# 依赖——获取数据库引擎（和 SQLAlchemy 集成）
def get_engine():
    engine = create_engine(os.getenv('DATABASE_URL'), pool_size=3)
    try:
        yield engine
    finally:
        engine.dispose()

@app.get("/api/gmv")
def get_gmv(city: str = Query(None), engine=Depends(get_engine)):
    """city 参数从 URL 来——engine 参数由 FastAPI 自动注入。"""
    df = pd.read_sql("SELECT * FROM orders", engine)
    # ... 过滤 + 返回

# 缓存——昂贵查询的结果缓存 5 分钟——减少数据库负载
from functools import lru_cache
import time

@lru_cache(maxsize=32)
def _cached_query(query_key: str, _timestamp: int):
    """实际查询——被缓存包装。_timestamp 参数用于手动刷新缓存。"""
    return pd.read_sql(query_key, engine)

def get_gmv_cached():
    """带缓存的 GMV 查询——每 5 分钟最多查一次数据库。"""
    return _cached_query('SELECT SUM(amount) FROM orders', int(time.time() / 300))
```

# 模块 6：S3——当数据不在本地磁盘上

## 🔴 认知冲突

W1-W28 你所有的数据都在本地 `data/` 目录下。但真实的公司——数据在 S3（AWS）或 OSS（阿里云）上。文件路径不是 `data/orders.csv`——是 `s3://xianguoduo-data/raw/orders/2026/09/01/orders.csv`。

---

## 📖 核心原理

**S3 = "云上的文件系统"——没有文件夹（只有扁平的对象 key），但通过 `/` 模拟目录结构。**

```python
import boto3
import pandas as pd
from io import StringIO

# 初始化客户端
s3 = boto3.client(
    's3',
    aws_access_key_id='YOUR_KEY',       # 或从环境变量读取
    aws_secret_access_key='YOUR_SECRET', # 不要硬编码——用 os.getenv()
    region_name='us-east-1'
)

# 读 S3 上的 CSV
obj = s3.get_object(Bucket='xianguoduo-data', Key='raw/orders/2026-09-01.csv')
df = pd.read_csv(obj['Body'])

# 写 Parquet 到 S3
from io import BytesIO
buffer = BytesIO()
df.to_parquet(buffer, index=False)
s3.put_object(Bucket='xianguoduo-data', Key='dws/daily_kpi.parquet', Body=buffer.getvalue())

# 列出 S3 上某目录下的所有文件
response = s3.list_objects_v2(Bucket='xianguoduo-data', Prefix='raw/orders/2026/09/')
for obj in response.get('Contents', []):
    print(obj['Key'], obj['Size'])
```

**路径抽象——给你现有的 pathlib 代码加 S3 支持：**

```python
def smart_read(path_or_s3_uri):
    """统一读取本地路径或 S3 URI。"""
    if str(path_or_s3_uri).startswith('s3://'):
        bucket, key = parse_s3_uri(path_or_s3_uri)
        obj = s3.get_object(Bucket=bucket, Key=key)
        return pd.read_csv(obj['Body'])
    else:
        return pd.read_csv(path_or_s3_uri)
```

这样你的代码不需要"改路径处理逻辑"——`smart_read('data/orders.csv')` 和 `smart_read('s3://bucket/orders.csv')` 都能用。

### 📖 S3 进阶——预签名 URL + 生命周期策略 + 分区数据管理

**预签名 URL——生成临时下载链接——不需要把文件设为公开——也不需要给对方 AWS 密钥：**

```python
# 生成一个 1 小时内有效的临时下载链接
url = s3.generate_presigned_url(
    'get_object',
    Params={'Bucket': 'xianguoduo-data', 'Key': 'reports/daily_2026-09-01.xlsx'},
    ExpiresIn=3600  # 秒——1 小时后链接失效
)
# 把这个 url 发给运营总监——她直接在浏览器里下载——不需要 AWS 账号
```

**生命周期策略——自动归档或删除旧数据——降低存储成本：**

```python
# S3 生命周期规则——30 天后自动转为更便宜的存储层——90 天后删除
s3.put_bucket_lifecycle_configuration(
    Bucket='xianguoduo-data',
    LifecycleConfiguration={
        'Rules': [{
            'Id': 'archive-old-logs',
            'Status': 'Enabled',
            'Filter': {'Prefix': 'raw/logs/'},
            'Transitions': [{'Days': 30, 'StorageClass': 'STANDARD_IA'}],  # 30天->低频存储
            'Expiration': {'Days': 90}  # 90天->自动删除
        }]
    }
)
```

# 模块 7：DVC——数据集的 Git

## 📖 核心原理

**DVC = `git` 的思维 + 数据文件的实际存储分离。**

```
# 安装
pip install dvc

# 初始化（在已有的 Git 项目中）
dvc init

# 跟踪数据文件——类似 git add
dvc add data/orders.csv

# git 里存的不再是数据文件本身——而是 .dvc 元数据文件（几 KB）
git add data/orders.csv.dvc .dvc/
git commit -m "add orders.csv v1"

# 以后恢复这个版本的数据：
git checkout <某个commit>   # 先恢复 .dvc 元数据
dvc checkout                # 根据元数据恢复数据文件
```

**工作流**：

```

2. dvc add data/orders.csv   → 数据存到 .dvc/cache（或远程 S3）

4. 两周后你老板问"9月1号的数据和9月15号的有什么不同？"
5. git checkout <两周前的commit> && dvc checkout → 数据回退到两周前的版本
6. pd.read_csv('data/orders.csv') — 你看到的是两周前的数据
```

### 📖 DVC 进阶——Pipeline + 远程存储 + 实验追踪

**DVC Pipeline——定义数据处理的 DAG——自动追踪依赖——只重跑需要重跑的步骤：**

```bash
# dvc.yaml——定义数据处理 Pipeline 的 DAG 结构
# 类似 dbt 的 ref()——DVC 自动推导执行顺序——只重跑"上游变了"的步骤

# 步骤 1: 从 S3 拉取原始数据
dvc stage add -n pull_raw   -d s3://bucket/raw/orders.csv   -o data/raw/orders.csv   aws s3 cp s3://bucket/raw/orders.csv data/raw/orders.csv

# 步骤 2: 清洗——依赖步骤 1 的输出
dvc stage add -n clean   -d data/raw/orders.csv   -d src/data/clean.py   -o data/clean/orders_clean.parquet   python src/data/clean.py

# 步骤 3: 分析——依赖步骤 2 的输出
dvc stage add -n analyze   -d data/clean/orders_clean.parquet   -d src/analysis/metrics.py   -o output/gmv_report.md   python src/analysis/metrics.py

# 一键重跑——DVC 自动判断哪些步骤需要重跑（数据或代码变了）
dvc repro
# 输出: Stage 'pull_raw' didn't change——skipping
#       Stage 'clean' is changed——running
#       Stage 'analyze' is changed——running
```

**远程存储——数据不存 Git（太大）——也不存本地磁盘（不能共享）——存在 S3/DVC 远程：**

```bash
# 配置远程存储——数据自动同步到 S3
dvc remote add -d myremote s3://xianguoduo-dvc-cache
dvc push  # 推送——类似 git push——但推的是数据文件——不是你写的代码
dvc pull  # 拉取——类似 git pull——但拉的是数据文件
```

**实验追踪——DVC 和 Git 一起——完整记录"哪个代码版本 + 哪个数据版本 = 哪个结果"：**

```bash
# 每次实验后:
git tag exp-2026-09-01  # 标记代码版本
dvc push                 # 标记数据版本
# 以后复现: git checkout exp-2026-09-01 && dvc checkout && dvc repro
```

# 模块 8：Sphinx——从 docstring 自动生成文档

## 🔴 认知冲突

## 📖 核心原理

**Sphinx = 扫描你的 `.py` 文件 → 读取 docstring → 自动生成 HTML 文档网站。**

```bash
pip install sphinx

# 初始化文档目录
mkdir docs && cd docs
sphinx-quickstart --sep -p "鲜果多" -a "你的名字" -r "1.0" -l "zh_CN"

# 编辑 docs/source/conf.py——加 Sphinx 扩展
# extensions = ['sphinx.ext.autodoc', 'sphinx.ext.napoleon', 'sphinx.ext.viewcode']
# napoleon: 支持 Google Style docstring（你从 W2D5 开始写的格式）

# 在 docs/source/index.rst 中引用你的模块：
# .. automodule:: src.data.clean
#    :members:

# 生成 HTML
cd docs
make html  # 或 sphinx-build -b html source/ build/
```

生成的 HTML 在 `docs/build/html/index.html`——用浏览器打开——看到你所有模块、所有函数的文档——都是自动从 docstring 提取的。你不需要再手写一份文档。

### 📖 Sphinx 进阶——主题定制 + GitHub Pages 自动部署 + 文档即测试

**Sphinx 主题——不只是默认的 alabaster——用 Read the Docs 主题——和主流 Python 项目保持一致：**

```bash

# html_theme = 'sphinx_rtd_theme'
```

**GitHub Actions 自动部署——每次 push 到 main——自动构建文档——自动部署到 GitHub Pages：**

```yaml
# .github/workflows/docs.yml
name: Build and Deploy Docs
on:
  push:
    branches: [main]
jobs:
  docs:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install sphinx sphinx-rtd-theme
      - run: cd docs && make html
      - uses: peaceiris/actions-gh-pages@v3
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: docs/build/html
```

配置完成后——每次 push 到 main——GitHub Actions 自动构建文档——自动发布到 `https://yourname.github.io/xianguoduo/`——任何人都能访问。面试官点开链接——看到你项目完整的 API 文档——这比简历上写"有文档编写能力"有力 100 倍。

### Sphinx 在团队协作中的价值——不只是"生成文档网站"——是"让文档成为 CI 的一环"

**Sphinx 的四个 CI 集成——确保文档永远和代码同步——不是靠自觉——靠 CI 强制：**

**1. 构建检查——每次 push——CI 中 make html——如果有 RST 语法错误——CI 标红——不允许合并：**

```yaml

```

**鲜果多项目配置了这四项后——每次 push——CI 自动检查——"文档能不能构建 + 链接有没有断 + 示例代码能不能跑 + 有没有拼写错误"——四项全过才允许合并。面试官听到这四个检查——知道你不是"会装 Sphinx"——你理解文档工程化——把文档当成代码的一部分来管理。**
