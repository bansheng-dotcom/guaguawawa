## D1（周一 11/17）：测试金字塔——数据分析师的三层测试策略

> 📓 今日主课：ML 全景图——三大范式/三大类算法

---

### 🔴 认知冲突

你写过一个 `clean_amounts()` 函数。你"手动测试"过——跑了一次——`print` 了几个中间值——看起来对——然后你把它忘了。

三个月后同事改了函数——把 `amount >= 0` 改成了 `amount > 0`——因为"金额为 0 的订单不可能存在"。GMV 少了 3%。没有测试能拦住这次改动。docstring 写了"假设 amount 无负数"——但同事没读。你也没有 review 他的改动——因为那天项目赶 deadline——你只是扫了一眼——"看起来合理"。

**测试的价值不在"你写代码的时候"——在"三个月后别人改你的代码的时候"。** 那时候你不会在旁边解释"为什么要用 `>=` 而不是 `>`"。测试会替你解释——测试会替你拦住。

但"所有函数都写测试"是不现实的——你每天只有 30 分钟做工程化。你怎么决定哪些函数值得测、用什么方式测？

---

### 📖 核心原理

**测试金字塔——三层，越往下越多、越快、越稳定。数据分析师版——和纯软件工程师版不同——你的"集成测试"对象是数据管道——不是 API 接口。**

```
        ┌──────────────┐
        │   E2E 测试    │ ← 极少（1-3个）: python main.py 全流程跑通
        ├──────────────┤
        │   集成测试    │ ← 少量（3-8个）: 数据管道——load→validate→clean 链路
        ├──────────────┤
        │   单元测试    │ ← 大量（10-30个）: 单个函数——输入→输出的纯逻辑验证
        └──────────────┘
```

**数据分析师的三层测试策略——你的版本：**

| 层 | 测什么 | 多少个 | 跑一次多久 | 你的项目中——具体是什么 |
|---|--------|-------|----------|---------------------|
| **单元测试** | 单个清洗/验证/计算函数——纯输入→输出 | 10-30 | < 1 秒 | `clean_amounts(df)→df` / `compute_gmv(df)→float` |
| **集成测试** | 数据管道链路——load→validate→clean→analyze | 3-5 | < 5 秒 | 加载样例数据→验证→清洗→确认输出格式正确 |
| **E2E 测试** | `python main.py` 全流程 | 1-2 | < 30 秒 | CI 里的冒烟测试——确保不会 push 一个跑不通的版本 |

**判断什么函数值得写单元测试——三个问题：**

1. **这个函数有明确的"输入→输出"映射吗？** 有→值得测。`clean_amounts(df_with_negative)` → `df_without_negative`
2. **这个函数有边界条件吗？** 有→必须测。空 DataFrame 输入？全 NaN 的列？单行数据？全重复行？这些边界条件下函数的行为——docstring 里写了吗？测试能验证吗？
3. **这个函数的 docstring 里写了"假设"吗？** 写了→测试就是在验证"这些假设被违反时——函数的行为是否符合 docstring 的承诺"。如 docstring 写"Raises ValueError 如果 amount 列不存在"→测试验证——传入不含 amount 列的 DataFrame——确实抛出了 ValueError

**判断什么函数不需要单元测试——同样重要——节省你的时间：**

- **画图函数**（`plot_trend()`）——输出是图片——不是数据——无法用 assert 验证"图片看起来对不对"。可以用 E2E 测试验证"没有报错"——但不需要单元测试
- **日志配置函数**（`setup_logger()`）——副作用是全局配置——不是输入→输出。不需要单元测试
- **`main()` 入口函数**——它只是调其他函数。用 E2E 测试覆盖——不需要单元测试

---

**❓ 常见偏差**

| 偏差 | 原因 | 🔧 |
|------|------|-----|
| "测试函数名太模糊——`test_clean`——不知道测什么" | 函数名应该描述"什么场景下——预期什么行为" | `test_removes_negative_amounts`——读函数名就知道测什么 |
| "只测了正常场景——没有测异常场景" | 正常场景是你"设计"的——异常场景是别人"误用"的。测试更应该覆盖后者 | 每个函数至少含 1 个异常场景 test——传错类型/缺列/空数据 |
| "assert 消息是空的——失败了不知道原因" | `assert len(result) == 3`——失败了只显示"assert 3 == 5"——不知道哪个 DataFrame | 加消息——`assert len(result) == 3, f"应保留 3 行，实际 {len(result)}"` |


## D2（周二 11/18）：pytest fixture——不让测试数据在 8 个 test 里重复 8 遍

> 📓 今日主课：有监督学习——分类 vs 回归/逻辑回归/决策树

---

### 🔴 认知冲突

你昨天写了 3 个 test——每个 test 里都有 `pd.DataFrame({'amount': [...], 'city': [...], ...})`。今天你又写了 5 个 test——又重复了同样的数据构造代码。想改某个列的默认值——你得改 8 个地方。测试代码和业务代码一样需要 DRY（Don't Repeat Yourself）。

这不是"多敲几行代码"的问题——是**测试数据的"标准形态"散布在各处——没有人知道"正确的测试数据长什么样"**。新同事加了一个 test——自己构造了一份测试数据——和你的 fixture 不一致——可能"在他的数据上通过——在你的数据上失败"。测试数据不统一——测试结论不可信。

**pytest fixture = 把"测试数据的标准形态"定义在一处——所有 test 引用它。改一处——所有 test 自动更新。**

---

### 📖 核心原理

**fixture = "测试数据工厂"。定义在 `tests/conftest.py` 中——所有 test 文件自动发现——不需要 import。**

```python
# tests/conftest.py
import pytest
import pandas as pd
import numpy as np


@pytest.fixture
def sample_orders():
    """标准订单测试数据集——含正常值、负值、零值、空值——覆盖所有边界。"""
    return pd.DataFrame({
        'order_id': [1, 2, 3, 4, 5, 6],
        'user_id': ['u1', 'u2', 'u3', 'u4', 'u5', 'u6'],
        'amount': [-10.0, 0.0, 50.0, 100.0, None, 200.0],
        'city': ['北京', '上海', None, '北京', '上海', '深圳'],
        'order_date': pd.to_datetime([
            '2026-09-01', '2026-09-02', None,
            '2026-09-03', '2026-09-04', '2026-09-05'
        ]),
        'status': ['paid', 'paid', 'cancelled', 'paid', 'refunded', 'paid']
    })


@pytest.fixture
def sample_orders_clean():
    """标准清洗后数据集——不含负值、不含空值——用于测试分析函数。"""
    return pd.DataFrame({
        'order_id': [3, 4, 6],
        'user_id': ['u3', 'u4', 'u6'],
        'amount': [50.0, 100.0, 200.0],
        'city': ['上海', '北京', '深圳'],
        'order_date': pd.to_datetime(['2026-09-03', '2026-09-03', '2026-09-05']),
        'status': ['paid', 'paid', 'paid']
    })
```

**使用 fixture——test 函数声明需要哪个 fixture——pytest 自动注入：**

```python
# tests/test_clean.py
def test_removes_negative_amounts(sample_orders):  # ← fixture 名字 = 参数名字
    result = clean_amounts(sample_orders)
    assert (result['amount'] >= 0).all()

def test_fills_missing_city(sample_orders):
    result = clean_city(sample_orders)
    assert result['city'].isna().sum() == 0, "清洗后 city 不应有缺失"

# tests/test_analyze.py
def test_compute_gmv(sample_orders_clean):  # ← 用清洗后的 fixture
    gmv = compute_gmv(sample_orders_clean)
    assert gmv == 350.0, f"GMV 应为 350，实际 {gmv}"
```

**fixture 的设计原则：**
1. **一套"脏"数据**（`sample_orders`）——含负值/零值/空值——给清洗和验证函数用
2. **一套"干净"数据**（`sample_orders_clean`）——不含异常值——给分析函数用。分析函数不应该再测"脏数据"——那已经由清洗函数测过了
3. **名称自描述**——`sample_orders` 不是 `df1`——看到名字就知道"这是订单样本数据"

---

### 🏢 鲜果多案例

鲜果多项目有 15 个 test——分布在 4 个 test 文件中。以前——每个 test 自己构造数据——"脏数据"的版本不一样——有的含 None——有的不含——有的含 3 行——有的含 10 行。你统一了两套 fixture（`sample_orders`/`sample_orders_clean`）——所有 test 引用同一套数据。新同事加 test 时——不需要"想测试数据长什么样"——直接用 fixture——他会自动继承你的"边界覆盖"（负值/零值/空值）——不会漏掉边界。

## D3（周三 11/19）：数据分析的 5 种核心测试模式——每种模式防一类 bug

> 📓 今日主课：无监督学习——K-Means/DBSCAN/降维

---

### 🔴 认知冲突

D1-D2 你学会了写单元测试——但"该测什么"还是凭直觉。直觉会漏——你只会想到"正常输入应该得到正常输出"——这是最基础的——也是最不容易出 bug 的。真正的 bug 藏在**边界条件**（空数据/全 NaN/单行）、**接口变更**（函数改了返回格式但调用方不知道）、**幂等性**（跑两次结果不一样）。

你需要的不是"更多测试"——是**系统的测试模式**——每种模式针对一类常见的 bug——每种模式有一个固定的代码模板——你只需要替换函数名和 fixture 名。

---

### 📖 核心原理

**数据分析代码的 5 种核心测试模式——每种模式解决一类真实 bug：**

### 模式 1：输入验证测试——"传了不该传的东西——函数应该炸"

**防什么 bug**：调用方误传了错误的 DataFrame（缺了必需列/列名拼错/类型不对）——函数没有检查——静默执行——在更深的地方才报错——traceback 离根因很远。

```python
def test_raises_on_missing_required_column(sample_orders):
    """传入缺少必需列的 DataFrame——应抛出明确异常。"""
    df_missing = sample_orders.drop(columns=['amount'])
    with pytest.raises(ValueError, match='amount'):
        clean_amounts(df_missing)

def test_raises_on_wrong_dtype():
    """传入类型错误的输入——应抛出明确异常。"""
    with pytest.raises(TypeError):
        compute_gmv("not_a_dataframe")
```

### 模式 2：边界条件测试——"极端数据——函数不能崩"

**防什么 bug**：数据在某天异常（全是空值/只有一行/全是重复行）——函数崩溃或产生错误输出——但没有报错——下游分析基于错误数据做出错误决策。

```python
def test_handles_empty_dataframe():
    result = clean_amounts(pd.DataFrame({'amount': []}))
    assert len(result) == 0

def test_handles_single_row(sample_orders):
    single = sample_orders.iloc[:1]
    result = clean_amounts(single)
    assert len(result) <= 1  # 单行不应崩溃

def test_handles_all_nan_column():
    df = pd.DataFrame({'amount': [None, None, None]})
    result = clean_amounts(df)
    # 取决于函数设计: 可能是清理后全空→返回空 DataFrame——也可能 raise
    assert isinstance(result, pd.DataFrame)
```

### 模式 3：输出结构测试——"输出 DataFrame 的列名、类型、行数——和 docstring 承诺的一致"

**防什么 bug**：函数改了返回的列名/类型/顺序——但调用方不知道——调用方按旧列名取数据——KeyError。

```python
def test_output_structure(sample_orders):
    result = clean_amounts(sample_orders)
    assert 'amount' in result.columns
    assert result['amount'].dtype in [float, np.float64]
    assert len(result) <= len(sample_orders)  # 清洗可能减少行——不会增加
```

### 模式 4：幂等性测试——"跑一次和跑两次——结果完全一样"

**防什么 bug**：函数内部使用了随机数（没设种子）/ 时间戳（`datetime.now()`）/ 全局状态——每次跑结果不同。这在分析场景中极其危险——"上周的报表和这周的报表——数据没变——但结论变了"。

```python
def test_idempotent(sample_orders):
    first_run = clean_amounts(sample_orders)
    second_run = clean_amounts(first_run)  # 清洗过的数据再清洗——结果应该不变
    pd.testing.assert_frame_equal(first_run, second_run)
```

### 模式 5：回归测试——"输出和上次保存的快照一致"

**防什么 bug**：你"优化"了函数——觉得行为应该不变——但某个角落 case 被改变了。回归测试告诉你——"输出和改之前不一样了——这是故意的还是意外的？"

```python
def test_output_matches_snapshot(sample_orders, tmp_path):
    result = clean_amounts(sample_orders)
    snapshot_path = tmp_path / 'clean_amounts_snapshot.csv'
    # 第一次跑: result.to_csv(snapshot_path, index=False)——然后 git commit
    # 以后跑: 加载快照——对比——assert_frame_equal
    expected = pd.read_csv(snapshot_path)
    pd.testing.assert_frame_equal(result, expected)
```

---

### 🏢 鲜果多案例

鲜果多 `clean_amounts()` 的幂等性测试——第一次跑了之后发现幂等性不成立——因为函数内部使用了 `np.random.choice` 来填充缺失值——没有设种子。每次跑——缺失值被填成不同的随机数。修复——用 `np.random.default_rng(42)` 固定种子——幂等性测试通过。**如果没有人写幂等性测试——"每次结果不一样"这个 bug 永远不会被发现——因为单次跑"看起来都对"——但两次跑之间的差异会慢慢累积到"结论反转"。**

2. 确认 5 种模式全部覆盖——每种至少 1 个 test。

4. `git commit -m "add 5 test pattern coverage across core data functions" && git push`

### 测试优先级的决策框架——不是"所有函数都测"——是"按风险排序"

**数据分析项目中——不是所有 bug 的代价相同。按风险排序——先测高风险函数：**

| 风险等级 | 函数特征 | 如果出 bug——影响 | 测试优先级 | 鲜果多例子 |
|---------|---------|----------------|----------|----------|
| 高 | 数据变换——输出被下游 3+ 个函数依赖 | 下游分析全错——GMV 报表错误——决策层基于错误数据决策 | 必须测——5 种模式全测 | clean_amounts(), compute_gmv() |
| 中 | 数据变换——输出只被 1-2 个函数依赖 | 局部错误——可能被发现——但排查成本高 | 应该测——至少正常+边界两种模式 | validate_input(), filter_by_city() |
| 低 | 数据变换——只在 main() 中使用 | 错误容易发现——因为输出直接给用户——用户会反馈 | 可以测——至少 1 个正常场景 test | generate_report() |
| 免测 | 画图/日志/入口函数——侧输出——不是数据 | 不影响下游数据——只影响视觉/日志 | 不需要单元测试——用 E2E 验证"不报错" | plot_trend(), setup_logger() |

### 🔴 认知冲突

### 📖 核心原理

**危险区域 = 包含数据变换逻辑的函数。判断标准：输入是数据（DataFrame/number/Series），输出是数据——中间做了变换。** 这类函数如果出错——下游分析结果全错——且 traceback 不指回根因。

| 函数 | 输入→输出 | 危险区域？ | 需要测试？ |
|------|----------|----------|----------|
| `clean_amounts(df)→df` | 数据→数据 | ✅ 是 | ✅ 必须测 |

| `setup_logger()` | 无→副作用 | ❌ 不是 | ❌ 不需要 |
| `main()` | 无→调用链 | ❌ 不是 | ❌ 用 E2E 测 |

**危险区域覆盖率 = 危险区域函数中有测试的比例。目标 ≥ 80%。**

### 测试覆盖率的三个层次——不只是"数字"——是"这个数字意味着什么"

**层次 1——代码行覆盖率（最弱）：** `pytest --cov=src tests/` 输出 45%。这个数字告诉你"哪些行被执行过"——但不告诉你"执行过的行有没有被 assert 验证"。你可以写一个没有 assert 的 test——覆盖率 100%——但测试质量为零。

**层次 2——危险区域覆盖率（D4 标准）：** 只统计"数据变换函数"中有测试的比例。目标 >= 80%。这个数字比代码行覆盖率更有意义——因为它针对的是"出错了会污染下游数据"的函数。

**层次 3——场景覆盖率（最强——但最贵）：** 每个危险区域函数——覆盖了所有"可能导致错误"的场景吗？正常/异常/边界——三种场景全有 test？这个层次需要人工判断——自动化工具帮不了——但你可以在函数 docstring 中加"测试清单"——作为未来的自己和同事的指引。

```python

    [x] 异常: 缺少 amount 列 -> raise ValueError (test_raises_on_missing_amount_column)
    [x] 边界: 空 DataFrame -> 返回空 DataFrame (test_handles_empty_dataframe)

    """
```

**面试时——面试官问"你怎么评估测试质量"——你打开 clean_amounts 的 docstring——指着"测试清单"——说"我对每个危险区域函数维护了测试清单——标注了正常/异常/边界场景的覆盖情况——这是场景覆盖率——比代码行覆盖率更有意义。"**

### 集成测试的三种模式——不只是"测链路"——每种模式防一类接口 bug

**模式 2——参数传递集成：** 验证"分析参数的变动能正确传递到下游"。比如——用户通过 CLI 指定 `--city=北京`——这个参数是否正确传递到了 load_orders(city='北京')->clean_amounts()->compute_gmv()——最终 GMV 是否确实只含北京的数据？

**模式 3——异常处理集成：** 验证"当管道中某个步骤失败时——整个管道优雅失败——而不是在深处崩溃"。比如——load_orders 找不到文件——应该 raise FileNotFoundError 并附带"请从 S3 下载数据"的提示——而不是在 clean_amounts 里因为传入了 None 而 AttributeError。

### CI 集成 pytest 的完整配置——不只是"加一行"——是"加一个完整的 test workflow"

```yaml
# .github/workflows/test.yml
name: Test

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ['3.10', '3.12']  # 测试两个 Python 版本

    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt
          pip install -r requirements-dev.txt

      - name: Run tests with coverage
        run: |
          pytest tests/ -v --cov=src --cov-report=term --cov-report=xml

      - name: Upload coverage to Codecov (optional)
        uses: codecov/codecov-action@v4
        with:
          file: ./coverage.xml
          fail_ci_if_error: false
```

**关键配置说明——不是"加个 workflow 文件就行"——这些细节决定了 CI 是否有用：**

1. **matrix 测试两个 Python 版本——**你的代码可能在 Python 3.10 上跑通但在 3.12 上报错（比如 W14 的 f-string 问题）。Matrix 让你在合并前就知道。

2. **requirements-dev.txt 单独管理——**pytest/ruff/mypy 只在开发时需要——不应该和生产依赖混在一起。CI 安装 requirements-dev.txt——生产部署只装 requirements.txt。

3. **--cov-report=xml——**生成的覆盖率 XML 可以被 Codecov/Code Climate 等服务可视化——在 PR 上直接看到"这个 PR 增加了还是减少了覆盖率"。

4. **fail_ci_if_error: false——**Codecov 上传失败不应该让 CI 变红——因为 Codecov 可能偶尔挂了——不应该因为第三方服务的问题阻止合并。

```python
    )
```

**这个 test 的价值——不是"验证功能正确"——是"固化一个团队决策——防止静默修改"。** 数据分析中有很多"阈值"和"默认参数"——这些值被改了——整个分析的结论可能逆转——但改动者可能觉得"这是个小调整"——不知道影响。test 就是"在这个值被改的时候——让人停下来——确认这是故意的"。

**鲜果多项目中适合用 TDD 思维固化的假设：**
- 显著性阈值 = 0.05——不是 0.1
- GMV 口径——include_tax=True, exclude_refunded=True——运营默认口径
- 清洗函数中——amount >= 0（含 0——因为赠品订单 amount=0 是合法的）
- 缺失值填充策略——城市用'unknown'——不是众数——因为城市缺失可能有业务含义（新用户未填写）

**面试时——面试官问"你用过 TDD 吗"——你说"我用了数据分析版的 TDD——在 Jupyter 探索后把关键假设固化为 test——防止静默修改——特别是阈值和默认参数——这些值被改了会影响整个分析结论"。这比你回答"我学过 TDD 但没用过"或者"我所有的代码都先写 test"（数据分析师不会这么做——也不可能这么做）更真实——也更可信。**

## D7（周日 11/23）：W17 审计——闭卷测试金字塔 + 5 种模式 + 覆盖率策略

### 📝 闭卷自测（5 题）

**Q1**：数据分析师的三层测试策略？为什么"画图函数不需要单元测试"？

> **A**：单元测试（单个函数——输入→输出）/ 集成测试（管道链路——3-5 个函数协作）/ E2E（`python main.py`）。画图函数输出是图像——不是数据——无法用 assert 验证"图片对不对"——用 E2E 验证"不报错"即可。偏差：说"所有函数都要测试"——这会浪费大量时间在无法有效测试的函数上。

**Q2**：pytest fixture 的两个设计原则？为什么需要"脏"和"干净"两套数据？

> **A**：①定义在 `conftest.py` 中——所有 test 自动发现 ②名称自描述——`sample_orders` 不是 `df1`。两套：脏数据（含边界——给清洗和验证函数用）+ 干净数据（给分析函数用——分析函数不应该再处理脏数据——那是清洗函数的职责）。偏差：只用一套"全干净"的数据——测不到边界条件。

**Q3**：5 种测试模式——每种防什么 bug？哪种模式最容易发现"沉默的 bug"？

> **A**：输入验证（防调用方误传）/ 边界条件（防极端数据崩函数）/ 输出结构（防接口变更调用方不知）/ 幂等性（防随机/时间依赖导致结果不可复现）/ 回归（防"优化"意外改变行为）。幂等性最容易发现沉默的 bug——单次跑"看起来对"——但两次之间差异累积——没有人注意到——直到结论反转。

**Q4**："危险区域"是什么？为什么覆盖率目标是"危险区域 80%"而不是"全代码 100%"？

> **A**：危险区域 = 数据变换函数（输入是数据——输出是数据）。不需要测试画图/日志/入口函数——它们不产生"可能被下游依赖的数据输出"。追求 100% 覆盖会浪费时间——而且会让你对"覆盖率数字"产生虚假的安全感——"覆盖率 100%"不等于"测试有效"。偏差：说"覆盖率越高越好"——你可以在不写 assert 的情况下"覆盖"所有行——覆盖率 = 执行过——≠ 验证过。

**Q5**：集成测试和单元测试的本质区别？集成测试发现什么问题——单元测试发现不了？

> **A**：单元测试验证"单个函数的行为符合 docstring"。集成测试验证"函数 A 的输出能作为函数 B 的输入"——接口一致性。单元测试发现不了——"A 的输出列名改了——B 还在用旧列名"。集成测试能——因为它跑的是真实的数据流。偏差：说"集成测试就是多个单元测试串起来"——不是——它测的是"接口"——不是"功能"。


**Q6**（面试模拟）：面试官问"你写过测试吗——给我看看你的测试代码"。你打开 GitHub——给他看什么？

> **A**：先打开 `tests/conftest.py`——"这是我的测试数据工厂——两套 fixture——sample_orders（脏数据——含边界）和 sample_orders_clean（干净数据——分析函数用）。所有 20+ 个 test 共享这两套数据——保证了测试数据的一致性。"然后打开 `tests/test_clean.py`——"'这是 clean_amounts 的测试——三个 test 分别覆盖正常场景（去负值）、异常场景（缺列抛异常）、边界场景（空 DataFrame）。注意 test 函数名——`test_removes_negative_amounts`——不是 `test_clean`——读函数名就知道测什么。"最后打开 `.github/workflows/test.yml`——"CI 里每次 push 自动跑 pytest——20+ 个 test 全绿才允许合并——这个 badge 在 README 顶部——实时显示。"

**Q7**（深度追问）：面试官追问"你怎么知道你的测试够了——而不是'测了一堆不重要的东西'？"

> **A**："我用三个层次评估。第一——危险区域覆盖率（D4）——所有数据变换函数都有至少 1 个 test——目标 100%——我现在的鲜果多项目是 100%。第二——场景覆盖率（D4 docstring 中的测试清单）——每个函数标注了正常/异常/边界三种场景的覆盖情况——目标每个函数至少覆盖 3 种场景。第三——反向验证——故意引入 bug——确认至少一个 test 变红。如果引入 bug 后 test 全绿——说明测试没有真正验证核心逻辑。这和'烟雾报警器'的道理一样——你不需要每天测试报警器——但你需要知道——如果着火了——它会响。"
