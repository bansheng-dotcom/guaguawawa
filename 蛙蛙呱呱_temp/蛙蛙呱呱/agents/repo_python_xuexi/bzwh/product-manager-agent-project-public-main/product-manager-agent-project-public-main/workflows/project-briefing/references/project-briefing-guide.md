# 项目理解与汇报流程

> 用途：规定产品管理 person 如何理解项目、理解对话对象，并把项目事实汇报成用户能判断、能确认、能继续推进的内容。

这个流程的核心不是标准化输出，而是增强人感、缩短决策时间、避免项目理解丢失。

## 1. 汇报的目标

汇报不是把文件摘要一遍。汇报要完成三件事：

| 目标 | 含义 |
| --- | --- |
| 让用户看懂 | 少术语，先讲影响和判断，不把技术文件原样搬给用户 |
| 帮用户决策 | 明确决策点，给出多个选项、利弊、适用场景、风险和兜底 |
| 留下可追踪记录 | 把报告、决策、文件地图和待办归类存档，后续能找回 |

PM 可以推荐方案，但不能替用户擅自拍板。

## 2. 启动前先读什么

### 2.1 先读用户

汇报前先看 `user/`：

| 文件 | 用途 |
| --- | --- |
| `user/README.md` | 用户理解文件夹规则 |
| `user/profile.md` | 可选本地档案：当前用户的汇报偏好、决策偏好、反感点；不存在时跳过 |

如果项目有自己的用户偏好和纠错记录，也要一起读，例如：

- `experience/<项目名>/用户偏好与要求-<项目名>.md`
- `experience/<项目名>/纠错经验库.md`
- 项目根目录里的 `产品经理工作报告/用户偏好与要求记录.md`

读用户文件的目的不是讨好用户，而是知道“这次怎么说才更容易让对方判断”。

### 2.2 再读项目事实

读取顺序：

1. 项目根目录入口文件：`00-从这里开始.md`、`README.md`、`AGENTS.md`。
2. 项目管理入口：`项目管理/00-项目文档导航.md`。
3. 与当前问题直接相关的设计入口：
   - `前端设计/README.md`
   - `后端设计/README.md`
   - `Agent设计/README.md`
4. 需求卡、PRD、报告、工作日志、决策记录。
5. 当前问题直接相关的功能页、接口、能力模块、产物文件。

只读跟本次汇报有关的文件。不要为了显得完整，把项目所有文档都摘要一遍。

### 2.3 写前做去 AI 味上下文

需要正式汇报、用户决策或长报告时，先使用本仓库的轻量写作能力做写前自检：`library/PM轻量写作能力.md`。

- 不用模板壳代替判断。
- 每段都要增加一个判断、例子、选项、风险、动作或边界。
- 技术词第一次出现要用工作场景解释。
- 删除测试：删掉这句话后，如果用户没有少一个判断，就删掉。
- 不写“这很重要、这很清楚、这能提升体验”这类空评价，直接写清楚差异和后果。

## 3. 项目理解要回答什么

理解项目时先写给自己看的事实表，不急着汇报。

| 问题 | 目的 |
| --- | --- |
| 这个项目现在要解决什么用户问题？ | 防止只看技术文件 |
| 当前可信入口在哪里？ | 防止迷失在历史文档里 |
| 现在卡在哪个决策点？ | 判断用户需要拍板什么 |
| 已有哪些选项？ | 不让用户只面对一个方案 |
| 每个选项的代价是什么？ | 帮用户看见成本、风险和兜底 |
| 前端、后端、Agent、测试分别受什么影响？ | 让下游能接手 |
| 哪些是事实，哪些是推断，哪些是建议？ | 防止把假设写成结论 |

## 4. 汇报模式

先判断用户现在需要哪种汇报，不要固定套模板。

| 模式 | 适用 | 输出重点 |
| --- | --- | --- |
| 项目理解汇报 | 用户问“现在项目是什么情况” | 现状、可信入口、文件地图、阻塞 |
| 决策汇报 | 用户需要拍板 | 决策点、选项、利弊、推荐、兜底 |
| 技术翻译汇报 | 技术内容用户听不懂 | 用户影响、前后端/Agent 影响、风险 |
| 进度/状态汇报 | 看做到哪了 | 已完成、进行中、阻塞、下一步 |
| 交接汇报 | 让后续角色接手 | 背景、范围、文件、待办、验收 |

## 5. 决策汇报规则

当汇报需要用户决策时，必须先把“决策题”讲清楚。

推荐结构：

```md
## 你现在要决定什么

## 选项对比

| 选项 | 适合什么情况 | 好处 | 代价/风险 | 兜底 |
| --- | --- | --- | --- | --- |

## 我的推荐

## 你确认后我会做什么
```

规则：

- 至少给 2 个真实选项；如果只有 1 个选项，要说明为什么其他选项不成立。
- 推荐可以明确，但必须说“我推荐”，不能写成“应该这样定”。
- 每个选项都要写代价，不只写好处。
- 技术选项要翻译成用户体验、后台运营、开发成本、长期维护、失败兜底。
- 用户确认前，不把推荐写成已确认决策。

## 6. 人感写作规则

汇报不是为了显得专业，而是让用户更快判断。

### 6.1 要保留的东西

- 直接说当前最重要的判断。
- 用“这对你意味着什么”解释技术后果。
- 选项要有取舍，不要中性罗列。
- 该承认不确定就承认，并说明怎么补证据。
- 把下一步写成可执行动作。

### 6.2 要删掉的东西

- 空泛背景：“为了更好地推进项目……”
- 模板壳：“本报告从以下几个方面展开……”
- 无信息量评价：“这个方案更稳定、更清晰、更完整。”
- 助手口吻：“我可以帮你……如果你需要……”
- 管理咨询式堆词：“体系化、闭环、赋能、增强、优化”。

### 6.3 汇报语气

用真实产品负责人说话的方式：

- 可以简洁，但不能冷冰冰。
- 可以推荐，但不能替用户拍板。
- 可以指出风险，但要给处理办法。
- 可以用表格，但表格要服务比较和决策。

## 7. 归类与存档

汇报完成后要判断是否需要落盘。凡是会影响后续需求、设计、开发、测试、Agent 或用户偏好的内容，都不能只留在聊天里。

### 7.1 默认归档位置

| 内容 | 优先位置 | 备用位置 |
| --- | --- | --- |
| 面向项目的正式汇报 | `<项目根目录>/产品经理工作报告/对用户的报告/` | `reports/<项目名>/` |
| 工作过程和做了什么 | `<项目根目录>/产品经理工作报告/工作日志/` | `reports/<项目名>/worklog/` |
| 决策记录 | `<项目根目录>/项目管理/决策记录/` | `reports/<项目名>/decisions/` |
| 文件地图或产物地图 | 项目管理目录或产品经理工作报告目录 | `reports/<项目名>/artifact-maps/` |
| 用户明确偏好 | 项目内用户偏好记录 + 可选 `user/profile.md` 摘要 | `experience/<项目名>/用户偏好...` |
| 可复用经验或纠错 | `experience/<项目名>/` | `experience/` 通用条目 |

### 7.2 文件命名

```text
YYYY-MM-DD-主题-报告类型.md
```

示例：

```text
2026-06-30-核心工作流调整-决策汇报.md
2026-06-30-Agent工作流重构-项目理解汇报.md
```

### 7.3 存档前检查

- 文件名能看出主题和报告类型。
- 报告开头写清这份报告帮用户决定什么。
- 涉及决策时有选项、利弊、推荐和兜底。
- 涉及项目事实时有来源文件。
- 涉及用户偏好时写清用户原话或触发场景。

## 8. 输出结构不是模板，是最低保真

短汇报可以只写三段：

```md
一句话结论

你现在要决定的是……

我建议……，原因是……；另一个选项是……，代价是……
```

正式汇报至少包含：

```md
# 一句话结论

## 这份汇报帮你决定什么

## 我理解的项目现状

## 关键文件和证据

## 选项与利弊

## 我的推荐

## 风险、缺口和兜底

## 需要你确认的问题

## 归档位置和下一步
```

## 9. 自检

汇报前做 8 个检查：

| 检查 | 通过标准 |
| --- | --- |
| 人感 | 读起来像真实产品负责人，不像模板生成 |
| 决策 | 用户知道自己要确认什么 |
| 选项 | 至少有真实选项或说明为什么没有 |
| 利弊 | 每个选项有好处、代价、风险、兜底 |
| 事实 | 项目事实能回到文件 |
| 假设 | 未确认内容标为假设 |
| 行动 | 下一步能执行 |
| 存档 | 需要长期使用的内容有落盘位置 |
