## W3D1：SQL基础 + 聚合 + 子查询

### 能力簇
**SQL入门到聚合** —— 从零理解SQL思维，掌握SELECT/GROUP BY/子查询，理解SQL执行顺序

### 具体知识清单

**1. SQL是什么 + pandas对照**
- SQL = Structured Query Language，操作关系型数据库的标准语言，1974年诞生
- SQL是声明式语言：你告诉数据库"我要什么结果"，它自己决定"怎么去取"。pandas是命令式：你告诉Python"每一步做什么"
- 同样的分析——pandas vs SQL对照：
  ```python
  # pandas: df.groupby('city')['amount'].sum().sort_values(ascending=False).head(5)
  ```
  ```sql
  -- SQL: SELECT city, SUM(amount) FROM orders GROUP BY city ORDER BY SUM(amount) DESC LIMIT 5
  ```
- SQL的三大子语言：DQL(查询SELECT)、DML(增删改INSERT/UPDATE/DELETE)、DDL(建表CREATE/ALTER/DROP)。本周学DQL
- 工具：用Python的sqlite3模块在内存中创建数据库+插入模拟数据+执行SQL。不需要安装MySQL

**2. SELECT / FROM / WHERE / ORDER BY / LIMIT**
- `SELECT 列1, 列2, 列3 FROM 表名` — 选哪些列（`*`=所有列）
- `WHERE 条件` — 行级过滤。`WHERE amount > 500 AND city = '北京'`
- `ORDER BY 列1 DESC, 列2 ASC` — 排序。DESC降序/ASC升序（默认）
- `LIMIT n` — 只取前n行。`LIMIT 10` 或 `LIMIT 5, 10`（跳过5行取10行）
- `DISTINCT 列` — 去重。`SELECT DISTINCT city FROM orders`
- `AS 别名` — 给列或表起别名。`SELECT SUM(amount) AS 总销售 FROM orders`
- 字符串拼接：`'hello' || 'world'`（SQLite/PostgreSQL）或 `CONCAT('hello','world')`（MySQL）
- **陷阱1：SQL里`=`就是比较（不是赋值！赋值是`INSERT/UPDATE`的事）。`WHERE amount = 500`意思是"金额等于500的行"**
- **陷阱2：`NULL`不能用`=`比较！`WHERE city = NULL`永远返回空→必须用`WHERE city IS NULL`或`IS NOT NULL`**
- **陷阱3：`LIMIT 5,10`在不同的数据库里语法不同。MySQL是`LIMIT offset, count`，PostgreSQL是`LIMIT count OFFSET offset`**

**3. 聚合函数 + GROUP BY / HAVING**
- 聚合函数：`COUNT()/SUM()/AVG()/MAX()/MIN()`
- `COUNT(*)`包含NULL行（数行数），`COUNT(列名)`不包含NULL行（数该列非空值）
- `COUNT(DISTINCT 列)` — 不重复值的个数
- `GROUP BY 列` — 按该列分组。`SELECT city, SUM(amount) FROM orders GROUP BY city`
- 多列分组：`GROUP BY city, category` → 同时按城市和品类分组
- `HAVING 条件` — 分组后的过滤。`HAVING SUM(amount) > 10000`（只保留总销售额>10000的组）
- **WHERE vs HAVING — SQL最高频面试题之一**：
  - WHERE = 分组前过滤行（原始数据筛选）
  - HAVING = 分组后过滤组（聚合结果筛选）
  - WHERE不能用聚合函数，HAVING必须用聚合函数或分组列
  - 执行顺序：WHERE先→GROUP BY→HAVING→SELECT
- **陷阱：SELECT里放了不在GROUP BY里也不在聚合函数里的列→SQLite/MySQL允许但结果不确定，PostgreSQL/Oracle直接报错**

**4. SQL执行顺序 —— 理解这个=理解SQL**
```
FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```
- 这条顺序解释了几乎所有的SQL困惑：
  - 为什么WHERE不能用SELECT的别名？→ 因为WHERE在SELECT之前执行！
  - 为什么HAVING能用聚合函数而WHERE不能？→ 因为HAVING在GROUP BY之后，聚合已经完成
  - 为什么ORDER BY能用SELECT别名？→ 因为ORDER BY在SELECT之后
  - 为什么LIMIT最后？→ 前面所有步骤完成后才截断输出

**5. 子查询**
- 标量子查询（返回一个值）：`SELECT * FROM orders WHERE amount > (SELECT AVG(amount) FROM orders)`
- 行子查询（返回一行）：`WHERE (city, category) = (SELECT city, category FROM ... LIMIT 1)`
- 表子查询（返回一张表）：放在FROM后面 → `FROM (SELECT user_id, SUM(amount) AS total FROM orders GROUP BY user_id) AS user_stats` — 派生表必须给别名！
- `IN` / `NOT IN`：`WHERE user_id IN (SELECT user_id FROM vip_users)`
- `EXISTS` / `NOT EXISTS`：`WHERE EXISTS (SELECT 1 FROM orders WHERE orders.user_id = users.user_id AND amount > 1000)`
- `ALL` / `ANY`：`WHERE amount > ALL (SELECT amount FROM orders WHERE city = '北京')`（比北京所有订单都大）
- **陷阱1：子查询返回多行→用`=`报错"subquery returned more than 1 row"→改用`IN`**
- **陷阱2：`NOT IN`子查询里有NULL→整个NOT IN返回空！** 因为`x NOT IN (1, 2, NULL)`→等价于`x != 1 AND x != 2 AND x != NULL`→`x != NULL`永远NULL→整个AND变成NULL→返回空
- **陷阱3：派生表必须给别名——`FROM (SELECT ...) `→报错"every derived table must have its own alias"→`FROM (SELECT ...) AS t`**

## W3D2：JOIN全系 + 陷阱

### 能力簇
**多表连接** —— 掌握5种JOIN，理解ON vs WHERE的根本区别，防止行数膨胀和数据丢失

### 具体知识清单

**1. 五种JOIN的直观理解**
- `INNER JOIN`：两表都有的行才保留（交集）。90%的业务场景用的是这个
- `LEFT JOIN`：左表全部保留，右表匹配不上的填NULL。**最常用**—订单关联用户
- `RIGHT JOIN`：右表全部保留（等价于LEFT JOIN调换顺序，很少用）
- `FULL OUTER JOIN`：两表并集，匹配不上的各自填NULL。MySQL不支持→用LEFT JOIN UNION RIGHT JOIN模拟
- `CROSS JOIN`：笛卡尔积，左表每行×右表每行。**慎用！** 100×100=10000行。唯一合理场景：生成日期序列(`CROSS JOIN`日期表)
- **陷阱：LEFT JOIN和LEFT OUTER JOIN是同一个东西（OUTER可省略）。误解为两个不同东西=浪费时间**

**2. ON vs WHERE陷阱 —— SQL最高频考点之一，面试必问**
- `ON`：JOIN过程中的条件——决定"哪些行被连接起来"。在JOIN阶段生效
- `WHERE`：JOIN完成后的过滤——决定"哪些行保留在最终结果里"。在JOIN结果上生效
- **核心陷阱：`LEFT JOIN ... WHERE 右表.列 = 值` → 等价于INNER JOIN！**
  - 为什么：LEFT JOIN先执行→右表没匹配的行填NULL→WHERE再执行→`NULL = 值`→条件为假→这些行被过滤→结果里只剩两表都有匹配的行→和INNER JOIN一模一样
  - 验证：同一条SQL，分别把条件放在ON vs WHERE→结果行数完全不同
- **口诀**：表连接条件放ON，业务筛选条件放WHERE。不要混

**3. 自连接 Self Join**
- 同一张表自己JOIN自己→必须取别名（`FROM orders o1 JOIN orders o2 ON ...`）
- 用途1：找"买了A也买了B的用户"（同一用户买了两个不同的商品）
- 用途2：计算留存（今天登录的用户JOIN昨天登录的用户→匹配上的=留存用户）
- 用途3：比较同一用户不同时期的消费（本月JOIN上月）

**4. SEMI JOIN / ANTI JOIN —— 不用写JOIN的JOIN**
- SEMI JOIN = "在右表中有匹配的"左表行 → 用`WHERE EXISTS (SELECT 1 FROM 右表 WHERE 条件)` 或 `WHERE 列 IN (SELECT ...)`
- ANTI JOIN = "在右表中没有匹配的"左表行 → 用`WHERE NOT EXISTS (...) ` 或 `LEFT JOIN ... WHERE 右表.key IS NULL`
- **NOT EXISTS > NOT IN，永远优先用NOT EXISTS** → NOT IN有NULL陷阱，NOT EXISTS没有
- **陷阱1：`IN` vs `EXISTS`——IN先把子查询跑完再比较（适合子查询结果小），EXISTS每行判断一次（适合主查询结果小但子查询大）**
- **陷阱2：`NOT IN (SELECT ...)`和`NOT EXISTS (SELECT ...)`在子查询有NULL时结果完全不同！** NOT IN返回空行，NOT EXISTS依然正确

**5. 行数膨胀——JOIN的隐形地雷**
- 膨胀场景1：左表1个用户→右表5条订单→LEFT JOIN后=5条（一对多，正常膨胀）
- 膨胀场景2：左表user_id有重复+右表user_id有重复→笛卡尔积式膨胀。左表3条×右表2条=6条（异常膨胀！）
- 预防措施1：JOIN前检查关联键是否有重复→`SELECT key, COUNT(*) FROM 表 GROUP BY key HAVING COUNT(*)>1`
- 预防措施2：如果右表有重复→先聚合去重再JOIN
- 预防措施3：JOIN前后打印行数对比→膨胀倍数不对马上排查
- **陷阱：膨胀了没发现→分析"每个城市有多少订单"→城市重复计数→结果翻倍→结论错误**

## W3D3：窗口函数全量

### 能力簇
**SQL进阶的分水岭** —— 窗口函数是面试和工作中区分初级和高级的核心能力

### 具体知识清单

**1. 窗口函数是什么——三种武器谁都不如它**
- 用一句话理解：窗口函数在**不折叠行**（不像GROUP BY）也**不需要额外JOIN**（不像自连接）的情况下，让每一行访问其他行
- 三个对比：
  - GROUP BY：折叠行→多行压成一行→丢失明细
  - 自连接：保留明细→但需要自己JOIN自己→复杂且慢
  - 窗口函数：保留明细+不需要额外JOIN→兼具两者优点
- 语法：`函数() OVER (PARTITION BY 分组列 ORDER BY 排序列 ROWS/RANGE 窗口帧)`
  - PARTITION BY = "和谁比"（分组）
  - ORDER BY = "按什么顺序比"（组内排序）
  - ROWS/RANGE = "比的范围有多大"（窗口帧）

**2. 排名函数——面试90%会考**
- `ROW_NUMBER()`：1,2,3,4,5... 无并列，严格排名 → 每组精确取TopN
- `RANK()`：1,2,2,4,5... 有并列跳过后续 → 体育比赛排名（并列第一→没有第二→直接第三）
- `DENSE_RANK()`：1,2,2,3,4... 有并列不跳过 → 连续排名（并列第一→接着第二）
- `NTILE(n)`：把数据均分成n份→标记1到n → 百分位分组（如NTILE(4)=四分位数/分4档）
- **三种排名的业务选择**：
  - ROW_NUMBER：运营发"每城市消费Top3用户"优惠券→严格3个不能多→用ROW_NUMBER
  - RANK："真正的第一梯队"→如果有并列就要保留→用RANK
  - DENSE_RANK："连续排名第几名"→不跳号→用DENSE_RANK
- **陷阱：ROW_NUMBER取TopN时，如果第N名有并列→会被随机丢掉一些并列者**

**3. 偏移函数**
- `LAG(列, n, 默认值)`：往前n行取数据 → n=1前一行。计算环比(本月-上月)、相邻两次行为间隔
- `LEAD(列, n, 默认值)`：往后n行取数据 → n=1后一行。预测下一笔、计算到下一次的时间
- `FIRST_VALUE(列)`：窗口内的第一个值
- `LAST_VALUE(列)`：窗口内的最后一个值
- **LAG最常见用途**：
  - 环比：`(本月销售额 - LAG(本月销售额,1) OVER (ORDER BY 月份)) / LAG(本月销售额,1) OVER (ORDER BY 月份)`
  - 用户行为间隔：`本次登录日期 - LAG(本次登录日期,1) OVER (PARTITION BY 用户 ORDER BY 登录日期)` → 大于1天=非连续
- **陷阱：LAST_VALUE默认窗口帧是`RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`→不加ROWS的话只能看到"到目前为止的最后一个"而非"整个窗口的最后一个"**

**4. 聚合窗口函数**
- `SUM(列) OVER (ORDER BY 日期)` → 按日期累计（每天的累计GMV）
- `SUM(列) OVER (PARTITION BY 用户 ORDER BY 日期)` → 每用户累计（每用户自己的累计消费）
- `AVG(列) OVER (...)` → 移动平均
- `COUNT(列) OVER (...)` → 累计计数（每用户第几次购买）

**5. 窗口帧规范 ROWS vs RANGE —— 面试常问**
- `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW`：当前行+前2行（物理行数，共3行）
- `ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING`：当前行到末尾
- `RANGE BETWEEN INTERVAL '3' DAY PRECEDING AND CURRENT ROW`：前3天内的所有行（用值来界定范围）
- `ROWS`按物理行数，`RANGE`按列值范围
- **什么时候用ROWS？移动平均（固定窗口行数，如"最近3天的平均"）**
- **什么时候用RANGE？时间窗口（固定时间范围，如"前3天内的所有行"，哪怕某天有10条记录也全包含）**
- **陷阱：ORDER BY列有重复值时，RANGE会包含所有等值的行→可能比预期的多很多行**

**6. 两个ORDER BY的区别**
- 窗口内的ORDER BY：`OVER (ORDER BY 日期)`→决定窗口函数的计算顺序
- 查询尾部的ORDER BY：`ORDER BY 日期 DESC`→决定最终输出行的排序
- 两者互不影响！可以窗口内按日期升序累计，但最终结果按用户ID降序展示

| 4 | 进阶 | **电商(速卖通)** | TOP-N+NTILE：每城市消费Top3(用ROW_NUMBER)+所有用户按消费分4档(用NTILE)→合并输出"高消费用户集中在哪些城市" | L3 |
| 5 | 进阶 | **游戏** | ROWS vs RANGE对比：30天内每日充值→用ROWS算3天移动平均(前2天+今天÷3)→用RANGE算前3天内的所有充值→对比差异→解释差异产生的原因 | L3 |
| 6 | 挑战 | 番茄阅读 | Session切分：用LAG计算相邻行为时间差→如果>30分钟=新session开始→给每个session编号(用SUM+窗口函数标记新session) | L4 |

### 必须覆盖的陷阱
1. **ROW_NUMBER vs RANK vs DENSE_RANK并列行为不同**：ROW_NUMBER无并列→TopN严格N个。RANK有并列跳号→可能实际多于N个
2. **PARTITION BY和ORDER BY的作用域不同于查询尾部ORDER BY**：查询尾部ORDER BY只影响最终展示，不影响窗口函数计算
3. **ROWS vs RANGE**：有重复值/时间不规则时行为不同→RANGE可能包含意外多的行
4. **LAST_VALUE默认窗口帧只是UNBOUNDED PRECEDING→CURRENT ROW**：`LAST_VALUE(金额) OVER (PARTITION BY 用户 ORDER BY 日期)` → 每行看到的"最后"只到当前行→加`ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`才能看到整个窗口

## W3D4：CTE + 复杂查询模板

### 能力簇
**查询工程化与三大模板** —— 用CTE让复杂SQL可读可维护，模板化留存/漏斗/连续登录

### 具体知识清单

**1. CTE (Common Table Expression) —— 给子查询起名字**
- 基本语法：
  ```sql
  WITH 名字 AS (
      SELECT ... -- 子查询
  )
  SELECT ... FROM 名字 ...
  ```
- 链式CTE：多个CTE用逗号分隔→后面的CTE可以引用前面的
  ```sql
  WITH step1 AS (SELECT ...),
       step2 AS (SELECT ... FROM step1 ...),
       step3 AS (SELECT ... FROM step2 ...)
  SELECT ... FROM step3
  ```
- CTE vs 子查询：嵌套3层子查询→人脑无法一次理解。CTE把每一步拆成一个"逻辑块"→每步单独理解→阅读复杂度从乘积变成加法
- **陷阱1：CTE在MySQL 8.0之前不支持→老版本只能用子查询或临时表**
- **陷阱2：CTE默认不物化（不存中间结果）→同一个CTE被多次引用可能被多次执行→数据量大时性能差。PostgreSQL可以加`MATERIALIZED`强制物化**

**2. 递归CTE —— 用SQL做循环**
- 语法：`WITH RECURSIVE cte AS (初始SELECT UNION ALL 递归SELECT引用cte自身) SELECT ...`
- 两要素：①锚定成员(起点) ②递归成员(引用自己的SELECT) ③`UNION ALL`连接 ④终止条件(WHERE递归SELECT返回空时自动停止)
- 用途1：组织树（CEO→VP→总监→经理→员工→递归找出某人所有下属）
- 用途2：生成日期序列（生成从'2025-01-01'到'2025-12-31'每一天的一行）
  ```sql
  WITH RECURSIVE dates(d) AS (
      SELECT DATE('2025-01-01')
      UNION ALL
      SELECT DATE(d, '+1 day') FROM dates WHERE d < '2025-12-31'
  )
  SELECT d FROM dates
  ```
- **陷阱：没有终止条件→无限递归→数据库崩溃。必须确保递归最终会停止**

**3. 🔥 留存率模板 —— 大厂面试通过率18%的生死题**
- 次日留存 = 第一天登录的用户中，第二天也登录的比例
- 四步标准写法：
  1. 找每个用户的首登日：`SELECT user_id, MIN(date) AS first_date FROM login GROUP BY user_id`
  2. 标记次日是否登录：LEFT JOIN login表 ON user_id相同 AND date=首登日+1天
  3. 聚合计算：按first_date分组→计数次日登录用户÷当日新用户数
  4. 处理NULL：分母可能为0→用`NULLIF`(`COUNT(DISTINCT user_id)`,0)或直接排除
- **四大易错点（面试官就盯着你这些）**：
  1. 新用户定义：用全局`MIN(date)`而非"当天第一次登录"（登录表中某天出现了该用户=那天是当天）
  2. 日期对齐：留存日期=首登日+1天→用`DATE_ADD`不要手算跨月
  3. 分母为0：某天可能0新用户→留存率为NULL而非0→`NULLIF`或先过滤
  4. 聚合层级：需要两层聚合→先按用户+首登日聚合找是否留存→再按首登日聚合算比率

**4. 🔥 漏斗模板 —— 字节最爱考**
- N步漏斗：浏览→点击→加购→下单→支付→完成
- 两种写法：
  - 横向：每步一个`SUM(CASE WHEN action='xxx' THEN 1 ELSE 0 END)`→一行出所有步骤
  - 纵向：每步一个CTE→UNION ALL合并→按步骤排序
- 分群漏斗：`GROUP BY 渠道/新老用户`→每个分群一个漏斗→横向对比"哪个渠道的哪一步流失最严重"
- **分析的两种视角**：
  - 最大绝对值损失：哪一步失去的用户数最多→补最大的洞
  - 最大相对下降：哪一步转化率下降最大→修最弱的环节

**5. 🔥 连续登录模板 (Gap-and-Island) —— 腾讯最爱考**
- 核心数学技巧：`日期 - ROW_NUMBER() OVER (PARTITION BY 用户 ORDER BY 日期)`
  - 日期列减去连续序号→连续日期的差值相同→把"连续"转化为"相同"→GROUP BY即可
- 步骤：
  1. 去重：`SELECT DISTINCT user_id, login_date FROM login`
  2. 编号：`ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date)`
  3. 做差：`login_date - ROW_NUMBER()`→连续日期得到相同的参考日期
  4. 分组聚合：`GROUP BY user_id, 参考日期 HAVING COUNT(*) >= N`
- **直觉理解**：1/1-1=12/31、1/2-2=12/31、1/3-3=12/31→连续3天→同一个参考日。1/5-4=1/1→断了一天→另一个参考日
- 变体：30分钟内行为合并为一个session→用`时间戳 - ROW_NUMBER() * INTERVAL '30 minutes'`

## W3D5：查询优化 + 反模式

### 能力簇
**SQL性能调优** —— 看懂EXPLAIN，识别并修复8大反模式，写出不被人骂的SQL

### 具体知识清单

**1. EXPLAIN解读 —— 看执行计划**
- `EXPLAIN SELECT ...` → 显示数据库如何执行这条SQL
- 关键字段逐一看：
  - `type`：连接类型。从优到劣：const(常量)→eq_ref(唯一索引)→ref(非唯一索引)→range(范围扫描)→index(全索引扫描)→ALL(全表扫描=性能灾难)
  - `rows`：预估扫描行数。越少越好。几百万→要优化
  - `key`：实际使用的索引名。NULL=没用索引→全表扫描
  - `Extra`：额外信息。`Using filesort`(需要额外排序)=坏信号、`Using temporary`(需要临时表)=坏信号、`Using index`(覆盖索引)=好信号
- **遇到`type=ALL`就要警惕→全表扫描→看能不能加索引。遇到`Extra=Using filesort`→看能不能优化ORDER BY**

**2. 索引基础**
- B+Tree索引直觉：所有值存在有序的树结构里→二分查找→O(log n)找到→比全表扫描O(n)快几个数量级
- 覆盖索引：查询需要的所有列都在索引里→不需要"回表"查完整行（Using index）
- 最左前缀原则：`INDEX(a, b, c)`→`WHERE a=1`能用索引、`WHERE a=1 AND b=2`能用、`WHERE b=2`不能用（没有a在前）
- **索引的代价**：每个索引减慢INSERT/UPDATE/DELETE（因为索引也要更新）、占存储空间。索引不是越多越好

**3. 🔥 8大反模式 —— 每条都能通过EXPLAIN验证**

| # | 反模式 | 为什么是反模式 | 正确做法 |
|----|--------|-------------|---------|
| 1 | `SELECT *` | 拿所有列→索引覆盖失效（选了不在索引里的列必须回表）+网络带宽浪费+列变化时代码崩溃 | `SELECT 列1, 列2`→明确需要的列 |
| 2 | 函数包裹列名：`WHERE DATE(create_time)='2025-01-01'` | 对每行的create_time先套DATE函数再比较→索引用不了→全表扫描 | `WHERE create_time >= '2025-01-01' AND create_time < '2025-01-02'` |
| 3 | 前缀模糊：`LIKE '%关键词'` | B+Tree最左匹配→前缀模糊意味着不知道从哪个节点开始找→索引失效→全表扫描 | 用全文索引(Elasticsearch/Solr)或反转字符串后做前缀精确匹配 |
| 4 | 隐式类型转换：VARCHAR列用数字比较 | `WHERE phone = 13800138000`→数据库把phone列的值逐个转成数字再比较→索引用不了 | `WHERE phone = '13800138000'`（字符串要加引号！）|
| 5 | OR跨列：`WHERE a=1 OR b=2` | a和b各有一个索引→优化器可能不知道怎么用→可能全表扫描 | 拆成两条查询UNION：`SELECT ... WHERE a=1 UNION SELECT ... WHERE b=2` |
| 6 | `ORDER BY RAND()` | 需要每一行分配一个随机值→然后排序→全表扫描+临时表排序→几十万行直接挂 | 应用层随机：先`SELECT MAX(id), MIN(id)`→应用层生成随机id→`WHERE id BETWEEN` |
| 7 | 深分页：`LIMIT 1000000, 20` | 数据库会扫描前1000000行→扔掉前面→只留最后20行→越翻越慢 | 基于主键游标：`WHERE id > 上一页最后的id ORDER BY id LIMIT 20`（延迟关联也可以）|
| 8 | 大表`COUNT(*)`vs`COUNT(col)`vs`EXISTS` | 每次COUNT都扫全表→高频调用=慢。`COUNT(*)`包含NULL/`COUNT(col)`不包含NULL/`EXISTS`只判断有无→更快 | 用缓存/汇总表。如果只判断"有没有"用`EXISTS` |

**4. 优化策略组合**
- 建索引：给WHERE/ORDER BY/JOIN中最高频的列建索引
- 改写SQL：避免函数包裹/避免OR/用JOIN替代子查询
- 深分页优化：基于主键游标 / 延迟关联
- 分区：大表按日期分区→查询只扫相关分区→IO省99%

### 必须覆盖的陷阱
1. **SELECT * 在生产环境是致命操作**：线上表几十列全扫→内存炸/带宽满/索引失效

3. **深分页越翻越慢**：`LIMIT 1000000,20`扫描百万行只取20→永远用游标分页
4. **`ORDER BY RAND()`是性能杀手**：每行分配随机值→排序→全表扫。永远不要在线上用

## W3D7：Hive初识 + 月度过渡

### 能力簇
**从单机SQL到分布式数据仓库的思维转换** —— 理解为什么大数据不能用MySQL

### 具体知识清单

**1. 为什么需要Hive——MySQL的极限**
- MySQL能处理的数据量：几百万到几千万行→有索引的情况下查询很快（毫秒到秒级）
- 但互联网公司的数据量：每天几亿到几百亿行→MySQL直接崩溃
- 根本原因：MySQL是单机架构→一台机器的CPU/内存/磁盘有上限
- Hive的思路：把数据分布在几百台机器上→每台机器处理自己那部分数据→再把结果汇总
- **OLTP(MySQL)追求"快"——单条查询毫秒级，支持并发读写。OLAP(Hive)追求"大"——一次查询可能几分钟到几小时，但能处理PB级数据**

**2. Hive不是数据库，是数据仓库工具**
- Hive = 把SQL(HQL)翻译成MapReduce/Tez/Spark任务→在Hadoop集群上执行→结果返回给你
- Hive的数据存在HDFS上（Hadoop分布式文件系统）→Hive本身不存数据
- Metastore存表的元数据（列名/类型/分区/存储位置）→不存实际数据
- **"移动计算而非移动数据"**：把计算逻辑发到数据所在的机器→在数据本地执行→避免海量数据网络传输

**3. Hive vs MySQL核心差异（10条必须知道）**
1. **操作类型**：Hive不支持单行UPDATE/DELETE→用`INSERT OVERWRITE`（覆盖整个分区）替代
2. **分区**：Hive用PARTITIONED BY把数据按目录存放→如按日期分区→`WHERE dt='2025-01-01'`只读该日期目录→跳过99%数据
3. **数据类型**：Hive多了复合类型`ARRAY`(数组)、`MAP`(键值对)、`STRUCT`(结构体)→可以用`LATERAL VIEW EXPLODE`展开
4. **NULL行为**：Hive的NULL在聚合时被完全忽略→`COUNT(列)`和MySQL一样不数NULL，但`AVG`只除以非NULL数量
5. **索引**：Hive没有传统索引概念→靠分区+分桶+ORC文件格式（带轻量级min/max统计信息）优化查询
6. **事务**：Hive不支持ACID事务（新版开始支持但不建议在分析场景用）
7. **外部表vs内部表**：`EXTERNAL TABLE`→DROP时只删元数据保留HDFS文件。`MANAGED TABLE`→DROP时连数据一起删
8. **查询语法**：HiveQL和标准SQL大部分兼容→但有些自己的函数（如`get_json_object`解析JSON、`LATERAL VIEW EXPLODE`展开数组）
9. **延迟**：Hive查询慢（分钟到小时级，因为要启MapReduce任务）→不适合在线业务/实时看板
10. **Metastore**：用关系数据库(MySQL/PostgreSQL)存元数据→和HDFS上的实际数据分开

**4. 分区与分桶——Hive加速的两个核心概念**
- 分区(PARTITION BY)：数据按目录存放→`/user/hive/warehouse/orders/dt=2025-01-01/`→查询时只读必要目录
  - 如何选择分区键：选查询中最常过滤的列→通常是日期
  - **陷阱：分区键选太多→目录爆炸→小文件太多反而慢（建议分区数<百万级目录）**
- 分桶(CLUSTERED BY)：同一分区内按hash分文件→主要用于两个大表做SMB JOIN→两个表桶数相同或倍数→JOIN在Map端完成无需Shuffle

**5. Python模拟分区裁剪——直观感受**
- 生成100万行模拟数据→全表扫描聚合→计时
- 按日期分成10个"分区"（10个CSV文件）→只读相关的分区→聚合→计时
- 性能差异：10倍（10分区）× 100倍（100分区）→理解"跳过99%的数据"的真正意义

### 必须覆盖的陷阱
