## W7D1：CUPED方差缩减

### 能力簇
**让实验跑得更快** —— 用实验前数据做协变量调整，降低方差→减少样本量需求→缩短实验时间。入职后leader说"这个实验要跑4周太久了,能不能加速?"——你的第一反应就是CUPED。

### 为什么今天重要
字节/腾讯的实验平台标配CUPED。入职后你不是从零实现CUPED——平台已经内置了。但你需要理解：①什么时候CUPED有效(ρ>0.5)②怎么选协变量(实验前+和Y相关+不受处理影响)③为什么CUPED不是"作弊"。这些理解决定了你能否正确使用平台功能、能否在"协变量选错→方差反而增大"时诊断问题。

### 具体知识清单

**1. CUPED核心直觉——"用过去预测现在,剩下的才是策略造成的"**
- 问题：用户阅读时长本身波动大→σ大→需要大量样本→实验时间长
- CUPED洞察：实验前一周你已知道A用户日均读5分钟/B用户读180分钟→这个信息可以用来"减去已知的个体差异"
- 公式：**Y_adj = Y - θ×(X - E[X])**
  - Y=实验期指标。X=实验前同一指标。θ=Cov(Y,X)/Var(X)。E[X]=X在两组的均值
- 方差缩小幅度=**1-ρ²**。ρ=0.5→缩小25%。ρ=0.7→缩小~50%。ρ=0.9→缩小~81%
- **业务翻译**：实验前行为和实验期行为越相关(ρ越大)→CUPED效果越好。如果ρ<0.3→CUPED基本无效→不要硬用

**2. 协变量选择三标准——选错了方差反而增大**
- 标准1(最重要)：和Y高度相关→算Corr(X,Y)→ρ>0.5才值得用
- 标准2：实验前数据→**绝对不能受实验处理影响**。用实验期数据做协变量→会"吸走"部分策略效果→低估真实效应
- 标准3：不受处理影响→X是用户固有特征(活跃度/历史行为)，不是被策略影响的结果
- **入职后你的操作**：拉过去30天用户数据→算多个候选协变量和Y的相关性→选ρ最高的1-3个→CUPED→验证方差缩小

**3. CUPED的局限——新用户没历史数据**
- 新用户→没有实验前数据→CUPED不可用→只能用群组级替代(同城市/同渠道用户的均值)→效果打折
- 协变量选错→方差可能反而增大→选之前必须算ρ
- 假设X和Y线性相关→非线性→CUPED效果差

**4. 给leader解释CUPED的一句话**
"CUPED利用用户历史行为数据→把'用户之间本来就有的差异'从指标中剥离掉→剩下的波动=策略效果+纯随机→波动更小→需要更少样本就能看到效果→实验更快。"

## W7D2：Peeking + 序贯检验

### 能力簇
**对抗"忍不住偷看实验"** —— PM天天催你看数据，你告诉他偷看的统计代价+序贯检验的解决方案。入职后最常见的沟通场景。

### 为什么今天重要
入职后PM每天早上都可能问你"今天显著了吗"。你不能只说"不能看"——要解释为什么+给替代方案。今天学会：①用Python模拟证明偷看的危害②用序贯检验给PM一个"既能提前停又可控风险"的方案③写一封PM看得懂的解释邮件。

### 具体知识清单

**1. 🔥Peeking的危害——每天偷看→假阳性从5%飙升到30%**
- α=0.05→每次5%假阳性。每天看一次连续7天→至少1次p<0.05的概率=1-(1-0.05)⁷≈30%
- 14天→约51%。30天→约79%
- Python模拟亲眼看到：
  ```python
  fp = 0
  for sim in range(2000):
      A = np.random.normal(100,15,1000); B = np.random.normal(100,15,1000)
      for day in range(1,8):
          n_today = day * 143
          if stats.ttest_ind(A[:n_today], B[:n_today])[1] < 0.05:
              fp += 1; break
  print(f"7天Peeking假阳性率={fp/2000:.3f} ≈ 0.30")  # 应该≈0.30
  ```
- **业务后果**：每10个无效策略有3个被错误推全→浪费开发资源→上线无效功能→产品事故

**2. 序贯检验——既能提前停,假阳性又不失控**
- O'Brien-Fleming边界：**最常用**。早期α极严格→几乎不可能提前停。越接近计划结束→边界越接近0.05
- t=25%时→需要p<0.0001才能停→几乎不可能。t=50%→p<0.005。t=75%→p<0.018。t=100%→p<0.048
- **业务直觉**："刚跑25%数据→极不确定→边界极严→几乎不可能停。越到后面→数据越多→越确定→边界越宽松。"

**3. 给PM的沟通——不是"不能看",是"有更好的方法"**
- 错误说法："不能看！看了实验就不准了"(PM内心:为什么?数据放在那不就是看的吗?)
- 正确说法："每天看然后根据p值提前停→每3个推全的'有效策略'就有1个是假的。建议①只看护栏指标(确认没问题)②如果想提前停,用序贯检验③如果不急,等跑满再看。你要哪一种?"

## W7D3：网络效应 + Switchback

### 能力簇
**用户互相影响时怎么做实验** —— 社交/出行/外卖产品。入职后leader说"这个产品有网络效应，标准AB可能不行"——你能设计替代方案。

### 为什么今天重要
很多产品不是"用户之间独立的"——社交产品互相分享、出行司机互相竞争、外卖商家互相抢客流。在这些产品上用标准AB→SUTVA违反→结论偏了。今天学会：①识别网络效应②设计Switchback(时间维度实验)③判断Geo Testing是否适用。入职后你的价值不是"只会做标准AB"，而是"能判断该用什么方法"。

### 具体知识清单

**1. 网络效应的三种典型场景**
- 社交裂变：实验组用户分享→对照组看到→被间接触及→效应泄漏→可能低估
- 出行抢单：实验组司机新算法→多接订单→对照组司机单量减少→两组不独立→可能高估
- 外卖竞食：实验组商家补贴→吸引用户→附近对照组商家客流减少→可能高估

**2. Switchback——用时间维度做随机化**
- 核心：一段时间全量ON(上线策略)、一段时间全量OFF(下线策略)→交替进行→对比ON和OFF时段的指标
- 为什么有效：同一批用户→ON时段体验策略、OFF时段不体验→自身对照消除个体差异
- 关键设计：①时间窗口长度(应覆盖策略效果充分体现的最短时间→如1天)②交替次数(越多→统计效力越高→但切换开销大)③分析单元=时间段(不是用户！)→用聚类标准误
- **入职场景**：leader让你设计出行新派单算法的实验→你判断标准AB不适用(司机抢单)→设计Switchback→窗口=1天,交替=14天(7个ON+7个OFF)

**3. Geo Testing——按地域分流**
- 核心：城市A=实验组、城市B=对照组→地域间交叉最小
- 优点：简单。缺点：地域间不完全可比(北京和上海本来就不同)→需DID调整
- Switchback vs Geo Testing：地域流动可忽略→Geo。地域不可分割→Switchback。溢出发生在短时间内→Switchback。溢出慢性的→Geo

## W7D4：长期效应 + Holdout

### 能力簇
**短期的显著≠长期的可持续** —— 新颖性效应衰减→Holdout保护长期决策。入职后PM说"上周实验效果很好,推全"，你检查是否有长期数据支撑。

### 为什么今天重要
新功能上线→短期数据好看→全量推全→3周后效果消失→浪费开发资源+丢掉产品方向。你的价值：在实验报告中区分"短期效应(新颖性)"和"长期效应(可持续)"。Holdout=用5%流量换长期决策准确性。

### 具体知识清单

**1. 新颖性效应——"新东西总是先吸引注意力"**
- 衰减模式：第1-3天效果最强→第4-7天回落→第2-3周稳定在真实水平
- 影响程度：UI改动(弱,1-3天)<功能改动(中,3-7天)<产品模式改动(强,1-3周)
- Python模拟衰减曲线→第一天+13%(3%真实+10%新颖)→第七天+7%→第14天+4%→第28天+3.2%
- **只看前7天=严重高估→推全=犯错**

**2. Holdout——保留5-10%用户永远不接受新策略**
- 用途：①测量长期累积效应②检验短期→长期是否一致③检测"对照组被连续迭代污染"
- 入职场景：leader让你评估"过去3个月的累积策略效果"→对比"Houldout组(从未更新)"和"一直在更新组"→差值=3个月所有迭代的累积效果

**3. 可信决策时间窗口——效果曲线趋于稳定后才适合做决策**
- 关键决策(推全)至少等衰减曲线稳定→通常≥2周

## W7D5：实验平台 + 流量分层

### 能力簇
**理解公司实验基础设施** —— 为什么500个实验同时跑互不干扰。入职后你能看懂实验平台的配置、理解正交分流、知道为什么同一个用户可能同时在3个实验中

### 为什么今天重要
入职后你不会搭建实验平台——已经有现成的。但你需要在实验平台里配置实验参数(分流比例/流量层/指标)、阅读实验报告(理解为什么"这个用户在这个实验中")、排查问题(两个实验效果重叠)。今天理解正交哈希=理解实验平台底层。

### 具体知识清单

**1. 流量分层——同时跑500个实验的秘密**
- 问题：不分离→实验A和实验B的用户重叠→互相污染
- 解法：流量分成多层→每层独立分流→同一个用户在不同层分到不同组→层间互不干扰
- 用户A→推荐层=实验组、UI层=对照组、注册层=实验组。三个实验完全独立

**2. 正交哈希——实现层间独立**
- `hash(user_id + layer_name) % bucket_count`→每层不同种子→分配独立
- 验证：推荐层对照组中→UI层实验组≈50%、UI层对照组≈50%→独立！

**3. 实验平台数据流**
- 分流→行为日志(每用户+每层的组别)→指标计算→统计检验→可视化看板
- 平台自动做：样本量计算/AA/SRM/p值+效应量+CI/分群/校正→你只需要理解+审核

**4. 🔥入职后实验平台的实操问题（v6.1新增）**

今天学的是"实验平台怎么工作的"。但入职后你面对的不是"搭建平台"——是"用平台"。以下几个场景是你入职后100%会遇到的：

**4.1 怎么验证平台算对了**
- 入职第一周→做一次手动验证：从平台导一组实验数据→自己用Python跑t检验+p值+效应量→和平台显示的结果对比→如果不一致→要么你算错了（90%）要么平台配置有问题（10%）。两种情况都值得搞清楚
- 验证AA：平台自动跑AA→但你要会看AA结果→如果连续多天p<0.01→联系平台工程师排查分流逻辑

**4.2 怎么设计"实验平台改进需求"给工程团队**
- 入职场景：leader说"我们的实验平台少了XX功能，你写个需求文档给工程团队"
- 需求文档要素：①为什么需要（业务场景+频率）②功能描述（用户怎么用）③验收标准（怎么验证做对了）④优先级
- 示例需求："实验平台需要支持分群分析——按城市/会员等级/新老用户分别展示实验效果。因为每次实验PM都会追问'对不同用户效果一样吗'，现在每次手动导数据分群分析要花半天。验收：平台实验报告页增加'分群分析'Tab，至少支持按城市/会员等级/新老用户分群。"

**4.3 CUPED在平台里的三种实现——知道选哪个**
- 常规CUPED：用实验前7-30天的同一指标做协变量。平台默认开启
- 分层CUPED（Stratified CUPED）：先按协变量分箱→箱内调整。协变量是类别时（如会员等级）比常规CUPED更优
- ML CUPED（高级，了解即可）：用XGBoost等模型预测Y→残差做CUPED。方差缩小幅度更大但解释性更差
- 怎么选：看平台默认→一般默认常规CUPED就够了。如果实验前行为和实验期行为ρ<0.3→CUPED基本无效→关掉

**4.4 实验平台的使用边界——什么时候不能信平台**
- 平台自动计算的样本量→要检查是否用了正确的MDE
- 平台自动筛选的"显著指标"→可能是多重检验的结果→要看是否做了校正
- 平台的CUPED→检查协变量选择是否合理（是否用了实验后数据？）
- 平台报SRM→不要点"忽略"→排查原因（分流逻辑/数据管道/bot用户）
