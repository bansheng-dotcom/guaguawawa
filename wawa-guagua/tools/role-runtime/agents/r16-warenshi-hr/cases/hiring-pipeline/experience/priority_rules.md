# 优先级规则 · 招聘管道跃迁前置

## 判定顺序（不可跳步）

1. **录用前置状态 > 一切**
   `offer.status == Accepted 且 prior_status ∉ {Shortlisted, Accepted}` → **BLOCKER**，直接拒绝。
   拒绝话术只讲状态机，不讲"这候选人多优秀"。跳过筛选不存在"特殊情况"。

2. **工件必填 > 业务讨论**
   邮箱、录用日期、职位缺一不可。缺项直接拒绝，不进入"要不要录用"的讨论。

3. **流程跳步决定处置性质（跳步 vs 常规）**
   | 候选人状态 | 录用前置 | R16 动作 |
   |---|---|---|
   | Open / Replied | 不合法 | 拒绝，退回重走筛选 |
   | Shortlisted / Accepted | 合法 | 产出工件，单级授权 |
   | Hold | 异常态 | 先核对 Hold 原因，是合规暂停还是漏更新 |

4. **状态机只走白名单**
   Open → Replied → Shortlisted → Accepted 是合法管道；任何跳过 Shortlisted 直达 Accepted 的路径非法。

5. **对外发出必须人工**
   录用通知书对外发出是人工动作，R16 只产出工件 + 前置校验结论。

## 冲突取舍

- **用人部门"急着要人" vs 前置门禁**：前置门禁永远优先。跳步录用一律退回。
- **"候选人是熟人" vs 流程**：流程优先。熟人也要走完整管道，否则留痕不完整。
- **多角色诉求**：若同时要求"录用 + 定薪 + 签合同"，R16 只处理录用前置；定薪移交 R03/R01，合同移交 R03。

## 授权层级建议

| 录用场景 | 建议授权层级 |
|---|---|
| 常规 Shortlisted → Accepted | 用人部门负责人 |
| Open 直接录用（被拒后仍坚持） | 用人部门 + R01 决策 |
| 任何跳过筛选的录用 | 一律拒绝，不做授权讨论 |

## 常见误判清单

- 把 `Replied` 当成"已筛选"而发 Offer → 错，Replied 只是回复，未过筛选。
- 把 `Accepted` 候选人当成可重复录用而不校验 prior → 错，仍需 prior ∈ {Shortlisted, Accepted}。
- 用"用人部门已同意"替代 prior_status 校验 → 错，状态机是事实，口头同意不能替代状态迁移。
