## W12D1：数仓分层 + 维度建模

### 能力簇

### 为什么今天重要
你写的所有SQL都在数仓上跑。不理解数仓分层=不知道为什么有的表"每天8点才更新"、有的"实时的"、有的"只能查最近3个月"。不理解维度建模=不知道为什么"订单表有100列但还要Join用户表"、不知道"什么是事实表什么是维度表"。今天学完=你能看懂公司的数仓架构文档、能判断"这个分析该用DWD还是DWS"、能跟数仓工程师说清楚"我要一个什么样的表"。

### 具体知识清单

**1. 数仓为什么要分层——"每层解决一个特定的问题"**

**1.1 不分层有什么问题**
- 原始数据（业务系统的快照）有很多问题：重复（同一订单在不同时间被同步了两次）、脏数据（金额=负数/日期=1970）、格式不一致（同一产品在不同系统里名字不同）
- 如果每个分析都直接从原始数据查→每个人都要处理这些问题→重复劳动+口径不一致
- 如果只建"一张大宽表"→列数太多（几百列）→查询慢、存储浪费、维护混乱、上游变更下游全部崩溃

**1.2 四层分层的本质——"从下到上是不断GROUP BY+列筛选的过程"**
- **ODS（Operational Data Store，操作数据层）**：原始数据快照，几乎不做加工或只做基本清洗（统一编码、去明显的错误）。数据量和源系统一样→最全但最"脏"。用途：①数据回溯（如果下游出了问题,回到ODS重新处理）②审计（原始数据没被修改过）③新分析需要原始字段时
- **DWD（Data Warehouse Detail，数据仓库明细层）**：清洗后的明细数据。做了：去重、统一格式、维度退化（把"城市编码123"变成"北京"）、关联补充（把user_id关联到用户信息）。**粒度保持和ODS一样（一行=一条订单/一次行为）但更干净**。用途：①明细级别的分析（如"某用户的所有行为轨迹"）②作为DWS层的输入
- **DWS（Data Warehouse Summary，数据仓库汇总层）**：轻度聚合。如从DWD的"每次阅读行为"聚合到"每人每天阅读时长"。**粒度变粗了（一行=一个用户一天）但查询快得多**。用途：①日常分析（"昨天DAU多少""上周各品类GMV"）②作为ADS层的输入
- **ADS（Application Data Service，应用数据层）**：面向特定业务场景的报表/看板。如"CEO日报""渠道ROI周报""实验分析数据集"。**最面向业务、最方便使用**。用途：①直接给BI看板用②给PM/运营自助查询③给数据分析师做专题分析
- **核心认知**：数仓从下到上是不断GROUP BY的过程——ODS（原始明细）→DWD（干净明细）→DWS（GROUP BY到轻度汇总）→ADS（GROUP BY到最终报表）。每层"缩小"数据量和列的数量→越往上越快但粒度越粗

**1.3 每层的数据特征和SLA**
- ODS：数据量最大（TB级）、延迟最低（分钟级,跟在业务库后面同步）、保留时间最短（通常7-30天,因为太占空间）。SLA：每天8:00前产出昨天数据
- DWD：数据量略小于ODS（去重+清洗后）、延迟中等（小时级,需要等ODS产出+ETL清洗）。保留时间中等（1-3个月）
- DWS：数据量小得多（聚合后行数减少100-1000倍）、延迟中等。保留时间较长（6-12个月）
- ADS：数据量最小（只保留核心指标）、延迟根据业务需求（实时/小时/天）。保留时间最长（可能永久保留,因为CEO要对比历年数据）

**2. 维度建模——"怎么把表组织起来方便查询"**

**2.1 星型模型（Star Schema）——最常用**
- 结构：中间一张**事实表**（Fact Table），周围一圈**维度表**（Dimension Table）。像个星星→中间是事实,四周是维度
- 事实表（Fact）：存"发生了什么"。特点：行数极多（每条订单/每次行为一行）、列很多（各种度量值：金额/数量/时长）、列主要是数值和外键（user_id/product_id→关联到维度表）
- 维度表（Dimension）：存"描述这个东西是什么"。特点：行数较少（用户数远小于订单数）、列很多（用户的各种属性：年龄/性别/城市/注册日期/会员等级）、变化慢（用户改一次手机号一年也就一次）
- 为什么要拆成事实+维度：①存储效率（维度信息只存一次→不用每条订单都存一遍用户的全部信息）②更新效率（用户改了手机号→只改维度表一行→不需要把该用户的所有历史订单都改一遍）③查询效率（查询时先过滤维度表→再用主键去事实表取数→比直接扫一张几百列的大宽表快）
- 示例——电商订单星型模型：
  ```
  事实表: fact_orders (order_id, user_id, product_id, date_key, amount, quantity)
  维度表: dim_user (user_id, name, city, register_date, vip_level)
          dim_product (product_id, name, category, cost, price)
          dim_date (date_key, date, year, month, day, day_of_week, is_weekend)
  ```

**2.2 雪花模型（Snowflake Schema）——星型模型的规范化版**
- 结构：维度表本身也可以进一步拆分成多级。如dim_product里有category_id→关联到dim_category表（category_id, category_name, parent_category）。dim_city→关联到dim_province→关联到dim_country
- 优点：更"规范化"→消除冗余→存储更少。缺点：查询时需要更多JOIN→更慢。**互联网公司几乎不用雪花模型——查询慢的代价远大于存储成本**
- 选择：**永远用星型模型**。存储便宜,查询时间是瓶颈。面试中"星型vs雪花"→回答："星型,冗余换性能。互联网场景查询响应时间比存储成本更重要"

**2.3 事实表的三种类型——不同分析场景用不同事实表**
- **事务事实表（Transaction Fact）**：一行=一个事务（一条订单/一次行为）。最细粒度。用途：分析"每笔交易的明细"。示例：fact_orders,每行一个订单
- **周期快照事实表（Periodic Snapshot Fact）**：一行=一个实体在一个时间点的快照。如"每用户每天的行为汇总"。用途：看趋势和变化。示例：fact_user_daily(每人每天一行,含当日阅读时长/订单数/GMV)
- **累积快照事实表（Accumulating Snapshot Fact）**：一行=一个实体的整个生命周期。如"从下单到支付到发货到签收"。一行跟踪整个过程→每步完成后更新对应的日期列。用途：分析流程效率和瓶颈。示例：fact_order_fulfillment(每订单一行,含order_date/pay_date/ship_date/deliver_date)
- **入职场景**：你想分析"订单从下单到签收需要多久"→不能用事务事实表（它只记录"下单了"这一个事件→需要和支付表/发货表/签收表JOIN后才能算出时间差）。应该建一张"累积快照事实表"→每订单一行→有各个步骤的日期→直接一列相减

**3. 🔥SCD缓慢变化维度——"用户换了手机号,历史订单该显示新号码还是旧号码?"**

**3.1 SCD的类型**
- **Type 0（不处理）**：维度永不变化。适合"出生日期""身份证号"等不可变属性。操作：什么都不做
- **Type 1（覆盖）**：直接覆盖旧值。所有历史数据都显示"最新值"。适合"用户的昵称""商品的标题"等不怕追溯的字段。操作：`UPDATE dim_user SET phone='新号码' WHERE user_id=123`→所有历史订单关联到的都是新号码→追溯不了"当时用的什么号码"
- **Type 2（拉链表——最常用）**：保留所有历史版本。每一行有一个`start_date`和`end_date`→当前版本end_date=NULL（表示"当前"）。查询"某天的事实"→WHERE 事实日期 BETWEEN start_date AND end_date（或end_date IS NULL）。操作：INSERT新行(start_date=今天,end_date=NULL)+UPDATE旧行SET end_date=今天。代价：维度表会膨胀→但历史可追溯
- **Type 3（新增旧值列）**：只保留"当前值"和"上一个值"。增加一列`previous_phone`存旧值→只保留最近一次变化→更早的变化被覆盖。适合"你只关心最近一次变化"的场景

**3.2 怎么选？——业务需求决定**
- 需要追溯"当时用了什么"→Type 2。如CRM系统需要知道"发券时用户的手机号是什么"→如果被覆盖了就联系不上
- 不需要追溯"不重要"→Type 1。如用户的"收货地址"(每次下单都会重新填,历史订单已经有当时的地址了→维度表覆盖没关系)
- 只关心最近一次变化→Type 3

**3.3 Type 2拉链表的实现**
```sql
-- 新版本生效
UPDATE dim_user SET end_date = '2025-07-15' WHERE user_id = 123 AND end_date IS NULL;
INSERT INTO dim_user (user_id, name, phone, city, start_date, end_date) 
VALUES (123, '张三', '13900001234', '北京', '2025-07-15', NULL);
-- 查询"2025-06-01的用户信息"
SELECT * FROM dim_user WHERE user_id=123 AND start_date <= '2025-06-01' AND (end_date > '2025-06-01' OR end_date IS NULL);
```

**4. 入职后——你怎么跟数仓工程师提建表需求**
- 需求文档要素：①目的（这个表要回答什么业务问题）②粒度（一行代表什么：一个订单?一个用户一天?）③字段列表（字段名/类型/业务含义/来源表/来源字段）④分区策略（按什么分区：日期?城市?）⑤产出SLA（每天几点前产出/允许延迟）⑥数据质量要求（缺失率<1%/不允许重复/金额不能为负）
- **入职场景**：增长团队需要"每天各渠道的新用户量和7日留存"→你去数仓团队提需求→数仓问"粒度是什么"→你回答"一行=一个渠道一天（channel+date）。包含新用户数+7日留存用户数+7日留存率"。数仓问"数据源在哪"→你回答"DWD层有user_behavior_di表→其中register_channel字段=渠道,register_date字段=注册日期"。数仓确认→开发→上线→你验收

### 必须覆盖的陷阱
1. **星型模型 vs 雪花模型不是"哪个更好"**：互联网用星型（冗余换查询速度）。雪花适合"存储有限但查询不频繁"的传统数仓
2. **SCD Type 2会让维度表膨胀**：用户表原本100万行→每次变化新增一行→一年后可能300万行→查询时需要加end_date过滤→否则得到多行
3. **事实表粒度选错→分析能力被限制**：如果选了"用户天级别"(DWS)，无法回答"用户在各时段的分布"。粒度=你能分析的最细维度→选之前想清楚"需要分析什么"
4. **建表需求不写SLA→数仓开发完了你发现"数据每天早上10点才出来"→来不及做日报**：SLA必须事前约定

## W12D2：数仓协作实战 + SQL

### 能力簇
**成为"数据分析师→数仓工程师"桥梁** —— 入职后JD要求的"独立与数仓、研发对接，完成底层库表的开发与优化迭代"，就是今天的活。你不是数仓工程师（不需要写ETL代码），但你要会提需求、会验收、会沟通——让数仓工程师觉得"这个分析师懂行,沟通顺畅"。

### 为什么今天重要
入职后你最常跟两类人协作：PM/运营（业务方）和数仓/研发（技术方）。跟数仓协作不好→你提的需求工期排不上→你自己的分析没表可用→工作卡住。今天学的是"怎么提一个数仓工程师愿意接、能高效开发、验收不扯皮的需求"——这是入职后的核心生存技能。

### 具体知识清单

**1. 数据分析师←→数仓工程师的协作界面**

**1.1 你提需求（甲方），数仓开发（乙方）——协作中的典型问题**
- 需求不清晰："我要一个'用户分析表'"→数仓不知道你要什么粒度、什么字段→开发出来的不是你想要的→重新开发→双方都浪费时间
- 对数据源不熟悉："帮我从'用户表'取个字段"→数仓问"哪个用户表？ODS层的还是DWD层的？"→你不知道→数仓觉得你不专业
- 验收标准模糊：表建好了→你不知道怎么判断"数据对不对"→用了两周发现数据有问题→返工→双方都烦
- 变更频繁：表刚建好→PM说"再加5个字段"→过一周又说"再加3个"→数仓排期被打乱→你和数仓的关系紧张
- **怎么解决**：需求文档完整（粒度/字段/来源/分区/SLA/验收标准）、数据源熟悉（知道每个字段从哪张表来）、验收标准明确（知道"对"长什么样）、变更管理规范（集中评审→批量变更→不要散打）

**1.2 需求文档模板——入职后每次提需求都用这个格式**
```markdown
# 建表需求：{表名}

## 1. 业务目的
这个表要回答什么业务问题？谁会用？使用频率？（日/周/月）

## 2. 数据粒度
一行代表什么？（一个订单?一个用户一天?一个渠道一天?）
粒度越细=分析越灵活但查询越慢→折中选"能满足所有核心需求的最粗粒度"

## 3. 字段列表
| 字段名 | 类型 | 业务含义 | 来源表 | 来源字段 | 计算逻辑 | 备注 |
|--------|------|---------|--------|---------|---------|------|
| dt | string | 日期分区 | dwd_orders | order_date | — | 分区键 |
| user_id | string | 用户ID | dwd_orders | user_id | — | — |
| channel | string | 渠道 | dim_user | register_channel | — | 关联用户维度表 |
| order_cnt | bigint | 订单数 | dwd_orders | order_id | COUNT(DISTINCT) | — |
```

### 为什么今天重要

### 具体知识清单

**1. Hive vs MySQL——十个核心差异**

**1.1 架构差异**
- MySQL：单机架构→一台机器处理所有查询→数据量>千万行→开始吃力。有索引(B+Tree)→查询快。支持事务→数据一致性有保证
- Hive：分布式架构→数据存在HDFS上→查询被翻译成MapReduce/Tez/Spark任务→在多台机器上并行执行→可以处理PB级数据。**没有传统索引**→靠分区+分桶+ORC格式加速查询。**不支持单行UPDATE/DELETE**→用INSERT OVERWRITE覆盖整个分区
- **为什么Hive不支持单行UPDATE**：单行更新=需要找到那行+修改+写回→在分布式存储(HDFS)上代价极大（HDFS不擅长随机写）。Hive的设计哲学="批量处理,不是在线事务"

**1.2 HiveQL特有语法**
- `LATERAL VIEW EXPLODE(array_col)`：把数组(ARRAY)展开成多行。如用户的"搜索关键词"存为`['Python','SQL','AB实验']`→EXPLODE后变成3行→和SQL的`UNNEST`概念一样
- `get_json_object(json_col, '$.path')`：从JSON字符串中提取字段。互联网的埋点日志大多JSON→这个函数是解析埋点的核心工具
- `COLLECT_LIST(col)` / `COLLECT_SET(col)`：把多行聚合成一个数组（列转行）。COLLECT_SET自动去重
- `TRANSFORM`：嵌入自定义脚本(Python/Shell)→类似MapReduce中的Map→适合复杂转换
- `INSERT OVERWRITE TABLE ... PARTITION(dt='2025-07-15')`：覆盖指定分区的数据（相当于删除旧数据+插入新数据）。没有WHERE条件=覆盖全表→**极危险！**
- **陷阱：INSERT OVERWRITE没有任何确认→不会说"你确定吗"→执行就覆盖→数据永久丢失**。如果要保护→加`IF EXISTS`检查

**1.3 分区与分桶——Hive加速的核心机制**
- **分区(PARTITION BY)**：数据按分区键的值放在不同目录→查询时只读相关目录→跳过99%的数据。例如按日期分区→`WHERE dt='2025-07-15'`→只读`/warehouse/orders/dt=2025-07-15/`这一个目录→其他364个目录直接跳过
- **分区键的选择**：查询中最常过滤的列。通常是日期→90%的查询都会过滤日期范围。**不要选"高基数"的列做分区键**（如user_id→几十万个分区→每个分区只有几行→目录爆炸→小文件问题）
- **动态分区(DPP)**：自动根据数据内容创建分区。`INSERT OVERWRITE TABLE orders PARTITION(dt) SELECT ..., dt FROM ...`→Hive自动为每个dt值创建分区。**陷阱：如果数据有1000个不同的dt→瞬间创建1000个分区→如果数据倾斜→单个Reduce处理大量数据→OOM**
- **分桶(CLUSTERED BY)**：同一分区内按hash值分成多个文件→主要用于两个大表做SMB JOIN(两个表桶数相同或倍数关系→JOIN在Map端完成→无需Shuffle→极快)。**分桶数选择**：桶数=数据量/每个文件的目标大小。如100GB数据→每文件1GB→100个桶

**2. 🔥数据倾斜——"一个Reduce卡在99%,其他都跑完了"**

**2.1 什么是数据倾斜**
- Hive的查询被翻译成MapReduce→Map阶段（拆分数据）→Shuffle阶段（按键重新分配）→Reduce阶段（聚合）。如果某个Key的数据量远大于其他Key→处理这个Key的Reduce节点成为瓶颈→整个任务卡在"99%"
- 为什么互联网数据容易倾斜：用户行为天然服从幂律分布→Top10城市贡献80%订单→少量Key占巨量数据

**2.2 倾斜的三现象——看到这些就诊断"数据倾斜"**
1. 任务进度卡在99%不动→只剩一两个Reduce在跑
2. 某个Reduce的输入数据量远大于其他Reduce（GB vs MB）
3. 某个Reduce的GC时间异常（垃圾回收频繁→内存不够）→甚至OOM杀掉容器

**2.3 倾斜的三解法——从根因到解决**
- **解法1-加盐(Salting)**：给倾斜的Key加随机后缀→打散到多个Reduce→聚合完再去后缀再聚合一次。适用：GROUP BY倾斜。例如：北京的数据有500万条→其他城市平均5万条→北京那个Reduce卡住。加盐：北京_1,北京_2,北京_3...→打散到10个Reduce→每个50万条→不再卡。然后再聚合"北京_1+北京_2+..."→得到真正的北京值
- **解法2-MAPJOIN**：如果一张表很小（<25MB）→把它全量加载到每个Map的内存中→在Map端完成JOIN→完全不需要Reduce（也不需要Shuffle）→**最快**。适用：大表JOIN小表。例如：订单表(10亿行)JOIN城市表(300行)→城市表全量进内存→Map端直接关联→没有Shuffle→没有倾斜
- **解法3-两阶段聚合**：先局部聚合缩小数据量→再全局聚合。适用：GROUP BY倾斜且不能加盐(如需要精确COUNT DISTINCT)。第一阶段：加随机数+部分聚合。第二阶段：去随机数+全局聚合

**2.4 Hive的倾斜优化参数（平台已经内置）**
- `hive.optimize.skewjoin=true`：自动检测倾斜Key→单独处理→不再卡
- `hive.groupby.skewindata=true`：GROUP BY倾斜时→自动两阶段聚合
- `hive.auto.convert.join=true`：自动把小表转MAPJOIN（不用手动写hint）

**3. 🔥小文件问题——"每个文件只存几百KB→产生几百万个文件"**
- 问题：如果Hive表有太多小文件（每个几百KB→不是每个几百MB）→MR需要为每个文件启一个Map→几百万个Map→任务调度的开销远超实际计算→极慢
- 原因：①频繁INSERT小批量数据②分区过细（每天一个分区但每天的数据只有几MB）③Reduce数设得太多（每个Reduce输出一个文件）
- 解决：①合并小文件：`ALTER TABLE ... CONCATENATE`（合并ORC文件）②控制Reduce数量：`SET mapreduce.job.reduces=10`（不设太多）③定期合并分区：每周把过去7天的小文件合并成几个大文件

**2. 监督学习——有"标签"的学习**
- 有标签=数据里已经知道"正确答案"。如给10万张图片→每张标注了"是猫/不是猫"→训练一个"识别猫"的分类器。给10万条用户数据→每条标注了"是否付费"→训练一个"预测付费概率"的分类器
- **分类 vs 回归**：分类=预测类别(是/否、A/B/C)。回归=预测连续值(金额/时长/概率)。推荐系统的核心=分类("用户是否点击/是否喜欢")
- **线性回归**（入门）和**逻辑回归**（分类）：你的第一行ML代码：
  ```python
  from sklearn.linear_model import LogisticRegression
  model = LogisticRegression()
  model.fit(X_train, y_train)  # 训练
  predictions = model.predict_proba(X_test)[:, 1]  # 预测"购买概率"
  # 3行代码跑完你的第一个ML模型
  ```

**3. 训练/验证/测试集——为什么要分三份**
- 训练集（Training, 60%）：模型"学习"的数据→拟合模型参数
- 验证集（Validation, 20%）：调超参数→选最好的模型版本
- 测试集（Test, 20%）：最终评估模型的泛化能力→**只在最后用一次**
- 为什么分三份：①只用训练集评估→模型"记住了训练数据"→评估结果虚高→上线后泛化差②用训练+测试两份→调参时你反复用测试集评估→测试集"被污染"→失去了"独立评估"的意义→分三份→验证集用于调参→测试集只在最终用一次→保证评估无偏
- **入职场景**：算法团队汇报"测试集上AUC=0.82"→你问"训练集AUC多少？"→如果训练集AUC=0.98、测试集=0.82→差距很大→可能过拟合。"验证集用来调参了吗？"→是的→"那测试集只用了一次吗？"→是的→评估可信

**4. 过拟合 vs 欠拟合——ML最核心的诊断**
- **过拟合（Overfitting）**：模型"记住了训练数据"→训练集上表现出色但在测试集/新数据上表现差。就像学生"背了题库"→考试出原题=满分→题一变=不会。症状：训练集AUC≈0.99、测试集AUC=0.75（差距大）。原因：模型太复杂(树的深度太大/特征太多)→"记"了太多训练集的噪声
- **欠拟合（Underfitting）**：模型太简单→连训练集上的规律也学不会。症状：训练集AUC=0.65、测试集AUC=0.64（都低,差距小）。原因：模型太简单/特征太少→不足以捕捉数据中的规律
- **偏差-方差权衡**：简单模型→高偏差(欠拟合)+低方差。复杂模型→低偏差+高方差(过拟合)。最优=平衡点
- **入职场景**：算法团队说"模型在测试集上效果不好"→你问"训练集效果怎么样"→"训练集也不好"→欠拟合→建议加特征/换更复杂的模型。"训练集很好但测试集差"→过拟合→建议正则化/减少特征/增加训练数据

**5. 决策树直觉——最直观的ML模型**
- 决策树=一系列"if-else"规则。如"年龄<25?→是→学生?→是→预测会购买(YES)"。"年龄≥25?→收入>5000?→是→预测不会购买(NO)"
- 优点：可解释性强→每个分支都能用白话解释→适合"给PM解释模型为什么推荐这个"。缺点：容易过拟合（树太深=规则太多=记住了训练数据的噪声）

### 具体知识清单

**1. 🔥XGBoost/LightGBM——工业界表格数据的王者（30分钟）**

**1.1 为什么XGBoost统治了表格数据**
- 逻辑回归：简单、可解释、但只能捕捉线性关系
- 决策树：能捕捉非线性、但单棵树容易过拟合
- 随机森林：多棵树投票→减少过拟合→但"随机"部分限制了优化方向
- **XGBoost（eXtreme Gradient Boosting）**：一棵接一棵地"修正前一棵的错误"→每棵新树专门学习"前面的树预测不好的地方"→逐步逼近→精度比随机森林高
- **和随机森林的核心区别**：随机森林=多棵树并行训练→投票。XGBoost=树串行训练→每棵树"修正"前一棵的残差→像"一个学生不断改错题"。串行=不能并行训练→但每棵树更精准
- **LightGBM**：微软出的XGBoost竞品→速度更快（使用直方图加速）→内存占用更少→大数据集上比XGBoost快。**面试金句**："XGBoost精度略高，LightGBM速度更快。数据量<100万→XGBoost。数据量>1000万→LightGBM。不确定→XGBoost（更成熟/社区更大）"
- Python三行代码：
  ```python
  from xgboost import XGBClassifier
  model = XGBClassifier(n_estimators=100, max_depth=5, learning_rate=0.1)
  model.fit(X_train, y_train)
  # XGBoost自动处理缺失值、自动特征重要性排序、不需要特征缩放
  ```

**1.2 XGBoost的优势——为什么面试爱问**
- ①自动处理缺失值：XGBoost在训练过程中"学习"缺失值该走树的左边还是右边→不需要手动填充
- ②内置正则化：防止过拟合的效果比随机森林更好
- ③特征重要性：`model.feature_importances_` → 直接告诉你"哪个特征对预测最重要"
- ④不需要特征缩放：树模型基于"分割点"→不受量纲影响→不用StandardScaler
- ⑤GPU加速：`tree_method='gpu_hist'` → 大数据集上快10倍

**1.3 什么时候不用XGBoost**
- 数据全是类别特征（如"城市/性别/会员等级"）→有时简单模型就够了
- 需要强解释性（给监管机构解释）→逻辑回归
- 深度学习擅长的领域（图像/文本/NLP）→XGBoost不适用于非结构化数据

**2. 🔥聚类——DA做用户分群的基础工具（30分钟）**

**2.1 K-means——最常用的聚类算法**
- 原理：指定K个群→随机选K个中心→每个点归属最近的中心→重新计算每个群的中心→重复直到稳定
- `from sklearn.cluster import KMeans`
- 关键参数：`n_clusters=K`。K怎么选？→**肘部法则**：依次K=2,3,4,...→画K-惯性曲线→找"拐点"（增加K带来的改善开始变缓）
- **业务应用**：RFM的下一层——"把用户聚成4类→高价值/中价值/低价值/流失风险→每类不同运营策略"
- **陷阱1：K-means假设群是球形的（各方向方差相同）→对"长条形"的群效果差**
- **陷阱2：K-means对初始中心敏感→不同初始值可能收敛到不同结果→用`n_init=10`多轮取最优**
- **陷阱3：K-means要求数值型特征→类别特征需要先做独热编码**

**2.2 层次聚类（Hierarchical Clustering）——不需要提前指定K**
- 两种方式：①凝聚(自底向上)：每个点自己一个群→逐步合并最相似的群→直到只剩一个群。②分裂(自顶向下)：全数据一个大群→逐步拆分
- 输出——**树状图(Dendrogram)**：横轴=样本，纵轴=距离。在某个高度"切一刀"→得到对应数量的群
- **什么时候用层次聚类**：①不确定K是多少→看树状图决定②想看到"群之间有多远"的层次结构③数据量不大（<5000，复杂度O(n²)）
- **什么时候用K-means**：①已知道大概几个群（业务说了要分3-5类）②数据量大③追求速度

**2.3 DBSCAN——能发现任意形状的群**
- 不需要指定K→指定"多少距离算邻居(eps)"和"至少几个邻居算核心点(min_samples)"
- 优点：①能发现非球形群（如环形/弯月形）②自动标记"噪声点"（不属于任何群的点）→天然支持异常检测
- 缺点：①eps参数需要调（可以用k-distance图辅助）②密度差异大时效果差③高维数据上效果差（"维度灾难"→距离在高维空间不再有区分度）
- **业务应用**：异常检测——"哪些用户的行为和其他人都不一样？"→DBSCAN标记为噪声

**2.4 聚类在DA工作中的应用全景**
- 用户分群：RFM→聚类→4-6类→每类画像+运营策略
- 异常检测：识别行为异常的用户/订单（作弊/刷量/系统故障）
- 探索性分析：拿到新数据→先聚类→看"数据天然分成几类"→帮助理解数据结构
- 特征工程：把"用户属于哪个群"作为特征→输入到下游的预测模型

**3. 🔥SHAP——给PM解释"模型为什么这样预测"（20分钟）**

**3.1 为什么需要SHAP**
- 逻辑回归→每个特征的系数直接可解释（"年龄加1→购买概率增加β"）。但XGBoost→100棵树×每棵6层→完全黑盒→PM问"为什么推荐这本书给我"→你不能说"因为模型预测你会喜欢"→PM:"为什么模型预测我会喜欢？"→SHAP能回答
- **面试高频问题**："模型预测用户不会付费，你怎么跟PM解释？"→标准答案=SHAP

**3.2 SHAP的核心思想**
- SHAP值=每个特征对**这一个预测**的贡献。正值→推高了预测（让模型更倾向"会付费"）。负值→拉低了预测（让模型更倾向"不会付费"）
- `import shap` → `explainer = shap.TreeExplainer(model)` → `shap_values = explainer.shap_values(X)` → `shap.summary_plot(shap_values, X)` → 看每个特征的整体重要性
- 单个预测的解释：`shap.force_plot(explainer.expected_value, shap_values[0], X.iloc[0])` → 看"这一个样本为什么被预测为0.8"
- **业务应用**：
  - 用户A被预测"不会付费"→SHAP显示"最近7天登录次数=0"拉低了20%、"历史消费=0"拉低了15%→"因为这是新用户且最近没登录→模型认为付费概率低"
  - 用户B被预测"会付费"→SHAP显示"历史消费=5000"推高了30%→"因为过去花了很多钱→模型认为付费概率高"

**3.3 SHAP vs 特征重要性**
- 特征重要性：全局的，"这个特征在整个数据集上平均贡献了多少"
- SHAP：局部的，"这个特征对这个特定样本贡献了多少"
- 例子：整体看"年龄"不重要（特征重要性低）。但对特定用户（18岁，学生）→"年龄"非常重要→SHAP能捕捉这种"局部效应"

**4. 🔥特征工程——决定了模型80%的效果（20分钟）**

**4.1 为什么特征工程比模型选择更重要**
- "数据和特征决定了机器学习的上限，模型和算法只是逼近这个上限而已"
- 给XGBoost喂"原始数据"→AUC=0.72。加了几个好的特征→AUC=0.80。换更复杂的模型→AUC=0.81。**特征工程的收益远大于换模型**

**4.2 类别特征编码**
- **独热编码（One-Hot Encoding）**：每个类别→一列0/1。"北京/上海/深圳"→三列(Is_北京/Is_上海/Is_深圳)。`pd.get_dummies(df['城市'])`。优点：简单。缺点：类别多时列数爆炸(100个城市=100列)
- **标签编码（Label Encoding）**：每个类别→一个数字。"北京→0,上海→1,深圳→2"。优点：不增加列数。缺点：模型会认为2>1>0（"深圳>上海>北京"）→对线性模型有误导（树模型无所谓）
- **目标编码（Target Encoding）**：用目标变量(Y)的均值替代类别。"北京→北京用户的平均付费率=0.12"。`df.groupby('城市')['付费'].transform('mean')`。优点：信息量大。缺点：容易过拟合（需要正则化/smoothing）

**4.3 数值特征处理**
- **标准化（Standardization）**：`(X-mean)/std`。适合：线性模型、K-means、PCA。不适合：树模型（树模型不在乎量纲）
- **归一化（Normalization/MinMax）**：`(X-min)/(max-min)`。缩放到[0,1]。适合：神经网络、需要固定范围的场景
- **分箱（Binning）**：连续值→类别。"年龄0-18/18-30/30-50/50+"。`pd.cut(df['年龄'], bins=[0,18,30,50,100])`。优点：捕捉非线性关系+可解释性强。缺点：丢失信息
- **对数/平方根变换**：`np.log(df['金额'])`。为什么：偏态数据→对数变换→接近正态→对线性模型有帮助。树模型不需要

**4.4 特征交叉（Feature Crossing）**
- 两个特征组合成新特征→捕捉交互效应。"城市×品类"→"北京+数码""上海+数码""北京+运动"...
- 为什么：单看"北京"和"数码"各自有用，但"北京+数码"的购买概率可能远高于单独的两者之和→特征交叉捕捉这种"组合效应"
- 实现：`df['city_category'] = df['城市'] + '_' + df['品类']` → 再独热编码

**4.5 时间特征**
- 从时间戳提取：`df['hour']`(时段), `df['dayofweek']`(周几), `df['is_weekend']`(周末), `df['is_holiday']`(节假日)
- "距上次行为的间隔"：`df.groupby('user_id')['timestamp'].diff()` → 行为间隔→用户活跃度的重要信号
- "过去N天的行为计数"：`df.groupby('user_id').rolling('7D').count()` → 近期活跃度

**4.6 🔥特征缩放全矩阵——选错=模型失效（v6.1补全）**

前面讲了标准化和归一化，但面试中常问"什么时候用哪个"。特征缩放的完整决策表：

| 方法 | 公式 | 输出范围 | 对异常值 | 适用模型 | 不适用模型 |
|------|------|---------|---------|---------|-----------|
| **StandardScaler** | (X-μ)/σ | 均值0方差1 | 敏感 | 线性模型/PCA/K-means/SVM | 树模型 |
| **MinMaxScaler** | (X-min)/(max-min) | [0, 1] | 极敏感 | 神经网络/需要固定范围 | 有异常值的数据→范围被极端值压缩 |
| **RobustScaler** | (X-median)/IQR | IQR归一化 | **鲁棒** | 有异常值的场景+线性模型 | 小样本(IQR不稳定) |
| **PowerTransformer** | Box-Cox/Yeo-Johnson | 接近正态 | 较鲁棒 | 偏态数据→正态化后给线性模型 | 已经是正态的数据 |
| **QuantileTransformer** | 映射到指定分布 | 均匀/正态 | **最鲁棒** | 需要完全消除偏态（如收入/销售额）| 数据量小时分位不稳定 |

```python
from sklearn.preprocessing import StandardScaler, MinMaxScaler, RobustScaler
from sklearn.preprocessing import PowerTransformer, QuantileTransformer

# 对比三种Scaler在"有异常值的数据"上的表现
X = df[['金额']].values  # 金额有严重右偏和极端值

# StandardScaler → 被极端值压缩（大部分数据挤在-0.5~0.5之间）
# RobustScaler → 大部分数据在-2~2之间 → 更适合

# Box-Cox = 仅正数（最常用）
pt_boxcox = PowerTransformer(method='box-cox', standardize=True)
# Yeo-Johnson = 可处理负数/零（更通用）
pt_yeo = PowerTransformer(method='yeo-johnson', standardize=True)

# QuantileTransformer → 极端值完全不影响分布形状
qt = QuantileTransformer(output_distribution='normal', n_quantiles=100)
```

**4.7 🔥PCA载荷图（Biplot）——降维后的特征解释（v6.1补全）**

W12D4.5的聚类部分没讲PCA的"载荷"如何解读。PCA不只是降维工具——更重要的是**理解每个主成分代表什么**。

- **载荷（Loading）**：原始特征与主成分的相关系数。载荷的绝对值越大→该特征对该主成分越重要
- **Biplot**：把样本投影到PC1×PC2空间，同时把"特征向量"（载荷）画成箭头——一个图里同时看到"样本怎么分布"和"哪些特征推动了这个分布"
```python
from sklearn.decomposition import PCA

pca = PCA(n_components=0.95)
X_pca = pca.fit_transform(X_scaled)

# 载荷矩阵
loadings = pd.DataFrame(
    pca.components_.T,
    columns=[f'PC{i+1}' for i in range(pca.n_components_)],
    index=feature_names
)

# 画Biplot——看哪些特征在PC1/PC2上最重要
fig, ax = plt.subplots(figsize=(10, 8))
for i, feature in enumerate(feature_names):
    ax.arrow(0, 0, loadings.iloc[i, 0]*3, loadings.iloc[i, 1]*3,
             head_width=0.05, fc='steelblue', ec='steelblue', alpha=0.7)
    ax.text(loadings.iloc[i, 0]*3.3, loadings.iloc[i, 1]*3.3, feature)
ax.axhline(y=0, color='gray', ls='--', alpha=0.5)
ax.axvline(x=0, color='gray', ls='--', alpha=0.5)
ax.set_xlabel(f'PC1 ({pca.explained_variance_ratio_[0]:.1%})')
ax.set_ylabel(f'PC2 ({pca.explained_variance_ratio_[1]:.1%})')
ax.set_title('PCA载荷图——哪些特征定义了主成分', fontsize=14, fontweight='bold')
```
- **面试考点**："PCA做完后怎么解释每个主成分？"→"看载荷矩阵→载荷最高的特征决定主成分的含义。如PC1上'消费金额''购买次数'载荷高→PC1≈'消费能力因子'"

```python
# 判断：点在直线上=残差正态→t检验/CI有效
# 问题信号：尾部翘起=厚尾/一端偏离=偏态

# 3. 实际值 vs 预测值 → 整体拟合质量
axes[2].scatter(y_test, y_pred, alpha=0.5, edgecolors='white')

# 判断：点在对角线附近→预测准
# 问题信号：系统性偏离对角线/某区域预测差(模型在该区域失效)

plt.tight_layout()
```

### 具体知识清单

**1. 分类模型的评估指标——不是"准确率"越高越好**

**1.1 准确率的陷阱——"预测全员不付费→准确率90%"没有任何意义**
- 如果100个用户中只有10个付费→模型A"预测所有人都不付费"→准确率=90%→但漏了所有付费用户→毫无价值。模型B只预测对了5个付费用户→准确率=85%→但至少抓住了5个付费用户→更有用
- **准确率只看"所有预测中对了多少"→在样本不均时完全误导**

**1.2 混淆矩阵——四种结果**
- TP(真阳性)=预测会付费+真的付费了（正确的预测）
- FP(假阳性)=预测会付费+实际没付费（误报,浪费了给"假付费用户"发券的成本）
- FN(假阴性)=预测不会付费+实际付费了（漏报,错过了一个真付费用户）
- TN(真阴性)=预测不会付费+实际没付费（正确的预测）

**1.3 精确率(Precision)和召回率(Recall)——两种不同的"准确"**
- **精确率=TP/(TP+FP)**："在你说'会付费'的人里,有多少真的付费了"。精确率高=你推荐的人"基本都对"→不会浪费资源在"不会付费的人"上
- **召回率=TP/(TP+FN)**："在所有真的付费的人里,你抓住了多少"。召回率高=你不会漏掉付费用户→"把所有可能付费的人都抓到了"
- **精确率和召回率是trade-off**：你想提高精确率→少推荐→只推荐最确定的→召回率下降。你想提高召回率→多推荐→覆盖更多人→精确率下降
- 什么时候优先精确率：推荐成本高(如给用户发大额优惠券)→不能浪费→精确率优先。什么时候优先召回率：漏掉代价大(如疾病筛查→漏掉一个患者=严重后果)→召回率优先

**1.4 F1-Score——精确率和召回率的调和平均**
- F1=2×(Precision×Recall)/(Precision+Recall)。当两者不平衡时→F1给你一个综合分数

**1.5 🔥AUC-ROC——最重要的分类模型评估指标**
- ROC曲线：横轴=FP率(误报率,1-特异性)→纵轴=TP率(召回率,敏感性)。曲线上每个点=一个阈值。AUC=曲线下的面积=0到1之间的值
- AUC=1→完美预测。AUC=0.5→和随机猜测一样→没用。AUC=0.7→说得过去。AUC=0.8→不错。AUC=0.9→优秀
- **AUC的业务翻译**：AUC=0.8→"随机选一个真付费用户和一个未付费用户→模型给真付费用户更高'付费概率'的概率是80%"
- **AUC的局限**：在极度不平衡的数据中(如付费率只有0.1%)→AUC看起来很好(0.9)但精确率可能极低(大部分"预测付费"都是错的)→同时看PR曲线
- PR曲线：Precision-Recall曲线→在不平衡数据中比ROC更敏感

**1.6 为什么不同场景该看不同的指标**
- 推荐系统（猜你喜欢）：精确率重要（推错了=用户反感）。同时看召回率（别漏掉用户真正喜欢的）
- 反欺诈（识别作弊订单）：召回率最重要（漏掉一个=公司损失）。代价：可能误判一些正常订单→需要人工复核
- 流失预警（预测谁会流失）：召回率重要（漏掉一个=失去一个用户）。代价：可能给一些不会流失的用户发券→精确率低=浪费一些券

**2. 🔥推荐系统——字节/小红书最核心的ML应用**

**2.1 推荐系统的三种基本方法**
- **协同过滤（Collaborative Filtering）**："用户A和用户B都喜欢看书A和B→用户A还喜欢书C→推荐书C给用户B"。基于"相似用户喜欢相似东西"的假设。优点：不需要理解内容。缺点：新用户/新物品无数据（冷启动）
- **内容推荐（Content-Based）**："用户喜欢'玄幻小说'→推荐更多玄幻小说"。基于"物品本身的特征"（类型/作者/标签）。优点：没有冷启动问题（新物品也能推荐,只要有标签）。缺点：推荐范围窄→"你一直看玄幻→只推荐玄幻→看不到其他类型"
- **混合推荐**：协同+内容结合→取长补短。字节/快手/YouTube都在用混合推荐

**2.2 冷启动——推荐系统的经典难题**
- 新用户冷启动：用户刚注册→没有任何行为数据→不知道他喜欢什么→怎么推荐？解法：①热门推荐(推荐大家都在看的东西→可能命中)②注册时选兴趣标签→用标签做内容推荐③用设备/地域信息(同城市同年龄的人喜欢什么)
- 新物品冷启动：一本新书上架→没有人看过→不知道谁喜欢→怎么推荐出去？解法：①基于标签推荐给"对同类书籍感兴趣"的用户②给新物品"探索流量"(Explore→主动推荐给部分用户→收集反馈→优化推荐)
- **入职场景**：算法团队说"新用户留存低,因为冷启动推荐不准"→你分析→新用户冷启动推荐的CTR只有老用户的30%→原因是新用户无历史行为→协同过滤无效→建议：①加强注册时的兴趣标签引导(让更多新用户选标签→内容推荐有输入)②把"热门书籍"作为冷启动默认推荐→"什么都不了解时→推荐大家都在读的→至少不会太差"

**2.3 Explore vs Exploit——推荐系统的永恒矛盾**
- Exploit（利用）：推荐系统"已知用户喜欢的"→推荐大概率会被点击的内容→短期指标好但长期无惊喜
- Explore（探索）：推荐系统"尝试用户没看过但可能喜欢的"→冒一定的"用户不点击"的风险→收集新反馈→更新对用户的理解→长期改善推荐效果
- **为什么需要Explore**：如果一直只推荐同类内容→用户会觉得"推荐太窄"→对平台失望→长期留存下降。Explore=给推荐系统"尝试新东西"的机会
- **AB实验中的Explore**：实验组可以调高Explore比例(如从5%→10%)→看"推荐多样性"提升→短期CTR可能微降→但长期留存提升
- **入职场景**：你分析推荐效果→发现"推荐CTR很高但用户30日留存在下滑"→诊断：推荐系统在过度Exploit→只推"保险的"内容→用户觉得单调→流失→建议：增加Explore比例→推荐更多样的内容→做AB实验验证→看长期留存是否改善

**3. 🔥深度学习推荐入门——字节面试必问（v6.1新增）**

传统推荐方法（协同过滤/内容推荐）是主流，但字节/快手/抖音的核心推荐系统早已升级到深度模型。面试时用"协同过滤"回答推荐系统→面试官会追问"深度模型呢"。你不训练模型，但你要理解概念——因为算法团队跟你沟通时用的就是这些概念。

**3.1 Embedding——把一切变成向量**
- **核心直觉**：用户和内容都被表示成一个"向量"（一串数字，比如256个float）。向量之间的距离=相似度。距离近=相似→推荐。距离远=不相似→不推荐
- **类比**：把每个用户、每本书放在一个"多维空间"里。喜欢玄幻的用户聚集在空间的一角、喜欢悬疑的用户聚集在另一角。《斗罗大陆》的向量和"玄幻用户"的向量距离很近→推荐。这和协同过滤本质一样——但Embedding的"距离"能捕捉比"同时购买过"更丰富的信号
- **怎么得到Embedding**（知道概念就够了）：
  - 早期方法（Word2Vec）：从文本中学习→"经常出现在相似上下文中的词→向量相近"
  - 推荐系统（双塔模型）：一个塔把用户特征"压缩"成向量→另一个塔把内容特征"压缩"成向量→两个向量内积=预测的"用户会喜欢的概率"
- **面试金句**："Embedding把离散的用户和内容特征映射到连续向量空间→相似用户/内容的向量距离近→推荐就变成了'找最近邻居'。和协同过滤的区别是：协同过滤只看行为、Embedding能融合行为+内容+上下文多种信号。"

**3.2 双塔模型（Two-Tower Model）——工业界推荐系统的事实标准**
- 为什么叫"双塔"：用户塔（User Tower）→把用户的所有特征（年龄/性别/历史行为/最近浏览）压缩成一个向量。内容塔（Item Tower）→把内容的所有特征（标题/品类/作者/长度）压缩成一个向量。两个向量求内积→得分→得分高=推荐
- **为什么用双塔**：①两个塔可以独立计算→内容塔的向量可以离线预计算（每天更新一次）→线上只需要算用户塔→快速 ②用户塔在线、内容塔离线→可以支撑百万级QPS
- **和协同过滤的关系**：协同过滤=早期的"单塔"→只用了行为数据→捕捉"用户-物品的交互模式"。双塔=可以融合更多信号（用户侧：行为+人口统计+场景。内容侧：标签+文本+作者+时长）→效果远超协同过滤
- **入职场景**：算法团队说"我们升级了用户塔，加入了'最近5分钟行为序列'特征→AUC提升了1.5pp"。你不需要知道怎么设计塔——但你要听懂这句话，并且能设计AB实验来验证这个升级对业务指标的实际影响

**3.3 NLP在内容理解中的应用——字节/小红书的内容推荐为什么好**
- **分词**：把"玄幻小说斗罗大陆"→["玄幻","小说","斗罗","大陆"]。中文NLP的第一步
- **TF-IDF**：一个词的"重要性"=在这篇文章里出现得多×但在所有文章里出现得少。"的"在所有文章里都出现→不重要。"双塔"只在ML文章里出现→对识别技术文章很重要
- **BERT/语言模型**（知道概念即可）：传统方法把"苹果"映射为一个向量→不管上下文。"苹果很好吃"vs"苹果发布了新iPhone"→同一个"苹果"但含义完全不同→BERT能根据上下文生成不同的向量→比传统方法强很多
- **为什么DA需要知道这些**：内容推荐模型用"BERT生成的文本向量"作为Item Tower的输入特征→BERT越强→内容理解越准→推荐越准→留存/时长越好。这不是你的工作——但理解这个链路=能和算法团队对话。算法团队说"文本特征要升级到新版BERT"→你能听懂为什么这会影响推荐效果

**3.4 传统ML vs 深度推荐——选择决策表**
| 维度 | 传统ML（协同过滤/逻辑回归） | 深度学习（双塔/BERT） |
|------|------------------------|------------------|
| 信号来源 | 只用行为（用户×物品的交互历史） | 行为+内容+上下文+序列 |
| 效果 | 中等（AUC 0.7-0.8） | 较好（AUC 0.8-0.95） |
| 计算量 | 低 | 高（需要GPU） |
| 可解释性 | 较好（"因为你喜欢X"） | 较差（"因为向量距离近"→听不懂） |
| 什么时候够用 | 中小规模/行为数据丰富/内容特征少 | 海量用户+内容/行为稀疏/内容理解重要 |
| DA需要做的 | 评估模型效果+设计AB实验 | 同左+理解特征升级对业务的影响 |

**3.5 面试怎么聊推荐系统**
- 面试官："你对推荐系统有什么了解？"
- 错误回答："就是协同过滤，根据相似用户的喜好推荐"→不全面
- 正确回答："推荐系统从协同过滤发展到现在的深度模型。核心思想是把用户和内容映射到向量空间→向量相似=推荐。工业界常用双塔架构——用户塔在线计算、内容塔离线预计算→融合用户行为+内容文本+场景等多维信号。作为一个DA，我的角色是评估推荐模型升级的业务效果——把AUC的提升翻译成DAU/留存/GMV的增长，通过AB实验验证。同时关注推荐在不同用户群的效果差异、冷启动问题、Explore-Exploit的平衡。"
- **如果面试官追问"双塔模型的用户塔可以加入什么特征"**："用户塔可以加入四类特征：①人口统计特征（年龄/性别/地域）②历史行为特征（过去N天浏览/点击/购买序列）③实时行为特征（最近5分钟的行为→捕捉即时兴趣）④上下文特征（时段/设备/网络类型）。内容塔可以加入：①标签/品类/作者 ②文本Embedding（比如用BERT生成的标题向量）③内容消费特征（平均阅读时长/完播率）。两个塔独立计算→最后内积得到预测分数。"

## W12D6：分析师如何配合算法团队 + 周项目

### 能力簇
**算法团队的"数据翻译官"** —— 把算法指标(AUC/特征覆盖)翻译成业务语言、把业务需求翻译成算法可理解的特征需求。入职后你不是写推荐算法的人——你是"让推荐算法更好服务业务"的人。

### 具体知识清单

**1. 分析师的三个角色**
- **效果评估者**：算法团队新推荐模型→你设计+执行AB实验→评估"业务指标有没有提升"。算法关注的AUC→你翻译成"人均阅读时长/留存/付费"→告诉PM"算法更新带来了多大业务价值"
- **特征需求方**：算法团队说"推荐需要更多用户特征"→你从数据仓库中提取"用户近30日活跃度/品类偏好/阅读时段"→给算法提供特征数据。你能理解"特征覆盖率低→模型学不到→效果差"
- **业务翻译官**：PM说"要推荐'多样化'的内容"→你翻译成"推荐列表里不同品类的占比>30%""同一个作者的书不超过2本"。算法团队说"AUC提升2pp"→你翻译成"预计人均阅读时长+5%→DAU+3%"

**2. 推荐模型AB实验的特殊性**
- **模型版本管理**：和标准AB实验不同→推荐模型实验需要管理"模型版本"(如v1.2)。上线后如果模型效果变差→需要回滚到v1.1
- **流量切换**：模型更新通常按比例逐步扩大流量(1%→5%→25%→50%→100%)→而非一步到位50/50。原因：模型更新如果出问题(推荐全崩)→流量小→影响小
- **长期效应**：推荐算法的实验需要更长时间(通常2-4周)→因为用户需要"适应"新推荐(新颖性效应衰减)+推荐模型需要"收集反馈"来优化。不建议只跑1周就下结论
- **护栏指标**：推荐多样性(不能只推同类)、长尾内容曝光(不能只推头部)、用户举报率(不能推低质内容)
