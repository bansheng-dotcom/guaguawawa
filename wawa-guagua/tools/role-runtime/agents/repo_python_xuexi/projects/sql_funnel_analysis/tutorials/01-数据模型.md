# 01 数据模型设计

---

## 一、白话理解

### 你先想想——美团优选每天产生了哪些数据？

1. **团长**在微信群分享商品链接 → 这需要一张表记录**团长是谁、在哪个小区、每天能带多少流量**
2. **用户**看到链接 → 这需要一张表记录**用户是谁、常去哪个团长、注册多久了**
3. **商品**被分享出去 → 这需要**商品表**，包括价格、品类、保质期、供应商距离
4. 用户**点击→加购→下单** → 这需要一个**行为日志表**，记录每一步的时间和动作
5. 下单后产生**订单** → **订单表**+**订单明细表**（一单多品）
6. 订单需要**履约**（网格仓→团长→用户自提）→ **履约表**记录配送距离、成本、损耗

**这就是社区团购的7张核心表。** 面试时如果被问"你用过哪些数据",你能说清楚这7张表的关系，就已经比90%的候选人强。

### 这7张表的关系（ER图）

```
group_leaders(团长)    users(用户)       products(商品)
   leader_id ◄───────── leader_id           product_id
       │                    │                    │
       │           ┌────────┼────────┐           │
       │           │        │        │           │
       ▼           ▼        ▼        ▼           ▼
 behavior_logs      orders              order_items
(分享→点击→加购→下单)  order_id ──────────► order_id
                          │
                          ▼
                     fulfillment
                     (履约/成本/损耗)
```

## 二、7张表详解

### 表1: group_leaders（团长表）— 200人

| 字段 | 含义 | 示例 |
|------|------|------|
| leader_id | 团长唯一ID | 1, 2, 3... |
| leader_name | 团长名 | leader_54 |
| city_tier | 城市等级 | tier_1_new / tier_3_5 |
| community_name | 小区名 | community_54 |
| leader_density | 团长密度 | high / mid / low |
| daily_traffic_base | 日均流量(人) | 90.5 (这团长每天群里约90人看消息) |
| conversion_ability | 转化能力0-1 | 0.35 (他看到商品的用户有35%最终下单) |

**关键理解：daily_traffic_base × conversion_ability = 这个团长的GMV天花板。**

### 表2: users（用户表）— 30,000人

| 字段 | 含义 |
|------|------|
| user_id | 用户ID |
| leader_id | 常购团长（用户最常去哪个团长取货） |
| city_tier | 所在城市等级 |
| register_date | 注册日期 |
| user_type | 用户类型（new/regular/vip） |
| age_group | 年龄段 |

**为什么用户要关联团长？** 因为社区团购是"团长制"——一个用户基本固定在1-2个团长那里取货。

### 表3: products（商品表）— 800款

| 字段 | 含义 | 为什么重要 |
|------|------|----------|
| product_id | 商品ID | |
| category_name | 品类 | 蔬菜/肉禽/日用/零食/粮油/速冻/家清 |
| unit_price | 单价 | |
| cost_price | 成本价 | 用于计算毛利 |
| shelf_life_days | 保质期(天) | 生鲜3天 vs 日用品365天 → 完全不同的推荐策略 |
| supplier_distance_km | 供应商距离 | 直接影响履约成本 |
| is_perishable | 是否易损耗 | 生鲜类=1 → 损耗风险高 |
| is_hot_product | 是否爆品 | 今日爆品坑位的候选 |

### 表4: behavior_logs（行为日志表）— 96万条

**这是最核心的表，记录了完整的用户行为链路：**

| 字段 | 含义 |
|------|------|
| log_id | 日志ID |
| leader_id | 哪个团长分享的 |
| user_id | 哪个用户 |
| product_id | 哪个商品 |
| action | **impression(曝光) / click(点击) / add_cart(加购) / order(下单)** |
| action_time | 行为时间 |

**漏斗分析全靠这张表。** 96万条记录，30天，每一条都是用户从"看到"到"下单"的一个步骤。

### 表5-6: orders + order_items（订单+明细）— 6.5万单 / 6.7万条

- **orders**：每行一个订单（user_id、leader_id、total_amount、item_count、order_date、delivery_date T+1、is_first_order）
- **order_items**：每行一个订单中的一个商品（order_id、product_id、quantity、unit_price、subtotal）

为什么要拆成两张表？因为一个订单可能包含多个商品——这叫"一单多品"，社区团购的典型场景（用户一次买3-4件）。如果不拆表，一个订单有5个商品就要存5行订单数据（冗余）。拆表是数据库规范化的基本操作。

### 表7: fulfillment（履约表）— 6.5万条

| 字段 | 含义 |
|------|------|
| order_id | 关联订单 |
| grid_warehouse_id | 网格仓ID |
| delivery_distance_km | 配送距离(km) |
| fulfillment_cost | 履约成本(元) |
| loss_amount | 损耗金额 |

**社区团购的特色表——电商没有"履约成本"这个概念（快递一件也是送，100件也是送），但团购的履约成本跟距离和件数强相关。**

## 三、代码怎么生成这些数据

打开 [generate_data.py](../generate_data.py)：

### 团长表生成（第35-55行）
```python
base_traffic = np.random.lognormal(mean=4.5, sigma=0.6, size=n)
conversion_ability = np.random.beta(a=3, b=5, size=n)
```
- lognormal生成"偏态分布"——大部分团长日流量中等，少数团长流量特别大（头部门店效应）
- beta分布生成0-1之间的转化率——大部分团长转化率在0.3-0.5

### 行为日志生成（第120-180行）— 核心逻辑
```python
# impression → click(概率35%)
if np.random.random() < 0.35 * (1 + conv):
    # click → add_cart(概率30%)
    if np.random.random() < 0.30 * (1 + conv):
        # add_cart → order(概率45%)
```

这里conv是团长的转化能力——**转化能力强的团长，每一步的概率都更高**。这是真实业务逻辑的模拟。

### 订单生成（第195-260行）
同一个用户同一天可能下1-2单（模拟追加购买），每单包含多个商品。履约距离基于团长密度（高密=近，低密=远）。
