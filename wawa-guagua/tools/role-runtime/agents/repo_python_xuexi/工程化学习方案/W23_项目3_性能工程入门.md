### cProfile + pstats 的完整使用指南

```python
import cProfile
import pstats
from pathlib import Path

def profile_and_report(func, *args, output_dir: str = 'output', **kwargs):
    """运行 cProfile——生成可读的性能报告。

    输出 3 个文件:
    - profile_baseline.prof: 原始 profile 数据（可用 pstats 交互式分析）
    - profile_by_cumtime.txt: 按 cumtime 排序——定位瓶颈函数
    - profile_by_ncalls.txt: 按 ncalls 排序——定位频繁调用的函数
    """
    out = Path(output_dir)
    out.mkdir(exist_ok=True)

    profiler = cProfile.Profile()
    profiler.enable()
    result = func(*args, **kwargs)
    profiler.disable()

    # Save raw profile data
    profiler.dump_stats(str(out / 'profile_baseline.prof'))

    # Generate readable report——sorted by cumtime
    stats = pstats.Stats(profiler)
    stats.sort_stats('cumtime')

    with open(out / 'profile_by_cumtime.txt', 'w') as f:
        stats.stream = f
        stats.print_stats(20)  # Top 20 functions

    # Generate readable report——sorted by ncalls
    stats.sort_stats('ncalls')
    with open(out / 'profile_by_ncalls.txt', 'w') as f:
        stats.stream = f
        stats.print_stats(20)

    # Return the function's original result + profile summary
    return {
        'result': result,
        'top_by_cumtime': [
            (fn, data[2]) for fn, data in
            list(stats.stats.items())[:5]
        ]
    }
```

**把 profile 输出文件提交到 Git——以后任何人想知道"这个优化值不值"——对比两个 .txt 文件即可。** 这是性能工程的"可追溯性"——不是"我记得当时优化了"——是 Git 里有每次优化的 before/after profile 对比。

**cProfile 的三个关键列——不是"数字越大越慢"——是要理解每个数字的含义:**

| 列 | 含义 | 什么时候关注 | 什么时候忽略 |
|-----|------|------------|------------|
| ncalls | 被调用次数 | ncalls 很大 + tottime 很小 = "频繁调用"——解法是减少调用次数 | ncalls 大但 cumtime 小 = 不影响总时间——不用优化 |

### 🔴 认知冲突

你有一个函数跑了 15 分钟。你"猜"是 pandas 的 groupby 慢。你花了一下午重写了 groupby——用上了 transform、agg、rolling——结果还是 14 分钟。你的瓶颈不在 groupby。

**问题**："猜"是最不可靠的优化策略。cProfile 精确告诉你——哪个函数、哪一行、花了多少秒。

---

### 📖 核心原理

```bash
python -m cProfile -s cumtime main.py
```

输出解读：
- `ncalls`：被调用了多少次——如果某个函数被调了 100 万次但每次很快 → 不是"慢"，是"频繁调"——解法不是优化函数体，是少调几次。
- `tottime`：函数自身的执行时间（不含调用的子函数）
- `cumtime`：含子函数的总时间——**这是你应该优先看的列**

**经验法则：先看 cumtime 最高的前 3 个函数——它们合计通常占总时间的 80%+。**

### line_profiler 完整实战——从定位瓶颈到验证优化

**line_profiler 不是"跑一次看看"——是"优化前测一次、优化后测一次——对比加速倍数"。**

```python
# 安装: pip install line_profiler

# Step 1: 在需要测量的函数上加 @profile 装饰器
@profile
def compute_features(df):
    df['feat_1'] = df['amount'] / df['count']              # 0.1s
    df['feat_2'] = df.groupby('user_id')['amount'].transform('sum')  # 8.2s
    df['feat_3'] = df['amount'].rolling(7).mean()          # 0.3s
    df['feat_4'] = df['amount'].shift(1)                   # 0.05s
    return df

# Step 2: 命令行跑——kernprof -l -v main.py
# 输出每行的 % Time——精确到 0.1%
# Line #   % Time   Line Contents
# ==============================
#    42      1.2%   df['feat_1'] = df['amount'] / df['count']
#    43     95.3%   df['feat_2'] = df.groupby('user_id')['amount'].transform('sum')
#    44      3.5%   df['feat_3'] = df['amount'].rolling(7).mean()

# Step 3: 优化瓶颈行——groupby transform -> groupby agg + merge
user_totals = df.groupby('user_id')['amount'].sum().reset_index(name='user_total')
df = df.merge(user_totals, on='user_id')  # 8.2s -> 0.4s（20x 加速）

# Step 4: 重新测量——验证加速——记录到 commit message
# git commit -m "optimize compute_features: groupby transform -> agg+merge (20x speedup)"
```

**cProfile 和 line_profiler 的分工——不是替代——是互补：**

| 工具 | 回答什么问题 | 输出 | 使用时机 |
|------|------------|------|---------|
| cProfile | 哪个函数慢？ | 每个函数的 ncalls/tottime/cumtime | 首次诊断——定位瓶颈函数 |
| line_profiler | 函数的哪一行慢？ | 每行的 % Time + 执行次数 | 二次诊断——定位瓶颈行 |

**工作流——cProfile 定位函数 -> line_profiler 定位行 -> 优化那一行 -> cProfile 验证总时间下降。** 不是凭感觉优化——是数据驱动的性能工程。

**面试时——面试官问"你怎么优化代码性能"——你回答"不是靠猜——是靠测量。cProfile 定位瓶颈函数——line_profiler 定位瓶颈行——优化后重新测量——记录加速倍数。我在项目 3 中把一个 15 分钟的特征工程 pipe 优化到 2 分钟——靠的是测量——不是直觉。"**

> 📓 今日主课：项目 3——特征工程

---

### 📖 核心原理

cProfile 告诉你是哪个**函数**慢。line_profiler 告诉你是函数的**哪一行**慢。

```python
@profile
def compute_features(df):
    df['feat_1'] = df['amount'] / df['count']              # 0.1s
    df['feat_2'] = df.groupby('user_id')['amount'].transform('sum')  # 8.2s  ← 瓶颈！
    df['feat_3'] = df['amount'].rolling(7).mean()          # 0.3s
```

优化目标明确——`feat_2` 的 groupby transform。解法：用 `groupby().agg()` 提前算好汇总表，再 merge 回去——省掉 transform 的重复排序开销。

### 6 种性能瓶颈的诊断与优化——完整实战指南

**每种瓶颈的完整诊断流程——从症状到 cProfile 特征到优化到加速比:**

**瓶颈 1——for 循环逐行操作:**
- 症状: 1 万行 30 秒——10 万行 5 分钟（O(n)——线性——但常数大）
- cProfile 特征: cumtime 集中在一个 for 循环调用栈——tottime 大——ncalls 大
- 优化: 向量化——np.where() 替代 df.apply()——pd.eval() 替代逐行计算
- 加速比: 10-100x
- 鲜果多实战: clean_amounts 中逐行检查负值->np.where——8s->0.5s（16x）

**瓶颈 2——groupby transform:**
- 症状: 每组重新排序——O(n log n) per group
- 优化: groupby().agg() 算好汇总表——merge 回去——O(n log n) 只一次
- 加速比: 5-20x
- 项目 3 实战: compute_features 中 groupby transform 8.2s->0.4s（20x）

**瓶颈 3——多次 read_csv:**
- 症状: IO 占大半——CPU 空闲——cumtime 在 read_csv 上高
- 优化: 一次读完->内存筛选。或转 Parquet（列式+压缩——快 5-10x）
- 加速比: 3-10x
- 项目 3 实战: 每天读 30 个 CSV->转为一个 Parquet 文件——3min->0.3min（10x）

**瓶颈 4——内存不够（Swap）:**
- 症状: 系统内存用满->Swap->速度降 100x。dmesg 或任务管理器可见
- 优化: chunksize 分块。category dtype（字符串列转 category——内存减 80%）。删不需要的列
- 加速比: 10-100x
- 鲜果多实战: 5000 万行——全读入内存 OOM->chunksize=100000——分块聚合——3h->15min（12x）

**瓶颈 5——链式索引:**
- 症状: SettingWithCopyWarning——慢在细碎操作——无明显 cProfile 集中
- 优化: 单次 .loc[]
- 加速比: 2-5x（单次少——但项目中散布各处——累积显著）

**瓶颈 6——字符串操作:**
- 症状: .str.replace() 百万次——cumtime 在 str 方法上高
- 优化: .str 已经是向量化的——不需要改。如果仍需加速——先过滤再操作
- 加速比: 2-3x

## D4（周四 1/1）：新年——数据库 vs pandas：什么时候用 SQL 什么时候用 Python

### 性能优化的"够用"标准——不是"优化到极致"——是"优化到可以接受"

**判断是否需要优化的三个标准——不是"慢就要优化":**

1. **这个操作的运行时间影响了谁？** 如果是"你自己调试时等待 15 分钟"——需要优化——因为影响开发效率。如果是"每天凌晨 3 点自动跑——15 分钟没问题"——不需要优化——因为不影响任何人。

2. **数据量会增长吗？** 当前 10 万行——跑 2 秒——不需要优化。但数据量每月增长 20%——6 个月后 30 万行——跑 10 秒——1 年后 100 万行——跑 60 秒。如果数据量在增长——现在就要在代码中标注"当前数据量 OK——数据量 > N 时考虑迁移到 SQL/Parquet/Chunksize"。

3. **优化后代码的可读性下降了吗？** 如果优化让代码从 10 行变成 50 行——从"一个新人能看懂"变成"只有你能看懂"——不值得。在注释中写上"当前实现 O(n)——可读性优先。数据量 > N 时考虑 O(n log n) 实现"——让后来者知道这是"有意为之"——不是"不知道怎么优化"。

**"够用"标准——数据分析师版本——不是追求极致的性能——是追求"不影响分析效率"的性能:**

| 操作 | "够用"标准 | 超过这个才需要优化 |
|------|----------|-----------------|
| 单次数据加载 | < 10s | > 30s |
| 单次 groupby 聚合 | < 5s | > 15s |
| 全流程（load->clean->analyze->export） | < 2min | > 5min |

### SQL vs pandas 决策——完整决策树

**不是"SQL 好还是 pandas 好"——是"什么场景用什么工具"：**

```
数据在哪？
├── 数据库中，量级 > 内存 -> SQL
├── 本地文件 < 1GB -> pandas
└── 数据库中，量级 < 内存 -> 看操作类型
    ├── JOIN / FILTER / GROUP BY（无复杂逻辑） -> SQL——优化器做了 40 年优化
    │   例: SELECT city, SUM(amount) FROM orders GROUP BY city
    ├── 窗口函数 / 复杂特征工程 -> SQL 或 pandas——两者都能做
    │   例: SUM() OVER (PARTITION BY user_id ORDER BY date)
    └── 自定义函数 / 复杂逻辑 / 可视化 -> pandas
        例: df.apply(my_custom_scoring_function)——SQL 做不了
```

**综合策略——大数据用 SQL 做——小数据用 pandas 做——接口处用 Parquet:**

1. 在数据库中跑 SQL——完成"重量级"的 JOIN + 聚合 + 过滤——结果集压缩到 < 10 万行
2. 用 pd.read_sql() 或 read_parquet() 拉回 pandas——做"轻量级"的特征工程 + 可视化
3. 不要用 pandas 做数据库的工作——不要 pd.read_sql("SELECT * FROM orders") 然后 df.groupby()
4. 不要用 SQL 做 pandas 的工作——不要在 SQL 里写 200 行 CASE WHEN 做复杂的用户分群

**性能对比——同样的操作——SQL vs pandas vs Parquet:**

| 操作 | SQL（数据库内） | pandas（本地） | Parquet（文件） | 推荐 |
|------|--------------|-------------|---------------|------|
| 读 1000 万行 | 10s（网络传输） | N/A（内存不够） | 2s（列式+压缩） | Parquet |
| GROUP BY + SUM（1000 万行） | 5s（数据库引擎） | 30s（pandas 单机） | N/A | SQL |
| 复杂特征工程（1 万行） | 100s（SQL 写复杂逻辑） | 2s（df.apply） | N/A | pandas |
| 画图（1000 行） | N/A | 0.5s | N/A | pandas |

### W23 闭卷自测——性能工程

**Q1:** cProfile 的三个关键列——ncalls/tottime/cumtime——分别回答什么问题？

> **A:** ncalls——被调用了多少次（如果某个函数被调 100 万次但每次很快——不是"慢"——是"频繁"——解法是少调几次——不是优化函数体）。tottime——函数自身的执行时间（不含子函数）。cumtime——含子函数的总时间——这是应该优先看的列。先看 cumtime 最高的前 3 个函数——它们合计通常占 80%+ 的时间。

**Q2:** cProfile 和 line_profiler 的分工？

> **A:** cProfile 回答"哪个函数慢"——定位瓶颈函数。line_profiler 回答"函数的哪一行慢"——定位瓶颈行。工作流——cProfile 定位函数->line_profiler 定位行->优化那一行->cProfile 验证总时间。互补——非替代。

**Q3:** 6 种性能瓶颈模式中——哪种最容易被忽视？为什么？

> **A:** 链式索引（chained indexing）——df[df['a']>0]['b']。它"不是明显的慢"——单次操作只比 .loc 慢 2-3x——但它在大型项目中散布在各处——累积效果显著。而且 pandas 会发出 SettingWithCopyWarning——但很多人忽略了。修复成本最低——单次 .loc[]——收益是累积的。
