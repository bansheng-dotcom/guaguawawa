# 模块 1：SQLAlchemy——Python 连接数据库的正确方式

## 🔴 认知冲突

你写过 `pd.read_sql("SELECT * FROM orders", connection)`。每次执行这行代码——Python 去连接数据库→执行查询→返回结果→断开连接。你跑了 5 条查询——Python 连了 5 次数据库，断了 5 次。

生产环境中如果有 100 个用户同时查——数据库的连接数会被打爆。所以你需要**连接池**——预先建好几个长连接，用完不关，还给池子——下一个人复用。

---

## 📖 核心原理

**SQLAlchemy 不是"ORM 框架"——它的核心是一个连接池管理器。**

```python
from sqlalchemy import create_engine, text
import pandas as pd

# 创建引擎 = 建立一个连接池（默认 5 个连接）
engine = create_engine(
    'postgresql://user:password@localhost:5432/xianguoduo',  # PostgreSQL
    # 或 'mysql+pymysql://user:password@localhost:3306/xianguoduo'  # MySQL
    pool_size=5,         # 连接池大小
    max_overflow=10,     # 超出池后最多再创建几个
    echo=False           # 设为 True 可以看到每条 SQL 的执行日志
)

# pd.read_sql 可以直接用 engine——SQLAlchemy 自动管理连接的获取和归还
df = pd.read_sql("SELECT * FROM orders WHERE dt = '2026-09-01'", engine)

# 需要事务时——用 contextmanager 保证异常时自动回滚
from contextlib import contextmanager
@contextmanager
def get_connection():
    conn = engine.connect()
    try:
        yield conn
        conn.commit()
    except Exception:
        conn.rollback()
        raise
    finally:
        conn.close()  # 归还到连接池

with get_connection() as conn:
    conn.execute(text("INSERT INTO reports VALUES (:date, :gmv)"),
                 {"date": "2026-09-01", "gmv": 5230000})
```

**为什么必须用 `text()` 包装原始 SQL？**

防止 SQL 注入。上面的 `:date` 和 `:gmv` 是参数化查询——值会被安全地转义，不会被当成 SQL 代码执行。永远不要用 f-string 拼 SQL：`f"INSERT ... VALUES ('{date}', {gmv})"`——如果一个变量里含有 `'; DROP TABLE orders; --`——你的表就没了。

### 📖 SQLAlchemy 进阶——ORM 基础 + 数据库迁移工具

**SQLAlchemy 有两层 API——Core（你刚学的——连接池+text()）和 ORM（把表映射为 Python 类）。数据分析师日常用 Core——但理解 ORM 能让你和后端工程师说同一种语言：**

```python
from sqlalchemy import Column, Integer, String, Float, Date
from sqlalchemy.orm import DeclarativeBase

class Base(DeclarativeBase):
    pass

class Order(Base):
    __tablename__ = 'orders'

    id = Column(Integer, primary_key=True)
    user_id = Column(Integer)
    amount = Column(Float)
    city = Column(String(50))
    order_date = Column(Date)

# ORM 方式查询——和 Core 的 text() 不是替代——是两种不同的使用场景
# Core (text()): 你写原始 SQL——适合复杂分析查询
# ORM: Python 对象操作——适合简单的 CRUD——和 Web 框架配合
```

**数据库迁移——当表结构变更时——不是"手动 ALTER TABLE"——是用 Alembic 自动生成迁移脚本：**

```bash
pip install alembic
alembic init alembic  # 初始化迁移环境

# 修改 Order 模型（如新增一列 status）
# 然后:
alembic revision --autogenerate -m "add status column to orders"
alembic upgrade head  # 自动执行 ALTER TABLE——不需要手动写
```

**鲜果多项目中——当 DWD 层表结构变更时——Alembic 迁移脚本和代码一起提交——任何环境下都能一键升级到最新表结构。这解决了"测试环境和生产环境表结构不一致"的经典问题。**

### SQLAlchemy 在生产环境——不只是"能连上"——是"连不上时有合理的退路"

```python
from sqlalchemy import create_engine, exc
from sqlalchemy.pool import NullPool, QueuePool
import logging

def create_robust_engine(db_url, for_batch_job=False):
    """创建生产级的数据库引擎——含超时+重试+合适的池策略。

    for_batch_job=True: 使用 NullPool——每次用完就关——适合定时任务
    for_batch_job=False: 使用 QueuePool——保持 3-5 个连接——适合 API 服务
    """
    poolclass = NullPool if for_batch_job else QueuePool
    return create_engine(
        db_url,
        poolclass=poolclass,
        pool_size=3, max_overflow=2,
        pool_timeout=10,           # 等待连接的最长时间
        pool_recycle=1800,         # 30分钟自动回收连接
        connect_args={'connect_timeout': 5}
    )

# 带重试的查询——处理瞬时网络故障
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, min=2, max=10))
def safe_read_sql(query, engine):
    """带重试的 SQL 查询——最多重试 3 次——指数退避。"""
    try:
        return pd.read_sql(query, engine)
    except exc.OperationalError as e:
        logging.warning('Database query failed, retrying: %s', e)
        raise
```

**数据分析师的数据管道——SQLAlchemy 是第一环：** SQLAlchemy (DB->Python) -> pandas (清洗+分析) -> openpyxl/Matplotlib (输出)。如果 engine 配置错误——后续所有分析都拿不到数据。面试时如果你能说出 pool_recycle + connect_timeout + retry——面试官知道你不是"只在本地跑过"。

# 模块 2：openpyxl——用 Python 生成格式化的 Excel 报表

## 🔴 认知冲突

运营总监说"报表发我 Excel"。你的 `df.to_excel('report.xlsx')` 生成了一张表——但：
- 单元格全是默认格式——金额没有千分位、百分比没有 %
- 需要合并单元格做标题
- 需要条件格式——红色显示负增长、绿色显示正增长
- 需要图表嵌入在 Sheet 里——而不是分开的 png 文件

**`df.to_excel()` 只做了 10% 的工作。**

---

## 📖 核心原理

**openpyxl 的三层模型——Workbook（文件）→ Worksheet（Tab 页）→ Cell（单元格）。**

```python
from openpyxl import Workbook
from openpyxl.styles import Font, PatternFill, Alignment, numbers
from openpyxl.chart import BarChart, Reference
from openpyxl.utils import get_column_letter

wb = Workbook()
ws = wb.active
ws.title = '日报'

# ---- 标题行（合并单元格 + 格式化） ----
ws.merge_cells('A1:E1')
ws['A1'] = '鲜果多 2026-09-01 日报'
ws['A1'].font = Font(name='微软雅黑', size=16, bold=True)
ws['A1'].alignment = Alignment(horizontal='center')

# ---- 表头 ----
headers = ['日期', 'GMV(万元)', '环比(%)', '订单量', '客单价(元)']
for col, h in enumerate(headers, 1):
    cell = ws.cell(row=3, column=col, value=h)
    cell.font = Font(bold=True, color='FFFFFF')
    cell.fill = PatternFill(start_color='4472C4', end_color='4472C4', fill_type='solid')

# ---- 数据行（条件格式——正增长绿色，负增长红色） ----
data = [
    ['2026-09-01', 523.4, 5.2, 12450, 42.0],
    ['2026-09-02', 518.2, -1.0, 12200, 42.5],
    ['2026-09-03', 535.1, 3.3, 12800, 41.8],
]
for i, row_data in enumerate(data):
    for j, val in enumerate(row_data):
        cell = ws.cell(row=4+i, column=j+1, value=val)
        # 环比列——负值红色
        if j == 2:
            cell.font = Font(color='FF0000' if val < 0 else '008000')
            cell.number_format = '0.0%' if abs(val) < 1 else '0.0'

# ---- 嵌入图表 ----
chart = BarChart()
chart.title = '每日 GMV'
chart.y_axis.title = '万元'
data_ref = Reference(ws, min_col=2, min_row=3, max_row=3+len(data), max_col=2)
cats_ref = Reference(ws, min_col=1, min_row=3+1, max_row=3+len(data))
chart.add_data(data_ref, titles_from_data=True)
chart.set_categories(cats_ref)
ws.add_chart(chart, 'A10')

wb.save('output/daily_report.xlsx')
```

**关键点**：
- `merge_cells` 做标题行
- `Font` / `PatternFill` / `Alignment` 控制样式
- `number_format` 控制数字格式——`'#,##0'`（千分位）、`'0.0%'`（百分比）
- `chart` 对象嵌入 Sheet——不是分开的图片文件

### 📖 openpyxl 进阶——条件格式 + 数据验证 + 公式 + 多 Sheet 报表

**数据分析师最常用的 openpyxl 模式——不只是"格式化"——是"让 Excel 替你做计算"：**

```python
# 条件格式——不只是"手动标红"——是设置 Excel 规则——用户改了数据后格式自动更新
from openpyxl.formatting.rule import CellIsRule

# 规则: 如果 E 列单元格 >= 500——自动绿色填充
ws.conditional_formatting.add(
    'E2:E100',
    CellIsRule(operator='greaterThanOrEqual', formula=['500'],
              fill=PatternFill(start_color='C6EFCE', end_color='C6EFCE', fill_type='solid'))
)

# 数据验证——限制单元格输入——防止运营同事手动改错
from openpyxl.worksheet.datavalidation import DataValidation

dv = DataValidation(type='list', formula1='"北京,上海,广州,深圳"', allow_blank=True)
dv.error = '请从下拉列表中选择城市'
ws.add_data_validation(dv)
dv.add('C2:C1000')  # C 列只能选四个城市之一

# 公式——在 Excel 中嵌入 =SUM() / =VLOOKUP()——打开文件就能自动计算
ws['F2'] = '=SUM(D2:E2)'           # 自动求和
ws['G2'] = '=IF(E2<0,"异常","正常")'  # 自动标记异常

# 多 Sheet 报表——一个 Excel 文件含多个 Tab 页
ws_summary = wb.active
ws_summary.title = 'KPI 汇总'
ws_detail = wb.create_sheet('城市明细')
ws_raw = wb.create_sheet('原始数据')
```

**鲜果多周报中——你在 Excel 里嵌入了条件格式和下拉列表——运营总监可以在"城市"列选择具体城市——GMV 和订单量自动筛选——不需要找你改 SQL。**

**openpyxl 和 pandas 的分工：** to_excel() 做 90% 的简单导出——省时间。openpyxl 做最后 10% 的格式化——合并单元格、条件格式、嵌入图表。流程——先 to_excel() 写入数据——然后 load_workbook() 加载——追加格式和图表——最后保存。

# 模块 3：Makefile——10 分钟学会，每天省 5 分钟

## 🔴 认知冲突

你的鲜果多项目有 6 个常用命令：

---

## 📖 核心原理

**Makefile = 给常用命令起名字 + 声明依赖关系。**

```makefile
# Makefile——放在项目根目录
.PHONY: run test lint typecheck docker all clean

# 运行主流程
run:
	python main.py

# 格式化+检查
lint:
	ruff check src/ --fix
	ruff format src/

# 类型检查
typecheck:
	mypy src/

# 测试
test:
	pytest tests/ -v

# 全量检查（CI 三重门）
check: lint typecheck test
	@echo "✅ 全部检查通过"

# Docker
docker:
	docker build -t xianguoduo-analysis .

# 一键全流程
all: check docker
	@echo "✅ 构建完成——可以部署了"

# 清理临时文件
clean:
	rm -rf __pycache__ .pytest_cache .mypy_cache
	find . -type d -name __pycache__ -exec rm -rf {} +

# 帮助（make 或 make help——显示所有可用命令）
help:
	@echo "可用命令:"
	@echo "  make run       - 运行分析主流程"
	@echo "  make lint      - 代码风格检查+自动修复"
	@echo "  make typecheck - 静态类型检查"
	@echo "  make test      - 运行测试"
	@echo "  make check     - CI 三重门 (lint+typecheck+test)"
	@echo "  make docker    - 构建 Docker 镜像"
	@echo "  make all       - 全流程: check + docker"
	@echo "  make clean     - 清理临时文件"
```

使用——在项目根目录：
```bash
make check         # 一行跑完 ruff + mypy + pytest
make all           # check + docker build——全流程
make clean         # 清理所有缓存文件
```

# 模块 4：正则表达式深度——数据清洗的第一工具

## 🔴 认知冲突

W3D4 你学了字符编码。但编码解决的是"文件级别的乱码"。文件里面的**内容**乱——比如用户输入的手机号格式五花八门（`138-1234-5678`、`(138)12345678`、`138 1234 5678`）——编码帮不了你。你需要的是**模式匹配**——正则表达式。

---

## 📖 核心原理

**正则表达式不是"学一次就会"——是"5 个核心模式覆盖 80% 的清洗场景"。**

| 模式 | 正则 | 匹配 | 不匹配 | 数据分析场景 |
|------|------|------|--------|-----------|
| **提取数字** | `\d+\.?\d*` | `123` `45.6` | `abc` | 从文本中提取金额/数量 |
| **匹配手机号** | `1[3-9]\d{9}` | `13812345678` | `12345678901` `138-1234-5678` | 验证手机号格式 |
| **非贪婪匹配** | `<.*?>` | `<html>` | 贪婪版 `<.*>` 会吞掉整行 | 清洗 HTML 标签 |
| **分组提取** | `(\d{4})-(\d{2})-(\d{2})` | 从 `2026-09-01` 提取年月日 | — | 从文件名/日志提取日期 |
| **零宽断言** | `(?<=¥)\d+` | 从 `¥523` 提取 `523` | — | 提取"¥"后面的金额 |

**核心 Python 操作——`re.sub`（替换）、`re.findall`（查找全部）、`re.search`（查找第一个）：**

```python
import re

text = "订单金额: ¥523.4万，日期: 2026-09-01，手机: 138-1234-5678"

# 提取金额
amount = re.search(r'¥(\d+\.?\d*)', text).group(1)   # '523.4'

# 提取日期
date_match = re.search(r'(\d{4})-(\d{2})-(\d{2})', text)
year, month, day = date_match.groups()  # ('2026', '09', '01')

# 清洗手机号——统一格式为纯数字
phone_raw = '138-1234-5678'
phone_clean = re.sub(r'[\s\-\(\)]', '', phone_raw)  # '13812345678'

# 清洗 HTML 标签
html = '<p>北京用户</p>'
clean = re.sub(r'<.*?>', '', html)  # '北京用户'
#                              ↑ 注意 ?——非贪婪！没有 ? 会吞掉整行
```

**最容易踩的坑——贪婪 vs 非贪婪：**

```python
text = '<p>北京</p><p>上海</p>'

re.sub(r'<.*>', '', text)     # 错误——输出 ''（吞了整行！）
re.sub(r'<.*?>', '', text)    # 正确——输出 '北京上海'
#           ↑ 这一个小小的 ? 改变了匹配策略——从"尽可能多吃"变成"吃最少"
```

### 📖 正则进阶——环视断言 + 回溯陷阱 + 编译优化

**五个进阶模式——让你的正则从"能匹配"到"精确匹配"：**

| 模式 | 正则 | 含义 | 场景 |
|------|------|------|------|
| **正向后顾** | `(?<=¥)\d+` | 匹配 ¥ 后面的数字——但不包含 ¥ | 提取金额——¥523 -> 523 |
| **负向后顾** | `(?<!\d)-?\d+` | 匹配数字——但前面不能是数字 | 提取独立数字——不匹配电话号码中的片段 |
| **正向前瞻** | `\d+(?=元)` | 匹配数字——但后面必须是"元" | 提取"523元"中的 523——不要"523万" |
| **负向前瞻** | `\d+(?!万)` | 匹配数字——但后面不能是"万" | 排除"万"结尾的数字 |
| **命名分组** | `(?P<year>\d{4})-(?P<month>\d{2})` | 给分组命名——代码中按名字提取 | date.group('year') 比 date.group(1) 更可读 |

**正则的性能——编译一次、反复使用——不是每次调用 re.search 都编译一次：**

```python
import re

# 错误做法——每次函数调用都重新编译正则
def extract_amount_bad(text):
    return re.search(r'¥(\d+\.?\d*)', text)

# 正确做法——模块级编译一次——所有调用复用
AMOUNT_PATTERN = re.compile(r'¥(\d+\.?\d*)')
def extract_amount(text):
    return AMOUNT_PATTERN.search(text)

# 在 10 万行数据上——编译版本的差距: ~0.3s vs ~1.2s——4 倍差距
```

**鲜果多数据清洗——你的 clean.py 里有 8 个正则——全部用 re.compile() 放在模块顶部——注释标注每个 pattern 匹配什么——新同事打开文件——前 15 行就是"正则索引"——不需要从函数体中找正则。**

### 正则表达式在数据清洗 Pipeline 中的位置——从"写到哪算哪"到"正则即文档"

**你的鲜果多项目 clean.py 里应该有"正则常量区"——放在文件顶部——作为整个清洗模块的模式字典：**

```python
# === 正则常量——所有清洗函数共享——编译一次、全局复用 ===
import re

PHONE_CLEAN = re.compile(r'[\s\-()\.]')
AMOUNT_EXTRACT = re.compile(r'(?:¥|￥)?(\d+\.?\d*)\s*(?:元|万)?')
DATE_EXTRACT = re.compile(r'(\d{4})[-/年](\d{1,2})[-/月](\d{1,2})[日]?')
STATUS_MAP = {'已取消': 'cancelled', '退款': 'refunded', '已完成': 'completed',
              '待支付': 'pending', '已支付': 'paid'}

# 使用——clean.py 的函数引用这些常量——而不是在函数体内写正则
def clean_phone(series):
    return series.str.replace(PHONE_CLEAN, '', regex=True)
```

**为什么要把正则放在文件顶部而不是函数内部？** (1) 可发现性——新同事打开 clean.py——前 20 行就是这个文件能处理的所有模式 (2) 可测试性——每个正则常量可以独立测试 (3) 可维护性——同一个正则模式如果在多个函数中使用——不需要改 N 个地方 (4) 性能——re.compile() 只执行一次——模块加载时——不在每次函数调用时重复编译。

**在 10 万行数据上——模块级编译版本 vs 函数内每次编译——速度差距约 4 倍（~0.3s vs ~1.2s）。** 面试时你展示 clean.py 的顶部"正则常量区"——面试官知道你不是"用到哪写到哪"——你是"把正则作为项目基础设施来管理"。
