## D1（周一 7/28）：Shell 与终端——为什么你要用一个黑窗口

> 📓 今日主课：Python 数据模型与容器（四大容器、容器选择决策树）

---

### 🔴 认知冲突

你在 Windows 上装了 Python，双击打开了那个黑色的 Python 窗口，输入 `print("hello")`——能跑。然后教程让你"打开终端，输入 `python main.py`"——你打开了 cmd，输入之后报错：`'python' 不是内部或外部命令`。

你搜了一下，有人让你用 Git Bash，有人让你用 PowerShell，有人让你用 WSL。你装了 Git Bash，发现里面的命令和 cmd 完全不一样——`ls` 而不是 `dir`，`rm` 而不是 `del`，`/` 而不是 `\`。

**问题**：为什么你的 Windows 电脑上要装一个模仿 Linux 的东西才能正常写 Python？终端、Shell、命令行——这三个词到底是同一个东西还是三个不同的东西？

---

### 📖 核心原理

**终端、Shell、命令行——是三个东西。**

用一句话说清楚：

- **终端（Terminal）** 是你看到的那个窗口——它是一个**显示器和键盘的组合**。它的工作是把你的按键传进去，把文字显示出来。终端不懂任何命令。
- **Shell** 是终端里面运行的那个程序——它是**翻译官**。你输入 `ls`，Shell 把这个词翻译成"列出当前目录下的文件"，然后去执行。常见的 Shell 有 bash、zsh、PowerShell、cmd.exe。
- **命令行（Command Line）** 是**交互方式**——用文字而非鼠标来操作电脑。Shell 是命令行的一种实现。

所以：你打开 Git Bash → 看到的是一个**终端窗口** → 里面跑的是 **bash 这个 Shell** → 你用**命令行的方式**和它交互。

**为什么 Windows 上要装 Git Bash？**

因为 Python 的生态是建立在 Unix 惯例之上的。说人话：绝大多数 Python 教程、工具、文档都假设你的 Shell 是 bash 而不是 cmd。举三个例子：

1. **路径分隔符**：Linux/Mac 用 `/`，Windows 用 `\`。Python 代码里写 `data/orders.csv` 在两个系统上都能跑，但 cmd 里你只能打 `data\orders.csv`。
2. **命令名称**：bash 里是 `ls`、`cp`、`rm`，cmd 里是 `dir`、`copy`、`del`。pip 和 python 命令在两个 Shell 里都能用——但一旦报错，搜索引擎 99% 的答案用的是 bash 语法。
3. **环境变量**：bash 用 `export VAR=value`，cmd 用 `set VAR=value`。venv 的激活脚本就依赖这个差异——`source venv/bin/activate` 是 bash 语法，`venv\Scripts\activate` 是 cmd 语法。

**PATH 环境变量——为什么 cmd 里敲 `python` 报"不是内部命令"？**

当你在终端输入 `python` 时，Shell 不是全盘搜索一个叫 `python.exe` 的文件。它在**一组预先指定的目录**里按顺序找。这组目录就叫 PATH。

安装 Python 时如果没勾选"Add Python to PATH"，Python 的安装目录就不在 PATH 里——所以 Shell 找不到它。

```
# 看看你的 PATH 里有什么（在 Git Bash 里执行）：
echo $PATH

# 你会看到一串用冒号分隔的路径，类似：
# /c/Users/你的用户名/bin:/mingw64/bin:/usr/bin:/c/Program Files/Python310
```

每个 Shell 启动时会加载自己的 PATH。Git Bash 和 cmd 的 PATH 是**独立的**。这就是为什么同一个 `python` 命令可能在 Git Bash 里能找到，cmd 里找不到——两个 Shell 的 PATH 列表不一样。

---

### 🏢 鲜果多案例

你入职鲜果多第一天，打开前任留下的电脑。桌面上有三个 `.py` 文件，双击运行——闪了一下就没了。你在 cmd 里 `python 数据分析_最终版_v3_改.py`，报错 `No module named 'pandas'`。你明明记得装过 pandas。

问题出在哪？前任用 Anaconda 装的 Python，PATH 指向 Anaconda 的目录。你又用官网安装包装了一个 Python。现在系统里有两个 Python，cmd 找到的是你没装 pandas 的那个，Anaconda 的那个藏在 PATH 的另一个角落里。

你在 Git Bash 里输入 `which python`，发现指向 `/c/Program Files/Python310/python`——这是你装的裸 Python。你又输入 `which python3`，发现指向 `/c/Users/前任/Anaconda3/python`——这才能用 pandas。

**这就是为什么你要理解终端和 Shell。** 不理解这层，你连"这个脚本为什么在一台电脑上能跑、另一台上不能跑"都解释不了。这是工程化最底层的元问题。

### ✅ 自检反馈

**✅ 参考答案**

- `echo $PATH` 输出一串冒号分隔的路径。至少应该看到 `/c/Program Files/Python3xx` 或类似路径。
- `which python` 应该返回一个具体的路径，如 `/c/Program Files/Python310/python`。
- `$SHELL` 在 Git Bash 中通常是 `/usr/bin/bash`。
- 如果两个终端找的 Python 不一样，说明两个 Shell 的 PATH 不同。

**❓ 常见偏差**

| 偏差 | 原因 | 🔧 补救 |
|------|------|---------|
| "`which python` 没输出" | Python 不在 PATH 里 | 重装 Python 时勾选"Add Python to PATH"，或手动添加。先确认 Python 装在哪（通常 `C:\Program Files\Python3xx` 或 `C:\Users\用户名\AppData\Local\Programs\Python`） |
| "Git Bash 和 cmd 找的 Python 是同一个" | 很正常，因为安装时选了"Add to PATH"，两个 Shell 都从系统 PATH 找到了同一个 Python | 没问题。但理解"这是结果，不是必然"就够了 |
| "不明白为什么要学这个" | 因为你以后会重装系统、换电脑、帮同事配环境——每一次出问题，根因都在这 20 分钟的内容里 | 保存 `which python` 和 `echo $PATH` 的输出，以后排查环境问题时这是第一步 |

## D2（周二 7/29）：Git 认知模型——三棵树与时间机器

> 📓 今日主课：控制流全量（if/for/while/try）

---

### 🔴 认知冲突

你花了一个下午写了一段数据清洗代码，效果很好。晚上你想"再优化一下"，改了三行，又改了五行——然后整个脚本崩了。你按 Ctrl+Z，发现已经超过了撤销步数。你的代码丢了。

有人告诉你"用 Git 就不会有这个问题"。于是你按照教程执行了 `git init`、`git add .`、`git commit -m "first commit"`，然后继续改代码、继续 `git add .`、继续 `git commit -m "update"`。一周后你想找回"那个版本"——但你所有的 commit message 都是 `update`，根本分不清哪个是哪个。

**问题**：Git 真的是"备份工具"吗？如果是，为什么它不能像百度网盘一样自动同步？`git add` 和 `git commit` 为什么要分两步？中间那个"暂存区"到底在暂存什么？

---

### 📖 核心原理

**Git 不是备份。Git 是"时间机器"——但更重要的是，它是你自己选择时间点的机器。**

备份工具的逻辑：每隔一段时间自动保存所有文件。时间到了就存一份。你不知道每份之间改了什么。

Git 的逻辑：**你来决定什么时候值得记录。** 你完成的每一个有意义的小步骤（"清洗函数写好了"、"merge 验证加上了"）——你来按下快门。而且每一次快照之间，Git 精确地知道哪一行变了。

**Git 的"三棵树"——理解这个，所有 Git 命令都有意义了。**

```
工作目录 (Working Directory)    暂存区 (Staging Area)      仓库 (Repository)
=======================        ======================      =====================
这是你实际编辑文件的地方。       这是你"选中"的修改。         这是 Git 永久存储快照的地方。
用编辑器改代码，改的是这里。    git add 把修改放进这里。     git commit 把暂存区变成
                                                          一个永久的快照（commit）。
     │                              │                           │
     └──── git add ────────────────→│                           │
                                    └──── git commit ──────────→│
```

**为什么 `add` 和 `commit` 要分两步？**

因为在任何时刻，你可能改了三个文件：`io.py`（新增了一个读 CSV 的函数）、`clean.py`（修了一个 bug）、`analyze.py`（还在改，没改完）。三个改动混在一起——

- 你只想提交前两个（它们是一个完整的逻辑单元："增加读 CSV 功能 + 修复清洗 bug"）
- 你不想提交第三个（它只改了一半，提交了会破坏代码）

暂存区给了你**挑选的权力**。你 `git add io.py clean.py`——只把这两个放进暂存区——然后 `git commit`。`analyze.py` 的改动留在工作目录，等你改完再提交。

**Commit 是"完整快照"，不是"增量"**

很多人以为 Git 只存储每次修改的"差异"（就像 Word 的修订模式）。实际上，**每一次 commit 都存储了当时所有文件的完整副本**。

那岂不是很快会占满硬盘？不会。Git 内部有巧妙的压缩机制：
- 如果 `analyze.py` 在两个 commit 之间没变，Git 就不再存第二份——它存一个指针说"这个文件和上个 commit 一样"
- 如果只改了 3 行，Git 内部会把相似的文件打包压缩

但对你来说，概念上每个 commit 就是"那个时刻的完整项目"。这意味着你可以随时跳回到任何一个 commit，看到当时完整的项目状态。**这就是为什么 Git 是时间机器。**

**HEAD——"你现在在哪"**

HEAD 是一个指针，指向你当前所在的 commit。通常它指向最新的 commit（你在时间线的最前端）。但你可以让它指向任何一个历史 commit——
```bash
git checkout <某个旧commit的hash>
```
此时 HEAD 就指向那个旧 commit。你的工作目录会变成那个时刻的样子——你可以看、可以运行、可以比较。

`git checkout main`（或 `git switch main`）让 HEAD 回到最新。

**一张图总结：**
```
commit A  ←── commit B  ←── commit C  ←── HEAD (main分支)
(初始)       (加清洗)      (修bug)        你在这
```

---

### 🏢 鲜果多案例

你开始整理鲜果多的数据代码。前任留下的脚本里有一段清洗逻辑——去掉了金额为负的订单。你把它搬到 `src/clean.py` 里，写好函数后执行——

```bash
git add src/clean.py
git commit -m "add clean_amounts: remove negative orders"
```

然后又写了数据加载函数，放进 `src/io.py`——

```bash
git add src/io.py
git commit -m "add load_orders: read CSV with type conversion"
```

注意：这两个 commit 说的不是"update"或"fix"。每个 commit message 回答了"如果我三个月后看到这个 commit，我能知道发生了什么吗？"——`add clean_amounts: remove negative orders` 知道。`update` 不知道。

晚上你改 `clean.py` 改崩了——删了一段不该删的。你不需要 Ctrl+Z。你只需要：

```bash
git diff src/clean.py   # 看看自己改了什么
git checkout -- src/clean.py  # 回到上次 commit 的状态
```

文件恢复。因为你上次 commit 时，Git 已经存了一份完整的快照。

## D3（周三 7/30）：文件系统——路径、扩展名、文本与二进制

> 📓 今日主课：函数与函数式编程（def/lambda/推导式/LEGB）

---

### 🔴 认知冲突

你的 Python 脚本在 Windows 上写好了，`pd.read_csv('data/orders.csv')`——跑通了。你把整个项目文件夹发给同事（他用 Mac），他打开后运行——`FileNotFoundError: data/orders.csv`。

你把 `data/orders.csv` 改成 `data\orders.csv`——同事那边反而好了？但你的 Windows 上报错了。

然后同事发现 users.csv 打开后中文全是乱码——但你打开是正常的。你查了一下，你用的是"记事本"保存的，同事用的是 VS Code。

**问题**：为什么同样是 `data/orders.csv` 这个路径，在你的电脑上能找到，他的电脑上找不到？为什么同一个 CSV 文件，你打开正常他打开乱码？这些问题和你写的 Python 代码没有关系——它们发生在更底层。

---

### 📖 核心原理

**1. 路径分隔符：`/` vs `\`**

Windows 原生使用 `\`（反斜杠）作为路径分隔符：`C:\Users\你的名字\Desktop`。
Linux/Mac 使用 `/`（正斜杠）：`/home/你的名字/Desktop`。

但 Python 里两种都能用——因为 Python 会自动转换。`pd.read_csv('data/orders.csv')` 在 Windows 上能跑，Python 内部把它转成了 `data\orders.csv`。

那为什么同事的 Mac 上找不到？不是因为路径分隔符——是因为**相对路径的起点不一样**。

`data/orders.csv` 是相对路径。它说的是"从当前工作目录出发，找 data 文件夹里的 orders.csv"。当前工作目录是什么？是你启动 `python main.py` 时的那个目录。如果你的终端在 `C:\Users\你\project\` 下执行，那 `data/orders.csv` 就是 `C:\Users\你\project\data\orders.csv`。如果同事的终端在 `/home/同事/Downloads/project/` 下，那就是 `/home/同事/Downloads/project/data/orders.csv`。

**这就是为什么后面（W3-W4）我们要用 pathlib 来避免这个坑。** 现在你只需要知道：相对路径的起点是"你执行命令时所在的目录"，不是"脚本文件所在的目录"。

**2. 文件扩展名是约定，不是强制的**

`orders.csv` 的 `.csv` 只是一个名字的一部分。你可以把一个 Excel 文件命名为 `report.csv`——系统不会阻止你。`pd.read_csv()` 会尝试把它当 CSV 解析——然后报错，因为里面其实是 Excel 的二进制格式。

**3. 文本文件 vs 二进制文件**

这是本周最重要的一个概念。

- **文本文件**（`.txt` `.csv` `.py` `.json` `.md`）：内容是字符。你可以用记事本打开，看到可读的文字。
- **二进制文件**（`.xlsx` `.parquet` `.png` `.mp4`）：内容是字节。用记事本打开看到乱码。

但真正的区别不是"能不能看懂"——而是：**文本文件有"编码"的概念，二进制文件没有。**

编码是什么？说白了就是：**计算机只认识数字（字节）。要把字符变成字节，需要一个对照表。这个对照表就是编码。**

**4. 编码——为什么中文 CSV 总乱码**

ASCII：最早的编码，只能表示 128 个字符（英文大小写+数字+标点）。中文？放不下。

GBK/GB2312：中国自己搞的编码，能用。但日本人搞了 Shift-JIS，韩国人搞了 EUC-KR——各国各搞各的。

UTF-8：现代标准。全球所有字符统一编码。英文字符用 1 个字节，中文字符用 3 个字节。

问题来了：一个 CSV 文件本身不标注"我是 GBK 编码"。你用记事本打开一个 GBK 编码的中文 CSV——记事本可能用 GBK 打开（Windows 中文版默认），中文正常。你把同一个文件发给 Mac 同事——Mac 默认用 UTF-8 打开——乱码。

**Python 里怎么处理？**
```python
# 如果 CSV 是 GBK 编码的（最常见的情况：从 Excel 导出）
df = pd.read_csv('data/users.csv', encoding='gbk')

# 如果 CSV 是 UTF-8 编码的
df = pd.read_csv('data/orders.csv', encoding='utf-8')

# 怎么看一个文件是什么编码？试试 VS Code 右下角——它会自动检测并显示
```

**5. BOM——Excel 导出的 CSV 第一列多了个看不见的字符**

这是 Windows 上最经典的数据分析坑。用 Excel 导出 CSV 时，UTF-8 文件开头可能被加了一个隐藏字符 BOM（Byte Order Mark，字节序标记 `\ufeff`）。你 `pd.read_csv()` 之后发现第一列的列名变成了 `\ufefforder_id` 而不是 `order_id`。

解法：`pd.read_csv('file.csv', encoding='utf-8-sig')`——`utf-8-sig` 会自动去掉 BOM。

**6. 换行符**

Windows：`\r\n`（回车+换行，两个字符）
Linux/Mac：`\n`（换行，一个字符）
旧版 Mac：`\r`（回车，一个字符）

Git Bash 可以配置自动转换。Python 的 `open()` 默认用 `\n`。这个问题通常不严重，但如果你在 Windows 记事本里写代码然后放到 Linux 上跑——可能出问题。

## D4（周四 7/31）：项目骨架设计——为什么 src/tests/data/output 不是随便分的

> 📓 今日主课：文件 IO 与字符串与正则（csv/json/re）

---

### 🔴 认知冲突

你按照教程执行了 `mkdir -p src tests data output`，建了标准目录结构。然后在 `main.py` 里写 `from src.io import load_orders`——运行——`ModuleNotFoundError: No module named 'src'`。

你搜了一下，有人说要在项目根目录执行 `python main.py`。你照做了——还是报错。又有人说要加 `sys.path.insert(0, '.')`。你加了——能跑了。但你不知道为什么有时候需要加，有时候不需要。

**问题**：`from src.io import load_orders`——Python 是怎么找到 `src/io.py` 的？`__init__.py` 文件到底干什么用的？为什么同样是导入，有时候要从项目根目录执行，有时候不需要？

---

### 📖 核心原理

**Python 的 import 搜索机制**

当你写 `from src.io import load_orders`，Python 在找什么？

1. Python 先找 `src`——它去哪里找？去 `sys.path` 里列出的目录，一个一个找。
2. `sys.path` 第一个条目永远是**执行脚本所在的目录**（而不是脚本文件所在目录）。
3. 如果你的 `main.py` 在项目根目录、你也在项目根目录执行 `python main.py`——那么项目根目录在 `sys.path` 里——Python 能找到 `src/` 文件夹——`from src.io import ...` 成功。
4. 如果你在别的目录执行 `python /path/to/main.py`——`sys.path` 第一个条目是那个"别的目录"——Python 找不到 `src/`——报错 `ModuleNotFoundError`。

**所以规则是：在你的项目根目录下执行 `python main.py`。不要从别的地方执行。**

**`__init__.py` 到底干嘛的？**

两个作用：

**作用一：标识"这是一个包"。** 没有 `__init__.py`，Python 不会把 `src/` 目录当作一个包——`from src.io import ...` 仍然可能工作（Python 3.3+ 有隐式命名空间包），但不可靠。

**作用二：控制"`from src import *`"的行为。** 在 `__init__.py` 里定义 `__all__ = ['io', 'clean', 'analyze']`，`from src import *` 就只导入这三个模块。但一般很少用 `import *`。

对现在的你来说：**每个想被 import 的子目录里放一个空的 `__init__.py`，就够了。**

```bash
touch src/__init__.py
touch tests/__init__.py
```

**为什么要有 `src/` 这一层？不能直接把 `.py` 文件放根目录吗？**

能。一个 200 行的脚本不需要 `src/`。但你的项目会长大——现在 3 个 `.py` 文件，3 个月后可能 15 个。`src/` 这一层有两个好处：

1. **命名空间隔离**：你的函数叫 `load_orders`，pandas 里也可能有个东西叫 `load_orders`。用了 `from src.io import load_orders`——明确告诉 Python 和读代码的人：这个 `load_orders` 是我项目里的，不是第三方库的。
2. **根目录干净**：别人打开你的仓库，看到的是 `src/` `tests/` `data/` `README.md`——一眼知道哪是代码、哪是测试、哪是数据。如果把 15 个 `.py` 文件全摊在根目录，找 `main.py` 都要翻半天。

**每个文件的职责为什么要分开？（io.py vs clean.py vs analyze.py）**

这背后是一个软件工程的核心原则：**分离关注点（Separation of Concerns）。** 说人话：每个文件只做一类事，换一个文件就是换了一种"关注视角"。

```
io.py      → 关注"数据怎么进出"——读 CSV、读 Excel、写 Parquet、连接数据库
clean.py   → 关注"数据怎么变干净"——去空值、去异常、类型修正
analyze.py → 关注"数据怎么变出结论"——聚合、分组、RFM、同期群
```

为什么要这样？因为修改的节奏不一样。你可能经常改分析逻辑（"老板说这周换一种分群方式"），但很少改 IO 逻辑（"读 CSV 的方式不会每周换"）。放在不同文件里——改分析时只改 `analyze.py`，不用担心不小心改坏了 `io.py`。

不是"规定"——是"你写 3 个月代码之后自己会想这样做"。现在先养成习惯。

## D5（周五 8/1）：.gitignore 的工作原理——为什么加了规则还是被跟踪

> 📓 今日主课：代码组织与模块化（import/venv/PEP8）

---

### 🔴 认知冲突

你在 `.gitignore` 里加了一行 `*.csv`，想让 Git 忽略所有 CSV 文件。但 `data/orders.csv` 还是出现在了 `git status` 里。

你又加了 `data/`——CSV 文件消失了。但过两天你新建了 `output/report.csv`——它又出现在 `git status` 里了。你明明写了 `*.csv`，为什么不管用？

然后同事告诉你："已经被 Git 跟踪的文件，加 `.gitignore` 规则不会生效。"你执行了 `git rm --cached data/orders.csv`——文件从 Git 跟踪中移除了，但也从你的本地目录消失了？

**问题**：`.gitignore` 到底是怎么工作的？为什么同样的规则，对"已经跟踪"和"还没跟踪"的文件行为不一样？glob 模式匹配是什么？

---

### 📖 核心原理

**`.gitignore` 只对"未跟踪"文件生效**

这是整个 `.gitignore` 机制的核心规则——也是最容易被误解的一条。

Git 把文件分成两类：
- **已跟踪（Tracked）**：曾经被 `git add` + `git commit` 过的文件。Git 在持续监控它们的变化。
- **未跟踪（Untracked）**：从未被 `git add` 过的文件。Git 看到它们在那里，但不管它们。

`.gitignore` 告诉 Git：**"遇到未跟踪的文件时，如果文件名匹配这些规则，就不要提醒我它们存在。"**

但是——**如果文件已经被跟踪了，`.gitignore` 对它无效。** 因为你已经告诉过 Git "这个文件值得跟踪"——Git 不会因为你后来改主意就自动放弃它。

**那已经跟踪的敏感文件怎么办？**

```bash
# git rm --cached：从 Git 的跟踪清单里移除，但不删本地文件
git rm --cached data/secret.csv

# 然后加到 .gitignore 里：
echo "data/secret.csv" >> .gitignore

# 提交这个变更：
git add .gitignore && git commit -m "stop tracking secret.csv" && git push
```

这里有一个容易踩的坑：**`git rm --cached` 只移除跟踪，不删本地文件。** `git rm`（不带 `--cached`）会同时删除本地文件。两个的区别：
- `git rm file` = 删本地文件 + 删跟踪记录 → 文件真的没了
- `git rm --cached file` = 只删跟踪记录 → 文件还在，Git 不再管它

**glob 模式匹配**

`.gitignore` 里的规则不是正则表达式。它用的是 shell glob 模式：

| 规则 | 匹配 | 不匹配 |
|------|------|--------|
| `*.csv` | `orders.csv`, `a/b/c.csv` | `orders.csv.bak` |
| `data/` | `data/orders.csv`, `data/subdir/file.csv` | `backup_data/file.csv` |
| `data/*.csv` | `data/orders.csv` | `data/subdir/orders.csv` |
| `data/**/*.csv` | `data/subdir/orders.csv`, `data/a/b/orders.csv` | `root/orders.csv` |
| `__pycache__/` | 任何目录下的 `__pycache__/` | `__pycache__` 这个文件 |

**规则文件路径是相对于项目根目录的。** `data/*.csv` 只匹配项目根目录下 `data/` 里的 CSV 文件，不匹配 `src/data/orders.csv`。要匹配所有子目录，用 `**/*.csv` 或直接 `*.csv`。

**`.gitignore` 的优先级和"反向规则"**

如果 `.gitignore` 在同一路径有矛盾规则，后面的覆盖前面的：
```
*.csv          # 忽略所有 CSV
!important.csv # 但不忽略 important.csv
```

`!` 开头的规则叫"反向规则"（negation pattern）——把之前被忽略的文件再拉回来。

---

### 🏢 鲜果多案例

前任在鲜果多的桌面文件夹里放了一个 `数据库密码.txt`。你不小心 `git add .` 把它也加入跟踪了。然后你 `git push` 到了 GitHub 公开仓库。

现在全世界都能看到你的数据库密码。你删除了这个文件，加了 `.gitignore`——但密码还在 GitHub 的 commit 历史里。任何人都可以用 `git log` 翻出那个 commit，看到完整的密码。

**工具链层面你学到的教训**：`.gitignore` 用来防止未跟踪的敏感文件被提交。但如果已经提交了，需要更多步骤（`git filter-branch` 或重设密码）。**最好的策略是从第一天就用 `.gitignore` 保护好敏感文件。**

鲜果多项目的 `.gitignore` 应该至少含：
```

.ipynb_checkpoints/

# 虚拟环境

# 数据文件（包含真实业务数据）

# 输出（可重新生成的）
output/

# 敏感信息
.env
```

3. 故意在项目根目录创建一个不在 `.gitignore` 里的文件：`echo "secret" > password.txt`，执行 `git status`——它应该出现。然后把这个文件加入 `.gitignore`：`echo "password.txt" >> .gitignore`——`git status` 再看——它消失了。

### ✅ 自检反馈

**✅ 参考答案**

- `data/test_ignore.csv` 不应该出现在 `git status` 的输出里（如果 `data/*.csv` 规则生效）。
- `password.txt` 在被 commit 之后，`.gitignore` 对它无效。`git rm --cached password.txt` 后它会从跟踪中移除，但本地文件还在。
- `git rm --cached` **不删除本地文件**。如果文件从电脑上消失了，说明你忘了加 `--cached`。

**❓ 常见偏差**

| 偏差 | 原因 | 🔧 补救 |
|------|------|---------|
| "加了规则但文件还出现在 git status" | 文件已经被跟踪了 | `git rm --cached 文件路径` 移除跟踪（注意加 `--cached`） |
| "`git rm --cached` 后文件消失了" | 忘了 `--cached`，用了 `git rm`——它删了本地文件 | 从回收站找回（或者从 commit 历史恢复：`git checkout HEAD -- 文件路径`） |
| "`*.csv` 规则不生效" | 规则在 `.gitignore` 里的位置可能不对——规则是按行读取的，后面的反向规则可能覆盖了它 | 检查 `.gitignore` 文件，确保没有 `!` 开头的规则在覆盖它 |

```python
"""数据读写模块：CSV/Excel/Parquet 的读取和写入。

所有 I/O 函数统一返回 pd.DataFrame，统一在 DATA_DIR 下操作。
"""
import pandas as pd
from pathlib import Path

DATA_DIR = Path(__file__).parent.parent / "data"


def load_orders(filename: str = "orders.csv") -> pd.DataFrame:
    """加载订单数据。

    Args:
        filename: 订单文件名，默认 orders.csv

    Returns:
        含订单数据的 DataFrame
    """
    filepath = DATA_DIR / filename
    return pd.read_csv(filepath)


def load_users(filename: str = "users.csv") -> pd.DataFrame:
    """加载用户数据。注意：users.csv 可能为 GBK 编码。

    Args:
        filename: 用户文件名，默认 users.csv

    Returns:
        含用户数据的 DataFrame
    """
    filepath = DATA_DIR / filename
    # 先尝试 UTF-8，失败则尝试 GBK
    try:
        return pd.read_csv(filepath, encoding="utf-8")
    except UnicodeDecodeError:
        return pd.read_csv(filepath, encoding="gbk")
```

**Step 6：创建 main.py 入口**
```python
"""鲜果多数据分析项目——主入口。

运行方式：在项目根目录下执行 python main.py
```

### 📝 8 道概念自测题

**Q1**：终端、Shell、命令行——这三个词的区别是什么？为什么 Windows 用户要装 Git Bash？

**Q2**：Git 的"三棵树"是哪三棵？`git add` 把文件从哪棵树移到哪棵树？`git commit` 呢？

**Q3**："Git 的每个 commit 都是完整快照，不是增量"——这句话是什么意思？如果每个 commit 都存完整文件，硬盘不会爆炸吗？

**Q4**：`data/orders.csv` 这个路径中的 `/` 在 Windows 上能用吗？为什么？相对路径的"起点"是哪？

**Q5**：你有一个中文 CSV 文件，`pd.read_csv()` 中文全是乱码——排查步骤是什么？

**Q6**：`from src.io import load_orders`——Python 是怎么找到 `src/io.py` 的？（提示：`sys.path` 的第一个条目是什么？）

**Q7**：`.gitignore` 对已经 git commit 过的文件生效吗？如果不生效，你怎么阻止它们继续被跟踪？

**Q8**：以下这段 `.gitignore` 规则各自匹配什么？
```
__pycache__/
*.pyc
data/*.csv
output/
.env
```

---

### ✅ 参考答案 + 偏差诊断

**Q1 答案**：
- 终端：窗口（硬件+界面的抽象）
- Shell：翻译官（bash/zsh/cmd/PowerShell）
- 命令行：交互方式（用文字而非鼠标）
- 为什么装 Git Bash：Python 生态基于 Unix 惯例。bash 的 `ls`/`/`分隔符/`export` 等语法和绝大多数教程一致。cmd 不一样。
- 偏差：把三者说成同一个东西 → 重读 D1 第一段。

**Q2 答案**：
- 三棵树：工作目录（你编辑文件的地方）→暂存区（git add 后文件到这里）→仓库（git commit 后存为永久快照）
- `git add`：工作目录 → 暂存区
- `git commit`：暂存区 → 仓库
- 偏差：分不清 add 和 commit 的区别 → 重读 D2"三棵树"图示。

**Q3 答案**：
- "完整快照"：每个 commit 概念上存储了那个时间点所有文件的完整状态
- 不会爆炸的原因：Git 内部有 dedup 机制——没变的文件不重复存储，相似文件被打包压缩
- 偏差：说"Git 存的是差异" → 这是 SVN 的模型，不是 Git 的。重读 D2"Commit 是完整快照"段。

**Q4 答案**：
- Windows 上 Python 能用 `/`，因为 Python 会自动转换
- 相对路径的起点是**当前工作目录**（cwd），即你执行 `python main.py` 时的目录
- 偏差：说"起点是脚本文件所在目录" → 这是错的。`os.getcwd()` 和 `__file__` 是两回事。重读 D3"路径分隔符"段。

**Q5 答案**：
1. 用 VS Code 打开文件，看右下角编码
2. 先试 `encoding='utf-8'`
3. 不行试 `encoding='gbk'`
4. 再不行试 `encoding='utf-8-sig'`（处理 BOM）
5. 如果还乱码，用 `chardet` 库检测
- 偏差：说"换一个文件" → 这是在回避问题。真实工作中你换不了数据源。

**Q6 答案**：
- Python 在 `sys.path` 的目录列表里逐个搜索 `src` 包
- `sys.path` 第一个条目是**执行脚本时所在的目录**（cwd）
- 如果 cwd 是项目根目录，`src/` 就在 `sys.path[0]` 下，Python 能找到它
- 偏差：说"Python 全局搜索" → Python 不会全盘搜索，只在 `sys.path` 里找。

**Q7 答案**：
- 不生效。已跟踪的文件被 `.gitignore` 忽略不了。
- 解法：`git rm --cached 文件路径`——从跟踪中移除但不删本地文件。
- 偏差：说"直接 git rm 就行" → `git rm` 不加 `--cached` 会删除本地文件。

**Q8 答案**：
- `__pycache__/`：任何目录下的 `__pycache__` 文件夹
- `*.pyc`：任何目录下以 `.pyc` 结尾的文件
- `data/*.csv`：仅 `data/` 目录下的 CSV 文件（不含子目录）
- `output/`：任何目录下的 `output` 文件夹
- `.env`：任何目录下的 `.env` 文件
