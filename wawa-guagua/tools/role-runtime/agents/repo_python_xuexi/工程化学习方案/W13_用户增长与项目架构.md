### 🔴 认知冲突

新同事 clone 后打开 `src/`——看到 8 个文件——哪个是入口？哪个是内部实现？`experiment.py` 和 `analyze.py` 是什么关系——experiment 调用 analyze——还是 analyze 调用 experiment？`tracking.py` 是独立的还是被其他人调用的？他需要打开每个文件——读 import 语句——手动画依赖图——才能理解架构。

这不是"文件太多了"的问题——是**模块之间的边界没有显式化**。8 个文件平铺 = 没有层次。没有层次 = 没有"从哪开始读"的入口。没有入口 = 每个新来的人都要从零推导架构。

**问题**：不是"建子目录就行了"——子目录之间必须有清晰的单向依赖——每个子目录必须有一个"对外的接口"（facade）。这样新同事打开 `src/data/__init__.py`——看到 5 个对外函数——就知道"数据层能做什么"——不需要打开 3 个内部文件。

---

### 📖 核心原理

**项目架构的进化——从平铺到分层。不是"文件多了就建子目录"——是有三个判断标准：**

**标准 1：子目录之间有清晰的单向依赖吗？**

你的 8 个模块的数据流向：加载(io) → 验证(validate) → 清洗(clean) → 分析(analyze) → 可视化(visualize)。实验(experiment)和归因(attribution)在分析之后、可视化之前。埋点(tracking)是独立的数据来源——在加载之前。

```
src/
├── data/          # 数据层——IO + 验证 + 清洗。依赖: 无（最底层）
│   ├── __init__.py    ← facade: 只暴露 load_orders, validate_input, clean_amounts
│   ├── io.py
│   ├── validate.py
│   └── clean.py
├── analysis/      # 分析层——分析 + 实验 + 归因。依赖: data/
│   ├── __init__.py    ← facade: 只暴露 compute_gmv, run_ab_test, run_attribution
│   ├── metrics.py
│   ├── experiment.py
│   └── attribution.py
├── viz/           # 可视化层。依赖: analysis/
│   ├── __init__.py    ← facade: 只暴露 plot_trend, plot_heatmap
│   └── charts.py
└── utils/         # 工具层——路径常量 + 日志配置。依赖: 无
    ├── __init__.py
    ├── paths.py
    └── logger.py
```

**单向依赖**：`data/` ← `analysis/` ← `viz/`。`utils/` 不依赖任何业务模块——被所有人依赖。没有循环——`analysis/` 不 import `viz/`——`viz/` 不 import `analysis/`（它只读 analysis 的输出——不调 analysis 的函数）。

**标准 2：每个子目录有一个"对外的接口"（facade）吗？**

`data/__init__.py`：
```python
# src/data/__init__.py —— 数据层的对外接口（Facade）
from src.data.io import load_orders, load_users
from src.data.validate import validate_input
from src.data.clean import clean_amounts, remove_outliers

__all__ = ['load_orders', 'load_users', 'validate_input', 'clean_amounts', 'remove_outliers']
```

调用方只需要 `from src.data import load_orders, validate_input`——3 个词。不需要知道 `load_orders` 在 `io.py` 里、`validate_input` 在 `validate.py` 里。内部文件可以任意重构——拆分或合并——只要 `__init__.py` 的接口不变——调用方完全不受影响。**这是 W2D1"隐藏实现、暴露接口"原则在项目级别的应用。**

**标准 3：新建子目录后——最常用的调用路径变简单了吗？**

以前：`from src.io import load_orders`（7 个目录层级——`src/io.py`）
现在：`from src.data import load_orders`（3 个词——`src.data`）

## D2（周二 10/21）：依赖关系管理——检测循环导入 + 依赖图文档化

> 📓 今日主课：获客分析——CAC/LTV/CAC 回收期/渠道归因

---

### 🔴 认知冲突

你昨天重构了子目录——一切正常——push 了。今天在 `src/viz/charts.py` 里加了一行 `from src.analysis.metrics import compute_gmv`——想在画图前自动聚合数据。然后 `python main.py` 报错：`ImportError: cannot import name 'plot_trend' from partially initialized module 'src.viz.charts'`——循环导入了。

你查了一下——`src/analysis/metrics.py` 在某处 import 了 `viz` 里的东西——可能是你三个月前写的一个"分析完自动出图"的便捷函数。和今天的改动叠在一起——循环闭合了——Python 报错了。

**问题**：循环导入不是 Python 的 bug——是**架构信号**：你的两个模块互相需要对方——说明它们之间的边界模糊了。A 需要 B——B 也需要 A——这说明 A 和 B 共享了一些东西——那部分应该提取到独立的 C——让 A 和 B 都只依赖 C。

---

### 📖 核心原理

**循环导入 = 两个模块互相 import。Python 的模块加载是自上而下的——A import B → B import A → 此时 A 还没加载完 → Python 报错。**

**检测——在重构前画依赖图——确保是单向无环的。** 在 README 中画模块依赖图（ASCII art）——以后重构时——第一件事就是更新这张图——检查有没有引入循环：

```
依赖方向（单向——从底层到上层）:

utils/          ← 不依赖任何业务模块
  ↑
data/           ← 依赖: utils/
  ↑
analysis/       ← 依赖: data/, utils/
  ↑
viz/            ← 依赖: analysis/, utils/
```

**如果出现循环——解法不是"把 import 挪到函数内部"（那是治标——下次还会踩）。解法是**提取共享逻辑**——创建独立模块——让双方都只依赖它。**

### 📖 自动化循环导入检测——不只依赖 Python 报错——而是在 CI 中预防

```python
import ast
from pathlib import Path
from collections import defaultdict

def build_import_graph(root_dir="src"):
    """构建项目的模块依赖图——AST 解析每个 .py 文件的 import 语句。"""
    graph = defaultdict(set)
    for py_file in Path(root_dir).rglob("*.py"):
        module = str(py_file.relative_to(root_dir)).replace("/", ".").replace("\\", ".").rstrip(".py")
        tree = ast.parse(py_file.read_text(encoding="utf-8"))
        for node in ast.walk(tree):
            if isinstance(node, ast.Import):
                for alias in node.names:
                    graph[module].add(alias.name)
            elif isinstance(node, ast.ImportFrom):
                if node.module:
                    graph[module].add(node.module)
    return dict(graph)

def detect_cycles(graph):
    """DFS 检测有向图中的环——返回发现的循环列表。"""
    WHITE, GRAY, BLACK = 0, 1, 2
    color = {node: WHITE for node in graph}
    cycles = []
    def dfs(node, path):
        color[node] = GRAY
        path.append(node)
        for neighbor in graph.get(node, []):
            if neighbor not in color:
                continue
            if color.get(neighbor) == GRAY:
                cycle_start = path.index(neighbor)
                cycles.append(path[cycle_start:] + [neighbor])
            elif color.get(neighbor) == WHITE:
                dfs(neighbor, path)
        path.pop()
        color[node] = BLACK
    for node in graph:
        if color.get(node) == WHITE:
            dfs(node, [])
    return cycles
```

**项目架构的三个反模式——每次重构时对照检查：**

| 反模式 | 症状 | 检测方法 | 修复 |
|-------|------|---------|------|
| **循环依赖** | Python ImportError——或某个模块的改动"莫名其妙"影响了不相关的模块 | detect_cycles()——CI 中自动跑 | 提取共享逻辑到 utils/——让双方都只依赖它 |
| **God Module** | 一个 .py 文件超过 500 行——含 IO / 清洗 / 分析 / 可视化 | wc -l src/**/*.py——排序——超过 500 行的拆分 | 按职责拆分——不是"按行数切"——是"按职责切"——IO 和清洗是不同的职责 |
| **Utility Dumping** | utils/ 里塞了 20+ 个不相关的函数 | utils/__init__.py 暴露 > 10 个函数——来自完全不相关的领域 | utils/ 只放真正的"工具"——路径常量 + 日志配置 + 类型定义。业务逻辑放回对应的业务模块 |

**三个架构反模式——每一个都是项目变大时的必然陷阱：**

| 反模式 | 症状 | 自动化检测 | 修复原则 |
|-------|------|----------|---------|
| **循环依赖** | Python ImportError——A import B, B import A | detect_cycles() 函数（DFS 环检测）——CI 中每次 push 自动跑 | 提取共享逻辑到 utils/——让 A 和 B 都只依赖 C |

## D3（周三 10/22）：用户画像工程化——从"跑一次 groupby"到"可复现的特征工程"

> 📓 今日主课：用户画像 + RFM 深度——RFM 三维分群/用户特征体系

---

### 🔴 认知冲突

你写了一个用户画像分析——RFM 分群 + 品类偏好 + 活跃时段。跑完了——给了运营总监。她一周后问"这个画像能每周更新吗？我想看用户结构的变化趋势。"——你说"可以"——然后你重新跑了脚本——结果和上周的**不完全可比**——因为你在两次之间微调了 RFM 的打分逻辑（从等频分箱改成了等距分箱）——但没有记录这个变化。

**问题**：用户画像不是"一次性分析"——是**需要定期更新、结果需要跨时间可比的特征工程**。每次分析的特征计算逻辑——必须在代码的 docstring 中显式声明——包括分箱策略、阈值来源、更新频率。否则——两周后的画像和两周前的画像不可比——趋势分析失去了基础。

---

### 📖 核心原理

**用户画像函数的标准接口——不只是"返回 DataFrame"——是"返回一个附带完整特征字典的 DataFrame"：**

```python
def build_user_profile(
    orders: pd.DataFrame,
    users: pd.DataFrame,
    reference_date: str
) -> pd.DataFrame:
    """构建用户画像特征表——可复现、可定期更新。

    粒度: 一行 = 一个用户（user_id 唯一）

    特征清单（10 维——每维标注计算逻辑和更新频率）:
    1. recency_days: 距参考日期的最近购买天数——天越少=越活跃
    2. frequency: 近 90 天购买次数
    3. monetary: 近 90 天累计消费金额
    4. r_score: R 分位打分（等频分箱 q=4, labels=[4,3,2,1]——最近=4分）
       为什么 q=4: 4 分位产生 4³=64 种 RFM 组合——合并为常见 8 类用户
    5. f_score: F 分位打分（等频分箱 q=4——频繁=4分）
    6. m_score: M 分位打分（等频分箱 q=4——高消费=4分）
    7. rfm_segment: 8 类用户标签（重要价值/重要发展/重要保持/重要挽留/一般价值/一般发展/一般保持/一般挽留）
    8. category_preference: 最常购买品类（按购买次数排序——取 Top1）
    9. active_hour_preference: 最活跃时段（按订单时间分组——取 Top1）
    10. avg_order_value: 平均客单价

    更新频率: 每周一 8:00 AM——处理截止上周日的数据
    注意: 分箱阈值基于当前快照——不同周期之间阈值可能不同——因此画像主要用于同期对比（本周 vs 上周的用户构成）——而非追踪个体用户的 RFM 分数变化（个体变化用 SCD Type2——W11D4）
    """
```

**为什么 docstring 里要写"分箱策略"和"更新频率"？** 因为这两项决定了"不同时间的画像是否可以比"。等频分箱→每次分的阈值不一样→同一用户的 RFM 分数可能因为别人变了而自己不变——这是"相对排名"——适合同期对比。等距分箱→阈值固定→同一用户的分数只有在自己行为改变时才变——适合追踪个体变化。如果你不声明——使用者（包括三个月后的你）不知道——会错误地对比不同分箱策略下的画像。

---

```python
    """构建项目的模块依赖图——AST 解析每个 .py 文件的 import 语句。"""
    graph = defaultdict(set)
    for py_file in Path(root_dir).rglob("*.py"):
        module = str(py_file.relative_to(root_dir)).replace("/", ".").replace("\\", ".").rstrip(".py")
        tree = ast.parse(py_file.read_text(encoding="utf-8"))
        for node in ast.walk(tree):
            if isinstance(node, ast.Import):
                for alias in node.names:
                    graph[module].add(alias.name)
            elif isinstance(node, ast.ImportFrom):
                if node.module:
                    graph[module].add(node.module)
    return dict(graph)

def detect_cycles(graph):
    """DFS 检测有向图中的环——返回发现的循环列表。"""
    WHITE, GRAY, BLACK = 0, 1, 2
    color = {node: WHITE for node in graph}
    cycles = []
    def dfs(node, path):
        color[node] = GRAY
        path.append(node)
        for neighbor in graph.get(node, []):
            if neighbor not in color:
                continue
            if color.get(neighbor) == GRAY:
                cycle_start = path.index(neighbor)
                cycles.append(path[cycle_start:] + [neighbor])
            elif color.get(neighbor) == WHITE:
                dfs(neighbor, path)
        path.pop()
        color[node] = BLACK
    for node in graph:
        if color.get(node) == WHITE:
            dfs(node, [])
    return cycles
```

**项目架构的三个反模式——每次重构时对照检查：**

| 反模式 | 症状 | 检测方法 | 修复 |
|-------|------|---------|------|
| **循环依赖** | Python ImportError——或某个模块的改动影响了不相关的模块 | detect_cycles()——CI 中自动跑 | 提取共享逻辑到 utils/——让双方都只依赖它 |

```python
def retention_curve_analysis(cohort_matrix):
    """分析留存曲线的形状——识别拐点。

    留存曲线通常有三个阶段:
    1. 快速流失期（第 1-2 周）: 斜率最陡——用户快速筛选——不适合你的用户离开
    2. 缓慢流失期（第 3-8 周）: 斜率放缓——留下的用户在"试用"——体验决定留存
    3. 稳定期（第 9 周+）: 斜率接近水平——核心用户群——"产品-市场匹配"证据
    """
    weekly_retention = cohort_matrix.iloc[:, 0]
    weekly_changes = weekly_retention.pct_change().dropna()
    stable_mask = (weekly_changes.abs() < 0.02).rolling(3).sum() == 3
    stable_week = stable_mask[stable_mask].index[0] if stable_mask.any() else None
    stable_rate = cohort_matrix.iloc[0, stable_week] if stable_week else None
    return {"stable_week": stable_week, "stable_retention_rate": stable_rate}
```

### 📖 流失预警的完整工程化工作流——从特征到模型到干预 ROI 的四个阶段

**阶段 1——特征工程（D5 内容）：** 至少 8 个自描述特征。核心原则——每个特征名 = 特征含义 + 计算口径——days_since_last_order 而不是 x1。不可干预的特征（如年龄、性别）不要放在特征列表的前三位——前三位应该都是可干预的特征（如近 30 天订单数、优惠券使用率、客单价）——因为运营看到特征重要度 Top3 后——需要能针对这三个特征设计干预策略。

**阶段 2——模型训练与评估：**

```python
from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import roc_auc_score, confusion_matrix

def train_churn_model(features, target_col="is_churned"):
    """训练流失预警模型——不只输出预测——输出"为什么"。

    模型选择: Random Forest——不是因为最准——是因为能输出特征重要度——
    告诉运营"哪些行为最预示流失"——这是可解释性 > 精度 的场景。

    ⚠️ 关键评估指标: 召回率（Recall）——不是准确率（Accuracy）。
    流失用户通常只占 5-10%——如果模型预测"所有人都不流失"——准确率 = 90-95%——
    但这个模型没有任何价值。召回率 = 真正流失的用户中被模型正确预测的比例。
    """
    X = features.drop(columns=[target_col])
    y = features[target_col]
    model = RandomForestClassifier(n_estimators=100, max_depth=5, random_state=42)
    model.fit(X, y)
    importances = dict(zip(X.columns, model.feature_importances_))
    top3 = sorted(importances.items(), key=lambda x: x[1], reverse=True)[:3]
    y_pred = model.predict(X)
    y_prob = model.predict_proba(X)[:, 1]
    cm = confusion_matrix(y, y_pred)
    recall = cm[1, 1] / (cm[1, 0] + cm[1, 1])
    return {
        "model": model, "top_features": top3, "recall": recall,
        "auc": roc_auc_score(y, y_prob), "confusion_matrix": cm
    }
```

**阶段 3——干预策略设计：** 流失预警不是"预测谁会流失"就结束了——是"预测后采取什么行动"。
- 如果 Top1 特征是 days_since_last_order（距上次购买天数）——干预策略 = "对 >= 30 天未购买的用户推送限时优惠券"
- 如果 Top1 特征是 coupon_usage_rate（优惠券使用率）——干预策略 = "对使用率低的用户推送'首张优惠券额外折扣'"
- 如果 Top1 特征是 age（年龄）——你的特征设计有严重问题——年龄是不可干预的——模型选了一个"没法用的"特征作为最重要的特征——这说明你的可干预特征不够强——需要补充更多行为特征

**阶段 4——干预 ROI 估算：**

```
流失预警 ROI 公式:
  干预成本 = N_flagged x cost_per_intervention
  挽回收益 = N_flagged x P(actual_churn|flagged) x P(save|intervention) x user_LTV
  ROI = (挽回收益 - 干预成本) / 干预成本

鲜果多案例:
  N_flagged = 5000 人/月
  P(actual_churn) = 40%（precision——预测会流失的用户中 40% 真的会流失）
  P(save) = 25%（发 10 元券后 25% 高风险用户下月继续购买）
  user_LTV = 200 元/年

  挽回收益 = 5000 x 0.40 x 0.25 x 200 = 10 万元
  干预成本 = 5000 x 10 = 5 万元
  ROI = (10 - 5) / 5 = 100%——投入 1 元——挽回 2 元
```

这个 ROI 计算不是"精确预测"——是"在不确定条件下给运营一个判断基础"。如果 ROI = 100%——即使 P(save) 高估了 2 倍（实际只有 12.5%）——ROI 仍然是 0%——不亏。如果 ROI = 30%——一点误差就可能变成负的——需要更谨慎。

### 📝 闭卷自测

**Q1**：多模块项目分层的三个判断标准？什么是 facade——它解决了什么问题？

> **A**：①子目录间单向依赖 ②每个子目录有 facade ③分层后调用路径简化。Facade = `__init__.py` 只暴露对外函数——隐藏内部实现——调用方不需要知道函数在哪个内部文件。解决的问题：内部重构不影响外部——只要 facade 接口不变——调用方不受影响。偏差：说"Facade = __init__.py"——不只是空文件——是只暴露对外函数——内部辅助函数不暴露。

**Q2**：循环导入的根因是什么？解法是什么？为什么"把 import 挪到函数内部"是治标不治本？

> **A**：根因 = 两个模块互相需要对方——边界模糊。解法 = 提取共享逻辑到第三个模块——让两边都只依赖它。函数内 import = 隐藏了循环——但架构问题还在——下次加新功能时循环会再次闭合。偏差：说"Python 设计不好"——Python 只是把你架构的问题暴露出来了。

**Q3**：RFM 分箱策略为什么需要在 docstring 里声明？等频分箱和等距分箱——对"跨时间可比性"有什么影响？

> **A**：分箱策略决定了画像是否跨时间可比。等频分箱 = 相对排名——阈值每次不同——适合同期对比。等距分箱 = 绝对阈值——适合同一个体的长期追踪。不声明——使用者会错误对比不同分箱策略下的画像。偏差：说"都差不多"——会直接导致分析结论错误。

**Q4**：留存分析的"周期"定义为什么必须显式？"第一周"有哪两种可能的理解？

> **A**："第一周"可能 = 自然周（Mon-Sun）或注册后第 1-7 天（自然日——不管星期几）。两种定义给出不同的留存率——必须显式声明。偏差：假设"大家都知道"——不同公司用不同定义。

**Q5**：流失预警的特征名为什么不能是 x1/x2？特征名 = 什么？

> **A**：特征名 = 特征含义 + 计算口径——`days_since_last_order` 而不是 `x1`。两周后、两个月后、新同事——不需要翻代码就知道每个特征是什么。偏差：说"方便理解"——不只是方便——是"可复现"的前提——不知道 x1 是什么就无法复现。



**Q6**（架构设计）：鲜果多项目现在有 8 个模块。新同事问"为什么分 4 个子目录而不是 3 个或 5 个？"你怎么回答？

> **A**："4 个子目录对应 4 种不同的变化频率。utils/ 几乎不变——路径和日志配置。data/ 当数据源变更时才变——比如新增一个数据表。analysis/ 最常变——每次新增分析需求都变。viz/ 当图表样式需求变时才变——比如 CEO 想要新的看板。分层的核心原则不是文件数——是变化频率——把变化频率不同的代码放在不同的层——改分析时不担心影响数据加载——改图表时不担心影响分析逻辑。3 层 or 5 层取决于你的项目有多少种变化频率——鲜果多有 4 种——所以是 4 层。"

**Q7**（用户增长面试）：面试官问"你怎么评估一个用户增长策略的效果？"

> **A**："我分四步。第一步——确认策略的成功指标——不是"DAU 涨了"——而是具体的、可归因的指标——如"新用户首周购买 3 次+占比"。第二步——AB 实验（如果可随机化）或 DID/因果推断（如果不可随机化——如地域性策略）。第三步——不光看短期效果——看对长期留存的影响——策略可能短期拉新效果好但带来低质量用户——第 12 周留存率说明一切。第四步——ROI 计算——策略带来的增量 LTV vs 策略成本——不是"做实验看看"——是"预测-实验-验证-计算 ROI"——只有 ROI 为正的策略才值得长期投入。"

**Q8**（架构面试）：面试官看到你的 GitHub 项目——问"你这个项目的架构设计思路是什么？"

> **A**："我的项目按变化频率分成 4 层。data/ 层是数据接入——当数据源变更时只改这一层。analysis/ 层是分析逻辑——最常变——新增分析需求只加在这一层。viz/ 层是可视化——图表样式变更只改这一层。utils/ 是基础设施——几乎不变。每层通过 facade（__init__.py）暴露 <= 5 个对外函数——隐藏内部实现。依赖方向是单向的——data/ -> analysis/ -> viz/——没有循环。我在 CI 中集成了循环导入检测——每次 push 自动验证架构约束没有被破坏。"
