## D1（周一 8/18）：图表工程化——为什么画图代码要和数据处理分开

> 📓 今日主课：matplotlib——fig, ax = plt.subplots() / 五种图表 / 美化

---

### 🔴 认知冲突

你在 `analyze.py` 里写了：
```python
def analyze_monthly_trend(df):
    monthly = df.groupby(df['order_date'].dt.month)['amount'].sum()
    plt.figure()
    monthly.plot(kind='bar')
    plt.title('Monthly Revenue')
    plt.savefig('output/revenue.png')
    return monthly
```

这个函数做了三件完全不同的事：聚合数据（分析）、画柱状图（可视化）、保存图片（IO）。三个月后你想改图表样式——颜色、字体、尺寸——但你不敢改，因为这段代码和"按月聚合"的逻辑缠在一起，改坏了分析结果就错了。

**问题**：分析、可视化、IO——这三件事为什么应该在不同函数甚至不同文件里？画图函数到底应该接收什么、返回什么？

---

### 📖 核心原理

**数据可视化的三层架构**

```
数据层（Data Layer）       → 映射层（Mapping Layer）     → 渲染层（Rendering Layer）
"数据说什么"                "数据怎么变成图形元素"         "图形元素长什么样"

analyze.py                 visualize.py                visualize.py
返回数值结果               接收数值→决定图表类型         决定颜色/字体/标题/尺寸
                          返回 (fig, ax) 元组          不碰数据，只碰样式
```

**为什么要把映射层和渲染层分开？**

因为它们的修改节奏不一样：
- 映射层：和你选择什么图表类型有关——"这个指标用折线图还是柱状图？"——这取决于数据和分析目的。改的不频繁，但一改就影响分析结论。
- 渲染层："标题字号多大？颜色用什么？"——这取决于给谁看（CEO 还是 PM）。改的频率高，但改了不影响数据结论。

**画图函数的标准化接口**

```python
# visualize.py
import matplotlib.pyplot as plt
from typing import Tuple

def plot_monthly_revenue(monthly: pd.Series, title: str = '月度营收趋势') -> Tuple[plt.Figure, plt.Axes]:
    """画月度营收柱状图。

    数据层（analyze.py）负责传入聚合好的数据。
    本函数只负责"把数据映射成图形"和"渲染样式"。

    Args:
        monthly: index=月份, values=营收
        title: 图表标题（应该是结论而非描述）

    Returns:
        (fig, ax) 元组——调用方可以用 fig.savefig() 保存
    """
    fig, ax = plt.subplots(figsize=(10, 6))
    monthly.plot(kind='bar', ax=ax, color='steelblue')
    ax.set_title(title, fontweight='bold', fontsize=14)
    ax.set_xlabel('月份')
    ax.set_ylabel('营收 (万元)')
    ax.tick_params(axis='x', rotation=0)
    return fig, ax
```

画图函数返回 `(fig, ax)` 元组——调用方自己决定怎么保存、要不要再叠加别的元素。画图函数不保存文件（那是 IO 的职责）。

**图表标题的信息密度——"说结论，不说内容"**

```python
# ❌ 内容式标题：看完标题不知道结论
ax.set_title("Monthly Revenue by City")

# ✅ 结论式标题：看完标题就知道结论
ax.set_title("北京贡献 45% 营收，杭州增速最快 (+32%)", fontweight="bold")
```

内容式标题是"数据描述"——它只是告诉读者这张图用了什么数据。结论式标题是"分析输出"——它直接把分析结论写在标题里。读者不需要看图表就能抓住信息。

**规则**：标题至少含一个具体的数字（绝对值或百分比）+ 一个比较维度。如果写不出这样的标题——说明你还没分析透。

## D2（周二 8/19）：列式存储 vs 行式存储——Parquet 为什么比 CSV 快 10 倍

> 📓 今日主课：seaborn——heatmap/pairplot/catplot + 图表叙事

---

### 🔴 认知冲突

你按照旧版任务清单的 W4D3 做了 CSV vs Parquet 对比实验。结果让你印象深刻——Parquet 文件比 CSV 小 8 倍，读取快 6 倍。你记住了"Parquet 更快更小"。

但面试官追问了一句："为什么？"你只能说"因为它是列式存储"。——"列式存储为什么就比行式存储快？""什么时候 Parquet 反而不如 CSV？"你答不上来。

**问题**："Parquet 更快"是结论不是理解。列式存储快在哪里——为什么分析型查询（SELECT amount, AVG(amount)）快，而全行扫描（SELECT *）不一定快？

---

### 📖 核心原理

**CSV 是行式存储——数据按行连续存放。**

```
CSV 文件在硬盘上的物理布局：
order_id=1, user_id=A, amount=100, city=北京\n
order_id=2, user_id=B, amount=200, city=上海\n
order_id=3, user_id=C, amount=150, city=北京\n
```

当你要"所有行的 amount 列"时——CPU 必须逐行扫描，读完第一行的 amount（跳过 order_id 和 user_id），读第二行的 amount（又跳过一堆），依次类推。这就是为什么 `pd.read_csv()['amount']` 虽然只需要一列，但**整个文件都要读进内存**——然后 pandas 再丢弃不需要的列。

**Parquet 是列式存储——数据按列连续存放。**

```
Parquet 文件在硬盘上的物理布局：
order_id:  [1, 2, 3, 4, 5, ...]     ← 这一整块全是 order_id
user_id:   [A, B, C, D, E, ...]     ← 这一整块全是 user_id
amount:    [100, 200, 150, 300, ...] ← 这一整块全是 amount
city:      [北京, 上海, 北京, ...]    ← 这一整块全是 city
```

当你只要 amount 列时——存储引擎直接跳到 amount 那块，连续读取。不需要碰其他列。

**Parquet 比 CSV 快的四个原因——不只是列式存储**

| 优势 | 原理 | 具体收益 |
|------|------|---------|
| **列式存储** | 只需要读用到的列，不需要读全表 | 2-10x 读取加速 |
| **列内压缩** | 同一列的数据类型相同、值域相似，压缩率极高 | 5-20x 文件缩小 |
| **Schema 内嵌** | 列名和类型写在文件元数据里，不需要像 CSV 那样猜类型 | 消除 `pd.read_csv()` 的自动类型推断开销 |
| **谓词下推** | 查询引擎在读文件之前就知道哪些行可以跳过（如果按某列排序的话） | 再加 5-100x 加速（在 SQL 引擎中使用时） |

**什么时候 Parquet 反而不如 CSV？**

1. **数据量很小**（< 1000 行）：Parquet 的元数据开销 > CSV 的简单性
2. **需要人肉眼阅读**：CSV 可以用记事本打开，Parquet 是二进制文件——人读不了
3. **一次性的、结构多变的数据**：Parquet 的 schema 是固定的，改列名/列类型需要重建文件
4. **需要 append 追加写入**：CSV 直接追加一行文本，Parquet 追加需要重写文件的 footer 元数据

**在你的阶段，记住这条规则就够了：**
- 中间结果（自己要读多次的）：用 Parquet
- 最终输出（要给运营总监看的）：用 CSV（他能双击打开）
- 原始数据（别人给你的）：保持原样，另存一份 Parquet 用于分析

---

## D3（周三 8/20）：pipe 模式——方法链不只是少写变量

> 📓 今日主课：数据清洗——MCAR/MAR/MNAR/IQR/Z-score/IsolationForest

---

### 🔴 认知冲突

你的 `main.py` 里现在有一个清洗序列：
```python
orders = load_orders()
orders = clean_dates(orders)
orders = clean_amounts(orders)
orders = remove_outliers(orders)
orders = fill_missing(orders)
```

你在这个基础上加了一个新步骤 `normalize_cities(orders)`，但放错了位置——放到了 `remove_outliers` 之前，后来发现应该放在 `clean_dates` 之后。你调整了顺序。然后某次调试时你注释掉了中间某一行——下面所有行都崩了，因为变量名对不上。

**问题**：用中间变量（`df1`/`df2`/`df3`）有什么不好？pipe 模式能解决什么问题——只是少写几个变量名吗？

---

### 📖 核心原理

**中间变量的三个问题**

1. **命名困难**：`df1`/`df2`/`df3`——这是偷懒。`orders_after_clean`/`orders_after_outliers`/`orders_after_fill`——太长了。而且每个步骤做完后数据"状态"变了，给它取名字等于在描述那个状态——洗了 5 步就要取 5 个名字。
2. **变量误用**：你把 `df2`（去掉异常值后的数据）传给了一个本应接收 `df1`（清洗后的数据）的函数——程序没报错（因为都是 DataFrame），但你得到的是"去异常值但没清洗"的结果。
3. **步骤增删改很难**：你要在第二步和第三步之间插入一个新步骤——需要重命名后续所有变量（`df2`→新步骤→`df3`→`df4`...）。

**pipe 解决的核心问题——名称污染和变量误用**

```python
# pipe 链式：没有中间变量，也就没有变量误用
orders = (pd.read_csv('data/orders.csv')
          .pipe(clean_dates)
          .pipe(clean_amounts)
          .pipe(remove_outliers)
          .pipe(fill_missing)
          .pipe(normalize_cities))  # 在 fill 之后加——语义正确
```

每一行的 `.pipe(step)` 语义清晰：把上一步的结果传给下一步。阅读顺序是线性的（从上到下），不像中间变量版本——你需要追踪"哪个变量传给哪个函数"。

**pipe 函数的签名规范**

pipe 能够工作，是因为每个函数的签名统一：
```python
def clean_dates(df: pd.DataFrame) -> pd.DataFrame: ...
def clean_amounts(df: pd.DataFrame) -> pd.DataFrame: ...
def remove_outliers(df: pd.DataFrame) -> pd.DataFrame: ...
```

输入 DataFrame → 输出 DataFrame。每一步都不改类型——只改内容。这就是 **DataFrame-in-DataFrame-out 模式**。

如果某个函数还需要额外参数：
```python
orders = (pd.read_csv('data/orders.csv')
          .pipe(clean_dates)
          .pipe(remove_outliers, cols=['amount', 'quantity'], method='iqr'))
# 额外参数跟在函数后面，pipe 自动传给函数
```

**pipe 不是万能的——哪些场景不适合 pipe？**

- 函数返回的不是 DataFrame（返回 dict、Series、tuple）——不能用 pipe
- 需要分支逻辑（"如果 A 则清洗方式 1，否则清洗方式 2"）——pipe 不适合条件分支
- 调试时想检查中间结果——pipe 的中间状态不可见。这时候可以注释掉 pipe 链，临时展开成变量

---

### 🏢 鲜果多案例

鲜果多的清洗步骤随着你发现的数据问题越来越多——从 3 步变成 7 步。变量名从 `df1` 到 `df7`——你在 W3D2 加了一个新的校验步骤，插在了"清洗金额"和"去异常"之间——不得不重命名所有后续变量。改完后 `analyze.py` 里的 import 崩了——因为变量名变了。

用 pipe 重构后——7 个步骤就是 7 行 `.pipe(xxx)`。插新步骤只需加一行。

**✅ 参考答案**

**❓ 常见偏差**

| 偏差 | 原因 | 🔧 补救 |
|------|------|---------|
| "pipe 报错 `'function' object has no attribute...`" | 写成 `df.pipe(fn())` 而不是 `df.pipe(fn)`——你调了函数而不是传函数引用 | `.pipe(fn)` 不加括号。有参数时：`.pipe(fn, arg1=val)` |
| "pipe 中间想加 logger 怎么办" | pipe 不阻止你在函数内部加 logger——`clean_dates` 内部的第一行就是 `logger.info('开始清洗日期...')` | logger 放在函数内部，pipe 链保持简洁 |
| "pipe 不如变量版容易调试" | 确实。pipe 牺牲了"可以用 print 看中间结果"的便利 | 这是 tradeoff。便捷性换正确性——你不需要 print 中间结果了（有 logging），你更需要防止变量误用 |

## D4（周四 8/21）：环境可复现——为什么"我电脑上能跑"是最危险的话

> 📓 今日主课：大文件——chunksize/category/Parquet/CSV vs Parquet 实测

---

### 🔴 认知冲突

W3 你在 `requirements.txt` 里列了直接依赖。今天你把这行代码加到 `main.py`：
```python
from datetime import datetime
```
——然后你在另一台电脑上 `pip install -r requirements.txt` → `python main.py` → 报错 `ModuleNotFoundError: No module named 'datetime'`。

不对——`datetime` 是 Python 标准库，不需要 pip install。出问题的不是库，是你的 Python 版本——一台是 3.10，一台是 3.11——但标准库的模块有什么差异呢？

然后你发现两边的 pandas 版本不一样——一台是 2.0.3（你的），一台是 2.1.0（新装的）。你的代码在 2.1.0 上报了一个 DeprecationWarning——某个参数在 2.1.0 被改名了。

**问题**：`requirements.txt` 只锁了直接依赖的版本。但 Python 版本、操作系统、文件路径分隔符——这些怎么保证一致？

---

### 📖 核心原理

**"可复现"有三个层次**

| 层次 | 内容 | 工具 | 你在 W4 应该做到 |
|------|------|------|----------------|
| **代码可复现** | 别人拿到你的代码能跑通 | Git + README | W1 ✅ |
| **依赖可复现** | 装上相同版本的库 | requirements.txt（锁版本） | W3 ✅ |
| **环境可复现** | 装上相同版本的 Python + 系统依赖 | Docker / 详细的环境文档 | W4 了解概念，W7 深入 |

**"我电脑上能跑"的三大根因**

1. **硬编码路径**：`pd.read_csv(r'C:\Users\你\Desktop\data.csv')`——别人电脑上没有这个路径。**解法：W1 就学了 pathlib，用相对路径。**
2. **操作系统差异**：`os.system('cls')`（Windows 清屏）在 Mac 上无效。文件名大小写：Windows 不区分大小写（`Orders.csv` = `orders.csv`），Linux 区分——你的代码在 Windows 上能跑，到 Linux 可能找不到文件。
3. **Python 版本差异**：Python 3.10 的 `str` 和 Python 3.11 的 `str` 没有区别。但 `pandas 2.0` 需要 Python 3.8+，如果你的机器上是最低支持的 Python 版本——某些功能可能不可用。

**你现在的阶段应该做什么**

不是装 Docker（那是 W7 的活）。而是——**明确声明你的环境。**

在 README 里加一个"开发环境"章节：
```markdown
## 开发环境

- 操作系统: Windows 11
- Python 版本: 3.10.x
- Shell: Git Bash (bash)
- 关键依赖: 见 requirements.txt

已在以下环境验证:
- Windows 11 + Python 3.10 + Git Bash ✅
- (待补充) Mac + Python 3.10 + zsh
```

以及——**做一次 clone 测试。** 这是 L1 验收的核心：cd 到另一个目录，clone，装依赖，跑。能跑通——你的环境是可复现的。跑不通——对照错误列出缺失的步骤，补到 README 里。

---

### 🏢 鲜果多案例

公司给鲜果多项目配了第二台电脑（一台台式机一台笔记本）。你在笔记本上 clone 鲜果多项目——装依赖时报错 `pip install -r requirements.txt` 在第 3 行失败，因为某个包只有 Windows 版本没有 Mac 版本（你笔记本是 Mac）。

**这就是环境可复现的含义**：不是"在所有操作系统上都能跑"，而是"知道在什么环境下能跑，在什么环境下不能跑"。

## D5（周五 8/22）：CI 思想——GitHub Actions 不是一个 yaml 文件

> 📓 今日主课：清洗流水线——pipe 链式 + 综合项目

---

### 🔴 认知冲突

你按照 W1D6 复制粘贴了一段 yaml 到 `.github/workflows/test.yml`，push 后看到绿色 ✓——"CI 通过了"。

但一个月后你改了代码——`main.py` 里引入了一个依赖：`from src.visualize import plot_trend`——本地能跑，但 GitHub Actions 显示了红色 ✗。你打开日志一看——`ModuleNotFoundError: No module named 'matplotlib'`。你忘了在 CI yaml 里加 `pip install matplotlib`。

**问题**：CI 不只是"push 后自动跑一下"。它的核心思想是什么？为什么数据分析师的代码也需要 CI？那个绿色 ✓ 到底意味着什么？

---

### 📖 核心原理

**CI（持续集成）的核心思想：每一次代码变更，都自动验证"代码还能正常工作"。**

"持续"的意思是——不只是"发布之前跑一次"，而是**每一次 push 都跑**。"集成"的意思是——你的改动和已有的代码合在一起（集成），而不是孤立地验证。

**CI 帮你防什么？**

1. **"忘了加依赖"**：你本地装了 matplotlib 但没更新 `requirements.txt`。CI 从零装依赖——炸了。这是最经典的 CI 发现的问题。
2. **"改了 A 但 B 崩了"**：你改 `clean.py` 的函数签名——改了参数顺序。`analyze.py` 里调这个函数——崩了。CI 跑了 `python main.py` 全流程——炸在 analyze 那一步。
3. **"在我电脑上能跑"**：CI 的环境是干净的 Ubuntu——没有你本地的各种缓存和配置。CI 能跑 = 你的环境可复现声明被验证了。

**CI 配置的三个层次**

| 层次 | 验证内容 | 你的 yaml 应该做什么 | 对应 L 级别 |
|------|---------|-------------------|-----------|
| **冒烟测试（Smoke Test）** | 代码至少能跑通 | `pip install -r requirements.txt && python main.py` | L1-L2 |
| **完整测试** | 每个函数的行为符合预期 | `pytest tests/ -v` | L4 |
| **代码质量门禁** | Type Hints 正确 + 风格规范 | `mypy src/` + `ruff check src/` | L4 |

你目前在 L1-L2，CI 做冒烟测试就够了。但你要**理解**这不仅仅是"跑通就行"——它是你项目的自动化验证器。

**那个绿色 ✓ 的真正含义**

不是"代码完美无缺"。是"在我声明的环境条件下，代码从加载数据到输出结果的全流程没有报错"。

它不保证：
- 分析结论正确（你需要验证数据、双源验证）
- 代码没有 bug（你需要测试）
- 能在所有环境跑（CI 只验证 Ubuntu，不是 Mac/Windows）

它保证的是：你不会 push 一个连 `python main.py` 都跑不通的版本。

---

### 🏢 鲜果多案例

鲜果多项目现在有一个 `.github/workflows/test.yml`（你在 W1D6 创建的）。你每天 push 代码，CI 自动跑——绿了就放心，红了就去排查。

今天你改了 `analyze.py`，加了一个新的聚合维度。push 后 CI 变红了。打开日志——`KeyError: 'product_category'`。原来你用了这个列名，但在数据加载时你没有加这个列到 `required_cols` 里——CI 在干净环境重新加载的数据没有这个列。你在本地能跑是因为本地 `orders.csv` 有这个列——但新的数据可能没有。

**CI 帮你发现了一个"侥幸正确"的 bug。** 这是 CI 的第二层价值——不只是防"依赖缺失"，还防"假设不成立"。

---

### ✍️ 动手练习

1. 确认你的 `.github/workflows/test.yml` 存在且内容正确。最小版本：
   ```yaml

   on: [push]
   jobs:
     run:
       runs-on: ubuntu-latest
       steps:
         - uses: actions/checkout@v4
         - uses: actions/setup-python@v5
           with:
             python-version: "3.10"
         - run: pip install -r requirements.txt
         - run: python main.py
   ```
2. 如果你还没有 sample data（因为 data/ 被 gitignore 了），在 CI yaml 里加一步生成样例数据。或者创建一个 `sample_data/` 目录（不被 gitignore）放 10 行样例数据，在 `main.py` 里优先读样例数据（如果 `data/` 为空）。
3. push 后打开 GitHub Actions tab——确认看到绿色 ✓。
4. 故意引入一个 bug（比如改一个 import 路径），push——确认 CI 变红。然后修好，push——确认 CI 恢复绿色。
5. `git add . && git commit -m "verify CI: smoke test passes" && git push`

---

### ✅ 自检反馈

**✅ 参考答案**

- GitHub Actions tab 显示绿色 ✓。
- 故意引入 bug 后变红，修好后恢复绿色——说明 CI 在工作。
- CI yaml 用的是 `pip install -r requirements.txt` 而非手动列依赖——确保 `requirements.txt` 和 CI 同步。

**❓ 常见偏差**

| 偏差 | 原因 | 🔧 补救 |

| "没有样例数据所以 CI 跑不通" | `data/` 被 gitignore 了，CI clone 后 `data/` 是空的 | 加一个 `sample_data/` 目录（不被 gitignore），含最小数据集。`main.py` 里如果 `data/` 为空就改用 `sample_data/` |

### ✅ 参考答案

**Q1**：三棵树 = 工作目录（你编辑文件的地方）、暂存区（git add 后的位置）、仓库（git commit 后的永久快照）。git stash 把"工作目录"和"暂存区"的改动暂存起来——所以它涉及两棵树。

**Q2**：Python 在 sys.path 列出的目录中搜索 src 包。sys.path[0] = 执行脚本时的 cwd（而非脚本文件所在目录）。因此必须在项目根目录执行。偏差：说"Python 自动找到的"——没有"自动"，只有 sys.path。

**Q3**：DEBUG = 排查时用，修好应删/降级。INFO = 流程节点，保留。WARNING = 需关注，保留。ERROR = 步骤失败，保留。CRITICAL = 程序中止，保留。排查时多加的 DEBUG 日志修完 b 应删掉（或用 `if logger.isEnabledFor(logging.DEBUG)` 包起来）。

**Q4**：五层：存在→类型→范围→跨表一致→业务规则。merge 行数检查属于第 4 层（跨表一致性）。

**Q5**：幂等 = 同样输入跑多次结果相同。不幂等的原因：①中间文件残留（上次生成的被读进去）②依赖当前时间（`datetime.now()` 在分析里）③随机数没设种子 ④extract 阶段又在中间调了读取 ⑤数据库在跑的过程中被更新。

**Q6**：Python 运行时完全不检查 Type Hints。大厂强制要求是因为：①降低代码阅读理解成本 ②mypy 静态检查能在跑之前发现问题 ③作为"可执行文档"——比注释更可信（注释会过期，Type Hints 被 mypy 验证）。

**Q7**：应该含：你 import 的包（pandas/numpy/matplotlib），每行锁版本。不应该含：传递依赖（six/python-dateutil/pytz 等）——它们是 pandas 的依赖，会被 pip 自动安装。偏差：把 `six` 留着——你没 import 过它。

**Q8**：验证了：①依赖声明完整（requirements.txt 正确）②代码无硬编码路径（pathlib 正确工作）③数据文件或样例数据可用 ④模块导入正确 ⑤没有"只在我电脑上能跑"的配置依赖。
