### 四场景 Case 面试——完整框架 + 标准回答 + 追问应对

**场景 1: Cold Start——"我们公司刚起步——没有历史数据——你怎么建立分析体系？"**

60 秒标准回答: "我会分三步建立分析体系。(1)第一周——和业务方对齐关键指标——GMV/用户数/留存率/获客成本——每个指标有明确的分子/分母/时间窗口。没有历史数据时——从竞品公开数据(财报/行业报告/App Store 评价)建立初步基线。(2)第二周——建立数据基础设施——埋点方案(W11D1)——确保从第一天起就能追踪关键用户行为——没有数据就是最大的数据质量问题。(3)第一个月——第一阶段的分析目标是建立基线——不是优化策略——优化需要数据积累。第一个月的产出是一份基线报告——含核心指标当前值+竞品对比+数据质量评估。"

追问:"如果竞品也没有公开数据——你怎么办？"——"用代理指标。比如用 App Store 的评论数量估算用户规模——用社交媒体的声量估算品牌认知度——用类似行业的公开数据做参考。代理指标不精确——但比'不知道'好——至少给团队一个方向性的判断。"

**场景 2: Launch——"新功能上线了——怎么评估效果？"**

60 秒标准回答: "这是 AB 实验的标准场景。先确认能否随机化——如果能——我的 AB 实验框架有 6 步——(1)确定核心指标+护栏指标 (2)计算样本量——n 正比于 1/MDE^2 (3)用户级别随机化——hash 分流 (4)SRM 前置检查——每天自动跑 (5)CUPED 方差缩减 (6)三段式决策。关注新奇效应——前 3-7 天数据可能不稳定——建议观察至少 2 周。效应量和 p 值并重——不只是 p<0.05——还要效果量 > MDE 且 > 实际重要性阈值。如果不能随机化——沿着因果推断决策树——DID/PSM/RDD/IV。"

**场景 3: Growth——"用户量在增长——但收入没涨。"**

60 秒标准回答: "这说明要么新增用户质量低(低价值用户)——要么现有用户消费降低了。我会做三层拆解。(1)第一层——新用户 vs 老用户的 GMV 同比增长分别是多少——如果新用户 GMV 增长远低于老用户——说明获客渠道带来的用户质量低。(2)第二层——转化漏斗——哪个环节的转化率下降了——浏览->加购->下单->支付——逐层排查。(3)第三层——按渠道/地区/设备下钻——找贡献最大的 2-3 个 Segment。最后——如果是渠道问题——建议调整获客策略(项目 1 的渠道 LTV 分析)——如果是转化问题——建议 AB 实验验证改进方案。"

**场景 4: Decline——"核心指标在下跌——怎么排查？"**

60 秒标准回答: "先用 MECE 拆解——GMV = UV x 转化率 x 客单价。Log 分解量化每项的贡献度——定位主因。然后五视角扫描(W12D3)——(1)时间维度——同比环比排除季节性 (2)结构维度——下钻城市/品类/渠道 (3)因子维度——UV/CVR/ASP (4)外部维度——竞品/节假日/政策 (5)数据质量——排除数据问题。最后给出判断——属于正常波动还是需要干预——含具体建议和预期效果。"

### 5 个生产故障——完整版——症状+根因+排查+修复+预防

**故障 1: 依赖爆炸——pip install 炸了**

症状: CI 突然红了——pip install 报 version conflict——昨天还是绿的。
根因: requirements.txt 含了传递依赖——或用了 >= 版本号——某个包发新版后不兼容。
排查: git diff requirements.txt——看最近谁改了什么。pip install --dry-run——在不安装的情况下检查冲突。
修复: pip freeze > requirements.txt——锁精确版本。手动删掉传递依赖——只留直接依赖。
预防: CI 中跑 pip check——检查依赖冲突。dependabot 自动 PR 依赖更新——在 CI 中验证通过再合并。

**故障 2: 数据漂移——模型效果突然变差**

症状: 流失预警模型——训练时 AUC=0.82——三个月后预测的高风险用户——一半都没流失。
根因: 特征分布变了——高价值用户比例从训练时的 15% 降到 8%——因为一次大促吸引了大量低价值用户。
排查: 跑 PSI——对比训练集和生产集的关键特征分布——全部 > 0.25 的告警。
修复: 用最近三个月数据重训练模型。调整正负样本权重。
预防: 每月自动跑 PSI——连续两个月漂移自动告警——创建重训练 ticket(W18)。

**故障 3: CI 失败——push 后突然红叉**

症状: push 后 GitHub Actions 红了——但本地 make check 是绿的。
根因: CI 的 Python 版本和本地不同——CI 用 3.12——本地用 3.10——某个语法在 3.12 上报错。或 CI 的 OS 不同——某个依赖在 Linux 上需要系统库。
排查: 读 CI 日志——定位失败的 step 和错误信息。git log——对比上次绿 commit 和这次红 commit 的 diff。
修复: 在 CI matrix 中加多个 Python 版本——确保跨版本兼容。本地用和 CI 相同的 Python 版本。
预防: CI matrix 含 3.10 和 3.12——本地和 CI 用相同的 lock file。

**故障 4: 编码错误——今天加载失败——昨天能跑**

症状: pd.read_csv() 报 UnicodeDecodeError——数据加载失败——昨天同样的代码还能跑。
根因: 数据源改了编码——从 UTF-8 变成了 GBK——或新增了特殊字符。
排查: chardet.detect() 自动检测编码。用 errors='replace' 临时跳过——记录被跳过的行数。
修复: 在 load 函数中先用 chardet 检测编码——如果检测失败——fallback 到 errors='replace'——并在日志中告警。
预防: smart_read() 函数——含编码自动检测+fallback——所有数据加载统一走这个函数。

**故障 5: 路径问题——服务器上报 File not found**

症状: cron 触发的脚本报 FileNotFoundError——但手动跑能通过。
根因: cron 的工作目录是 $HOME——不是项目根目录。代码中 pd.read_csv('data/orders.csv') 用的是相对路径。
排查: 在脚本开头加 pwd && ls——打印当前目录和文件列表。
修复: 脚本开头 cd 到项目根目录。或代码中使用 Path(__file__).parent / 'data' / 'orders.csv' 作为绝对路径。
预防: scripts/run_daily.sh 的开头写 cd /absolute/path/to/project——或使用绝对路径。

**面试时——面试官问"你遇到过什么生产故障？"——从这 5 个中选 2 个你真实遇到过的——用症状->根因->排查->修复->预防五段式回答。** 不要说"我遇到过依赖冲突"就结束了——要展示你的排查过程——"我先 git diff 看了 requirements.txt——然后 pip install --dry-run 确认了冲突——修复后我在 CI 中加了 pip check——防止再犯。"

### 工程化选择的面试叙事——不只是"我选了 X"——是"我知道不选 X 的后果"

面试官:"你的项目里——我看到你用了很多'工程化'的做法——比如 CI、Docker、测试。你为什么做这些——是不是过度工程化了？"

你的回答: "不是过度工程化——每一项选择都是因为'不这样做——我真实踩过坑'。(1)CI——因为我在 W4 的时候 push 了一个跑不通的代码——第二天同事 clone 后发现跑不了——从此我每个项目都有 CI。(2)Docker——因为我在 W27 换了一台电脑——花了两天配环境——pip install 炸了三次——从此每个项目都有 Dockerfile。(3)测试——因为同事改了我的 clean_amounts——把 >=0 改成 >0——GMV 少了 3%——从此每个数据变换函数都有 test。每一项工程化选择——背后都有一个'不这样做就出过问题'的故事——不是'教程说的'——是'我踩过坑'。"

这会比"因为这是最佳实践"有力 10 倍——因为面试官听到的是——这个人不是因为教程说应该这样做——而是因为真实遇到过不这样做的后果——所以建立了防御体系。

### 5 个工程化选择的标准回答——每个 30 秒

**1. 为什么用 logging 而不是 print？**
"print 有三个限制——无法区分消息级别(DEBUG/INFO/ERROR)、无法同时输出到屏幕和文件、日志格式无时间戳和来源。我的项目从 W2D3 开始用 logging——现在任何报错都能从日志中追溯到函数、参数和执行时间。"

**2. 为什么用 pytest 而不是手动测试？**
"手动测试会忘——会跳——会在赶 deadline 时省略。pytest 每次 push CI 自动跑——不通过不允许合并。我的鲜果多项目有 20+ test——5 种测试模式覆盖——危险区域覆盖率 100%。"

**3. 为什么用 CTE 分层注释？**
"子查询嵌套需要接手的人从内到外逐层在脑中展开——CTE 分层注释让每层粒度可读——从需要 30 秒推导变成读注释 3 秒理解。每条 CTE 第一行写粒度——这是 SQL 中最难追溯的信息。"

**4. 为什么用 Docker？**
"READme 里写六步手动操作——每步都可能因 OS 不同而失败。Docker 一行 docker-compose up——所有环境差异被容器化——保证跨平台一致性。新同事 clone 后不需要配环境。"

**5. 为什么数仓分四层(ODS/DWD/DWS/ADS)？**
"四层 = 四种信任级别。ODS 是源数据字节级复制——DWD 是统一清洗的干净水源——DWS 是预聚合的常用口径——ADS 是面向业务方的最终交付。分层不是建四张表——是定义谁在什么时候用哪一层。"

**每个选择的回答模板——三段式——(1)我选了 X (2)如果不选 X——会有什么后果 (3)在我的项目中——你在哪里可以看到这个选择的效果。** 面试官要的不是背诵——是"你理解你的选择——并且这个选择在你的代码中有体现"。

### 代码演示的 5 个常见失误——提前知道——提前修复

失误 1——打开 main.py 从头滚到尾。面试官看到的是"这个人在翻代码——不知道重点在哪"。修复——按 5 段式脚本——每段 30-40 秒——不超时。

失误 3——mouse 到处乱晃——找文件找了 10 秒。面试官会觉得"项目结构不清晰——你自己都找不到"。修复——用快捷键( Ctrl+P/Cmd+P )——直接输入文件名——秒开。

### 3 分钟代码演示——完整脚本——每个环节 30-40 秒

**0:00-0:30——README:** 打开鲜果多 GitHub——屏幕共享。"这是我最完整的项目——鲜果多生鲜电商数据分析平台。READme 第一段是 STAR 叙事——Situation/Task/Action/Result——每个含量化数字。往下——CI badge 全绿——Python/ruff/mypy/pytest。再往下——快速开始——四步命令——可复制粘贴。"
