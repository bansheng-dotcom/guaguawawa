# 采购单与库存单据校验（PO Validate）

> 一句话定位：**这个技能存在的意义，是防止"单据各填各的，库存账永远对不平"**。
> 采购与库存最贵的失败不是算错，而是**单据链断裂**：
> 采购单总额与行项目不一致、收货数量超过订单数量、库存分录用途不在白名单。
> 这些错误会一路传到成本核算和财务报表，最后谁也说不清差在哪。

## §1 何时用 / 何时不用

**该用（用户真实会这么说）**
- 「这张采购单对不对」「能不能下单」
- 「收货数量超了吗」「入库单为什么过不了」
- 「库存账对不平，帮我查单据」

**不该用，转给谁**

| 用户其实想要 | 转给 | 理由 |
|---|---|---|
| 付款审批 / 资金安排 | `r03` 财务 + 创始人 | 本技能只校验单据，不动钱 |
| 供应商准入 / 资质审核 | `r15` 主数据域 + `r03` | 那是准入流程 |
| 成交通知 / 对客户履约 | `r14` 交易 | 那是销售侧 |
| 成本核算与毛利 | `r03` / `r06` | 本技能只保证单据自洽 |

**最小可开工输入**：**一张单据（采购单 / 收货单 / 库存分录）**。

## §2 前置输入与最省追问

| 输入 | 是否必需 | 缺失时怎么办 |
|---|---|---|
| 单据类型与单号 | 必需 | 无类型无法选门禁 |
| 供应商与采购方 | 必需 | 主体不明无法过账 |
| 行项目（品/量/价） | 必需 | 无行项目无法算总额 |
| 订单日期 | 必需 | 缺则 `po.date_order` 失败 |
| 关联上游单号（收货关联采购单） | 收货时必需 | 无关联即无法判超收 |

**追问纪律**：最多一轮，只问**是哪张单、关联哪张上游单**。

## §3 执行流水线（Workflow）

### Step 1 · 采购单自洽（总额 = 行项目之和，日期合法）
```bash
python harness.py purchase_order --input <采购单.json>
```
门禁校验：`po.grand_total`（总额与行项目之和一致）、`po.date_order`（日期合法）。
门禁实测：总额不符或日期非法即 FAIL。

**常见坑**：手工改总额却没改行项目；日期填成未来或格式错。

- **产出**：采购单校验结论
- **过关条件**：`harness.py purchase_order` 退出码 0

### Step 2 · 收货数量约束（不得超订单）
```bash
python harness.py receipt --input <收货单.json>
```
门禁校验：`receipt.over_receipt`（收货数量 ≤ 订单数量）。
门禁实测：超收即 FAIL。

**为什么这条最硬**：超收会直接导致库存虚增与应付虚高，且很难在事后发现——
因为收货人"觉得多收了没事"。

- **产出**：收货校验结论
- **过关条件**：`harness.py receipt` 退出码 0

### Step 3 · 库存分录用途白名单
```bash
python harness.py stock_entry --input <库存分录.json>
```
门禁校验：`stock_entry.purpose` 在用途白名单内（采购入库/销售出库/调拨/盘盈盘亏/退货等）。

**自创用途名**是最常见的账不平原因——"暂存""借出""先放着"这类词一进系统，账就对不上了。

- **产出**：分录校验结论
- **过关条件**：`harness.py stock_entry` 退出码 0

### Step 4 · 三单匹配（采购单 / 收货单 / 发票）
| 匹配项 | 规则 |
|---|---|
| 数量 | 收货 ≤ 订单；发票 ≤ 收货 |
| 单价 | 发票单价 = 订单单价（差异需变更单） |
| 金额 | 三方差额可解释 |

不匹配时**不要改单据凑平**，先查是哪个环节错了。

## §5 质量门（一票否决，不过不给交付）

1. **采购单总额 = 行项目之和**（`po.grand_total`）；
2. **订单日期合法**（`po.date_order`）；
3. **收货数量 ≤ 订单数量**（`receipt.over_receipt`）；
4. **库存分录用途在白名单内**（`stock_entry.purpose`）；
5. **三单（订单/收货/发票）数量与单价可解释**；
6. **不通过改单据凑平**（发现差异先查环节）。

> 验收命令：`python harness.py purchase_order|receipt|stock_entry --input <json>`
> 命中任一项不过 → 回 §3 对应 Step，**不允许改总额让门禁变绿**。

## §6 交付前自检清单

- [ ] 总额是我算过的，不是手工填的
- [ ] 每一行数量 × 单价 都对得上总额
- [ ] 订单日期不在未来，格式正确
- [ ] 收货数量逐行与订单比过，没有超收
- [ ] 库存分录用途是白名单里的词，没有自创
- [ ] 三单数量、单价、金额差异我都解释过
- [ ] 差异没有靠改单据抹平
- [ ] 关联的上游单号都填了
- [ ] 三道门禁均退出码 0

## §7 易犯错误对照表

| # | 易犯错法 | 正确做法 |
|---|---|---|
| EX-01 | 手工改总额不改行项目 | 总额必须由行项目汇总；改就一起改 |
| EX-02 | 收货数量按"实际到了多少"填，不管订单 | 超收必须走变更单，不能在收货单上直接超 |
| EX-03 | 库存分录用途自创（"暂存""借出"） | 只用白名单用途；临时性事项走调拨或备注 |
| EX-04 | 日期填未来或格式随意 | 日期合法且在业务时点内 |
| EX-05 | 三单不匹配就改发票凑平 | 先查环节（下单/收货/开票），不抹平差异 |
| EX-06 | 收货单不填关联采购单号 | 无关联即无法判超收，必须先关联 |
| EX-07 | 单价变更无变更单 | 单价变更必须留变更单，否则无法审计 |
| EX-08 | 盘盈盘亏直接调数量 | 必须走盘盈盘亏分录，保留原因 |
| EX-09 | 用库存分录修历史错误 | 冲正而非修改；改历史会让账永久失真 |
| EX-10 | 单据校验靠肉眼 | 跑 `harness.py` 三道门禁 |

## §8 降级与边界

| 触发情况 | 处置 |
|---|---|
| `harness.py` 跑不了 | 按 §6 人工逐项核对，标注「未跑门禁」；**不得过账** |
| 上游采购单缺失 | 收货单标"无关联订单"，不得过账，退回补单 |
| 供应商未准入 | 标注"供应商未准入"，转 `r15` 主数据域 |
| 汇率/税率变更 | 按变更单处理，不直接改历史单据 |
| 历史单据有误 | 冲正（红字）而非修改，保留原单 |
| 涉及付款 | 只出单据校验结论，付款走 `r03` / 创始人授权 |

**明确不做**
- 不出财务意见与成本核算（归 `r03`）；
- 不执行付款与签约（归 `r14` + 创始人）；
- 不做供应商准入与资质审核；
- 不修改历史单据（只能冲正）。
