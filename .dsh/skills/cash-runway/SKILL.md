# 现金流跑道诊断（Cash Runway）

> 一句话定位：**这个技能存在的意义，是防止「现金还剩三个月，但没人算过什么时候耗尽」**。
> 现金流最贵的失败不是算错，而是**没人按月推演**：
> 只看到"账上还有 30 万"，没看到"每月净烧 6 万，第 5 个月就归零"。
> 跑道是唯一能提前三个月发现问题的指标。

## §1 何时用 / 何时不用

**该用（用户真实这么问）**
- 「我们的钱还能烧几个月」
- 「要不要融资 / 要不要降本」
- 「哪个月会缺钱」

**不该用，转给谁**

| 用户其实想要 | 转给 | 理由 |
|---|---|---|
| 正式财务口径 / 报表 | `r03` 财务域（月结） | 本包只做跑道推演 |
| 融资条款谈判 | 创始人 | 本包不算估值与条款 |
| 预算分配与排期 | `r02` | 那是资源分配 |
| 模型勾稽审计 | 本技能的 `model-audit` | 那是审计，不是推演 |

**最小可开工输入**：**期初现金 + 月净烧钱**（两项即可粗算；给出全部参数才算完整）。

## §2 前置输入与最省追问

| 输入 | 是否必需 | 缺失时怎么办 |
|---|---|---|
| `starting_cash`（期初现金） | 必需 | 无现金无法算跑道 |
| `starting_mrr` | 必需 | 无收入无法算净烧钱 |
| `monthly_headcount_cost` / `monthly_other_opex` | 必需 | 缺一项则净烧钱严重失真 |
| `gross_margin_pct` | 必需 | 缺则默认 0.7 并标注 |
| `mrr_growth_rate` | 必需 | 缺则默认 0 并标注（最保守） |
| `model_months` | 建议 | 缺则默认 24 |

**追问纪律**：最多一轮，只问**期初现金、月人力成本、月其他开支**。这三项定了就能出图。

## §3 执行流水线（Workflow）

### Step 1 · 参数建模（先对齐口径，再算）
```bash
python agent.py cfo runway --input <跑道模型.json>
```
最小模型：

```json
{"starting_cash": 300000, "starting_mrr": 50000,
 "monthly_headcount_cost": 60000, "monthly_other_opex": 40000,
 "gross_margin_pct": 0.7, "mrr_growth_rate": 0.02, "model_months": 24}
```

**口径三问**（不确认就会差一倍）：
1. 现金含不含受限资金 / 应收未收？
2. 人力成本含不含社保公积金与年终摊销？
3. 毛利口径含不含渠道分成与服务成本？

- **产出**：参数表 + 口径声明
- **过关条件**：参数齐全且口径写明

### Step 2 · 月度推演（净烧钱逐月算）
每个月算：`MRR → 毛利 → 净烧钱 = 人力 + 其他开支 − 毛利 → 期末现金`

**别用"平均净烧钱"**：增长会让净烧钱逐月变化，用平均值会低估前期烧钱速度。

- **产出**：24 个月逐月表
- **过关条件**：每行都有 `mrr` / `net_burn` / `cash_end` / `runway_months`

### Step 3 · 定位现金耗尽月（第一个负现金月）
**判据**：`cash_end < 0` 的第一个月即耗尽月。模塑期内耗尽 → `cash_out` 判 FAIL。

> 实测一份"期初 30 万、净烧 6.4 万"的模型，第 **5** 个月现金转负 ——
> 这就是"账上还有 30 万"给人的虚假安全感。

- **产出**：`cash_out_month`（无则 null）
- **过关条件**：模型期内现金不为负

### Step 4 · burn multiple（增长效率，比 runway 更早预警）
`burn multiple = 净烧钱 ÷ 净新增 ARR`

| 值 | 含义 |
|---|---|
| ≤ 1 | 增长几乎自给自足 |
| 1–2 | 健康区间（阈值上限 2.0） |
| 2–3 | 需要解释 |
| > 3 | 花钱买增长不划算，越融越亏 |

门禁上限 **2.0**。实测一份 burn multiple **5.03** 的模型被判 FAIL ——
意味着每新增 1 元 ARR 要烧 5 元，这种增长放大只会加速归零。

- **产出**：`burn_multiple`
- **过关条件**：`burn_multiple ≤ 2.0`

### Step 5 · 触发器（什么时候该动作）
模型会在 runway 触碰阈值时自动列出触发器：

| 触发器 | 触发条件（典型） | 动作 |
|---|---|---|
| `start_fundraising` | runway ≤ 6–9 个月 | 启动融资 |
| `cost_reduction` | runway ≤ 6 个月 | 制定降本方案 |
| `execute_cuts` | runway ≤ 3 个月 | 执行降本 |
| `emergency` | runway ≤ 2 个月 | 紧急处置 |

**触发器命中不等于要立刻做**，但**必须有人对每个触发器给决策**（决策归 `r01`）。

- **产出**：`triggers[]` + 每条的处置决策
- **过关条件**：每个触发器都有明确处置（做 / 不做 / 何时做）

## §5 质量门（一票否决，不过不给交付）

1. **参数齐全**，且三项口径已声明（现金范围/人力口径/毛利口径）；
2. **模型期内现金不为负**（`cash_out` 通过）；
3. **burn multiple ≤ 2.0**（`burn_multiple` 通过）；
4. **每个触发器都有处置决策**（`triggers`）；
5. **逐月表完整**（每月含 mrr/net_burn/cash_end/runway_months）；
6. **不用平均净烧钱**糊弄（逐月算）。

> 验收命令：`python agent.py cfo runway --input <跑道模型.json>`
> 命中任一项不过 → 回 §3 对应 Step 重做，**不允许把 model_months 改短让现金"不为负"**。

## §7 易犯错误对照表

| # | 易犯错法 | 正确做法 |
|---|---|---|
| EX-01 | 用"平均净烧钱"算 runway | 逐月算；增长会让净烧钱变化 |
| EX-02 | 现金口径含应收未收 | 只算可用现金，应收单列 |
| EX-03 | 人力只算工资不算社保年终 | 写明口径，含社保公积金与年终摊销 |
| EX-04 | 毛利不扣渠道分成与服务成本 | 按真实毛利口径，别用 GMV 毛利 |
| EX-05 | MRR 增长率用最好情况 | 用保守值；并给敏感性（见下） |
| EX-06 | 只看 runway 不看 burn multiple | burn multiple >3 时越融越亏 |
| EX-07 | 触发器命中了但不给决策 | 每个触发器都要有做/不做/何时做 |
| EX-08 | 把 model_months 改短让现金不为负 | 不许缩短窗口掩盖耗尽 |
| EX-09 | 结论写"大概还能撑一年" | 给具体月份与逐月表 |
| EX-10 | 跑道结论直接当资金决策 | 只给推演；决策归 `r01` + 创始人 |
| EX-11 | 忘记季节性（年底回款/大促） | 在假设里说明，或做分季度模型 |
| EX-12 | 把承诺的融资额算进现金 | 未到账的钱不算现金 |

## §8 降级与边界

| 触发情况 | 处置 |
|---|---|
| `agent.py` 门禁跑不了 | 按 §6 人工核对，标注「未跑门禁」；**不得据以做资金决策** |
| 无 MRR 增长数据 | `mrr_growth_rate` 设 0（最保守），标注"忽略增长" |
| 现金含受限资金 | 拆分"可用 / 受限"，只用可用现金算跑道 |
| 有季节性（大促/年底回款） | 标注"未做季节调整"，或改做季度模型 |
| 融资未到账 | **不算进现金**；到账后再更新模型 |
| 多主体/多币种 | 先统一币种与合并口径，否则 runway 无意义 |
| 要求"给个准数" | 给逐月表 + 保守/乐观两档，不给单点结论 |

**明确不做**
- 不出持牌财务意见（归外部审计）；
- 不谈判融资条款、不估值（归创始人）；
- 不做预算分配（归 `r02`）；
- 不替代模型勾稽审计（归 `model-audit`）。
