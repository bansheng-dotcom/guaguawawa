# 埋点与事件设计（event-tracking-design）

> **没有埋点的业务，所有「效果」都是猜的。** 而我们能做的只有「事后推断」——推断出来的数字最危险的地方不是不准，是**没人能证明它不准**。

## §1 何时用 / 何时不用

**该用（用户真实会这么说）**

- 「这个功能怎么加埋点」
- 「漏斗怎么定义」
- 「为什么这个数查不出来」
- 「事件名怎么起」

**不该用，转给谁**

| 用户其实想要 | 转给 | 理由 |
|---|---|---|
| 数据建模与测试 | r18 的 `dbt-unit-test` | 那是管道 |
| 数据质量六维 | r06 的 `data-validation` | 那是校验 |
| 分析结论 | r06 的 `analysis-method` | 那是分析 |
| 实验判定 | r12 的 `experiment-analysis` | 那是实验 |

**最小可开工输入**：**一个要度量的问题 + 涉及的功能路径**。没有问题就先别埋——埋了也不会有人看。

## §2 前置输入与最省追问

| 输入 | 是否必需 |
|---|---|
| 要回答的业务问题 | 必需 |
| 用户路径/功能流程 | 必需 |
| 已有事件清单（避免重复埋） | 建议 |
| 业务对象词表（订单/商品/会话等） | 建议 |

**追问纪律**：最多一轮，只问**这个埋点要回答哪个具体问题**。答不出「谁在什么情况下看到什么」就不要埋。

## §3 执行流水线（Workflow）

### Step 1 · 先写要回答的问题（一个埋点对一个问）
格式：**「<谁> 在 <什么场景> 做了 <什么>，我要知道 <哪个数>」**。

**判据**：问题里含主体、场景、动作、指标四项

### Step 2 · 按「对象_动作」命名（禁缩写、禁数字）
命名规范：`<对象>_<动作>`，全小写下划线，如 `order_paid`、`cart_item_added`、`page_viewed`。**禁止**：`click1`、`btn2`、`e1`、`track_a`。

**判据**：事件名能自解释：不看文档能猜出发生了什么

### Step 3 · 定义属性（必填 + 可选，分开列）
每个事件列**必填属性**（缺了这条数据不可用）与**可选属性**。必填项通常含：`user_id`、`occurred_at`、对象 id、来源渠道。

**判据**：必填属性 ≥3 个且含 user_id 与 occurred_at

### Step 4 · 写清触发时机（这是最容易吵的地方）
明确是**点击时 / 请求成功时 / 页面可见时**。典型坑：按钮点击埋了但请求失败，数据里全是「点击了却没成功」的假成功。

**判据**：触发时机写明，且区分「发起」与「成功」两个事件

### Step 5 · 声明漏斗（按步骤显式列，不靠推导）
漏斗 = 有序事件列表 + 每步唯一标识 + 时间窗。**不许用「事件 A 之后有过 B」推导漏斗**——那是相关不是路径。

**判据**：漏斗逐步列出，每步有时间窗上限

### Step 6 · 维护数据字典与版本
字典含：事件名、中文名、必填属性、触发时机、负责人、上线日期、版本。改属性 = 升版本，**不许原地改**（会让历史数据不可比）。

**判据**：字典齐全，且属性变更走版本升级

### Step 7 · 上线后 7 天回看（验证埋对了没）
看三件事：**量级是否合理**（不该为 0 也不该等于全站 UV）、**属性缺失率**、**漏斗是否有人卡在某步 100%**。

**判据**：7 天内回看过三项，并记录异常

## §5 质量门（一票否决）

1. 每个事件对应一个明确的度量问题（含主体/场景/动作/指标）；
2. 事件名遵循 `<对象>_<动作>`，无缩写与数字编号；
3. 必填属性 ≥3 个，且含 `user_id` 与 `occurred_at`；
4. 触发时机写明，且「发起」与「成功」分为两个事件；
5. 漏斗逐步显式声明，每步有时间窗；
6. 数据字典齐全，属性变更走版本升级（不原地改）；
7. 上线 7 天内做过回看（量级/缺失率/漏斗异常）；

> 本卡无自动门禁。可配合 `python agent.py quality check --input <事件.json>` 做结构校验（间接）。

## §7 易犯错误对照表

| # | 易犯错法 | 正确做法 |
|---|---|---|
| EX-01 | 事件名用 click1/btn2 | `<对象>_<动作>`，能自解释 |
| EX-02 | 一个事件答多个问题 | 一埋点一问，拆开 |
| EX-03 | 只埋点击不埋成功 | 发起与成功两个事件，分开埋 |
| EX-04 | 必填属性缺 user_id | 必填至少 user_id + occurred_at + 对象 id |
| EX-05 | 漏斗靠推导 | 逐步显式声明 + 时间窗 |
| EX-06 | 原地改属性 | 升版本，否则历史不可比 |
| EX-07 | 无数据字典 | 字典含负责人与上线日期 |
| EX-08 | 上线不回看 | 7 天内看量级/缺失/漏斗 |
| EX-09 | 埋点数量堆砌 | 每个事件都要能对应一个问题 |
| EX-10 | 把页面曝光当点击 | 曝光与点击是两个事件 |

## §8 降级与边界

| 触发情况 | 处置 |
|---|---|
| 无前端埋点能力 | 先用后端事件（订单/支付）替代，标注覆盖不足 |
| 无法传 user_id | 用匿名 id + 登录后回填，标注「匿名段不可归因」 |
| 历史数据无埋点 | 只做前瞻，标注「历史不可回溯」 |
| 隐私合规限制 | 不采个人敏感字段，只采行为与对象 id |
| 第三方 SDK 限制命名 | 在 SDK 内映射到本地标准名，字典记映射 |
| 埋点量过大 | 按问题重要性分级（P0 必埋/P1 择机） |

**明确不做**：不做采集管道、不做分析结论、不做实验判定、不做数据质量审计。
