# 测试驱动与双向评审（TDD Review Pair）

> 一句话定位：**这个技能存在的意义，是防止"测试跑绿了就合"**。
> 工程交付最贵的失败不是写错代码，而是**验证环节被绕过**：
> 测试被跳过不说明、材料不全没法复现、评审只看了 diff 没看行为、
> 作者自己「审」自己。这四件事任何一件发生，"已测试/已评审"就变成了社交说法。

## §1 何时用 / 何时不用

**该用（用户真实会这么说）**
- 「这个能不能合」「测试跑过了吗」
- 「帮我写测试」「按 TDD 来」
- 「评审一下这个 PR」「别人让我改，怎么接」

**不该用，转给谁**

| 用户其实想要 | 转给 | 理由 |
|---|---|---|
| 判成品合不合格（pass/fail） | `r04` 评审官 | 质量结论只有 R04 出 |
| 产品该不该做这个功能 | `r07` 产品 | 那是需求判断 |
| 架构选型 | `r09` 架构域 + `r01` | 本技能只管验证与评审流程 |
| 上线发布与回滚 | `r20` / `r09` ops 域 | 本技能到「可合并」为止 |

**最小可开工输入**：**改动清单 + 测试结果**。

---

## §2 前置输入与最省追问

| 输入 | 是否必需 | 缺失时怎么办 |
|---|---|---|
| 测试报告（通过/失败/跳过） | 必需 | 无报告不得合并 |
| 跳过项及原因 | 必需（有跳过时） | 跳过不说明＝隐藏风险 |
| 改动清单（改了哪些文件/行为） | 必需 | 材料门禁会拦 |
| 复现步骤 | 必需 | 无复现无法验证 |
| 验证方式（跑什么命令） | 必需 | 无验证方式＝无法复核 |

**追问纪律**：最多一轮，只问**改了什么、怎么验证**。

---

## §3 执行流水线（Workflow）

### Step 1 · 先写失败测试（TDD 的红线）
顺序不能反：**先写会失败的测试 → 看它失败 → 再写实现 → 看它通过**。
跳过"看它失败"这一步，就无法确认测试真的在测东西——
很多"通过"的测试其实什么都没断言。

**判据**：提交记录里能看到"测试先红后绿"的痕迹，或说明为什么没法这么做（如修线上故障）。

### Step 2 · 测试报告（跳过必须说明）
```bash
python harness.py testreport --input <测试报告.json>
```
报告必须含：通过数 / 失败数 / **跳过数及每条原因** / 覆盖率（若有）。
门禁实测：结构不合规即 FAIL。

**跳过的三种合法理由**：环境不具备、需求已废弃、待后续特性。其余一律视为掩盖。

### Step 3 · 交付材料齐备
```bash
python harness.py materials --input <材料清单.json>
```
必须含：改动清单 / 复现步骤 / 验证命令 / 影响面（哪些模块会受影响）。
门禁实测：缺项即 FAIL（`materials:*`）。

> 材料不全的 PR，评审者只能"看着像对的"——那不是评审，是猜。

### Step 4 · 请求评审（作者侧，三件套）
| 产出 | 要求 |
|---|---|
| 改了什么 | 行为级描述，不是文件列表 |
| 为什么这么改 | 与需求/缺陷的对应关系 |
| 想让评审重点看哪 | 明确 1–3 个重点，不是"都看看" |

**作者红线**：不夹带无关改动（格式化、重命名混在功能改动里），不隐藏已知问题。

### Step 5 · 接收评审（作者侧，三条纪律）
| 纪律 | 说明 |
|---|---|
| 不防御 | 先复述对方的顾虑，确认理解一致再回应 |
| 不照搬 | 评审建议是输入不是命令；不同意要说明理由 |
| 不静默 | 每条意见都要有响应（接受/拒绝/待议），不许无回应 |

**最容易违反的是第三条**：选择性回应会让评审者觉得在浪费时间，下一轮就不认真看了。

### Step 6 · 合并前门禁
```bash
python harness.py testreport --input <测试报告.json>
python harness.py materials  --input <材料清单.json>
python agent.py testing suites --input <套件.json>      # 可选：测试套件结构
python agent.py testing browser --input <浏览器验证.json> # 可选：端到端验证
```
四道全过才可合并；未跑的在交付物里标"未验证"，**不得合并**。

## §4 交付物清单

| # | 交付物 | 载体 | 骨架出处 |
|---|---|---|---|
| 1 | 测试报告（通过/失败/跳过+原因） | `.json` | `examples/testreport_good.json` |
| 2 | 交付材料（改动/复现/验证/影响面） | `.json` | `examples/materials_good.json` |
| 3 | 请求评审说明（三件套） | `.md` | 本文 §3 Step 4 |
| 4 | 评审响应记录（逐条状态） | `.md` | 本文 §3 Step 5 |
| 5 | 门禁结论 | 终端 JSON | `harness.py testreport/materials` |

- 命名：`pr_<编号>_<YYYYMMDD>/`
- **测试报告与材料是合并的必要条件**，不是"有空再补"。

---

## §5 质量门（一票否决，不过不给交付）

1. **测试报告含通过/失败/跳过计数**（`testreport`）；
2. **每条跳过都有原因**，无"暂时跳过"这类模糊表述；
3. **材料含改动清单/复现步骤/验证命令/影响面**（`materials`）；
4. **能看测试先红后绿的痕迹**，或说明为何不能；
5. **请求评审写了重点看什么**（1–3 项）；
6. **每条评审意见都有响应状态**（接受/拒绝/待议）；
7. **未跑的门禁在交付物里标"未验证"**，不假装通过。

> 验收命令：`python harness.py testreport|materials --input <json>`
> 命中任一项不过 → 回 §3 对应 Step，**不允许删掉测试让报告变绿**。

## §6 交付前自检清单

- [ ] 测试是先写（并看它失败）再写的实现，或说明了为何不能
- [ ] 报告里有失败数与跳过数，不只写"测试通过"
- [ ] 每条跳过都写了具体原因，没有"暂时跳过"
- [ ] 改动清单描述的是行为变化，不是文件列表
- [ ] 复现步骤别人照着能跑起来
- [ ] 验证命令是可以直接粘贴执行的
- [ ] 影响面写了（哪些模块/调用方会受影响）
- [ ] 请求评审时说了"重点看哪 1–3 处"
- [ ] 我没有夹带无关改动（格式化/重命名单独提）
- [ ] 已知问题我主动写在说明里，没有等人发现
- [ ] 对方每条意见我都回了状态
- [ ] 两道门禁均退出码 0

## §7 易犯错误对照表

| # | 易犯错法 | 正确做法 |
|---|---|---|
| EX-01 | 先写实现再补测试 | 先写会失败的测试，看它失败，再写实现 |
| EX-02 | 测试跳过不说明 | 每条跳过必须给原因，否则视为掩盖 |
| EX-03 | 报告只写"测试通过" | 必须含通过/失败/跳过计数 |
| EX-04 | 改动清单写成文件列表 | 写行为级变化："取消后 7 天内可恢复" |
| EX-05 | 复现步骤写"按正常流程" | 必须具体到命令与前置条件 |
| EX-06 | 评审请求写"都看看" | 指定 1–3 个重点，尊重对方时间 |
| EX-07 | 夹带格式化成吨的无关 diff | 功能改动与格式化分开提交 |
| EX-08 | 隐藏已知问题等人发现 | 主动写在说明里，标明影响与后续计划 |
| EX-09 | 对评审意见建议全盘照搬 | 建议是输入；不同意要说明理由 |
| EX-10 | 选择性回应评审意见 | 每条都要有状态（接受/拒绝/待议） |
| EX-11 | 自己审自己的 PR | 作者不能自审；质量结论归 `r04` |
| EX-12 | 门禁没跑就说"应该没问题" | 未跑的标"未验证"，不得合并 |

## §8 降级与边界

| 触发情况 | 处置 |
|---|---|
| `harness.py` 跑不了 | 按 §6 人工逐项核对，标注「未跑门禁」；**不得合并** |
| 线上故障紧急修复 | 可先修后补测试，但必须在说明里写"补救计划与时间点"，且 24h 内补 |
| 无法本地复现 | 标注"环境差异"，附日志与排查记录，不硬写复现步骤 |
| 覆盖率工具不可用 | 标注"未统计覆盖率"，不编数字 |
| 评审者长期不响应 | 升级到 `r02` 走排期；不自审，不自合 |
| 改动跨多个仓库 | 每个仓库单独一份材料；影响面写清依赖顺序 |

**明确不做**
- 不出 pass/fail 质量结论（归 `r04`）；
- 不做产品与架构决策（归 `r07` / `r01`）；
- 不执行发布与回滚（归 `r20` / ops 域）；
- 不自审、不自合。
