## 一、组织全景图

系统设计严密遵循**生成与校验分离**以及**单一主责**原则：

```
                              ┌─────────────────────────┐
                              │      创始人（用户）       │
                              │  最终裁决 · 不可逆签字   │
                              └────────────┬────────────┘
                         ┌─────────────────┴─────────────────┐
                         │  R01 蛙全局 · CEO 主理人 / 编排器  │←─ 汇总汇报
                         │  意图分级 · 拆解 · 决策 · 收口     │
                         └─────────────────┬─────────────────┘
                                           │ 下发 task_cards
        ┌──────────┬──────────┬────────────┼────────────┬──────────┬──────────┐
        ▼          ▼          ▼            ▼            ▼          ▼          ▼
   ┌────────┐ ┌────────┐ ┌────────┐  ┌────────┐  ┌────────┐ ┌────────┐ ┌────────┐
   │决策治理 │ │战略数据 │ │产品技术 │  │市场客户 │  │交易组织 │ │自动化可 │ │  R04   │
   │ R02 COO│ │ R05 研究│ │ R07 产品│  │ R11 内容│  │运营 R14 │ │靠性 R17 │ │蛙挑刺  │
   │ R03 CFO│ │ R06 分析│ │ R08 MVP │  │ R12 增长│  │交易 R15 │ │ R20 值守│ │独立评审│
   │        │ │ R18 数仓│ │ R09 工程│  │ R13 客成│  │供应 R16 │ │        │ │(旁路)  │
   │        │ │ R19 智模│ │ R10 设计│  │        │  │人事     │ │        │ │        │
   └────────┘ └────────┘ └────────┘  └────────┘  └────────┘ └────────┘ └────┬───┘
                                                                            │
                    ┌───────────────────────────────────────────────────────┘
                    │  R04 拥有旁路通道，不经 R01 拦截，独立向创始人汇报 pass/fail
                    ▼
```

### 汇报双线机制
1. **执行主线**：执行角色（R02～R20）→ R01 蛙全局汇总 → 提交创始人。
2. **独立评审线**：R04 蛙挑刺作为质检哨兵，直接对创始人输出独立审查报告与门禁判定（Pass/Fail），防止执行层包装与信息隐瞒。

## 三、核心架构与协同铁律

1. **单一责任人（Single Owner）**：
   - 任何任务、文件或交付物必须有且仅有一个主责 Agent；拒绝职责模糊的“共同负责”。
2. **编排器精简化（Thin Orchestrator）**：
   - R01 只负责接收意图、加载上下文、派发任务卡（Task Cards）、更新状态机与汇总交付，自身严禁直接编写业务输出。
3. **生成与校验分离（Separation of Production and Review）**：
   - 谁产出谁负责，严禁自评自审；R04 拥有完全独立的审查权重，`reviewer == producer` 即直接判定 FAIL。
4. **强契约与闭环机制（Contract-Driven Closing）**：
   - 所有交互基于 `core/protocol.py` 中的格式化契约；任务严格设置终止判定（Success Criteria / Kill Criteria），触发即收口复盘。

## 四、典型编排案例：营收最大化方案

以实际商业命题「**某业务一年内营收最大化方案**」为例，R01 编排器的流转链路：

```
[意图输入] "营收最大化策略制定"
    │
    ├─► ① 策略假设制定 (R07 蛙得明 - 产品经理)
    │     └─ 交付：定价、组合套餐、梯度时段、会员体系假设 (`strategy_hypotheses`)
    │
    ├─► ② 严谨数据验证 (R06 蛙得清 - 数据分析师)
    │     └─ 交付：历史营收因子归因分析、A/B 检验指标测算 (`analysis_report`)
    │
    ├─► ③ 落地页与方案组装 (R08 蛙建成 - MVP 构建)
    │     └─ 交付：交互式 HTML 方案报告、可视化看板展示 (`html_report`)
    │
    └─► ④ 旁路严格质检验收 (R04 蛙挑刺 - 评审官)
          └─ 交付：门禁复核判定（Pass / Fail）与独立修改意见书 (`critique_report`)
```

- 若 R06 的数据检验推翻了 R07 的假设，系统触发**协议回退机制**，由 R07 重拟假设，严禁硬凑结论。
