# 报告产线：统一架构与二次反思

> 对象：蛙蛙呱呱agents团 · 报告生产体系
> 日期：2026-11-17
> 证据分级：**实测**＝本次实际执行命令/读取原文；**代码路径**＝从源码确认；**推断**＝基于证据的判断，未直接验证。

---

## 0. 一页结论

1. **你说的“口径/路径/分支/纲领太多”是真的，但它是症状，不是根因。** 根因是系统在编码“输出”（报告类型、分支、入口），没有编码“问题、断言、覆盖度”。
2. **统一成一条产线是必要的，但它是手段，不是目标。** 目标是“任何业务 → 决策级报告，且新业务边际成本可控”。如果只统一产线、不定义“决策级”，会得到一个更快生产不可信报告的系统。
3. **“20 个角色已经覆盖这些维度”在组织层成立，在报告层不成立。** 实测：20 角色 / 195 技能中，只有 **94 技能 / 143 动作**可进报告；**4 个角色被标记“不进报告”**；**5 个角色可进报告技能 ≤1**。真正卡住“任何业务”的，是**能力深度 + 数据获取**，不是产线数量。

**更值得解决的问题（本文的核心主张）：**

> 不是“如何把 22 条产线合成 1 条”，而是“**如何用现有 20 角色和可获得的数据，稳定产出决策级报告，并让新业务的边际成本随能力复用而下降**”。

## 1. 现状诊断：不是“多”，是“输出分类学”

### 1.1 同一个东西有八套名字

| 现在存在的 | 有几套 | 本质 |
|---|---|---|
| 报告类型 | **22 个 thesis** + `market_research/business_review` profile + `doc_type` | 同一件事的三种标签 |
| 入口 | `run --results` / `pack + run --evidence --draft` / `produce` / `research` | 同一件事的四种入口 |
| 分支 | A 单角色 / B 跨角色 | 同一件事的两种判断 |
| 装配器 | `frames.py` / `frames_cheese.py` / `frames_framework.py` | 同一件事的三套章节顺序 |
| 合同 | `report_ship.json` / `contract.json` | 同一件事的两份契约 |
| 方法层 | `core/analysis_methods.py` / `core/methods/*` | 同一件事的两层方法 |
| 覆盖概念 | `covered` / `gaps` / `missing` | 同一件事的三个字段 |
| 门禁 | flow / quality / spec / grade | 同一件事的四套判据 |

这不是“功能丰富”，是**概念没有收敛**。每多一个同义词，就多一条要维护的路径，多一个可以漂移的地方。

### 1.2 三个结构性问题

**（1）两个分支：在不知道谁会参与之前，先判断“一个角色够不够”。**

`core/report_flow.py` 的 `route()` 先用关键词猜角色，再判 A/B；`run()` 又根据实际收到的 result 重算 branch。问题是：报告生产不是二选一，是**问题覆盖**。

```
问题 → 所需能力 → 可用角色 → 覆盖度 → 报告
```

单角色报告只是 `coverage = 1 个角色` 的退化情况，不是一条分支。

**（2）三个走法：把“输入状态”做成了“三条产线”。**

- 有 result：直接出；
- 有证据包 + 章节稿：校验后出；
- 什么都没有：从数据跑方法。

这不是三种方法，是**三种输入状态**。正确的做法是一个入口 + 可选输入：

```bash
guagua.py report build --intent "…" --dir <项目> --out <目录> \
  [--results <result.json…>]    # 可选：已有执行结果
  [--draft <sections.json>]     # 可选：已有章节稿
  [--lens market|ops|chain|fix] # 可选：维度权重，不改产线
```

**（3）22 个纲领：这是输出分类学，方向反了。**

22 个纲领是“先选报告类型，再决定章节”。真实业务不是这样——先有问题，报告类型是问题被回答后**长出来的**。

正确方向是**输入分类学**：一套与业务无关的问题/维度库；20 个角色各自回答“我能回答哪几类问题”；报告类型 = 这次选中了哪些维度（结果），不是入口参数（输入）。

### 1.3 为什么这不是审美问题

每多一个纲领/帧/入口，就多一处“承诺与实现可能不一致”的地方。实测已经出现：

- 文档说“技能覆盖 <6 或角色 <4 视为未完成”，代码不检查；`out_chain` 3 技能/3 角色仍 `ok=true`；
- 文档说 Q5 抓“每节三条”的套壳，代码只判 `boundary_share`，`uniform_item_share` 算了但不用；
- 文档说“标题即判断”，Q1 不在 research 档硬门禁，交付稿 Q1=0.385 仍 PASS。

**复杂度本身不致命；复杂度导致的“承诺漂移”才致命。**

## 2. 反方评审：七条能打穿当前产线的证据

### 2.1 头条数字自我取消资格

交付稿标题：

> 呼市批发价是赤峰的 **1.98 倍**，但零售只差 8.0%——钱不在价差里

第 3 节却写：

> 呼市 14.00 为**精品/礼盒**报价、赤峰 6.00 为**统货**；批零比只能证明口径不同，不能反推真实毛利。

即：**1.98 倍是“精品 vs 统货”的比，报告自己承认不可比，却把它放在标题上，并用它推出“钱不在价差里”。**

实测回抓 S01、S03 两个来源页：页面表格只有“富士苹果 14.00 / 6.00”，**没有等级、规格、精品/统货标注**。所以“精品/礼盒 vs 统货”是报告的推断，不是来源事实。

**边界情况**：如果 14.00 确实是精品价，报告是对的；如果 14.00 是同一规格的真实区域溢价，报告就漏掉了一个 2 倍套利机会。系统两种情况下都判 PASS，说明它没有能力区分对错。

### 2.2 “可解释”是算术自由

`_explainable()` 允许任意两个 ref 做 `a-b / a+b / a/b / |a/b-1|*100`，还允许 ×1/100/1000 换算。后果：

- 把“呼市苹果 14.00”除以“赤峰香蕉 5.80”得到 2.41，也算“可解释”；
- 任何两个不相关的数都能凑出一个“有出处”的新数。

还有三个更硬的绕过：

| 绕过 | 代码 | 后果 |
|---|---|---|
| 小于 31 的整数无条件放行 | `s09_interpret.py` `ok_num()` | 编一个“9 个品类”“12 个城市”不需要任何 ref |
| 假设参数白名单 | `assumptions` 里列的数直接放行 | 把任意数字塞进 assumptions 就能进正文 |
| 一条结论只需一个数可追溯 | `any(x in known …)` | “GMV 下降 3.2%、订单量下降 50%”只要 3.2% 是真的就过 |

**结论**：这套机制能防“完全凭空编数”，防不住“用真数算假结论”，也防不住“半真半假的一句话”。

### 2.3 门禁不在产线上

- `report produce` 会跑 `report_quality`、R04 清点、写 `quality.json`；
- `report run --evidence --draft`（**交付稿走的就是这条**）只跑 `check_sections` + layout，**不跑深度门禁、不跑 R04**。

交付稿的 `manifest.json` 里没有 `quality`、没有 `r04`，但 `ok=true`。**旗舰交付物的“合格”，是比 produce 路径更弱的一种合格。**

### 2.4 “独立评审”只是清点

`R04` 在产线里只做 `artifact inventory`：检查文件存在、非空、大小。它不看结论对不对、数字是否可比。

真正校验内容的是 `R01 s09`——而 R01 就是报告的作者/收口人。**作者校验自己的稿子，然后盖上“生成与校验分离”的章。**

### 2.5 文档承诺未被代码执行

| 文档说 | 代码实际 | 实证 |
|---|---|---|
| 技能覆盖 <6 或角色 <4，视为未完成 | 只记录 `covered`，不参与 `ok` | `out_chain` 3 技能/3 角色，`ok=true`、quality 100 |
| Q5 抓“每节三条”的套壳 | 只判 `boundary_share`，`uniform_item_share` 算了但不用 | 套壳报告仍可 100 分 |
| 标题即判断（Q1≥0.85） | Q1 不在 research 档硬门禁 | 交付稿 Q1=0.385，仍 PASS |
| target_level 是档位 | 硬编码 `"L4"` | 4 个来源的报告也自称 L4 |

### 2.6 四份报告，同一个标题，四个“真相”

pipeline 里四份报告的 H1 全是“内蒙古三城水果市场调研”，只有副标题不同（调研/经营/链路/整改）。`meta.json` 的项目标题覆盖了 `doc_name`，所以“整改方案”的标题仍是“市场调研”。

同一批数据产出四份“真相”，没有版本号、没有报告族、没有主报告。用户拿到四个文件，不知道哪份是决策依据。

### 2.7 证据单点 + 外推 + 文体门禁制造过度自信

- 三城批发是 **11-16 / 11-11 的单日快照**；零售是 2–3 周周报；“未来两个月 +2.0%”是按去年同口径做的情景假设。
- `sources.json` 只有 title/url，**没有 quote 字段**，所以 `research_intake` 的 quote 回抓校验根本跑不了。系统里明明有“回抓原文、quote 必须命中”的能力，但交付稿走的是 `pack + draft`，**绕过了这道校验**。
- 禁用词表禁掉了“值得注意 / 综合来看 / 有待观察”这类不确定性信号；标题必须带数字、带判断词；数字密度下限 25/千字；深度分 100 分。这套组合的系统性效果是：**奖励断言，惩罚犹豫**。

**这是激励错位，不是 bug。** 三个 100 分不是质量的证明，是“优化过门禁”的证明（Goodhart's law）。

## 3. 统一架构：一套全做

### 3.1 目标形态

```
意图 + 数据
   │
S0 能力扫描：数据画像 + 20 角色能力图（real/simulated/blocked）
   │
S1 问题定义（M1）：回答什么、不回答什么、3–5 个必答问题
   │
S2 证据采集（M2）：来源、A/B/C/D 等级、交叉验证、缺口
   │
S3 维度匹配：按问题 + 数据能力选 5–8 个 MECE 维度
   │
S4 多角色执行：问题 → 所需能力 → 角色并行跑方法（不是先判 A/B）
   │
S5 断言链（M3）：每个维度 观察 → 对照 → 机理 → 落点 → 证伪
   │
S6 风险（M4）+ 动作（M5）：证伪条件、敏感度、owner、停止条件
   │
S7 装配：章节 = 维度，不是纲领写死的 order
   │
S8 断言级门禁 + 模块级门禁
   │
S9 渲染：一份报告 + manifest（记录 coverage / 每道门禁是否真的跑了）
```

**通用的是结构，不是内容：**

- 深度：每个维度必须走完五段断言链，有方法、有 refs、有证伪条件；
- 数据：M2 证据包 + A/B/C/D 等级 + 至少一组交叉验证；
- 内容：维度来自 20 个角色的真实问题库，不是市场研究那 17 个维度；
- 广度：MECE 至少覆盖 3 组（目标 5 组）+ 多角色覆盖度；
- 任何业务：维度与业务无关，新业务只加数据/关键词，不加纲领、不加帧、不加产线。

### 3.2 一个入口

```bash
guagua.py report build --intent "…" --dir <项目> --out <目录> \
  [--results …] [--draft …] [--lens …] [--require-coverage 0.8]
```

`pack` 变成内部步骤，`produce`/`research` 变成 `build` 的兼容别名，一个版本后删除。

### 3.3 覆盖度替代分支

```
问题 → 所需能力 → 可用角色 → coverage = {questions, capabilities, roles, gaps}
```

`coverage` 低于阈值时，报告标 `INCOMPLETE` 并写缺口，**不再用 A/B 掩盖**。单角色只是 coverage=1 的退化，不是分支。

### 3.4 一个框架替代 22 纲领

代码里已经有半成品：`core/report_framework.py`（v9）。

- **M1–M5 五模块**：问题定义 / 数据校验 / 结构化推导 / 风险 / 动作；
- **17 个业务无关维度**：市场规模、需求结构、增长、价格、客群、供给、成本、链路、竞争、渠道、产品、单位经济、投入回报、经营周转、政策、风险、执行；
- **5 个 MECE 分组**：需求 / 供给 / 竞争渠道 / 财务 / 风险；
- **A/B/C/D 证据等级**；
- **`match()`**：按主题 + 数据能力选维度，保证 ≥3 个 MECE 组；
- **S0–S9 执行流**：每步有 gate。

`core/frames_framework.py` 是它的通用装配器：`FRAMES = {"analysis": build_analysis}`。

**问题在于：它只是 `THESES["analysis"]`，第 22 个纲领，不是默认路径。** 前面 21 个业务纲领、2 套业务帧、3 个入口仍然在主路上。第一步不是重写，是**扶正 v9，降级旧的 21 个**。

### 3.5 类型是结果，不是入口

不再有“选报告类型”这一步。报告类型由选中的维度“长”出来：

- 单位经济/成本/保本占主导 → 标签“经营诊断”；
- 链路/传导/供给占主导 → 标签“链路优化”；
- 风险/整改/执行占主导 → 标签“整改方案”；
- 市场/需求/增长占主导 → 标签“市场调研”。

`--lens` 只做维度权重和开篇语气，不改章节、不改方法、不改门禁。这样既保留“我要一份经营报告”的表达能力，又不需要 22 套代码路径。

## 4. 二次反思：你的问题定义可能错在哪

### 4.1 你真正想解决的底层需求

把你的表述按层次拆开：

| 层次 | 你的表述 | 翻译 |
|---|---|---|
| 表层 | 口径/路径/分支/纲领太多 | “系统太复杂，我要收敛” |
| 中层 | 一条产线、多角色、一套全做 | “我要任何业务都能出报告” |
| 底层 | 深度、数据、内容、广度；20 角色已覆盖维度 | “我要一套可复用、可信、低边际成本的决策生产能力” |
| 情绪层 | “这非常荒谬” | “我看不懂、不敢信；简化是重新获得控制感的方式” |

**你真正要的，不是“一条产线”，是“一条我能看懂、能信、能复用的产线”。** 可理解性是手段，可信度是目标。

### 4.2 症状 / 原因 / 目标辨析

| 层次 | 内容 | 判断 |
|---|---|---|
| 症状 | 22 纲领、3 走法、2 分支、口径多 | **事实，但只是症状** |
| 直接原因 | 系统编码“输出”而非“问题” | **成立** |
| 更深原因 | 没有“决策级”定义；没有结果闭环；能力层不均 | **这才是根因** |
| 手段 | 一条产线、一套框架、一个入口 | **必要，但不是目标** |
| 目标 | 任何业务、深度、数据、广度 | **需要翻译成可验收指标** |
| 可能的误判 | 20 角色已覆盖维度 | **报告层不成立（见 4.3）** |

### 4.3 三个可能的误诊

#### 误诊一：把“架构复杂”当根因

架构复杂是**症状**。根因是：

- **没有“决策级”定义**：什么算一个可行动的断言？现在的门禁只定义“文档合格”，没定义“断言可行动”；
- **没有结果闭环**：报告发出去之后，预测对不对、决策好不好，没有台账；
- **能力层不均**：报告能调用的能力，远少于 20 角色 × 195 技能。

如果只合并产线，不动这三件事，你会得到一个**更整齐的、但仍然浅的系统**。

#### 误诊二：把“一条产线”当目标

“一条产线”是手段。目标是：

> 任何业务 → 决策级报告，且新业务的边际成本随能力复用而下降。

一条产线可能更快地生产**浅报告**；22 条产线也可能产出**深报告**。产线数量与报告质量没有必然关系。**用“是否只剩一条产线”当验收标准，会优化错对象。**

#### 误诊三：把“20 角色覆盖维度”当事实

实测 `python guagua.py report capabilities`：

```
角色 20 / 技能 195 / 动作 337；可进报告 94 技能 / 143 动作
r08 蛙建成  技能 1/10  不进报告
r09 蛙稳码  技能 0/8   不进报告
r10 蛙成美  技能 1/14  不进报告
r17 蛙织网  技能 1/9   不进报告
r03 蛙守线  技能 1/8   进报告（仅 1 个可进报告技能）
```

这意味着：

- **4 个角色在报告层是“缺席”的**：工程、设计、MVP、自动化；
- **5 个角色可进报告技能 ≤1**：r03、r08、r09、r10、r17；
- 报告实际依赖的，是 r06（15/21）、r05（7/9）、r12（7/12）、r07（6/10）、r15（6/10）、r16（5/8）、r19（6/8）、r20（6/8）等少数角色；
- 水果调研实际只用了 **3 角色/4 技能**，经营用了 **4 角色/6 技能**。

所以“20 个智能体已经包含了这些维度”在**组织层**成立，在**报告层**不成立。把 22 纲领合并成 1 个，不会让 r09 的工程能力、r10 的设计能力、r17 的集成能力自动进报告。

**更值得解决的问题是：先把“哪些角色能回答哪些问题、以什么证据、到什么深度”这张能力图建起来，再谈统一产线。** 否则统一后的引擎会路由到“没有可进报告技能”的角色，报告只能靠少数几个角色撑，深度和广度都上不去。

### 4.4 更值得解决的问题

> **给定现有 20 个角色和可获得的数据，如何稳定产出“决策级”报告——每个头条断言可识别、可证伪、可行动，且新业务的边际成本可控？**

拆成五个子问题，按优先级：

1. **决策级定义**：一个 claim 必须有什么（refs、可比性、竞争解释、证伪条件、置信度、owner）？
2. **能力图**：role × question × status（real/simulated/blocked）× evidence；哪些角色进报告，哪些只做执行？
3. **数据 intake**：来源分级、quote 校验、交叉验证；没有数据时报告说“不能下结论”，而不是用假设补。
4. **结果闭环**：预测/决策/结果台账；半年后能算命中率，系统才会学习。
5. **产线统一**：以上四件有定义之后，v9 统一引擎才是“把能力组织起来”，而不是“把空洞组织起来”。

**顺序很重要：先定义质量，再建能力图，再统一产线。** 反过来，会得到一个漂亮但空的框架。

### 4.5 如果是我，会怎么排顺序

**0–2 周：一个业务、一个决策、一张 claim graph 的端到端试点。**

- 选水果项目（已有数据、已有 4 份报告）；
- 把 4 份报告的头条断言抽成 claim card；
- 量三个数：可行动断言比例、未识别断言比例、能力/数据缺口清单；
- 产出：一份“决策级”样例 + 一份“缺口清单”。

**2–6 周：能力图。**

- 用 `report_roles.classify()` + `docs/ROLE_CAPABILITY_MATRIX.md` 建 role × question 矩阵；
- 标记每个能力的 real/simulated/blocked；
- 决定：哪些角色进报告，哪些只做执行；r09/r10/r17 是补能力，还是从“报告承诺”里去掉；
- 产出：一份“谁能回答什么”的图，替代“20 角色都覆盖”的口号。

**6–10 周：数据 intake 一等公民。**

- 把 `research_intake` 的 quote 校验接进主路径；
- 每条来源必须有 quote；没有 quote 的来源降级；
- 单点数据不能进标题，只能进“观察”；
- 产出：证据等级分布 + 缺口清单。

**10–14 周：v9 统一引擎 + coverage。**

- `report build` 默认走 `report_framework`；
- `coverage()` 替代 `route()`；
- `--lens` 替代 22 纲领；
- 22 纲领下线，旧 CLI 保留别名一个版本。

**持续：结果台账 + 置信度校准。**

- 每个预测/动作登记到期日；
- 到期回填结果；
- 用命中率校准下一轮的置信度。

### 4.6 什么情况下你是对的、我不该拦

- **如果目标只是“降低维护复杂度、让系统可读”**：统一产线就是正确目标，能力缺口是另一件事。先统一，完全合理。
- **如果报告只是内部讨论稿、决策可逆**：“决策级”可以降级为“可追溯级”；当前系统已经够用，不需要 claim card 那套重武器。
- **如果 20 角色是未来产能规划，不是当前产能**：能力缺口是路线图问题，不是架构问题；统一产线可以为未来留接口。
- **如果报告是给外部客户看的咨询交付物**：完整性、版式、可辩护性可能比“可识别性”更重要；当前的长文档形态有它的价值，不该一刀切砍成 1 页 memo。

**我的批评成立的前提是**：你要的是“用报告做决策”，而不是“用报告做存档/展示”。如果是后者，当前系统的主要问题确实只是“太复杂”，统一产线就够了。

5. **暂缓产线大重构**：等 1–4 的结果出来，再决定 v9 扶正的节奏；避免“先重构、后发现能力不够”。

## 6. 验收指标（替代“只剩一条产线”）

**North Star：**

- 决策级报告 / 月（每个头条断言 actionable=true）；
- 新业务边际成本（人时 / 份，或 token / 份）；
- 可行动断言比例（actionable / total）；
- 未识别断言拦截率（被 claim gate 拦下的比例）；
- 结论半年命中率（结果台账回填）。

**护栏：**

- 不可比比较不进标题；
- 每个头条断言有 falsifier；
- 每份报告有 coverage 和 gaps；
- 每个数字有 ref，且没有 `<31`/assumptions 绕过；
- manifest 记录每道门禁是否真的执行过。
