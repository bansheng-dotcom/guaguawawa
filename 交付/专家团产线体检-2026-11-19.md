## 一、体检方法与口径

不看文档说法，只看三件事：

1. **入口能不能跑**：`guagua.py check`、`ci_report_checks.py`、`check_convergence.py` 三个门禁实跑；

## 三、断点清单（按严重度）

### A. 专家被选中，但产线不认它 → 静默出假报告（P0）

**机制**

- `configs/experts.yaml` 里 6 个「进报告」角色**没有任何方法**：`r01`、`r03`、`r04`、`r11`、`r18`、`r19`；
- `core/orchestrator.py:208-210`：无方法角色 `readiness=1.0`，于是被选进 roster；
- `core/decision_report.py:77-82`：按专家出题失败 → `except ValueError` → **静默改用数据题库**，报告照出；
- `decisions.json` 仍写 `mode=intent`、`roster=[r11]`，看不出换了问题。

**实测（可复现）**

```bash
python guagua.py report "小红书笔记怎么写才能带货" \
  --dir "…/内蒙古水果三城调研_2026-11-16_pipeline" --out <tmp>
```

| 观测 | 值 |
|---|---|
| 编排 | `mode=intent`，`roster=[r11 蛙点题]`，`blocked=[]` |
| 决策契约 | `drafted_from=data`，`owner` 全空 |
| 产物 | 《内蒙古三城水果市场调研》6 节 |
| 门禁 | `ok=true`、`binding=1.0`、`quality=100`、六道门禁全 `pass` |

同类触发：`模型评测能不能上线`（选中 r19）、`把采购单和库存对账`（选中 r03）、`数据仓库管道建设`（r18）。

**判据**：这是 2026-11 前「问招聘答水果」的老病，在「无方法角色」上复发。修复标准：**专家答不了就整份失败（INTENT_UNBOUND），不许换题库。**

---

### B. 角色 `result.json` 进不了报告产线，文档还在教（P0/P1）

**机制**

- 组织设计：执行角色只交 `result.json` + `evidence.json`，报告由 R01 统一出具（`REPORT-BRIDGE-GUIDE.md` 第 1–2 节）；
- 现实：v11 起 `report run --results` 已删除，`core/` 全仓**没有任何模块读取角色 `result.json`**；
- `REPORT-BRIDGE-GUIDE.md:111-112` 的验收步骤仍写 `report run --intent … --results …`，照做必失败：

```
guagua report: error: unrecognized arguments: --results
```

**后果**：20 个角色各跑一遍 → `result.json` 留在 `workspace/`；报告产线从原始数据**再算一遍**。两条计算路径并行，结论可能不一致，且没人对账。

**修复标准（二选一，不能两头挂空）**

1. 真接桥：`result.json` → `evidence_pack` 适配器，`report` 增加 `--results`；
2. 明确不接：删除文档死命令，写清「result.json 当前只做审计留痕，不进报告」，桥接排期到 P2。

本轮取 2（成本可控），并把桥接列入 P2 待办。

### C. 上游调研数据进不了下游报告线（P1）

**机制**

- 通道识别只认中文关键词：`core/analysis_desk.py:46-47`（零售/采价/门店价；批发/市场报价/东瓦窑）；
- 调研线 `build_data.py:261-273` 产出的是英文：`market_prices_long.csv` / `retail_weekly.csv` / `origin_prices.csv`；
- 结果：视图全空 → 所有价格类方法不可挂载 → 所有专家 blocked → `INTENT_UNBOUND`。

**实测**：`--dir 内蒙古水果三城调研_2026-11-16` → 报错缺 `price.series2 / price.momentum / price.economics …`。
仓内能跑的是**手工改名副本** `…_pipeline`（`零售价_周度.csv`、`批发价_市场长表.csv`、`产地价.csv`）——全仓 grep 不到生成它的脚本。

**后果**：每次调研完要人工改文件名/列名才能出报告；改名规则一旦记错，产线静默退化为「没有数据」。

### D. 发卡 16 张 → 收卡 3 张，报告照出（P1）

**机制**

**后果**：13 位专家掉线不会触发任何红灯；报告看起来完整，实则只代表 3 位专家。

## 四、根因

报告产线在 v11/v12 收敛成「方法库 + claims」两条路后，**角色层与报告层之间的适配器（`result.json` → `evidence_pack`）没有重建**：

- 编排器选出的专家只用来「起草问题」，不用来「作答」；
- 真正能作答的 `core/methods` 只覆盖「价格表」「通用业务表」两类数据形状；
- 于是「专家在场」与「专家作答」是两套名单，**没有任何一处校验两者一致**——A 节的静默换题就是它们的缝隙。

### 7.4 已闭环：版式改动导致的 CI 红（19:30–19:45 修复）

**背景**：18:19–18:20，工作区里四份文件被本任务之外的改动更新（引入 `report_editorial.enrich`
与逐节 `layout=rail/blocks`）：`report_flow.py`、`report_line.py`、`report_theme/flow.py`、
`report_theme/blocks.py`。此后水果两条 run-line 从 PASS 变 block（18:27/18:34/18:38 三次复现），
`tests/test_report_sections.py` 也红。归因已用 `git stash` 复现证明与 7 条修复无关。

**根因**（两处）：

1. `core/report_theme/pages.py::_section` 只渲染「事实/解释/所以 + 边界」，**漏了证伪与机理**：
   `report.html` 里 `什么会推翻它` 0 次、`sec-falsifier` 0 次、`rail-layout` 11 次；
