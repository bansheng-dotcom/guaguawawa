## 三、角色之间怎么协作（文档 vs 代码）

### 3.1 文档写的

```
创始人
  └─ R01 蛙全局（CEO/编排）
       ├─ 执行线：R02/R03/R05/R06/... → R01 → 创始人
       └─ 独立评审线：R04 蛙挑刺 → 直接创始人（旁路 R01）
```

三种模式：A 单角色五步（澄清→自查→展开→自评→汇报）、B 失败/越界移交（6 类触发 + handoff 字段）、C 多角色 GSD 五相环（Discuss→Plan→Execute→Verify→Ship）。

### 3.2 代码实际做的

| 文档承诺 | 代码事实 |
|---|---|
| 执行角色交 `result.json`，R01 解读后出报告 | `report_flow` 不读 `result.json`；A 路只读 `evidence_pack`，B 路只读 `claims` |
| `plan / dispatch` 把多角色结果汇总成报告 | `dispatch_results.jsonl` **零消费者**；报告线与任务卡线不交换数据 |
| R04 独立评审成品 | R04 不在报告路径上；`claim_consistency` 是「R04 的可执行版」，但 C2（D 级来源）只统计不拦 |
| R01 是唯一作者 | 是；但 R01 同时是逐节裁判（`_call_r01` 子进程），生成与校验在同一个 owner |
| 20 角色都可进报告 | `enters_report=false` 4 个（R08/R09/R10/R17）；R11/R19 有卡但零方法，R12 只有 2 个可用方法（`channel` 已不存在） |

### 3.3 真实的协作数据流

```
A 路：数据目录 ──scan──> desk ──plan──> 方法 ──run──> finding ──R01 过账──> HTML
        ↑ 没有角色；技能只是被 core 子进程调用的工具

B 路：intent ──research_protocol.plan──> brief
        └─> 16 张 TASK.md ──（模型在仓外跑）──> claims.json
              └─> collect（验完整性/合并/命名空间）──> compile ──> 同一出口
```

**结论**：系统有「角色」，但报告这条线更像「R01 + 一个工具库」；真正的多角色协作只在 B 路的 `brief/collect` 上成立，而它刚落地（11-18 20:29 才提交 v12.2）。

## 五、两套图表系统：选哪个、谁更好用

### 5.1 先纠正一个说法：**「做表」不是两套**

- 表格只有一套：`core/report_renderer.py:1723-1729`（blocks 简表）与 `:1766-1823`（section 表）。
- 两套是**图（chart）引擎**：v1 = `core/charts/chart_lib.py` + `chart_renderers_ext.py`（手写 SVG，纯标准库）；v2 = `core/charts/v2/`（matplotlib 后端，确定性 SVG）。
- 「两个都能做表」的三个来源：`chart_plan.choose()` 点数不足时返回 `{"type":"table"}`（死代码）；`decision.synth_from_table()` 从表反推图；R01 报错文案「改用表格」。都不是表格实现。

### 5.2 两套的真实现状

| 维度 | v1 手写 SVG | v2 matplotlib |
|---|---|---|
| 图型 | 48（`chart_lib.py:639-643` + `chart_renderers_ext.py:1897-1936`） | 48（`core/charts/v2/__init__.py:20-74`），lollipop→dot、bridge→waterfall 为别名，实际 46 实现 |
| 默认 | 仅回退 | **默认**（`report_renderer.py:1525-1527`，env/契约可覆盖） |
| 依赖 | 纯标准库 | 必须 matplotlib（`v2/base.py:14-18`） |
| 中文 | 随页面字体 | 硬编码字体栈（`v2/theme.py:19,82`；`base.py:27`），本机有微软雅黑 |
| 负值 | vbar/area/streamgraph 拒绝 | 统一画零线 |
| 长标签 | 固定 224px，不截断 | 14 字截断加省略号 |
| 可访问 | 带 `role` / `aria-label` | 无 |
| 性能 | 48 张 ~0.01s | 48 张 ~2.1s（44ms/张） |
| 失败行为 | 部分型直接抛异常 | **吞掉所有异常返回 None**（`v2/__init__.py:407-410`） |

### 5.3 关键发现：现在的「兜底」是假的

1. v2 异常被 `try/except: return None` 吞掉，`_CHART_STATS["error"]` 几乎永远为 0，只会记 `fallback`；
2. `report_bridge.py:53-55` 用 `capture_output` 收走 stderr，`report_renderer.py:1463` 的告警没人看得到；
3. v1 没有 v2 的反向归一，**本次复核把 v2 形状的样例喂给 v1：gantt / ridgeline / small_mult 直接抛 TypeError/KeyError**（22 个样例里 3 型崩；另一轮 48 型抽样测得 10 型崩）；
4. 所以「v2 画不了 → v1 兜底」在相当一部分型上是「报告直接 500」或「画出一张素图」，而不是降级。

三个图表门禁全绿（`check_chart_v2_coverage` 48/48、`check_chart_report_embed` 48/48、`check_chart_fallback` 48/0/0），但它们只证明「自带样例能画」，不证明真实数据能画、也不证明回退可用。

### 5.4 结论与迁移

**选 v2，但把 v1 从「运行时兜底」降为「显式对照」。**

1. `report_renderer.render_chart`：v2 失败不再 `except: pass`，记录 `{type, reason}` 并返回「数据不足」占位卡；只有 `engine="v1"` 显式请求才走 v1。
2. `manifest` 增加硬断言：`chart_stats.v2 == total` 且 `fallback == 0` 且 `error == 0`，否则 `ok=false`；至少把 fallback/error 列进 `gates`。
3. v1 只保留两个用途：① 无 matplotlib 环境的降级安装包（需先补 10 型归一）；② 快照/回归基准。二者都要有测试，否则删。
4. 删死接线：`chart_capabilities.render_chart`、`chart_plan.choose`（全仓 0 调用）。
5. 表格继续只在 `report_renderer`；把 `:1723-1729` 与 `:1766-1823` 合成一个 `render_table()`，并修单位推断（只给「率/量/额」中语义匹配的列补单位，不给 `变化率` 补 `元/斤`）。

## 六、名册为什么会有两个

### 6.1 第一层：`plugin.json` 自己声明了三遍

`agent-packs/plugin.json` 同时有：

| 字段 | 内容 | 生成处 |
|---|---|---|
| `agents` | 20 个 `./agents/*.md` 路径 | `gen_agent_packs.py:428` |
| `teamInfo.memberAgents` | 19 个目录名（不含 lead） | `:433` |
| `members` | 20 个对象（id/displayName/profession/avatar/description） | `:465` |

宿主如果既读 `agents` 又读 `members`，同 20 人会渲染两遍——**这是「名册出现两个」最可能的直接原因**。修法：只保留宿主实际消费的那一个（DSH/agents.md 用 `agents` + `.md`；WorkBuddy 用 `members`），另一个用生成器开关控制，默认不输出。

### 6.2 第二层：名册文档列了两张表，且主表错列

`交付/专家团名册-20人.md`：

- 主表表头 9 列：`# | 角色 | 姓名 | 职务 | 目录 | 动作 | 技能包 | 进报告 | 主责能力`
- 数据行只有 8 列：`r01 | 蛙全局 | CEO 主理人/编排器 | 目录 | 10 | 9 | 是 | 能力`
- 少了「姓名」一格 → 从第 3 列起整体右移，`角色` 与 `姓名` 看起来是两个身份列；
- 文末又有「20 人的分工（按报告相关性）」第二张表，把同一批人再列一遍。

生成器 `_make_roster_doc.py:15,21-23`：表头写 9 列，行模板只拼了 8 个值。

### 6.3 第三层：系统里名册有 4 个来源，口径还不一致

| 来源 | 规模 | 谁读 | 问题 |
|---|---|---|---|
| `core/registry.py::ROLES` | 20 条手写身份 | 启动/加载/`roles`/`info` | 没有技能，没有 `enters_report` 字段 |
| `core/roster.py` | 20 人 + 200 动作 + 196 技能包 | `dispatch.write_cards`、`find_action` | 从磁盘现算；`enters_report` 硬编码 r08/r09/r10/r17 |
| `configs/experts.yaml` | 20 张专家卡 | `orchestrator.plan` | 由 `gen_experts.py` 生成，但**当前已漂移**（r05 仍列 size/demand/consistency/coverage，r12 仍列 channel） |
| `agent-packs/` | 20 份 `.md` + `plugin.json` | 外部宿主 | 与源一致（`--check` PASS） |

**动作数两套口径**：名册文档 200 个、`guagua.py report capabilities` 337 个、技能 196 vs 195。原因：roster 数 `prompt_profile.actions`，`report_roles` 数另一套契约动作。

### 6.4 修复顺序（从便宜到贵）

1. `_make_roster_doc.py` 补「姓名」列、删文末第二张表（10 分钟）。
2. `plugin.json` 只输出一种成员声明（10 分钟）。
3. `enters_report` 收敛到 `core/registry.py` 一处（1 小时）。
4. `gen_experts.py --check` 接进 `ci_report_checks.py`（10 分钟），先重生成。
5. 名册只保留「身份 + 进报告」两件事，技能/动作交给 `roster.build()` 现场算，不再进文档（半天）。

## 八、共同根因（6 条，不是 6 个 bug）

### C1. 降级即通过（最贵的一条）

系统里每个「答不了」的地方，几乎都有一条「继续出报告」的路：

| 位置 | 降级方式 | 后果 |
|---|---|---|
| `decision_report.py:77-82` | 专家答不了 → 数据题库 | 问内容营销出水果报告，`ok=true` |
| `orchestrator.py:207-210` | 无方法 → `readiness=1.0` | 空壳专家可出场 |
| `analysis_methods.py:199` | 技能没 `ok` → True | R06 失败被计成功 |
| `claim_consistency.py:123-125` | C2 只统计不拦 | D 级来源可当结论 |
| `quality_gate.py:112-119` | 缺 HTML → 跳过两层 | 单层也能 ok |
| `report_quality.py:87-96` | 5 节 → baseline | Q1/Q2/Q4 门槛降为 0 |
| `charts/v2/__init__.py:407-410` | 异常 → None → v1 | 图静默变素图/崩 |
| `methods/spec.py:139-148` | 方法异常 → gap | 报告继续，缺哪条不进 manifest |
| `ci_report_checks.py:81` | 换意图没换内容 → 只验能跑 | 两份报告哈希相同仍「ALL PASS」 |
| `report_cli.py:310-312` | 未知子命令 → 当 intent | `report decide` 被吞，CI 测了个不存在的命令 |

**共同点**：降级动作本身不写进 manifest、不影响 `ok`。所以「门禁全绿」只证明「有产物」，不证明「答对了」。

### C2. 多源无校验（同一事实总有第二份）

- 名册 4 源、`enters_report` 2 处硬编码；
- 图表 6 套词汇表（48 型注册表 / `chart_by_relation.yaml` / `chart_type_by_question.json` / `CHART_POLICY` / 方法内 type / 渲染器分发）；
- 问题 4 套来源（QBANK / 旧 question_library / derive / roster）；
- 阈值 3 份（`report_policy.yaml` 0 引用 / `PROFILES` / 代码里 0.8）；
- `experts.yaml` 有生成器、有 `--check`，**但没接进 CI**，所以现在就是漂的。

### C3. 重写代替收敛

每次遇到「这条线不对」，选择是「再写一条新线」，而不是「把旧线删掉」。结果是：
- 新线能跑 → 验收通过；旧线还在 → 下次又踩；
- 旧线的参数/文档/配置继续被引用（`--lens` 56 处、`--thesis` 仍在 help、`report_flow` docstring 仍写 A/B）；
- 最后靠一次「大扫除」删 45+52 个文件，但删除本身又没提交。

### C4. 工作区当暂存区

1,464 条未提交、1,073 个删除、−857,092 行。根因不是「懒」，是**没有完成定义**：文档写「提交前自检全绿」，但自检清单里没有「工作区干净」「删除已归档」「旧路径已删」。

### C5. 文档先于代码，且双写

`README` 自己写着「双写必漂移」，然后 `REPORT-STANDARD.md` 同时在说「已删除」和教「怎么用」。文档不是索引，是第二份实现。

### C6. 只用 happy path 验收

233 个测试全绿，但没有一条「意图不匹配必须失败」「专家无方法必须失败」「v2 失败必须 block」。测试把「当前行为」当「正确行为」（历史上有 `assert chart_config_read_by_code is False` 这种把 bug 写成断言的例子）。

## 十一、红队：假设我上面的方案是错的

我最初想推的方案是：**停功能 → 合并两条内容路径 → 全量单一注册表 → 加失败门禁**。下面用最强反对者的角度打它。

### 反证 1：这几天的主要动作其实是「删」，不是「加」

11-18 的净增删是 **+13,010 / −20,551**；v12 删了 3 个域方法包、23 维语义层、45+52 个脚本、4 个 core 模块。把「重写」一棍子打死，会误伤这些正确的收敛。

**站得住吗？** 部分站得住。要区分两种 churn：
- **删代码**（v12 的死代码清理）→ 应该鼓励，问题只是没提交、没归档；
- **换抽象**（问题来源 5 轮、报告 5 轮）→ 才是返工，因为每轮都换了机制但没换结论（仍是关键词/优先级）。

所以规则不该是「禁止重写」，而是「**同一决策第二次重做前，必须写下上一版为什么失败**」；删除要保留，换抽象要拦。

### 反证 2：单一注册表会把系统做死

一个 20 角色、6000 文件的单人项目，强行 registry-as-data 会拖慢每一次改动；而且角色的价值就在「每个角色有自己的技能与话术」，统一 schema 会抹掉差异。

**站得住吗？** 对一半。全量注册表确实过度设计；但**只需要 3 个单一来源**：谁能进报告、图型集合、门禁阈值。这三处已经在漂，且修复成本是「改一行 + 接一个 check」，不是 DSL。方案应缩小到 3 项。

### 反证 3：「失败即失败」会让工具不可用

真实调研经常数据不全，硬失败会逼用户绕过工具；部分报告比没有报告好。

**站得住吗？** 站得住，所以不能一刀切。正确的区分是：
- **内容可以不完整**（允许部分报告）；
- **但不能声称完整**（`ok=false` / 头条不得用未答问题 / manifest 列 degraded）。
也就是「fail the claim of completeness」，不是「fail the report」。这比我最初的「全 block」更可用。

### 反证 4：A 路本身就该退役，补 fallback 是给死路刷漆

意图绑定做不稳，是因为 A 路用「关键词 → 专家 → 固定问题」硬凑语义；B 路让模型自己出题，才可能真正答对。花力气修 A 的 fallback，不如把 A 缩到「结构化 KPI 数据 + 人给 decision.json」。

**站得住吗？** 强反对，且我接受一半。A 路的正确边界是：**有结构化数据 + 有明确决策契约**；没有 decision.json 时不该 auto 出一份「像报告」的东西。所以不是「修 fallback」，是「删 auto 起草 + 删 fallback」，让 A 路只服务确定性问题。B 路成为模糊意图的默认。

### 反证 5：1,073 个删除可能是故意的清理，git 里还在，谈不上「不可恢复」

HEAD 仍有这些文件，`git checkout` 能恢复；「干净克隆看不到」只在未来提交后成立。

**站得住吗？** 事实层面对一半：现在能恢复。但风险是真实的——只要下一次 `git add -A && commit`，这些文件就永久消失；而这次的提交信息里没有任何「删除 1,073 个历史交付」的说明。规则仍要保留（删除前归档），但优先级从 P0 降到 P1。

### 反证 6：名册重复可能只是宿主渲染问题，不是系统问题

如果宿主只读 `agents`，`members` 不显示，那名册文档的两张表才是用户看到的「两个」。

**站得住吗？** 需要实测宿主读哪个字段（本机 asar 打包，未能确认）。但无论哪种，`plugin.json` 三处声明 + 文档两张表 + 系统四源都是可独立修复的冗余；修完两种解释都消失。

### 反证 7：我的「根因」可能只是症状的集合

C1–C6 每一条都能再问「为什么」：为什么降级？因为要出报告；为什么要出报告？因为产品承诺「一条命令出报告」；为什么承诺？因为这是卖点。再往下是产品定位，不是工程规则。

**站得住吗？** 这是最有力的一条。它说明：**规则只能防「同样的工程错误」，防不了「产品承诺与能力不匹配」**。所以方案里必须有一条产品级约束：**当系统答不了时，产品要允许「不出报告」**——否则所有工程门禁都会被「必须出报告」的压力腐蚀。这条应写进规则 R3 的说明里（已写：ok 不得为 true）。

### 红队后的结论

- 保留：删 fallback、单一来源（缩到 3 项）、失败显性、工作区纪律、反例测试。
- 修正：不合并两条内容路径（它们服务不同输入）；不全量注册表；不硬失败（改为 fail the claim）；不把 churn 一棍子打死（区分删与换抽象）。
- 新增：A 路去掉 auto 起草，只接受显式 decision；B 路补「节序」与「标题」两个真问题（见下）。
