**这个缺口的代价，不是「少读几个文件」，是四个判断错误：**

1. 没看到 `chart_type_by_question.json` → 造了重复的 `CHART_POLICY`；
2. 没看到 `report_policy.yaml` 里 `trace_min=1.0` → 把门禁阈值硬编码成 0.8；

而不是再加一个模块——这正是 §四、§六 要修正的地方。

## 一、你真正要的（Job to be done）

把三轮的原话放在一起看，你要的不是「报告好一点」，而是三个性质：

| 性质 | 含义 | 可验证的判据 |
|---|---|---|
| **不说谎** | 问 5 个问题就答 5 个；答不上要显式说；不能自证 100% | `binding` = 已答/已问；未答必须列出 |
| **可扩展** | 加一个业务域，不改六处代码、不新增一套词汇表 | 新域只在**一个注册表**里加边；`report_model --audit` 无悬空 |
| **会变准** | 判断到期能回填，命中率能校准下一轮置信度 | 每条判断有 deadline、hit/miss/partial/void |

报告质量、图表、节数，都是这三条的**症状**。只治症状，就会不断加门禁、加表、加入口——这正是过去 12 条产线 → 4 lens → 22 纲领 → 1 条产线反复发生的事。

## 二、跨领域对标：同一个结构问题，别人怎么解

报告系统的病是「**先有答案，再补问题**」，这在很多领域有名字、有成熟解。

| 领域 | 同构问题 | 成熟机制 | 映射到本系统 |
|---|---|---|---|
| 科学 | HARKing（先看结果再编假设）、p-hacking | **预注册 / Registered Reports**：问题、指标、分析计划先登记，再看数据 | 决策契约必须先于方法执行；`binding` 就是「预注册遵守率」 |
| 审计 | 管理层认定 vs 审计程序；证据等级 | **认定 → 程序 → 证据**，独立性、证据充分性 | 断言类型 → 方法 → 来源 A/B/C/D；R04 独立评审 |
| 系统工程 | 需求实现了吗 | **需求追溯矩阵（RTM）**：需求 → 设计 → 实现 → 测试，逐条可追 | 问题 → 方法 → finding → 章节 → 图，逐条可追；`trace_min=1.0` |
| 数据/BI | 一个指标十种口径 | **语义层（semantic layer）**：指标定义一次，多处消费 | 问题/能力/方法/图型只定义一次，planner、gate、renderer、docs 共用 |
| 控制论 | 多个控制器争一个设定值 | **一个设定值一个回路**；多回路会振荡 | 三个「出题人」= 三个控制器；只留决策契约一个 |
| 咨询 | 报告读完不知道要干嘛 | **金字塔 / SCQA / 行动标题**：结论先行、每页一个判断 | 节标题是判断、节末「所以」、动作带停止条件 |
| 情报 | 证据支持多个假设 | **ICD 203 + ACH**：竞争假设、置信度、来源交代、证伪 | ClaimCard 的 `rivals / confidence / falsifier` |
| 产品 | 做完了才发现不是要的 | **Working Backwards / PR-FAQ**：先写发布稿与 FAQ，再开工 | 先写决策记录与 3–5 问，再跑方法 |
| 法律 | 论证散 | **IRAC**：Issue → Rule → Application → Conclusion | 先问题、再规则（对照）、再适用（证据）、最后结论 |
| 航空/医疗 | 单人操作会漏 | **检查单 + 独立复诵**：生成与核对分离 | 每节过账 + R04 清点（已有） |

**十个领域收敛到三条不变量：**

1. **先声明，后观察**（预注册 / PR-FAQ / IRAC）；
2. **每条断言可追到问题与证据**（RTM / 审计认定）；
3. **一个定义，多个视图**（语义层 / 架构视图）。

本系统三条都破了：问题由结果反推（破 1）、维度与方法互相悬空（破 2）、五套词汇表各自为政（破 3）。

## 四、最优解：一个记录、一个注册表、一个循环、多个视图

```
                 ┌──────────────────────── DecisionRecord（唯一事实）────────────────────────┐
                 │ decision / audience / deadline                                        │
                 │ questions[3–5]（预注册）                                               │
                 │   └─ claim（对照 / 竞争解释 / 证伪 / 置信度 / 等级）                    │
                 │        └─ evidence（来源 A/B/C/D、quote、refs）                        │
                 │        └─ chart（由对照类型选型，带 claim_to_prove）                    │
                 │ outcomes（deadline、hit/miss/partial/void）                            │
                 └───────────────────────────────┬──────────────────────────────────────┘
                                                 │
                     registry（唯一注册表：question → capability → method → chart → grade）
                                                 │
                     one loop：resolve → execute → bind → render → calibrate
                                                 │
        views：report.html / report.md / manifest.json / trace.json / audit.json / 文档表格
```

五条设计规则：

1. **Report = projection。** 报告不是产线的终点，是记录的一个视图；换主题、换语言、换 PDF 都是重渲染，不重跑分析。
2. **Gate = invariant。** 门禁不再扫 HTML，而是校验记录上的不变量：每个问题有 claim、每个 claim 有 refs、每个 refs 有等级、每张图能表达对照。
3. **One loop。** 只有决策契约能改问题集；方法、图型、lens 都不能。控制论上，一个设定值只配一个控制器。
4. **Registry as data。** 问题/能力/方法/图型的边写在一份 YAML（或 JSON）里，由它生成 planner 规则、门禁规则、文档表格；代码只读，不各写一份。
5. **先合并，后新增。** 新增模块前必须先盘点已有模块（`claim_card`、`claims`、`question_bank`、`focus_contract`、`chart_type_by_question`、`report_policy`）；
   能接线的接线，能合并的合并，不允许用「新模块」绕过「旧模块没接」。这条是 §零·二 的直接教训。

### 选项对比

| 方案 | 做法 | 代价 | 二阶影响 | 判定 |
|---|---|---|---|---|
| **A. 继续加门禁/加表**（现状惯性） | 每发现问题加一条 gate、一张映射表 | 低（单次） | 词汇表越来越多，CI 越来越慢，新域仍要改 6 处 | 局部最优，长期负债 |
| **B. 薄模型 + 视图**（推荐） | 1 个 `record.json` + 1 个 `registry.yaml` + 3 个视图渲染 | 中（2–3 周） | 门禁变成不变量；新域只加边；文档可生成 | **最优** |
| **C. 报告 DSL / 编译器** | 自研查询语言、编译到 HTML | 高 | 团队只有一个人，维护不起 | 过度设计 |

**为什么 B 是「最优」而不是「最好听」：** 它用最小的新增（2 个数据文件 + 1 个校验器）换掉最多的重复（5 套词汇表、3 份死配置、2 个入口），并且不改变已有渲染器与方法库。

## 六、迁移路线（每步可验收、可杀死）

### P0 · 盘点与接线（1–2 天）

- **先出资产地图**：`core/*.py` + `configs/*` + 谁在读谁（本报告 §零·二 的缺口，不许再犯）；
  `decision.py` 的 claim 字段与 `claim_card.py` / `claims.py` 对齐，能合并就合并，不新增第六套；
- `decision.choose_chart` 改为读 `configs/chart_type_by_question.json`（按 question key / 对照类型查表），删除 `CHART_POLICY` 里重复的 8 行；
- 门禁阈值读 `configs/report_policy.yaml`（`trace_min` / `coverage_min`），不再硬编码 0.8；
- CI 增加 `python -m core.report_model --audit`，先把「8 维 15 方法 / 7 孤儿 / 84 死配置」作为**基线快照**，只允许下降。
- **验收**：同一份水果数据，`report decide` 输出不变；`chart_type_by_question` 从 0 引用变成 1 引用。
- **杀死标准**：如果接线后图型选择反而变差（对照表达不出来），回滚并保留 `CHART_POLICY` 作为 fallback。

### P1 · 单一记录（3–5 天）

- 新增 `core/record.py`：`record.json` 含 `decision / questions / claims / evidence / charts / outcomes`；
- `decide` 只写 `record.json`；`manifest / binding / chart_audit / trace` 改为从 record 生成的视图；
- 视图渲染保持 `core/report_renderer.py` 不变（它只吃 contract）。
- **验收**：删除任一视图文件后能一键重建；`record.json` 里每个 claim 能追到 question id 和 refs。
- **杀死标准**：如果 record 的 schema 在 2 周内改了 3 次以上，说明抽象错了，退回 P0 的「多文件 + 校验器」。

### P2 · 注册表（1 周）

- `configs/report_registry.yaml`：`question → capability → method → chart → grade`，由脚本从现有四份来源生成并去重；
- 修 8 个维度的悬空方法、7 个孤儿方法；`report_model --audit` 归零；
- 文档表格从注册表生成（不再手写 47 处 lens 字样）。
- **验收**：新增一个业务域 = 只加 YAML 节点 + 证据契约，不改 Python。
- **杀死标准**：如果新域仍需要改 3 处以上代码，说明注册表没覆盖住，先补边再宣布完成。

### P3 · 校准（1 周）

- `outcome_ledger` 按 `question.id` 登记，deadline 到期回填 hit/miss/partial/void；
- `calibration.json` 给出 hit_rate + 样本量；样本 <10 不出结论（沿用现有规则）。
- **验收**：2027-02 到期后，每个问题的命中率能回到决策契约。

## 八、风险与反方

| 风险 | 说明 | 处置 |
|---|---|---|
| 过度设计 | 一个人维护不了语义层 | 只做「薄模型」：2 个数据文件 + 1 个审计器，不做 DSL |
| 迁移破 CI | 门禁从 HTML 改到 record | P0 先并行跑双门禁，P1 再切 |
| 注册表漂移 | 手写 YAML 会腐烂 | 由脚本生成 + `--audit` 进 CI，只允许悬空边下降 |
| 自动起草冒充决策 | `auto=true` 仍是「数据能答什么」 | 报告标题标「数据探索」；要决策稿必须人给 `--decision` |
| 校准样本太少 | 命中率不可信 | 样本 <10 只记录、不排名、不调置信度 |
