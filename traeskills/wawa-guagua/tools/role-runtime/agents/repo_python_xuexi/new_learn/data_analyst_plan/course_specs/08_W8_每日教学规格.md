## W8D1：Linux Shell基础

### 能力簇
**服务器上干活** —— 入职后你的代码不在自己电脑上跑，在服务器上。今天学会在命令行里生存：找文件、看日志、跑脚本、查问题。不需要成为Linux专家，但要能在服务器上不慌。

### 为什么今天重要
入职第一天，mentor给你一个服务器地址："代码在 `/home/data/scripts/` 下面，日志在 `/var/log/`，你自己上去看。" 你不会SSH→连不上去。连上去了不会`ls`→不知道有哪些文件。找到文件了不会`grep`→不知道怎么看日志。这些不是"加分项"——是"生存技能"。今天每学一个命令都配真实工作场景。

### 具体知识清单

**1. 连接服务器——入职第一天第一件事**
- `ssh username@server_ip` → 输入密码→连上远程服务器。`ssh -p 端口号 user@ip` → 指定端口
- 配置免密登录：`ssh-keygen`生成密钥→`ssh-copy-id user@ip`→以后不用输密码
- `scp local_file user@ip:/remote/path/` → 把本地文件传到服务器
- `scp user@ip:/remote/file ./` → 从服务器下载文件
- **入职场景**：mentor给你IP和账号→`ssh data_analyst@10.0.1.100`→连上→看到命令行了

**2. 文件系统——在哪、有什么、怎么找**
- `pwd` → 当前在哪个目录。"我现在在哪？"
- `ls` → 列出当前目录的文件。`ls -la` → 详细信息(权限/大小/修改时间)。`ls -lh` → 人类可读的文件大小
- `cd /path/` → 切换目录。`cd ..` → 上一级。`cd ~` → 回到home。`cd -` → 回到上次的目录
- `mkdir -p /path/to/new/dir` → 创建目录(含父目录)。`rmdir` → 删空目录
- `cp source target` → 复制。`cp -r` → 复制整个文件夹
- `mv source target` → 移动/重命名
- `rm file` → 删除文件。`rm -r dir` → 删除文件夹。`rm -rf` → **强制递归删除→没有确认→没有回收站→删了就没了！慎用！**
- **入职场景**：mentor说"代码在 `/home/data/scripts/daily_report.py`"→你`cd /home/data/scripts/`→`ls`→看到`daily_report.py`→确认存在

**3. 查看文件内容——不用打开编辑器就能看**
- `cat file` → 全量输出(小文件)。`cat file1 file2` → 拼接多个文件
- `head -n 20 file` → 只看前20行。`tail -n 50 file` → 只看后50行
- `tail -f /var/log/app.log` → **实时追踪日志**→新日志滚动出来。按Ctrl+C停止。排查问题最高频命令
- `less file` → 分页查看(大文件)。空格翻页、`/关键词`搜索、`q`退出
- `wc -l file` → 统计行数。"这个CSV有多少行？"→`wc -l data.csv`
- **入职场景**：脚本报错了→`tail -50 /var/log/daily_report.log`→看最后50行错误信息→定位问题

**4. 搜索与过滤——在海量文件/日志里找到你想要的**
- `grep '关键词' file` → 在文件里搜关键词→输出包含该关键词的行
- `grep -i 'error' file` → 忽略大小写。`grep -v 'DEBUG' file` → 排除含DEBUG的行
- `grep -c 'ERROR' file` → 统计出现次数
- `grep 'ERROR' *.log` → 搜当前目录所有.log文件
- `grep -r '关键词' /path/` → 递归搜索整个目录(包括子目录)
- **管道 | ** → 把左边命令的输出传给右边命令：
  - `cat app.log | grep ERROR | wc -l` → 日志中ERROR出现了多少次
  - `cat app.log | grep '2025-07-01' | grep 'user_id=123'` → 逐步缩小范围
  - `history | grep 'ssh'` → 从历史命令中找ssh相关的
- **入职场景**：PM说"昨天有个用户ID=888888的订单处理失败了"→你`grep '888888' /var/log/order*.log`→定位到具体日志行→看报错信息→回复PM

**5. 重定向——把输出存成文件**
- `command > file` → 输出覆盖写入文件。`command >> file` → 输出追加到文件末尾
- `command 2>&1 > file` → 标准输出和标准错误都写入文件
- `command > /dev/null 2>&1` → 静默执行(不输出任何东西)
- **入职场景**：跑了一个长时间的分析脚本→`python analysis.py > result.log 2>&1`→输出和错误都存到`result.log`→跑完查看

**6. 权限——为什么有些文件操作被拒绝**
- `ls -l` → 每行开头：`-rwxr-xr--`→文件类型+所有者权限+组权限+其他人权限。r=读(4)、w=写(2)、x=执行(1)
- `chmod +x script.py` → 给脚本加执行权限→`./script.py`直接运行(而不是`python script.py`)
- `chmod 755 script.py` → 所有者rwx、组r-x、其他人r-x
- `sudo command` → 以超级用户权限执行。需要管理员给你sudo权限
- **入职场景**：mentor说"给这个脚本加执行权限"→`chmod +x daily_report.py`→`./daily_report.py`直接跑

**7. 进程管理——脚本挂了吗**
- `ps aux` → 列出所有运行中的进程。`ps aux | grep python` → 只看python相关的
- `top` → 实时查看系统资源(CPU/内存)→按q退出。"为什么跑这么慢？是不是内存满了？"
- `kill -9 PID` → 强制杀死进程(最后手段)
- **入职场景**：脚本跑了2小时还没结束→`top`看→发现内存占用99%→`kill PID`→优化脚本后再跑

**8. 环境变量——程序在哪里找配置**
- `echo $PATH` → 查看可执行文件的搜索路径
- `echo $HOME` → 查看home目录
- `export VAR=value` → 临时设置环境变量(当前session有效)
- `.bashrc` / `.bash_profile` → 永久设置(每次登录自动加载)
- **入职场景**：mentor说"把Python路径加到PATH里"→`export PATH=/opt/python3/bin:$PATH`→加到`.bashrc`里→下次登录自动生效

## W8D2：数据管道全链路 + Spark概念

### 能力簇
**看懂数据从哪来** —— 入职后你写的SQL不是"随便一张表"——数据经历了一条漫长的链路才到你手里。今天画清楚"用户点一下→数据到你分析表"的完整路径。看懂这个=你知道"为什么这个表每天8点才更新""为什么数据对不上(可能是ETL挂了)"。

### 为什么今天重要
入职后最尴尬的事：leader问你"这个指标为什么今天没更新"→你不知道数据从哪来、经过了几步、哪一步可能断了。今天把全链路搞清楚→以后数据出问题你能自己排查，而不是每次问数据工程师。

### 具体知识清单

**1. 数据全链路——用户点一下→到你分析表要走7步**
```
用户点击(客户端) → 埋点SDK采集 → Kafka消息队列(削峰填谷)
  → Flink/Spark实时计算(ETL) → ODS层(原始数据,原样存储)
    → DWD层(清洗后明细,统一格式) → DWS层(轻度聚合,主题宽表)
      → ADS层(面向业务的报表看板) → BI工具/你的分析查询
```
每一步解释：
1. **用户点击**：用户操作触发了埋点→客户端SDK把事件(含参数)打包发给服务器
2. **Kafka消息队列**：海量事件先进入Kafka(类似"缓冲区")→防止流量洪峰冲垮后面的ETL。"高峰期每秒百万条→Kafka先接着→ETL慢慢消费"
3. **Flink/Spark实时计算**：从Kafka读数据→清洗(去重/格式转换/补全)→写回存储。Flink是真正的实时(毫秒级/秒级)→适合实时看板。Spark可以实时也可以批处理→适合T+1报表
4. **ODS层**：原始数据同步过来→不做加工(或仅基本清洗)→保留完整原始信息→出问题时可以从ODS回溯
5. **DWD层**：数据清洗+标准化→维度退化→事实粒度统一→所有下游分析的干净基础
6. **DWS层**：轻度聚合(如按天/按用户预聚合)→主题宽表(把多张表Join好存成一张宽的)→加速查询
7. **ADS层**：面向特定业务场景的报表/看板→直接可读

**2. 每条数据的流转时间线——理解"为什么数据不是实时可查的"**
- 实时链路(秒级)：客户端→Kafka→Flink→实时看板(如"实时GMV大屏")→数据延迟几秒
- 准实时链路(分钟级)：Kafka→Spark Streaming→分钟级聚合→看板→延迟几分钟
- 离线链路(小时级/T+1)：Kafka→HDFS→Spark批处理→Hive表→你自己的分析查询→通常T+1(今天看昨天的数据)

**3. Spark是什么——不是"新东西要学"，是理解你每天用的Hive/数据管道底层**
- MapReduce的局限：每个步骤都要写磁盘→慢。Spark的核心洞察：**把中间结果放在内存里**→比MapReduce快10-100倍
- Spark和数据分析师的关系：你不需要写Spark代码→但你用Hive SQL查询时，底层可能是Spark在跑(而不是MapReduce)→所以快
- RDD(弹性分布式数据集)：Spark的核心抽象→一个分布式的、可以并行操作的数据集合
- Spark SQL：让你用标准SQL语法查Spark数据→和Hive SQL几乎一样→你不需要学新语法

**4. 为什么数据偶尔"对不上"——数据管道的常见断裂点**
- 埋点SDK：版本更新→参数名变了→新参数没采集→旧参数数据归零
- Kafka：消息积压→超过保留时间(如7天)→消息被丢弃→那几天的数据永远丢了
- ETL任务：凌晨定时任务因为上游表变更失败→数据没产出→你早上查表是昨天的→"今天数据怎么没更新"
- 分区问题：新的分区没有被正确创建→`WHERE dt='2025-07-15'`→返回空
- **入职场景**：PM问"为什么昨天的GMV数据和运营后台对不上"→你排查→发现是ETL任务凌晨失败了→昨天分区是空的→通知数据工程师重跑→数据对上了

### 必须覆盖的陷阱
1. **数据管道不是"一条线"——是多条线并行**：实时链路和离线链路是分开的→实时链路的数据可能和离线链路不一致(实时是预估值,离线是精确值)
2. **ETL凌晨挂了→你今天分析的数据是空/旧的**：每天早上第一件事→确认数据分区有没有产出→没有→通知数据工程师
3. **Kafka消息积压→消息被淘汰→数据永久丢失**：Kafka有消息保留期(如7天)→超过时间没消费→消息被删除→那几天数据永久没了

- **D1（昨天）**：昨天学了`tail -f`看实时日志→今天Flink/Spark的日志就在`/var/log/`下→昨天学的直接用来排查ETL日志
- **D3（明天）**：今天理解了数据是怎么流过来的→明天学"源头"：埋点怎么设计→从源头保证数据质量

## W8D3：埋点设计全流程

### 能力簇
**设计数据采集的源头** —— 埋点是数据全链路的起点。埋点设计不好→后续所有分析数据质量都受影响→分析结论不可靠。入职后PM要上线新功能→你来设计埋点方案。

### 为什么今天重要
入职后的真实场景：PM说"我们下周上线一个新功能,你帮我设计一下埋点,我要看新功能的转化漏斗和留存"。你不会设计埋点→PM自己瞎设计→参数类型不一致/漏了关键事件/上线后才发现没法分析→3个月后全组数据质量差→没人敢信数据。今天学会：①梳理"需要采集哪些事件和参数"②写成产品/开发看得懂的埋点需求文档③上线后验证埋点是否正确。

### 具体知识清单

**1. 埋点是什么——数据从哪里开始**
- 埋点=在产品代码里加一段"记录用户做了什么"的代码。用户点击"立即购买"→触发埋点→发送事件`click_buy`(含参数:商品ID/价格/页面/用户ID)→这些事件最终流转到你的分析表里
- **事件(Event)**：用户做了一件什么事。命名规范：`动词_名词`。如`click_buy`、`view_product`、`search_keyword`、`share_content`
- **属性(Property)**：这件事的上下文信息。如`click_buy`事件附带的属性：`product_id`(哪个商品)、`price`(当时价格)、`page`(在哪个页面点击)、`position`(在第几个推荐位)
- **公共属性**：所有事件都有的属性。如`user_id`(谁)、`device_id`(哪个设备)、`timestamp`(什么时间)、`app_version`(什么版本)

**2. 从业务需求反推埋点设计——不是"所有操作都埋"，是"分析需要什么数据"**
- PM说："我想看新功能的转化漏斗——从浏览到购买每一步的转化率"
- 你反推需要的事件和参数：
  - 事件1：`view_newfeature_page` → 属性：`source`(从哪个入口进来的/推荐算法/搜索/外部链接)
  - 事件2：`click_product` → 属性：`product_id`、`position`(第几个位)、`price`
  - 事件3：`add_to_cart` → 属性：`product_id`、`quantity`、`from_page`
  - 事件4：`click_buy` → 属性：`product_id`、`total_amount`、`payment_method`
  - 事件5：`purchase_complete` → 属性：`order_id`、`total_amount`、`coupon_id`(是否用券)
- 这样PM想看"从浏览到购买的每一步转化率"→用这些事件做漏斗。想看"哪个推荐位效果最好"→用`source`维度分群。想看"用了券的用户购买率是否更高"→用`coupon_id`标记

**3. 🔥埋点需求文档——入职后你写给开发看的**
```markdown

... (继续事件4-6)
```

**4. 埋点上线前验证——不等产品上线了再发现埋点错了**
- 开发说"埋好了"→你测试：打开App→触发新功能→上Charles/Fiddler查看网络请求→确认事件名/参数名/参数值都对→确认没有漏参数
- 上线后当天→拉一份埋点数据→检查：事件量是不是合理(不是0/不是异常多)→参数有没有空值→参数类型对不对(商品ID是字符串不是数字)
- **入职场景**：开发说"埋点加好了"→你打开测试版APP→触发点击→看Charles→发现`product_id`是空→回给开发："`product_id`没取到值,这个参数是点击按钮时动态传入的→可能页面加载时还没拿到商品ID→需要在拿到ID后再绑定埋点"→开发修复→你再测→OK→上线

**5. 埋点漏了/错了怎么补救**
- 如果可以后端补录：从服务器日志/数据库记录回溯→补上漏埋的数据
- 如果只能客户端埋：只能等下一个版本修复→这段时间的数据就没了→分析时标注"XX功能X月X日-X月X日数据缺失"
- 唯一不能补救的：历史数据完全丢失→分析时间窗口被截断。所以上线前验证非常重要
- **入职场景**：分析时发现1月数据正常→2月数据全是0→查埋点→发现2月版本更新时`event_name`改成新的了,但旧的分析表还在用旧名字→数据"丢失"了一个月→你标注"2月数据不可用,分析从3月开始"

### 必须覆盖的陷阱
1. **事件名不规范**：不要用缩写(别人看不懂)、不要用中文(编码问题)、用`动词_名词`统一命名

## W8D4：数据质量 + 指标口径 + SQL

### 能力簇
**确保自己用的数据没问题** —— 入职后你每天都要确认"数据对了吗"再开始分析。今天学会：①数据质量检查五维度②指标口径管理③写数据质量监控脚本。这些是你在分析前必做的事情——不检查就分析=建立在沙子上盖房子。

### 为什么今天重要
入职后最坑的事：分析了一整天→报告写好了→发现数据有问题(NA是NULL被忽略/2月数据缺失/指标口径和别人不一样)→重做。今天学会"分析前花5分钟跑数据质量检查"→避免"分析完才发现数据有问题"。

### 具体知识清单

**1. 数据质量五维度——每维度都有具体的检查方法**
- **完整性(Completeness)**：该有的数据都有吗？
  - 检查：`SELECT COUNT(*), COUNT(列) FROM table` → 看NULL比例。`SELECT dt, COUNT(*) FROM table GROUP BY dt ORDER BY dt` → 看每天数据量是否稳定→突然某天少了=可能ETL挂了
- **一致性(Consistency)**：不同表对同一个东西的记录一致吗？
  - 检查：`SELECT COUNT(*) FROM orders WHERE user_id NOT IN (SELECT user_id FROM users)` → 订单中有不在用户表里的user_id吗。`SUM(明细金额) ≈ 汇总表总金额`
- **准确性(Accuracy)**：数据和真实世界相符吗？
  - 检查：金额有没有负数？日期有没有未来的？年龄有没有>120的？
- **及时性(Timeliness)**：数据什么时候能查到？
  - 检查：`SELECT MAX(dt) FROM table` → 最新数据到哪天了。早上9点查还是昨天→可能ETL还没跑完
- **唯一性(Uniqueness)**：有没有重复记录？
  - 检查：`SELECT 订单号, COUNT(*) FROM orders GROUP BY 订单号 HAVING COUNT(*)>1` → 同订单号出现了多次

**2. 指标口径——"同一个指标，不同人算出不同数"是大厂最常见的问题**
- 什么是口径：DAU="当天至少打开过一次APP的去重用户数"。但如果有人定义DAU="当天至少有一次有效行为的去重用户数"→结果不一样
- 口径三要素：①分子是什么②分母是什么③时间窗口是什么。"7天留存率"→分子=首登后第7天还登录的用户数、分母=首登用户数、时间窗口=首登日期的7天后当天
- **入职场景**：PM质疑"你算的DAU和运营后台差了10%,为什么?"→你排查→发现你用的是`login`事件(被动登录也算)、运营后台用的是`active_behavior`事件(必须有主动行为)→口径不同→你解释口径差异→双方对齐

**3. 数据质量监控脚本——每周/每天自动检查**
```python
def check_data_quality(df, table_name):
    report = {}
    # 完整性
    report['null_pct'] = df.isna().sum() / len(df)
    # 一致性
    report['negative_amount'] = (df['金额'] < 0).sum()
    # 及时性
    report['latest_date'] = df['日期'].max()
    # 唯一性
    report['dup_orders'] = df.duplicated('订单号').sum()
    return report
```

## W8D5：自动化 + 定时任务 + SQL

### 能力簇
**让重复的事情自动跑** —— 日报/周报/数据质量检查→不需要每天手工跑→写成脚本→crontab定时触发→自动发邮件。入职后你会发现：50%的工作是在重复"昨天做的事"。把这50%自动化→省下时间做深度分析。

### 为什么今天重要
JD里写的"邮件播报""日报搭建"→就是今天学的东西。入职后最典型的场景：每天早上到公司→先跑3个脚本(拉数据/做日报/检查数据质量)→花1小时→全部自动化后→你到公司直接看邮件→省出1小时做深度分析。这1小时×250个工作日=250小时/年→相当于6周的工作时间。

### 具体知识清单

**1. crontab——Linux定时任务。让脚本在指定时间自动跑**
- 语法：`分 时 日 月 周 命令`
  - `0 8 * * * python /path/to/daily_report.py` → 每天早上8:00跑日报脚本
  - `*/30 * * * * python /path/to/check.py` → 每30分钟跑一次检查脚本
  - `0 2 * * 1 python /path/to/weekly.py` → 每周一凌晨2点跑周报
  - `0 9 1 * * python /path/to/monthly.py` → 每月1号早上9点跑月报
- `crontab -e` → 编辑定时任务。`crontab -l` → 查看当前有哪些定时任务
- **入职场景**：mentor说"每天到公司第一件事是跑日报脚本"→你把它加到crontab→`0 8 * * * cd /path/ && python report.py >> /var/log/report.log 2>&1`→以后每天早上8点自动跑→log输出到日志文件→你到公司直接看邮件

**2. Python自动发邮件——分析结果直接推送到PM邮箱**
```python
import smtplib
from email.mime.text import MIMEText
from email.mime.multipart import MIMEMultipart

def send_report(to_emails, subject, body, attachment_path=None):
    msg = MIMEMultipart()
    msg['Subject'] = subject
    msg['From'] = 'data-platform@company.com'
    msg['To'] = ', '.join(to_emails)
    msg.attach(MIMEText(body, 'html'))  # HTML格式→带表格+图表
    
    if attachment_path:
        with open(attachment_path, 'rb') as f:
            attach = MIMEText(f.read(), 'base64', 'utf-8')
            attach['Content-Disposition'] = f'attachment; filename="{attachment_path}"'
            msg.attach(attach)
    
    with smtplib.SMTP('smtp.company.com', 587) as server:
        server.starttls()
        server.login('data-platform', 'password')
        server.send_message(msg)

# 调用：每天早上发昨日GMV日报
send_report(['pm@company.com', 'leader@company.com'],
            f'番茄阅读日报 {yesterday}',
            f'<h3>昨日核心指标</h3><table>...</table>')
```

**3. 自动化脚本的最佳实践**
- 脚本开头写日志：`print(f"[{datetime.now()}] 开始执行日报脚本...")` → 出错时从日志里知道"跑到哪里了"
- 异常处理：`try/except`包裹可能出错的地方→出错时发邮件告警→不会默默失败
- 幂等性：同一天跑多次结果相同(不会多算一次GMV)
- 锁文件：防止上一个实例还在跑、下一个crontab又触发→`if os.path.exists('/tmp/report.lock'): sys.exit(0)`

### 具体知识清单

**1. dbt（data build tool）——SQL的版本管理+测试+文档（🔥核心）**

**1.1 dbt解决什么问题——传统SQL开发的三个痛点**
- 痛点1：SQL散落在各种客户端/Notebook/邮件里→"那个指标到底用的哪个口径？"→没人知道
- 痛点2：改了SQL→不知道会不会影响下游→"我改了orders_daily，dashboard_daily会不会炸？"→不知道，因为没人维护依赖关系
- 痛点3：SQL写完了→怎么验证数据对不对？→手动看几行→"看起来对的"→没有自动化测试
- **dbt的解法**：SQL代码像Python一样有版本管理(Git)+有测试+有自动文档+有依赖图

**1.2 dbt的核心概念——不需要安装，理解概念就够了**
- **模型（Model）**：一个`.sql`文件=一个dbt模型=数据库里的一张表/视图。如`orders_daily.sql`→SELECT过去30天的每日订单聚合→生成`analytics.orders_daily`表
- **依赖管理（ref）**：`{{ ref('orders_raw') }}` → dbt自动知道"这个模型依赖orders_raw→先跑orders_raw→再跑这个"。改了orders_raw→dbt知道哪些下游模型需要重跑
- **测试（Test）**：在`.yml`文件里声明"这个列不能为NULL""这个列的值必须唯一""这个列的值必须在(A,B,C)里"。每次dbt跑完自动跑测试→测试失败=数据有问题
- **文档（Docs）**：`dbt docs generate` → 自动生成数据文档→展示所有表/列/依赖关系→"新人入职第一件事：看dbt文档理解数据"
- **入职场景**：字节的DA不是在SQL客户端写SQL→是在dbt项目里写。你push一个`.sql`文件到GitLab→CI自动跑dbt→如果测试通过→表自动更新→下游看板自动刷新

**1.3 dbt的入门体验——用Python模拟dbt的核心逻辑**
```python
# 模拟dbt的ref()依赖管理
import sqlite3, os

# dbt模型文件：orders_daily.sql
# content = '''
# SELECT date, city, SUM(amount) as total, COUNT(*) as orders
# FROM {{ ref('orders_raw') }}
# WHERE date >= CURRENT_DATE - INTERVAL '30 days'
# GROUP BY date, city
# '''

# 模拟dbt编译：{{ ref('orders_raw') }} → analytics.orders_raw
def compile_dbt_model(sql_template, refs):
    """模拟dbt的编译：把{{ ref('xxx') }}替换成表名"""
    compiled = sql_template
    for name, table_name in refs.items():
        compiled = compiled.replace(f"{{{{ ref('{name}') }}}}", table_name)
    return compiled

# 模拟dbt的依赖图：找出"这个模型依赖哪些上游模型"
def get_dependencies(sql_template):
    import re
    return re.findall(r"\{\{\s*ref\('(\w+)'\)\s*\}\}", sql_template)

# 模拟dbt的测试：声明验证规则
tests = {
    'unique_order_id': 'SELECT order_id, COUNT(*) FROM orders_raw GROUP BY 1 HAVING COUNT(*) > 1',
    'not_null_amount': 'SELECT COUNT(*) FROM orders_raw WHERE amount IS NULL',
}

sql = "SELECT * FROM {{ ref('orders_raw') }} WHERE {{ ref('users') }}"
print(f"依赖的上游模型: {get_dependencies(sql)}")  # ['orders_raw', 'users']
print(f"编译后的SQL: {compile_dbt_model(sql, {'orders_raw': 'analytics.orders_raw', 'users': 'analytics.dim_users'})}")
```

**2. Airflow/DolphinScheduler——任务调度（30分钟）**

**2.1 为什么不用crontab了**
- crontab够用——当你只有2-3个脚本时。但大厂DA维护的是几十上百个任务→有复杂的依赖关系（"先跑A和B→两个都成功后再跑C→C成功后跑D和E并行"）
- crontab做不到：①任务依赖管理②失败自动重试③看"昨天的任务跑成功了吗"④任务跑了多久（性能监控）
- Airflow/DolphinScheduler就是做这些的

**2.2 Airflow核心概念——不需要安装，理解概念就够了**
- **DAG（有向无环图）**：一个DAG=一个有向无环图=一组有依赖关系的任务。如`订单日报DAG`=提取数据→清洗→聚合→画图→发邮件
- **Operator**：一个Operator=一个任务单元。PythonOperator=跑Python函数。BashOperator=跑shell命令。SQLOperator=跑SQL
- **Schedule**：`schedule_interval='0 8 * * *'` → 每天早上8点自动跑
- **依赖关系**：`task_A >> task_B >> task_C` → A跑完跑B，B跑完跑C。`task_A >> [task_B, task_C] >> task_D` → A跑完后B和C并行，都完成后跑D
- **Web UI**：看DAG的运行历史→昨天跑成功了吗？跑了一次花了多长时间？哪一步失败了？
- **入职场景**：你在Airflow Web UI上看到"昨天的订单日报DAG失败"→点进去看→SQL取数一步报错→数据库连接超时→手动重跑→成功

**2.3 Airflow vs DolphinScheduler**
- Airflow：Python写的→Python友好的那批公司的首选。字节/美团用Airflow变体
- DolphinScheduler：Java写的→国产开源→去IOE/信创场景下更常见。阿里/拼多多用类似的调度系统
- **面试说什么**："我们公司用的是Airflow。我日常工作是维护和优化DAG——确保每天按时产出、失败自动重试、性能优化（SQL优化减少DAG运行时间）。"

**2.4 Python模拟——理解DAG的依赖执行逻辑**
```python
# 模拟Airflow的DAG依赖管理
from collections import deque

tasks = {
    'extract_orders': {'deps': [], 'status': 'pending'},
    'extract_users': {'deps': [], 'status': 'pending'},
    'clean_data': {'deps': ['extract_orders', 'extract_users'], 'status': 'pending'},
    'aggregate': {'deps': ['clean_data'], 'status': 'pending'},
    'send_report': {'deps': ['aggregate'], 'status': 'pending'},
}

def run_dag(tasks):
    """模拟Airflow执行DAG：计算拓扑排序→按依赖顺序执行"""
    # 计算入度（还有几个上游没完成）
    indegree = {name: len(info['deps']) for name, info in tasks.items()}
    ready = deque([name for name, d in indegree.items() if d == 0])
    
    while ready:
        task_name = ready.popleft()
        print(f"执行: {task_name}")
        tasks[task_name]['status'] = 'done'
        # 所有下游的入度-1
        for name, info in tasks.items():
            if task_name in info['deps']:
                indegree[name] -= 1
                if indegree[name] == 0:
                    ready.append(name)

run_dag(tasks)
# 输出：
# 执行: extract_orders
# 执行: extract_users
# 执行: clean_data         ← 等前两个都完成才执行
# 执行: aggregate
# 执行: send_report
```

**3. GitLab CI / GitHub Actions——代码push后自动测试部署（20分钟）**

**3.1 为什么需要CI/CD**
- W8D5你学了crontab定时跑脚本。但crontab只管"定时触发"→代码怎么到服务器上的？手动scp？改了代码怎么确保不炸？
- CI/CD（持续集成/持续部署）= 代码push到Git→自动跑测试→自动部署→全程不需要手动操作

**3.2 CI/CD的DA视角——不需要你写CI配置，但要理解流程**
```yaml
# .gitlab-ci.yml（DA项目的CI配置示例——不需要你写，但要能看懂）
stages:
  - test
  - deploy

run_tests:
  stage: test
  script:
    - pip install -r requirements.txt
    - pytest tests/          # 跑测试→如果有测试失败→不进入deploy阶段
    - python -c "import dbt; dbt test()"  # dbt数据质量测试

deploy_to_production:
  stage: deploy
  only:
    - main                   # 只有main分支才部署
  script:
    - scp -r src/ user@prod-server:/app/
    - ssh user@prod-server "cd /app && python main.py"
```

**3.3 入职场景**
- 你改了一个SQL→push到feature分支→发Merge Request→同事review代码→合并到main→GitLab CI自动：
  1. 跑pytest（你的Python函数测试）
  2. 跑dbt test（你的SQL数据质量测试）
  3. 如果都通过→自动部署到生产服务器
  4. Airflow下一次调度自动用新代码跑
- 如果任何一步失败→你不会收到"上线成功"的通知→不会影响生产→你排查、修复、再push

**3.4 面试怎么聊CI/CD**
- 面试官："你们怎么保证上线不出问题？"
- 正确回答："我们有CI/CD pipeline。代码push后自动跑单元测试+数据质量测试→测试通过才允许合并和部署。部署后先在staging环境跑一次→确认产出正确→再推到生产。如果生产出问题→GitLab可以一键回滚到上一个版本。"
