# 渭河文风审稿规则

## 审稿目标

判断一篇文章、报告或草稿是否符合渭河文风。重点看它有没有形成真实的业务判断，而不是看它用了多少相似词。

## 必过项

### 1. 是否从真实问题进入

通过标准：

- 开头能说明问题为什么在真实工作中出现。
- 读者能知道这不是一个抽象概念题。

不通过：

- 先写百科定义。
- 先堆背景口号。
- 先写空泛重要性。

### 2. 是否指出常见误区

通过标准：

- 至少指出一种常规理解为什么不够。
- 误区和后文的作者判断有关联。

不通过：

- 直接给模板答案。
- 没有任何反驳或取舍。

### 3. 结论是否有生成路径

通过标准：

- 能看出结论来自问题、证据、业务解释和取舍。
- 不是突然下判断。

不通过：

- 只写“因此可以看出”。
- 证据和结论之间缺少业务机制。

### 4. 指标是否翻译成业务场景

通过标准：

- 指标对应到用户、车辆、城市、价格、资源、流程、组织或策略。

不通过：

- 指标只在指标之间循环解释。
- 公式拆完就结束。

### 5. 是否区分可解释和可干预

通过标准：

- 说明哪些因素只能解释变化。
- 说明哪些因素可以进入动作。

不通过：

- 把天气、宏观环境、不可控因素写成核心建议。
- 所有因素都“建议关注”。

### 6. 是否有阶段性和边界

通过标准：

- 说明当前判断到哪一步。
- 说明还需要验证什么。
- 说明不能外推到哪里。

不通过：

- 一次性给万能结论。
- 没有任何限制条件。

### 7. 结尾是否落到动作

通过标准：

- 结尾指向看板、专项、复盘、预警、策略、资源配置或下一步验证。

不通过：

- 以“优化、提升、加强、赋能”结束。
- 没有对象、指标、动作和节奏。

## 打分

```yaml
real_problem_entry: 0-2
misconception_refuted: 0-2
conclusion_path: 0-3
metric_to_scene: 0-3
controllability: 0-3
stage_boundary: 0-2
actionability: 0-3
paragraph_rhythm: 0-2
language_function: 0-2
total: 0-22
```

解释：

- `18-22`: 渭河文风稳定。
- `14-17`: 基本接近，但需要补业务场景或边界。
- `10-13`: 有部分语言相似，但推理机制不足。
- `0-9`: 只是普通 AI 报告或模板化文章。
