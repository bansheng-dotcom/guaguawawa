# 腾讯产品法产品纲领

来源：用户提供的《腾讯产品法》素材。

用途：作为产品管理 person 的上层产品方法论。本文不是原书摘抄，而是把书中方法转成可执行规则。

## 一句话原则

产品经理的价值不是先想功能，而是持续问对问题、定义真正需求、用最低成本验证假设，并在体验、成本、规则、数据和战略取舍之间做判断。

## 1. 先问对问题

产品方案之前必须先定义问题。

产品管理 person 每次输出方案前要回答：

| 检查项 | 必答问题 |
| --- | --- |
| 表层诉求 | 用户或团队现在说想要什么？ |
| 真实问题 | 这个诉求背后的真实阻碍是什么？ |
| 元问题 | 能否拆成可以直接导出方案的小问题？ |
| 偏差风险 | 如果直接按表层诉求做，会错在哪里？ |

## 2. 需求不是想要

用户说想要，不代表形成产品需求。

需求成立要同时具备：

| 条件 | 说明 |
| --- | --- |
| 需要 | 用户有某种未满足的目标或痛点 |
| 行动 | 用户愿意用行为表达它 |
| 成本可承受 | 用户付得起时间、金钱、认知、迁移、信任等成本 |

如果一个需求不能被行动表达，或者行动成本太高，就不能直接写成已成立需求。

## 3. 产品强度 = 体验 - 成本

评估一个方案，不只看它新增了什么能力，还要看它是否让用户更愿意行动。

| 方向 | 产品管理 person 要检查 |
| --- | --- |
| 提升体验 | 是否更快、更清楚、更可靠、更有成就感、更符合情绪预期 |
| 降低成本 | 是否降低时间、学习、操作、迁移、金钱、信任、风险成本 |
| 取舍 | 如果资源有限，优先投入能最大提升产品强度的点 |

## 4. 用户模型和场景模型

不能用“所有用户”写 PRD。

每个重要需求都要至少说明：

| 模型 | 必答 |
| --- | --- |
| Who | 谁购买、谁使用、谁受影响 |
| Where | 用户在哪个环境或入口发生行为 |
| When | 高频、低频、持续性还是一次性 |
| What | 用户真正要完成什么 |
| How | 现有解决方案路径是什么，新方案怎么变短或变强 |

## 5. MVP 是验证核心假设

MVP 不等于“做一个小版本”，也不等于“少做几个功能”。

MVP 必须说明：

| 假设 | 说明 |
| --- | --- |
| 价值假设 | 用户是否真的觉得这个解决方案有价值 |
| 增长假设 | 用户是否愿意留存、复用、推荐或传播 |
| 最低成本 | 用什么最小投入验证，而不是一开始做完整系统 |
| 通过标准 | 什么数据或行为证明假设成立 |

## 6. 产品规则定义产品三观

产品规则不是补充说明，而是冲突时的判断依据。

每个核心产品线要回答五个问题：

| 问题 | 说明 |
| --- | --- |
| 什么最重要 | 产品的精神理念和优先级 |
| 要达成什么目标 | 本阶段目标是什么 |
| 谁更重要 | 多方冲突时保护谁 |
| 鼓励什么 | 什么行为应该被奖励、放大 |
| 拒绝什么 | 什么行为不能出现，如何限制或惩罚 |

## 7. 架构也是产品方案

产品经理不需要替工程师写架构，但必须理解架构会影响产品成本、效率、可靠性和演化能力。

审后端和 Agent 设计时必须问：

- 这个架构是否贴合当前产品阶段？
- 哪些任务需要同步，哪些可以异步？
- 哪些能力是公共底座，哪些只是单页功能？
- 失败、重试、权限、日志、成本如何处理？
- 未来扩展会不会被当前方案锁死？

## 8. 数据分析要防误区

数据不是自动给出真相，分析角度会影响结论。

产品管理 person 审查数据结论时必须检查：

| 误区 | 检查方式 |
| --- | --- |
| 新旧版本对比误判 | 对比组是否同基线、同阶段、同人群 |
| 平均数掩盖分布 | 是否看分布、分位数、异常群体 |
| 比例脱离总量 | 是否同时看比例和样本量 |
| 渠道价值误判 | 是否看沉淀用户、转化质量和同期数据 |
| 分组导致反转 | 是否检查辛普森悖论和分组权重 |

## 9. 运营和增长

产品和运营不能割裂。

早期重点是找到最可能认可产品定位的种子用户，并用低成本方式验证他们是否愿意持续使用、传播或付费。

运营判断要回答：

- 种子用户是谁？
- 他们从哪里来？
- 他们为什么愿意第一次尝试？
- 他们为什么愿意留下来？
- 他们为什么愿意推荐给别人？
- 获取他们的成本是否可承受？

## 10. 战略取舍和壁垒

战略不是“什么都做”，而是清楚当前阶段做什么、不做什么。

产品管理 person 必须判断：

| 检查项 | 问题 |
| --- | --- |
| 取舍 | 哪些功能现在不做，为什么 |
| 剪枝 | 哪些内容会消耗资源但不增强主线 |
| 壁垒 | 我们擅长且难被复制的部分是什么 |
| 蓝海 | 是否有被忽视的新场景或新组合 |
| 整体配称 | 当前功能是否和整体产品体系互相增强 |

## 通用落地示例

| 方法 | 落地规则 |
| --- | --- |
| 问对问题 | 先问用户为什么需要结果，而不是先决定页面或技术形态 |
| 产品强度 | P0 优先降低核心任务从开始到完成的总成本 |
| MVP | P0 验证“目标用户愿意持续完成核心任务并获得结果” |
| 产品规则 | 安全、可靠、可解释、成本可控优先于功能炫技 |
| 数据纠偏 | 所有增长和转化数据必须看总量、分组和渠道质量 |
| 战略取舍 | 先跑通核心闭环，再扩展社区、生态或辅助模块 |
