### PSI 数据漂移检测——完整工程实现

**PSI（Population Stability Index）= 量化"数据分布变了多少"。不只是"看起来不一样"——是"变了多少——需要重新训练吗？"**

```python
import numpy as np
import pandas as pd

def detect_feature_drift(reference: pd.Series, current: pd.Series,
                         bins: int = 10, threshold: float = 0.25) -> dict:
    """PSI——检测单个特征的分布是否从参考期偏移。

    PSI < 0.1: 无漂移——模型继续使用
    PSI 0.1-0.25: 轻度漂移——需关注——考虑重训练
    PSI > 0.25: 显著漂移——模型可能需要立即重训练

    原理: PSI = sum((actual% - expected%) * ln(actual% / expected%))
    将参考分布(reference)和生产分布(current)分成 bins——
    计算每个 bin 中两期占比的差异——加权求和。

    面试常见追问: "PSI 和 KS 有什么区别？"
    KS 用于模型区分度评估——衡量正负样本的预测得分分布差异。
    PSI 用于数据/特征的分布变化检测——衡量训练集 vs 生产集的分布差异。
    两者测的是不同的东西——一个测模型——一个测数据。

    Args:
        reference: 训练时的特征值（参考分布）
        current: 生产环境中的特征值（当前分布）
        bins: 分箱数——默认 10——太少会漏掉局部漂移——太多每个 bin 太少样本不稳定
        threshold: PSI 超过此值——标记为"显著漂移"

    Returns:
        dict with: psi_value, drift_level, bin_details
    """
    # 等频分箱——基于 reference 的分布
    bin_edges = np.percentile(reference.dropna(), np.linspace(0, 100, bins + 1))
    bin_edges[0] = -np.inf
    bin_edges[-1] = np.inf

    ref_counts = np.histogram(reference.dropna(), bins=bin_edges)[0]
    cur_counts = np.histogram(current.dropna(), bins=bin_edges)[0]

    # 避免除零
    ref_pct = ref_counts / ref_counts.sum()
    cur_pct = cur_counts / cur_counts.sum()
    ref_pct = np.where(ref_pct == 0, 0.0001, ref_pct)
    cur_pct = np.where(cur_pct == 0, 0.0001, cur_pct)

    psi_values = (cur_pct - ref_pct) * np.log(cur_pct / ref_pct)
    psi_total = psi_values.sum()

    drift_level = 'no_drift' if psi_total < 0.1 else ('mild_drift' if psi_total < 0.25 else 'significant_drift')

    return {
        'psi_value': round(psi_total, 4),
        'drift_level': drift_level,
        'bins': bins,
        'per_bin_psi': psi_values.tolist()
    }


def test_drift_detection():
    """验证 PSI——相同分布->PSI~0——完全不同分布->PSI>0.25"""
    np.random.seed(42)
    ref = np.random.normal(100, 15, 10000)   # 训练时: 均值 100
    same = np.random.normal(100, 15, 10000)   # 生产时: 分布不变
    shifted = np.random.normal(120, 15, 10000) # 生产时: 均值偏移到 120

    result_same = detect_feature_drift(ref, same)
    result_shifted = detect_feature_drift(ref, shifted)

    assert result_same['psi_value'] < 0.1, f"相同分布 PSI 应 < 0.1, 实际 {result_same['psi_value']}"
    assert result_shifted['psi_value'] > 0.25, f"偏移分布 PSI 应 > 0.25, 实际 {result_shifted['psi_value']}"
```

**鲜果多流失预警模型的漂移检测——每月跑一次——监控 8 个关键特征的 PSI：** 如果某个特征的 PSI 连续两个月 > 0.25——自动发告警——"特征 days_since_last_order 出现了显著漂移——训练集中均值 15 天——生产集中均值 22 天——用户整体消费频率下降了——模型可能低估了流失风险——建议重训练。"

### 数据漂移的完整工程体系——不只是 PSI——是检测+告警+决策三件套

**漂移检测只是第一步——完整的漂移管理体系需要三层：**

**第 1 层——检测（D1 的 PSI）：** 每个月（或每次模型推理前）对所有关键特征跑 PSI——生成漂移报告。哪些特征漂移了？漂了多少？

**第 2 层——告警：** 漂移报告不能"存在某个文件里没人看"。PSI > 0.25 的特征连续两个月出现——自动发 Slack/邮件告警——"模型 churn_xgb_v3 的特征 days_since_last_order 连续 2 个月 PSI > 0.25——当前 PSI=0.32——建议重训练"。

```python
def drift_alert(drift_results: dict, previous_month_results: dict = None):
    """生成漂移告警——连续两个月显著漂移->发通知。"""
    alerts = []
    for feature, result in drift_results.items():
        if result['drift_level'] == 'significant_drift':
            # 检查上个月是否也漂移了
            prev = previous_month_results.get(feature, {}) if previous_month_results else {}
            if prev.get('drift_level') == 'significant_drift':
                alerts.append(
                    f'[CRITICAL] {feature} 连续两个月显著漂移——'
                    f'当前 PSI={result["psi_value"]:.3f}——上个月 PSI={prev["psi_value"]:.3f}——'
                    f'建议立即重训练'
                )
            else:
                alerts.append(
                    f'[WARNING] {feature} 本月出现显著漂移——'
                    f'PSI={result["psi_value"]:.3f}——下个月持续则建议重训练'
                )
    return alerts
```

**第 3 层——决策：** 收到告警后——判断是"重训练"还是"调查根因"。PSI 告诉你是谁漂了——但没告诉你"为什么漂"。根因调查需要回到业务——"days_since_last_order 的均值从 15 天变成了 22 天——是因为公司停止了 push 通知？还是因为竞品上线了新功能？"PSI = 触发调查的信号——不是诊断本身。

**鲜果多流失预警漂移管理——月度流程：** 每月 1 号自动跑 PSI——生成漂移报告——发到数据分析团队 Slack 频道。如果有连续两个月显著漂移的特征——自动创建 Jira ticket——分配给模型 owner——要求 3 个工作日内回复"重训练/调查根因/已知且可接受（附理由）"。

### sklearn Pipeline 在鲜果多项目中的完整实战——从手动 transform 到序列化部署

**Pipeline 不只是"把步骤串起来"——它解决了三个工程问题：**

**(1) 训练和预测使用完全相同的变换——消除"训练时做了标准化但预测时忘了"的 bug：**

```python
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler, OneHotEncoder
from sklearn.compose import ColumnTransformer
from sklearn.impute import SimpleImputer
import joblib

# ColumnTransformer——不同列用不同的预处理
numeric_features = ['amount', 'days_since_register', 'order_count']
categorical_features = ['city', 'device_type']

preprocessor = ColumnTransformer([
    ('num', Pipeline([
        ('imputer', SimpleImputer(strategy='median')),   # 缺失填中位数
        ('scaler', StandardScaler())                      # 标准化
    ]), numeric_features),
    ('cat', Pipeline([
        ('imputer', SimpleImputer(strategy='constant', fill_value='unknown')),
        ('encoder', OneHotEncoder(handle_unknown='ignore', sparse_output=False))
    ]), categorical_features)
])

# 完整 Pipeline——预处理 + 模型
full_pipeline = Pipeline([
    ('preprocessor', preprocessor),
    ('classifier', RandomForestClassifier(n_estimators=100, max_depth=5, random_state=42))
])

# 训练
full_pipeline.fit(X_train, y_train)

# 序列化——整个 Pipeline 保存为一个文件——含预处理器+模型
joblib.dump(full_pipeline, 'output/churn_model_pipeline.pkl')
```

**(2) 生产环境加载后——对新数据只需一行 transform——不需要手动重复特征逻辑：**

```python
# 生产环境——加载 Pipeline——一行完成预处理+预测
pipeline = joblib.load('output/churn_model_pipeline.pkl')
predictions = pipeline.predict_proba(new_data)  # Pipeline 自动先预处理再预测
```

**(3) Pipeline 的参数可追溯——`get_params()` 能完整复现配置：**

```python
params = full_pipeline.get_params()
# 保存到 model_metadata.json——以后任何人都能知道这个模型的完整配置
```

### SHAP 可解释性报告的工程化——不只是"画 summary plot"——是"生成可审查的业务报告"

```python
import shap
import matplotlib.pyplot as plt

def generate_shap_report(model, X: pd.DataFrame, feature_descriptions: dict = None,
                         output_path: str = 'output/shap_report.md', top_n: int = 10):
    """生成可审查的 SHAP 特征归因报告。

    不只是画图——输出 Markdown 报告——含:
    1. Top N 特征的 |SHAP| 均值 + 方向 + 业务解读
    2. SHAP summary plot（嵌入报告）
    3. 单个预测的 SHAP waterfall plot（解释"为什么这个人被预测为高风险"）

    Args:
        model: 训练好的 sklearn 模型（或 Pipeline）
        X: 特征矩阵——用于计算 SHAP 值
        feature_descriptions: {feature_name: "业务含义"}——用于生成可读的报告
        output_path: 报告保存路径
        top_n: 报告中展示前 N 个重要特征
    """
    if feature_descriptions is None:
        feature_descriptions = {col: col for col in X.columns}

    # 计算 SHAP 值
    explainer = shap.TreeExplainer(
        model[-1] if hasattr(model, 'named_steps') else model
    )
    X_processed = model[:-1].transform(X) if hasattr(model, 'named_steps') else X
    shap_values = explainer.shap_values(X_processed)
    if isinstance(shap_values, list):
        shap_values = shap_values[1]  # 二分类——取正类的 SHAP

    # 特征重要度——按 |SHAP| 均值排序
    mean_abs_shap = np.abs(shap_values).mean(axis=0)
    feature_order = np.argsort(mean_abs_shap)[::-1]

    # 生成 Markdown 报告
    lines = ['# SHAP 特征归因报告', '',
             '| 排名 | 特征 | 业务含义 | 平均 |SHAP| | 方向 | 业务解读 |',
             '|------|------|---------|----------|------|---------|']

    for rank, idx in enumerate(feature_order[:top_n], 1):
        feat_name = X.columns[idx]
        mean_val = mean_abs_shap[idx]
        direction = '正向' if shap_values[:, idx].mean() > 0 else '负向'
        desc = feature_descriptions.get(feat_name, feat_name)
        interpretation = _interpret_feature_direction(feat_name, direction)
        lines.append(f'| {rank} | {feat_name} | {desc} | {mean_val:.4f} | {direction} | {interpretation} |')

    # 保存报告
    with open(output_path, 'w', encoding='utf-8') as f:
        f.write('\n'.join(lines))

    # 保存 SHAP summary plot
    shap.summary_plot(shap_values, X, show=False)
    plt.savefig(output_path.replace('.md', '.png'), dpi=150, bbox_inches='tight')

    return output_path


def _interpret_feature_direction(feat_name: str, direction: str) -> str:
    """根据特征名和方向——生成业务解读。这是领域知识——需要人工维护映射表。"""
    interpretations = {
        'days_since_last_order': '距上次购买天数越长->流失风险越高（正向=高风险标志）',
        'orders_last_30d': '近30天订单越多->流失风险越低（负向=保护因子）',
        'coupon_usage_rate': '优惠券使用率越高->对价格敏感->可能等券才买（需结合其他特征）',
    }
    return interpretations.get(feat_name, f'{direction}影响——需要业务方确认具体含义')
```

**鲜果多流失预警 SHAP 报告的关键发现：** Top1 特征是 days_since_last_order——平均 |SHAP| = 0.34——距上次购买时间越长——流失风险越高（这是预期的）。Top3 特征是 coupon_usage_rate——平均 |SHAP| = 0.12——方向为正——说明"优惠券使用率越高——流失风险越高"——这不太直观——细看后发现——高优惠券使用率的用户是"只在有券时才买"的价格敏感型——一旦停止发券——他们就流失了。这个发现直接指导了运营策略——"对高 coupon_usage_rate 的用户——不要突然停止发券——梯度减少——观察反应"。

### W18 闭卷自测——ML 代码工程化

**Q1**：PSI 的三个阈值和对应的行动是什么？PSI 和 KS 的区别——用一句话说清楚。

> **A**：PSI < 0.1 = 无漂移——模型继续使用。PSI 0.1-0.25 = 轻度漂移——需关注——考虑重训练。PSI > 0.25 = 显著漂移——模型可能需要立即重训练。PSI vs KS——PSI 检测数据分布变化（训练集 vs 生产集特征分布），KS 检测模型区分度（正负样本的预测得分分布差异）——一个测数据——一个测模型。

**Q2**：sklearn Pipeline 的核心价值——不只是"把步骤串起来"——是解决了哪三个工程问题？

> **A**：(1) 训练和预测使用完全相同的变换——消除"训练时标准化了但预测时忘了"的 bug (2) 序列化——整个 Pipeline 保存为一个 .pkl 文件——生产环境一行 predict_proba (3) 参数可追溯——get_params() 能完整复现配置。偏差：说"方便"——Pipeline 不是"方便"——是"消除了一个整类 bug"——训练/预测不一致 bug。

**Q3**：SHAP 报告的工程化要求——不只是"画 summary plot"——还应该包含什么？

> **A**：(1) Top N 特征的 |SHAP| 均值 + 方向 (2) 每个特征的业务解读——不是"这个特征重要"——是"这个特征为什么对业务意味着什么" (3) 可复现——SHAP 值的计算应该用固定随机种子。偏差：只画图不写解读——图是给技术同事看的——业务解读是给运营总监和 PM 看的——两份输出——两份不同的价值。

**Q4**：模型文件命名规范——至少含哪 4 个信息维度？

> **A**：模型名 + 日期 + 版本号 + 关键参数。`churn_xgb_2026-11-27_v3_maxdepth6_lr0.01.pkl`——不需要加载模型文件就能知道这是什么模型、什么时候训练的、第几版、核心参数是什么。同时保存 model_metadata.json——含训练日期/数据源/特征列表/所有评估指标/完整参数。

**Q5**：模型部署 checklist——为什么必须是 pytest test 而不是"写个列表"？

> **A**：人工 checklist 会忘——会跳——会"这次赶时间——下次再补"。pytest test 在 CI 中自动执行——不通过不允许部署——强制执行。而且 checklist 的每个检查项是"可复现的"——下次部署时——同样的 test 再跑一遍——确保上次通过的条件这次仍然满足。人工 checklist 需要每次手动逐项确认——人脑不可靠——自动化不会偷懒。

**Q6**（面试模拟）：面试官问"你的模型上线后效果变差了——你怎么排查？"

> **A**："我的排查顺序是四步。第一步——检查数据漂移——跑 PSI——看关键特征在训练集和生产集之间有没有显著偏移。第二步——检查特征完整性——生产数据有没有缺失训练时用的特征。第三步——检查模型稳定性——在最近的生产数据上重跑评估指标——和训练时的指标对比——差距有多大。第四步——如果数据漂移确认——判断是否需要重训练——PSI > 0.25 的特征 >= 2 个->建议重训练。这个排查流程不是我'想到哪查到哪'——是 test_model_deployment_checklist.py 中的自动化检查——8 项检查每次部署都跑——出问题时第一件事就是重新跑这个 checklist。"

> "模型重训练是半自动的——make retrain-model 执行取数据->Pipeline fit->评估->SHAP 报告->checklist 检查->输出模型文件。但最后的部署决策是人工的——因为需要检查 SHAP 报告中的业务解读——确认模型的行为和业务直觉一致——比如'coupon_usage_rate 正向影响流失风险'这个发现——需要和运营团队确认——是不是高优惠券依赖用户确实在停止发券后容易流失。自动化能做 80% 的工作——但最后的 20% 需要人工判断——这是 ML 工程化的正确边界——不是追求 100% 自动化——是明确'哪些让机器做——哪些让人做'。"

**如果面试官追问"你的模型出过什么问题——你怎么发现的？"**

> "第一个问题是幂等性——流失预警的特征工程中用了随机填充缺失值——没有设种子——每次训练结果不同。W17 的幂等性测试发现了——修了。第二个问题是数据漂移——模型训练时高价值用户占比 15%——三个月后降到 8%——因为一次大促吸引了大量低价值用户。PSI 漂移检测连续两个月告警——触发了重训练。第三个问题是 SHAP 报告中的一个意外发现——coupon_usage_rate 正向影响流失风险——最初觉得是 bug——后来确认了——高优惠券依赖用户更可能在停止发券后流失——这个发现直接改变了运营策略（梯度减少发券而不是突然停止）。这些问题都不是'模型代码写错了'——是'模型和数据/业务的交互产生了意外行为'——这正是 ML 工程化要解决的问题。"
