## D1（周一 10/6）：埋点设计——从 PM 的模糊需求到精确的埋点方案

> 📓 今日主课：埋点设计全流程——事件名=动词_名词/公共属性 vs 私有属性/埋点验证

### 🔴 认知冲突

PM 告诉你"新功能上线后帮我看看效果"。你问"看什么效果？"PM 说"就是看看好不好用"。你追问"什么算好用？点击率高？加购率高？最终下单率高？"PM 沉默了。

这不是 PM 的错——PM 的业务直觉是对的（"新功能好不好用"），但 PM 没有义务把这五个字翻译成"需要在 4 个页面埋 5 个事件、每个事件带 6 个公共属性和 3 个私有属性、预期日量级 10 万次、上线后 30 分钟内验证数据到达"。

**这是你的工作。** 分析师如果在 PM 的模糊需求和精确的埋点方案之间不能搭桥——数据分析在"数据产生之前"就输了。因为没有埋点 = 没有数据 = 没有任何分析。

**但你有没有想过——为什么 PM 说的是"看看好不好用"而不是"我需要 click_product_card 事件的 position 参数"？** 因为 PM 用业务语言思考——你不用业务语言。你需要在两种语言之间翻译——把"好不好用"翻译成"需要曝光/点击/加购/购买/关闭五个事件——点击率衡量吸引力、加购率衡量转化意愿、关闭率衡量骚扰程度"。这个翻译过程——不是"需求澄清"——是**分析设计**。需求澄清是"PM 你说清楚"。分析设计是"PM 说的模糊——我用我的专业知识把它变成精确的"。

---

### 📖 核心原理

**埋点设计的工程化标准——四个要素：事件名规范、参数设计原则、埋点文档模板、验证自动化。**

**一、事件名规范：`动词_名词`（snake_case）——自描述是唯一目标。**

```
✅ view_recommendation           ← 动词在前——一眼就知道是"看到推荐"的事件
✅ click_product_card            ← 含动作对象——click 什么？product_card
✅ add_to_cart_from_rec          ← 含来源上下文——从推荐卡片加购（区分于从详情页加购）
✅ purchase_complete             ← 完整语义——不只是"点击购买按钮"——是"购买完成"
✅ dismiss_recommendation        ← 含负反馈——用户关闭推荐（衡量"推荐是不是骚扰"的关键指标）

❌ product_card_click            ← 名词在前——和业界惯例相反
❌ event1 / event_001            ← 无意义——三个月后完全不知道
❌ card_click                    ← 缺宾语——什么 card？推荐卡片还是优惠券卡片？
❌ rec_click / recommend_click   ← 缩写/动词后置——团队里每人写不同缩写
```

**为什么动词在前？** 因为当你搜索"所有 click 事件"时——`click_product_card`、`click_banner`、`click_search_result` 会按前缀聚在一起。名词在前——`product_card_click`、`banner_click`、`search_result_click` 分散在事件列表的各个位置。这不是审美——是**可检索性**。

**为什么 snake_case 而不是 camelCase？** 因为你的后端日志系统（如 Kafka topic 命名、Hive 列名）大概率统一用 snake_case。和整个数据管道保持一致。

**二、参数设计——公共属性是"每个事件都该带的"，私有属性是"这个事件特有的"。**

公共属性回答的是"谁、什么时候、在什么端、在哪个页面、在哪个 session"——这是任何分析都需要的最小上下文。私有属性回答的是"这个事件特有的业务信息"。

| 属性 | 类型 | 必填？ | 示例值 | 为什么必须 |
|------|------|--------|--------|----------|
| `user_id` | 公共 | ✅ | `"u_12345"` | 关联用户——没有它就不知道"这是谁" |
| `timestamp` | 公共 | ✅ | `1695340800` | Unix 时间戳——统一时区。客户端时间不准——以服务端接收时间为准——但这个字段保留客户端原始时间用于 diff |
| `platform` | 公共 | ✅ | `"iOS"/"Android"/"Web"` | 不同端的用户行为模式完全不同 |
| `app_version` | 公共 | ✅ | `"3.2.1"` | 某版本崩溃导致数据异常——靠版本号回溯 |
| `page` | 公共 | ✅ | `"home"/"search"` | 事件发生的页面上下文 |
| `session_id` | 公共 | ✅ | `"s_abc123"` | 串联单次会话内的所有事件——计算会话时长和路径 |
| `product_id` | 私有 | 商品事件 | `"p_67890"` | 被操作的商品 |
| `position` | 私有 | 推荐事件 | `3` | 推荐排序位置——衡量排序质量的核心指标 |
| `source` | 私有 | 推荐事件 | `"ai_rec"` | 推荐算法标识——AB 测试不同算法的效果 |

**参数的"必填 vs 选填"——谁来定？** 不是你来定——是你来**问自己**："如果这个参数缺失了——我最想做的那个分析还能做吗？"如果不能——必填。如果能——选填。比如：你想分析"推荐位置 1-3 的转化率 vs 位置 10+ 的转化率"——如果没有 `position` 参数——这个分析做不了。所以 `position` 必填。

**三、埋点事件的标准模板——不是"描述"，是"数据契约"。**

```markdown
### 事件: view_recommendation

- **触发时机**: 推荐卡片在用户屏幕上的可见面积 ≥ 50% 时触发
  - 去重策略: 同一 session 内同一 product_id 的曝光——5 分钟内不重复上报
  - 注意: 客户端去重不是 100% 可靠——服务端也需要去重逻辑
- **公共属性**: user_id, timestamp, platform, app_version, page, session_id
- **私有属性**: product_id (string), position (int, 1-N), source (string: "ai_rec"/"hot"/"new")
- **预期量级**: ~10 万次/天（DAU 2 万 × 人均浏览 5 个推荐卡片）
- **验证方法**:
  1. 上线后 30min 内——检查日志平台——是否有 view_recommendation 事件到达？
  2. 量级合理性: view_recommendation 数量 ≤ page_view（推荐页面 PV）——曝光不应超页面 PV
  3. 抽样验证: 取 20 条事件——手动查数据库——确认对应 user_id 在那个时间点确实在推荐页面
```

**四、验证自动化——不是"上线后手动验"，是"每次数据到达自动验"。**

## D2（周二 10/7）：埋点验证——从"上线后手动查日志"到"每次数据到达自动检查"

### 🔴 认知冲突

埋点上线了。你第一件事就是打开分析平台——看转化率——0%。排查了 2 小时——发现埋点 SDK 初始化失败了——根本没有数据上来。但从前端看一切正常——页面渲染没问题——只是埋点没发。

你浪费的这 2 小时——不是"分析做错了"——是"应该在分析之前做一个 30 秒的自动化检查"。

**问题**：埋点上线后第一件事不是做分析——是**验证**。验证数据有没有到达、量级对不对、格式是否正确。这三项不通过——所有后续分析都是在空数据上做的——结论全部错误。为什么不是"手动验证"——因为你会忘。某天 PM 说"这个事件的 position 参数好像没传上来"——你的回答是"我不确定——可能是 SDK 版本问题——可能是服务端过滤了——可能根本没埋"——这三个"可能"背后是**没有自动化验证**。

---

### 📖 核心原理

**埋点验证金字塔——四层检查，数据到达→量级合理→格式正确→业务逻辑一致。**

```python
def validate_tracking_pipeline(events_df: pd.DataFrame,
                                expected_events: List[str],
                                pv_count: int) -> List[str]:
    """埋点上线验证——4 层检查。每层独立——任何一层不通过立即报告。
    
    1. 到达检查: 每个预期事件有数据到达吗？
    2. 量级检查: 每个事件的量级在合理范围内吗？
    3. 格式检查: 必填参数完整吗？类型正确吗？（调用 D1 的 validate_tracking_events）
    4. 逻辑检查: 业务逻辑矛盾吗？（曝光量 ≤ PV？加购量 ≤ 点击量？）
    
    Returns:
        issues 列表——空列表表示全部通过
    """
    issues = []
    
    # === 层1: 到达检查——没有数据 = 一切分析都是空的 ===
    arrived_events = set(events_df['event'].unique())
    for event_name in expected_events:
        if event_name not in arrived_events:
            issues.append(
                f"⚠️ 事件 '{event_name}' 无任何数据到达。"
                f"可能原因: SDK 未初始化 / 事件名拼写错误 / 前端代码未部署"
            )
    
    # === 层2: 量级检查——对比预期和实际 ===
    for event_name in expected_events:
        if event_name not in arrived_events:
            continue
        actual = len(events_df[events_df['event'] == event_name])
        # 量级合理性——曝光不应超过页面 PV
        if 'view' in event_name and actual > pv_count * 1.1:  # 10% 容差
            issues.append(
                f"事件 '{event_name}' 量级({actual}) > 页面PV({pv_count})×1.1——"
                f"曝光量不应超过页面 PV。可能: 去重逻辑失效 / 机器人流量"
            )
        # 量级异常低——可能是埋点触发条件太严格
        if actual < pv_count * 0.001 and 'view' in event_name:
            issues.append(
                f"事件 '{event_name}' 量级({actual}) < 页面PV({pv_count})×0.001——"
                f"曝光量极低。可能: 触发条件设置过于严格 / 卡片未渲染"
            )
    
    # === 层3: 格式检查——调用 D1 的函数 ===
    format_issues = validate_tracking_events(
        events_df.to_dict('records')
    )
    issues.extend(format_issues)
    
    # === 层4: 逻辑检查——业务语义矛盾 ===
    # 加购量 ≤ 推荐卡片点击量（从推荐卡片加购——不可能超过点击）
    if 'click_product_card' in arrived_events and 'add_to_cart_from_rec' in arrived_events:
        clicks = len(events_df[events_df['event'] == 'click_product_card'])
        adds = len(events_df[events_df['event'] == 'add_to_cart_from_rec'])
        if adds > clicks * 1.05:  # 5% 容差——可能有"非卡片点击"的加购
            issues.append(
                f"加购量({adds}) > 点击量({clicks})×1.05——"
                f"从推荐卡片加购不应超过点击量。可能: 加购事件带了错误的 source 标记"
            )
    
    return issues
```

**这四层对应的是四种不同的失败模式：**

| 层 | 检查什么 | 如果失败——最可能的原因 | 修复时间 |
|---|---------|---------------------|---------|
| 1. 到达 | 数据来了吗 | SDK 初始化失败/事件名拼错/未部署 | 30 分钟（前端修） |
| 2. 量级 | 量在合理范围吗 | 去重逻辑问题/触发条件过于严格/过于宽松 | 1 小时（调整参数） |
| 3. 格式 | 参数完整且类型对吗 | 前端传参 bug/参数名拼错 | 30 分钟（前端修） |
| 4. 逻辑 | 业务逻辑矛盾吗 | 事件之间的因果关系反了/归因逻辑有问题 | 1 小时（分析+前端） |

### 📖 埋点验证的持续监控——不只是"上线 30 分钟验证"——是"每天自动检查"

**将 D2 的验证逻辑部署为每日定时任务——不只是上线那一天跑——是每天跑——因为数据管道会退化：**

```python
def daily_tracking_health_check(expected_events: List[str], pv_count: int):
    """每日埋点健康检查——放到 Airflow/CRON 中——每天 8:00 AM 跑。

    退化模式：
    - SDK 版本升级——某事件参数名变了——层 1（到达）不会报——层 3（格式）会报
    - 前端重构——某页面重写——埋点代码被误删——层 2（量级）会报
    - 后端日志系统迁移——数据延迟 2 小时——层 1（到达）在 9:00 AM 报——10:00 AM 恢复
    """
    today = date.today().isoformat()
    events_df = load_tracking_events(today)

    issues = validate_tracking_pipeline(events_df, expected_events, pv_count)

    if issues:
        # 不只是打印——发告警到 IM/邮件
        send_alert(f'埋点健康检查失败: {len(issues)} 个问题', chr(10).join(issues))
    else:
        log_metric('tracking.health', 1, tags={'status': 'pass'})

    return len(issues) == 0
```

**埋点管道的"退化模式"——你知道什么会出错——才能设计正确的监控：**

| 退化模式 | 发生时机 | 哪层检查能发现 | 修复方向 |
|---------|---------|-------------|---------|
| SDK 升级——参数名改变 | App 发版后 | 层 3——格式检查——参数缺失 | 回滚或更新埋点方案文档 |
| 前端重构——埋点代码被误删 | 页面改版后 | 层 2——量级检查——量骤降 | 前端回滚——或重新添加埋点 |
| 后端日志系统迁移——数据延迟 | 基础设施变更后 | 层 1——到达检查——无数据 | 等管道恢复——或切回旧管道 |
| 业务极端情况——如双 11 流量暴增 | 大促期间 | 层 2——量级检查——量远超 PV | 检查去重逻辑是否还生效 |

**这些退化模式回答了面试中常见的问题——"你做的埋点验证不是一次性的吗？为什么需要自动化？"**
> "因为数据管道会退化——不是写完之后就永远正确。SDK 升级、前端重构、后端迁移——都可能导致埋点静默失效。一次性的验证只能保证上线那一刻是正确的——持续监控才能保证上线后的每一刻都是正确的。这就像你的单元测试——不是只在提交时跑——每次 CI 都跑——因为依赖会变、环境会变、数据会变。"

## D3（周三 10/8）：数仓四层——不只是"建四张表"，是"四种信任级别"

> 📓 今日主课：数仓分层实战——ODS→DWD→DWS→ADS 四层

---

### 🔴 认知冲突

以前你的分析——一个 CSV → 一次清洗 → 一个结论。现在公司 5 个分析师——每个人各自打开 ODS——各自清洗——5 种不同的清洗逻辑——5 种不同的"GMV"。周会上运营总监问"GMV 到底是多少"——5 个人给了 3 个不同的答案。没有人撒谎——每个人的清洗逻辑都"看起来合理"——但合在一起——公司没有**统一的真相来源**。

你提议"为什么不建一套数仓——所有人从同一个 DWD 取数据？"——有人反问"那不是建四张表吗——我们已经有表了——为什么还需要四层？"

**问题**：数仓分层不是"多建几张表"——是**定义信任边界**。ODS 是"源系统吐出来的——一丁点没改——你可以信任这是原始数据"——但你不该信任它是干净的。DWD 是"经过统一清洗的——你可以信任每行是有效的、格式是统一的"——但你不需要信任它够快（明细层——每次查询都要扫全量）。DWS 是"常用的聚合口径已经帮你算好了——你可以信任它快——但你不该信任它是最新的（因为是预聚合——有延迟）。ADS 是"这是给业务方直接看的——你可以信任它经过了业务口径校验——但你不需要信任它的底层逻辑"。

**四层 = 四种信任级别。每层向下一层承诺"数据在这个层级上是可信的"——不会再往上推翻。**

---

### 📖 核心原理

**四层的信任边界——不只是技术划分：**

| 层 | 全称 | 一句白话 | 信任级别 | 谁在用 | 什么时候用 |
|---|------|---------|---------|--------|----------|
| **ODS** | Operational Data Store | "这就是源系统吐出来的——一丁点没改" | "这就是原始数据——但我不保证它干净" | 数据工程师 | 排查"数据源是不是有问题" |
| **DWD** | Data Warehouse Detail | "经过统一清洗的干净明细——所有分析师从这层开始" | "每一行都是有效的、格式统一的——你可以信任数据质量" | 所有分析师 | 做任何需要明细数据的分析 |
| **DWS** | Data Warehouse Summary | "常用的聚合口径帮你算好了——不需要每次从明细层重新算" | "这些聚合口径是正确的——但注意——它是 T+1 的（昨天之前的数据）" | 分析师+BI | 做日常报表/Dashboard |
| **ADS** | Application Data Service | "给业务方直接看的——字段名是中文的——可以直接导出" | "它经过了业务口径校验——可以直接用——但不要从这层往下追（往下追去 DWD）" | 业务方/运营 | 发邮件/做 PPT/给老板看 |

**为什么不能跳层？——三个真实场景：**

**场景 1：运营直接从 ODS 取数据做分析。** ODS 里 `status` 列——有的写 `'cancelled'`（英文）、有的写 `'已取消'`（中文）——没人清洗过。运营做了 `WHERE status != 'cancelled'`——漏掉了所有写 `'已取消'` 的行——GMV 多算了。跳层 = 信任了不该信任的数据质量。

**场景 2：老板直接从 DWD 取数据做日报。** DWD 是明细层——每天 5000 万行。老板的查询 `SELECT SUM(amount) FROM dwd_orders`——每次都扫 5000 万行——跑了 3 分钟。跳层 = 把"适合做明细分析"的数据层用来做高频聚合——慢且贵。

**场景 3：数据分析师从 ADS 取数据做深度分析。** ADS 里的 `city_breakdown` 是按城市×月份聚合的——粒度是一行 = 一个城市在一个月。你想做"按天×城市×品类的细分分析"——ADS 没有这个粒度——你回到 DWD 从明细开始做。跳层 = 用了"不适合分析的粒度"。

**每一层有自己的"使用者"和"不适用场景"。** 数仓分层规范的不是"数据怎么存"——规范的是"谁在什么时候用哪一层"。

- **DWD**: `dwd_order_detail`——去重（ERP bug→重复订单）、去负值（退款→另表）、去测试用户（`test_` 前缀）、金额类型统一（`DECIMAL(10,2)`）、日期格式统一（`DATE`）、编码统一（UTF-8）、**新增 `is_suspicious` 列**——标记可能异常的行（金额极端/日期异常/关键字段缺失）——不删除、只标记。**这一层的核心价值：所有分析师从这层开始——口径统一、数据可信。**
- **DWS**: `dws_daily_city_kpi`——按天×城市预聚合：GMV/订单数/客单价/用户数。每天 8:00 AM 跑——处理昨天全天的数据。**这一层的核心价值：日常查询——不用每次从 5000 万行明细中聚合——直接读 365×几百城市 = 几万行的聚合表。**
- **ADS**: `ads_ceo_dashboard`——面向 CEO 看板：7 个核心 KPI——字段名是中文的（"成交总额"/"订单数"/"客单价"）、含环比和同比列、含"和上个月对比"的箭头符号（↑/↓）。**这一层的核心价值：CEO 打开就能看懂——不需要知道 ODS/DWD/DWS 的存在。**

### 📖 数仓分层在实践中——不只是"画四层图"——是"定义每一层的数据质量 SLA"

**每一层承诺的质量保障——不只是"数据从哪来"——是"这一层向上一层承诺什么"：**

| 层 | 质量承诺 | 违反承诺的例子 | 如何自动化检查 |
|---|---------|-------------|-------------|

**为什么"不适用场景"是数仓文档中最重要但也最容易被省略的信息？**

因为**每个分析师拿到一个新的数据表时——她的默认假设是"这个表应该能回答我的问题"**——而不是"这个表的粒度和时效性决定了它能回答什么问题和不能回答什么"。如果文档没有明确说"这张表不应该用来做什么"——分析师会默认"可以"——然后做错分析。

每层文档的"不适用场景"不只是技术说明——是**防止下游误用的安全护栏**——就像你的 Python 函数的 docstring 里写的 `Raises ValueError if...`——它不仅告诉你"什么情况下能用"——更重要的是"什么情况下不能用"。

## D4（周四 10/9）：SCD Type2 拉链表——从"覆盖旧值"到"完整的时间旅行"

> 📓 今日主课：维度建模+SCD——星型模型/SCD Type2/事实表三种类型

---

### 🔴 认知冲突

你的 `users` 表有个 `user_level` 字段——普通/银卡/金卡/VIP。三个月前用户 u12345 是"银卡"——今天升级成了"金卡"。如果你在用户表里直接覆盖：

```sql
UPDATE users SET user_level = '金卡' WHERE user_id = 'u12345';
```

三个月前你做的"银卡用户 GMV 分析"就**永远无法复现了**。因为数据没了——你覆盖了历史。你永远不知道"用户 u12345 在 6 月份是什么等级"——你只知道他现在是金卡。

这不是"分析做不了"的问题——这是"数据被销毁了"的问题。在金融/医疗/电商场景中——维度属性的历史变化不是"nice to know"——是**合规要求**。审计需要知道"这个用户在 6 月享受了什么折扣"——如果你覆盖了——你答不上来——审计失败。

**问题**：怎么让每次"等级变化"都保留完整的生命周期记录——不是覆盖旧值——而是"关闭旧记录 + 开启新记录"——让分析能回到任何历史时点？

---

### 📖 核心原理

**SCD Type2（Slowly Changing Dimension Type 2）= 不覆盖旧行——而是"关闭"旧行 + "开启"新行——用 `start_date` 和 `end_date` 标记每行的有效期。**

每行有三列关键元数据：`start_date`（这条记录从哪天开始有效）、`end_date`（到哪天失效——9999-12-31 表示"至今仍有效"）、`is_current`（1=当前有效——方便快速过滤）。

```
SCD Type2 的实际效果——追踪 u12345 的三次等级变化:

user_id | user_level | start_date | end_date   | is_current
u12345  | 普通       | 2026-01-15 | 2026-04-20 | 0  ← 这条记录"有效"了 3 个月
u12345  | 银卡       | 2026-04-21 | 2026-06-20 | 0  ← 被后面那次升级"关闭"了
u12345  | 金卡       | 2026-06-21 | 2026-12-31 | 0  ← 这条也被关了
u12345  | VIP        | 2027-01-01 | 9999-12-31 | 1  ← 当前有效

想查 "u12345 在 2026-03 什么等级？"
→ WHERE start_date <= '2026-03-01' AND end_date > '2026-03-01'
→ 普通 (start=2026-01-15, end=2026-04-20——2026-03-01 在这个区间内)

想查 "u12345 现在的等级？"
→ WHERE is_current = 1
→ VIP
```

**用 Python 实现 SCD Type2 的自动更新——每天比对新旧快照、自动检测变化、自动关闭和开启：**

```python
from datetime import date, timedelta
from typing import List, Dict
import logging

logger = logging.getLogger(__name__)

FAR_FUTURE = date(9999, 12, 31)  # "至今仍有效"的标记


def update_scd_type2(
    snapshot_new: List[Dict],   # 今天的新快照——每个用户一行
    snapshot_old: List[Dict],   # 昨天已存在的拉链表数据（is_current=1 的行）
    key_col: str = 'user_id',   # 用于匹配新旧的键
    track_cols: List[str] = None  # 需要追踪变化的列——如果这些列中任一有变化——就关旧开新
) -> List[Dict]:
    """SCD Type2 日更——从新旧快照生成新拉链表行。
    
    核心逻辑:
    1. 新用户（只在新快照中）→ 创建新行——start_date=今天
    2. 无变化的用户（新旧一致）→ 保留旧行——不做任何修改
    3. 有变化的用户（track_cols 中任一列变了）→ 关闭旧行 + 开启新行
    4. 消失的用户（只在旧快照中）→ 关闭旧行——end_date=昨天（用户可能注销了）
    
    这个函数每次跑——输入今天的全量快照 + 昨天的拉链表（只看 is_current=1 的）——
    输出今天的新的全量拉链表数据。不需要手动管理——全自动。
    """
    if track_cols is None:
        track_cols = ['user_level', 'city', 'status']
    
    today = date.today()
    yesterday = today - timedelta(days=1)
    
    # 索引旧数据——方便按 key 查找
    old_by_key = {row[key_col]: row for row in snapshot_old}
    
    result = []
    
    for new_row in snapshot_new:
        key = new_row[key_col]
        old_row = old_by_key.get(key)
        
        if old_row is None:
            # 情况 1: 新用户——创建新行
            new_row['start_date'] = today
            new_row['end_date'] = FAR_FUTURE
            new_row['is_current'] = 1
            result.append(new_row)
            logger.debug("新用户: %s, start=%s", key, today)
            continue
        
        # 情况 2/3: 检查 track_cols 是否有变化
        has_changed = any(
            str(new_row.get(col)) != str(old_row.get(col))
            for col in track_cols
        )
        
        if has_changed:
            # 情况 3: 有变化——关闭旧行 + 开启新行
            old_closed = {**old_row, 'end_date': yesterday, 'is_current': 0}
            new_opened = {**new_row, 'start_date': today, 'end_date': FAR_FUTURE, 'is_current': 1}
            result.append(old_closed)
            result.append(new_opened)
            changed_cols = [c for c in track_cols if str(new_row.get(c)) != str(old_row.get(c))]
            logger.info("用户升级: %s, 变化列: %s, %s→%s (旧→新)",
                        key, changed_cols,
                        {c: old_row.get(c) for c in changed_cols},
                        {c: new_row.get(c) for c in changed_cols})
        else:
            # 情况 2: 无变化——保留旧行
            result.append(old_row)
    
    # 情况 4: 消失的用户——关闭旧行
    new_keys = {row[key_col] for row in snapshot_new}
    for old_row in snapshot_old:
        key = old_row[key_col]
        if key not in new_keys and old_row.get('is_current') == 1:
            closed = {**old_row, 'end_date': yesterday, 'is_current': 0}
            result.append(closed)
            logger.info("用户消失: %s, end_date=%s", key, yesterday)
    
    return result
```

| "end_date 用 9999-12-31——感觉有点 hack" | 标准做法——用极大日期表示"至今有效"——方便查询（不需要额外判断 NULL） | 这是行业惯例——不是 hack。所有 SCD Type2 实现都用这个或等价的 `9999-12-31` |
| "is_current 列是冗余的——从 end_date 就能判断" | 对——是冗余的。但给查询加了便利——`WHERE is_current=1` 比 `WHERE end_date='9999-12-31'` 更可读且更快（如果建了索引） | 保留两个——end_date 是精确的，is_current 是便捷的 |


## D5（周五 10/10）：dbt 依赖图——用 Python import 思维理解 dbt 的 ref()

> 📓 今日主课：数仓方案设计 + dbt 入门

### 🔴 认知冲突

你学会了 Python 的模块化——`from src.data.io import load_orders`。这行代码的含义不只是"导入一个函数"——更重要的是：**它声明了"我的代码依赖 io.py"**。如果 `io.py` 改了——所有 import 它的模块都需要重新运行。pip/poetry 内置了这个依赖关系——Python 不需要你手动管理"谁先执行"——import 图本身就是执行顺序。

现在你面对 dbt——文档告诉你"用 `ref()` 声明模型依赖"。你写 `{{ ref('stg_orders') }}`——它告诉 dbt"运行我之前先运行 stg_orders"。你觉得这是一个新概念。"声明依赖、让工具管理执行顺序"——你 8 个月前（W1D4）在 Python 里已经学过了。**dbt 的 `ref()` 和 Python 的 `import` 是同一个设计模式——只是换了一个名字。**

**问题**：你不是从零学 dbt——你是把 Python 模块化的心智模型迁移到数据建模。理解了这一点——dbt 剩下的 80% 你都知道（test = pytest、docs = Sphinx——你已经会了）。

---

### 📖 核心原理

**dbt 和 Python 的对应表——迁移你已经拥有的知识：**

| 概念 | Python | dbt | 相同的设计模式 |
|------|--------|-----|-------------|
| 声明依赖 | `from src.data.io import load_orders` | `SELECT * FROM {{ ref('stg_orders') }}` | 声明"我需要 X 先执行" |
| 管理执行顺序 | import 图 = 执行顺序。pip 处理依赖解析 | DAG 图 = 执行顺序。dbt 自动拓扑排序 | 工具自动推导依赖——你不需要手动排序 |
| 测试 | `pytest tests/` | `dbt test`（unique/not_null/自定义） | 用代码验证假设——数据应该满足的约束 |
| 文档 | `Sphinx` / docstring | `dbt docs generate` | 从代码/模型的 YAML 描述自动生成文档网站 |
| 模块的组织 | `src/data/` / `src/analysis/` | models/staging/ / models/marts/ | 按职责划分目录——staging = 清洗层、marts = 业务模型 |

**在 README 或注释中画你项目的"dbt 版"依赖图——以后迁移到 dbt 时——这就是你的设计稿：**

```
L0 (Staging——ODS→DWD):
  stg_orders ─── 从 raw_orders 洗出——去重/去无效/类型统一
  stg_users  ─── 从 raw_users 洗出——编码统一/缺失处理
  
L1 (Intermediate——DWD 之间的 JOIN):
  int_order_items ─── stg_orders + stg_products——订单×商品明细
  int_user_orders ─── stg_orders + stg_users——订单×用户画像

L2 (Marts——DWS→ADS):
  marts_customer_360 ─── int_user_orders——用户维度全景模型
  marts_product_perf ─── int_order_items——商品维度表现模型
  marts_daily_kpi     ─── stg_orders——每日核心指标
```

### 📖 dbt 实战入门——不只是"理解类比"——是"能写出第一个 dbt 项目"

**dbt 项目的标准目录结构——理解它——你就知道"dbt 期望我怎么组织数据模型"：**

```
my_dbt_project/
├── dbt_project.yml          # 项目配置——告诉 dbt: 模型在哪、profile 是什么
├── models/
│   ├── staging/             # L0: Staging——ODS->DWD——清洗+标准化
│   │   ├── stg_orders.sql   #   SELECT ... FROM {{ source('raw', 'orders') }}——加清洗逻辑
│   │   └── stg_users.sql
│   ├── intermediate/        # L1: Intermediate——DWD 之间的 JOIN 和转换
│   │   └── int_order_items.sql
│   └── marts/               # L2: Marts——DWS/ADS——面向业务方
│       ├── marts_customer_360.sql
│       └── marts_daily_kpi.sql
├── tests/                   # 数据质量测试——等价于 pytest
│   └── assert_orders_unique.sql
├── macros/                  # Jinja 宏——等价于 Python 的 def
└── analyses/                # 一次性分析——不在 DAG 中
```

**dbt 的测试——不是"检查代码"——是"检查数据"——这是和 pytest 的根本区别：**

```sql
-- tests/assert_orders_unique.sql
-- dbt test 会跑这个——如果返回任何行=测试失败=数据有重复
SELECT order_id, COUNT(*) as cnt
FROM {{ ref('stg_orders') }}
GROUP BY order_id
HAVING COUNT(*) > 1
```

```yaml
# schema.yml——声明"模型"和"它的约束"
models:
  - name: stg_orders
    columns:
      - name: order_id
        tests:
          - unique          # 内置测试: 唯一性
          - not_null        # 内置测试: 非空
      - name: amount
        tests:
          - not_null
          - dbt_utils.expression_is_true:
              expression: '> 0'   # 业务逻辑约束: 金额必须 > 0
```

**Python 视角——dbt 的每个概念都是你已知的：**

| dbt 概念 | Python 等价 | 你已经会的 |
|---------|-----------|----------|
| `{{ ref('stg_orders') }}` | `from src.data.io import load_orders` | 声明依赖——不需要管理执行顺序 |
| `dbt test` | `pytest tests/` | 自动化验证——CI 中运行——红了不能合并 |
| `dbt docs generate` | Sphinx / mkdocs | 从代码注释自动生成文档 |
| `schema.yml` 中的 test | `pytest.mark.parametrize` | 声明式测试——声明"数据应该满足什么" |
| `macros/` | Python 的 `def` | 不要重复自己——公共逻辑抽成宏 |
| `dbt run` | `python main.py` | 按 DAG 拓扑顺序执行所有模型 |

## D7（周日 10/12）：W11 审计——闭卷埋点 + 数仓 + SCD Type2

### 📝 闭卷自测

**Q1**（埋点）：事件名规范是什么？为什么动词在前？公共属性和私有属性的分界线是什么？

> **A**：`动词_名词`（snake_case）。动词在前 = 前缀相同的聚在一起——可检索。公共属性 = 每个事件都该带的（user_id/timestamp/platform）——任何一个分析都需要的最小上下文。私有属性 = 这个事件特有的业务信息（product_id/position/source）。分界线：缺了这个属性——你最重要的分析还能做吗？不能→必填公共属性。能→选填私有属性。

**Q2**（埋点验证）：四层验证是哪四层？"曝光量 > 页面 PV"是哪一层检测的？

> **A**：到达（数据来了吗）→量级（量合理吗）→格式（参数完整+类型对吗）→逻辑（业务语义矛盾吗）。曝光量 > PV 是量级层——检查量是否在合理范围。偏差：把量级和逻辑混在一起——量级 = 绝对值异常（太高/太低），逻辑 = 关系矛盾（A 不应该 > B）。

**Q3**（数仓）：ODS/DWD/DWS/ADS 的信任边界是什么？为什么不能让运营直接从 ODS 取数据？

> **A**：ODS="源系统吐出来的——未经任何加工"——不保证干净。运营从 ODS 取数据 = 信任了不该信任的质量——status 列英文和中文混写——没人清洗——分析会漏数据。DWD 是"经过了统一清洗"——所有分析师从这层开始。

**Q4**（SCD Type2）：SCD Type2 的四个列（start_date/end_date/is_current）各自的作用是什么？为什么 end_date 用 9999-12-31？

> **A**：start_date=这条记录从哪天开始有效。end_date=到哪天失效。is_current=快速过滤当前有效行。9999-12-31 = "至今仍有效"——替代 NULL——方便查询（不需要额外判断 NULL）——且如果建索引——等值查询比 NULL 查询更快。

**Q5**（dbt）：dbt 的 `ref()` 和 Python 的 `import` 在什么意义上是一回事？

> **A**：两者都是声明式依赖管理——告诉工具"A 依赖 B，B 必须先于 A 执行"。工具自动推导执行顺序（DAG/import 图）——你不需要手动排序。Python 的 pip 解析依赖版本——dbt 的 ref() 解析模型执行顺序——同一个设计模式。
