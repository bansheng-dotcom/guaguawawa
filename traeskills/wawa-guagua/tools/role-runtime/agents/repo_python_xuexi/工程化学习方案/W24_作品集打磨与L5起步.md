### 项目 1 的完整 STAR 叙事——面试时直接背诵

**项目 1——电商用户增长分析——STAR 叙事:**

- **S（Situation）:** 一家电商公司——Q3 投放了三个获客渠道（社交/搜索/展示）——但不知道哪个渠道的用户质量最高——三个渠道的预算分配靠"经验和感觉"——没有数据支撑。
- **T（Task）:** 我的任务——(1) 评估三个渠道的用户 LTV 差异 (2) 计算每个渠道的 CAC 回收期 (3) 给出基于 ROI 的预算重新分配建议 (4) 建立标准化的 RFM 用户分群——可复用至其他项目。
- **A（Action）:** (1) 实现了 compute_channel_ltv()——含完整口径（180 天时间窗口——SUM(amount)/COUNT(DISTINCT user_id)）(2) 计算了每个渠道的 CAC/LTV/ROI/回收期 (3) 把鲜果多的 RFM 函数改造成通用版——参数化所有维度——可在任何项目中复用 (4) 报告结论先行——CEO 版 3 句话——PM 版含可执行建议——Engineer 版含复现步骤。
- **R（Result）:** 渠道 A（社交）ROI=3.2——渠道 C（展示）ROI=0.8（亏钱——回收期超过 180 天）。建议渠道 C 预算的 60% 转移至渠道 A——预计 Q4 整体 ROI 从 1.8 提升至 2.5——年化 GMV 增量约 15%。RFM 函数被项目 2 和项目 3 复用——节省了约 4 小时的开发时间。

### 项目 2/3 的 STAR 叙事骨架——按同样结构补充完整

**项目 2——内容平台数据质量体系——STAR 骨架:**
- S: 内容平台——数据来自埋点+第三方 API+爬虫——质量参差不齐
- T: 建立数据质量体系——确保分析结论不受数据质量问题影响
- A: (1) 设计 3 张表的 data contract YAML (2) 实现 validate_against_contract() (3) 构建 UGC 文本清洗 pipeline (4) 建立内容质量评分体系——权重来源有数据依据
- R: [量化结果——如数据质量问题发现率从人工排查的 30% 提升到自动检测的 95%]

**项目 3——金融风控+性能工程——STAR 骨架:**
- S: 金融风控——百万级数据——特征工程初始耗时 15 分钟——无法高效迭代
- T: 优化特征工程性能——同时保持模型质量不下降
- A: (1) cProfile 定位瓶颈——groupby transform 占 68% (2) line_profiler 定位瓶颈行 (3) agg+merge 替代 transform——CSV 转 Parquet (4) 记录每一步的加速倍数
- R: 15min->2min（7.5x 加速）——AUC=0.84——建议收紧风控——年化节省坏账成本约 300 万

### STAR 方法的完整示例——四个项目各一个 STAR 叙事

**鲜果多——STAR 叙事:**

- **S（Situation）:** 鲜果多是一家生鲜电商——数据量从 10 万行增长到 5000 万行——pandas 单机跑不动了。同时需要评估 AI 推荐功能的因果效应——但不能做 AB Test——因为功能已全量上线。
- **T（Task）:** 我的任务——(1) 建立可扩展的数据仓库——支持从 10 万到 5000 万行的数据量增长 (2) 用准实验方法（DID/PSM/RDD）评估 AI 推荐的效果 (3) 建立完整的 CI/CD 测试体系——确保数据分析结果的可信和可复现。
- **A（Action）:** (1) 设计了 ODS->DWD->DWS->ADS 四层数仓——每层有不同的信任级别 (2) 实现了 DID（ATT=+8.2%）/PSM（ATT=+12%）/RDD（ATT=+14%）三种因果推断——含平行趋势检验+敏感性分析 (3) 建立了 pytest+ruff+mypy CI 三重门——>=20 个 test——每次 push 自动验证。
- **R（Result）:** AI 推荐让北京 GMV 提升 8.2%（p=0.031）——会员卡让用户消费提升 12-15%。数仓让日常查询从 3 分钟降到 10 秒。CI 三重门每次 push 自动跑——代码质量从"我觉得还行"变成"机器验证通过"。

**面试时——面试官问"介绍一下你最满意的项目"——你直接背这段——45 秒——含具体数字——不是"我做了很多事"——是"我做了 X——结果是 Y（量化数字）"。"**

### 四个项目徽章配置的完整操作流程

**每个项目的 README.md 顶部应该有的徽章（从 GitHub Actions 自动获取）:**

```markdown
[![CI](https://github.com/YOURNAME/PROJECT/actions/workflows/ci.yml/badge.svg)]
[![Python](https://img.shields.io/badge/Python-3.10+-blue)]
[![ruff](https://img.shields.io/badge/ruff-zero%20errors-brightgreen)]
[![mypy](https://img.shields.io/badge/mypy-passing-brightgreen)]
[![pytest](https://img.shields.io/badge/pytest-20%2B%20tests-brightgreen)]
```

**CI badge URL 的格式:**
```
https://github.com/{owner}/{repo}/actions/workflows/{workflow-file}/badge.svg
```

**操作流程——给每个项目加徽章——5 分钟/项目:**

1. 确认 .github/workflows/ci.yml 存在且最后一次 run 是绿色的
2. 把 CI badge URL 中的 {owner}/{repo}/{workflow-file} 替换为实际值
3. 在 README.md 第一行（标题下方）粘贴 5 个 badge 的 markdown
4. push——打开 GitHub——确认 badge 显示为绿色
5. 如果 badge 显示 "no status" 或灰色——说明 workflow 从未运行或 workflow 文件名不对——检查

**四个项目的 badge 一致性检查——确保 4 个 repo 的 README 顶部看起来是"同一个人的作品":**
- 同样的 Python 版本 badge
- 同样的 ruff/mypy/pytest badge
- 同样的 CI badge（各自指向各自的 workflow）
- badge 的顺序一致
