### 📖 核心原理

**"跑通"只是第一层。真正的数据验证有五层。**

这是数据工程中的一个经典框架——验证金字塔：

```
        ┌─────────────┐
        │ 5. 业务规则  │ ← 最高层：GMV不能为负/转化率≤100%/留存率≤1
        ├─────────────┤
        │ 4. 跨表一致  │ ← 订单表的user_id应该都在用户表中
        ├────────────┤
        │ 3. 值范围    │ ← amount在0到99999之间/日期在合理范围内
        ├───────────┤
        │ 2. 数据类型  │ ← amount是数字不是字符串/日期能被解析
        ├──────────┤
        │ 1. 存在性   │ ← 文件存在/列存在/行数>0
        └──────────┘
```

每一层依赖下一层。数据是日期格式了（第 2 层），然后才能检查日期范围（第 3 层）。绝大多数人只做了第 1 层（文件能找到）、第 2 层（Python 能解析），就认为"数据加载完成"了。第 3-5 层的检查才是区分"脚本能跑"和"数据可信"的分水岭。

**第 1 层：存在性检查**

```python
def validate_input(df: pd.DataFrame, required_cols: List[str]) -> None:
    """验证输入 DataFrame 的完整性。不通过直接抛异常。"""
    # 1a. 非空
    if df.empty:
        raise ValueError("输入 DataFrame 为空")

    # 1b. 必需列存在
    missing = set(required_cols) - set(df.columns)
    if missing:
        raise ValueError(f"缺少必需列: {missing}")

    # 1c. 没有全空列（表示数据源可能损坏）
    all_null = [c for c in df.columns if df[c].isna().all()]
    if all_null:
        logger.warning("以下列全为空，请检查数据源: %s", all_null)
```

**第 2 层：数据类型检查**

```python
# 检查关键列的数据类型
assert pd.api.types.is_numeric_dtype(df['amount']), "amount 应为数值类型"
assert pd.api.types.is_datetime64_any_dtype(df['order_date']), "order_date 应为日期类型"
```

**第 3 层：值范围检查**

```python
# 金额不应为负
assert (df['amount'] >= 0).all(), "存在负金额订单"

# 日期应在合理范围内
assert df['order_date'].min() >= pd.Timestamp('2024-01-01'), "存在过早的订单日期"
assert df['order_date'].max() <= pd.Timestamp.today(), "存在未来日期"

# 缺失率不应过高
missing_rate = df['amount'].isna().mean()
if missing_rate > 0.10:
    logger.warning("amount 缺失率 %.1f%%，超过 10%% 阈值", missing_rate * 100)
```

**第 4 层：跨表一致性**

```python
# merge 后的行数验证
before = len(df)
merged = df.merge(lookup, on='key', how='left')
after = len(merged)
assert after >= before, f"行数异常: merge 前 {before} 行, merge 后 {after} 行"
if after > before:
    logger.warning("一对多膨胀: %d -> %d 行 (+%d)", before, after, after - before)

# 外键完整性
missing_users = set(orders['user_id']) - set(users['user_id'])
if missing_users:
    logger.warning("有 %d 个 user_id 在用户表中不存在", len(missing_users))
```

**第 5 层：业务规则**

```python
# 聚合结果合理性检查
total = df['amount'].sum()
assert total > 0, f"总 GMV 为 {total}，可能数据有误"

# 占比和为 1
shares = df.groupby('city')['amount'].sum()
shares = shares / shares.sum()
assert abs(shares.sum() - 1.0) < 0.001, f"占比和不为 1: {shares.sum()}"

# 转化率不超过 100%
conversion = len(df[df['purchased']]) / len(df)
assert conversion <= 1.0, f"转化率异常: {conversion:.2%}"
```

**assert 的边界——什么该 assert，什么不该**

- ✅ 该 assert：数据假设被违反（"我假设这一列不会有负值，如果有，后面的逻辑就错了"）
- ✅ 该 assert：中间结果的一致性（"merge 之后行数不应该比之前少"）
- ❌ 不该 assert：用户输入的错误（"文件不存在"应该用异常处理，不是 assert）
- ❌ 不该 assert：可以恢复的错误（"这个值不太对但程序还能继续"应该用 logger.warning）

Python 可以用 `-O` 参数跳过所有 assert（生产环境有时这么做）。所以 assert 只应该用来检查"如果这条不成立，后面的逻辑一定出错"的条件——而不是用来做正常的错误处理。

### ✅ 自检反馈

**✅ 参考答案**

- 正常数据：所有 check 通过，程序正常输出。
- 异常数据（负值、缺列等）：验证函数抛异常或 logger.warning，程序在"错误数据流入分析逻辑之前"中止。

**❓ 常见偏差**

| 偏差 | 原因 | 🔧 补救 |
|------|------|---------|
| "加了验证后正常数据跑不过了" | 你的验证条件写错了。比如 `assert (df['amount'] >= 0).all()` 在有 NaN 时会失败（NaN >= 0 是 False） | 先 `.fillna(0)` 或用 `df['amount'].dropna()` 再检查 |
| "验证太多，代码变长了" | 验证代码本身也是代码——它和业务代码一样需要维护 | 把验证逻辑集中在 `validate.py`，业务代码只调一个函数。不要在每个函数里散落 assert |
| "不确定该 assert 还是 logger.warning" | 关键检查（数据不符预期则后续分析一定出错）→ assert。次要检查（数据有点怪但还能分析）→ logger.warning | — |

## D2（周二 8/12）：ETL 思维——你每天的 pandas 代码就是一个微型数据管道

### 🔴 认知冲突

你的 `main.py` 现在有三个步骤：`load_orders()` → `clean_orders()` → `analyze_orders()`。跑一次没问题。但你跑第二次的时候——发现结果和第一次不一样。

排查半天：因为 `analyze_orders()` 在清洗后的数据上做了 `df.to_csv('output/cleaned.csv')`——然后你第二次跑的时候，这个"中间文件"被当成输入读进来了。但中间文件是第一次跑的，第二次跑的原始数据已经变了——所以你分析的是"昨天的数据 + 今天新加的几行"。

**问题**：如果你的脚本跑一半失败了，重跑后会得到正确的结果吗？如果你的数据每天更新，跑三次会得到三个相同的结果吗？

---

### 📖 核心原理

**ETL 不只是大数据的概念。你每天写的数据处理代码，就是一个 ETL 管道。**

ETL = Extract（提取）→ Transform（转换）→ Load（加载）。你的 `main.py`:

```
Extract          Transform          Load
  ↓                 ↓                ↓
load_orders()  →  clean_orders()  →  df.to_csv('output/report.csv')
```

**ETL 的三个关键属性**

1. **幂等性（Idempotency）**：同样的输入，跑一次和跑十次，结果一样。如果你的脚本不幂等——"哎呀昨天跑的数据还在 output 里，今天的跑出来把昨天的覆盖了但又不是全量覆盖"——这就是非幂等。
2. **可恢复性（Recoverability）**：跑到一半失败了，能从失败的地方继续，不用从头跑。如果你的清洗跑了 10 分钟，分析跑了 2 分钟，分析那段崩了——你不想再跑 10 分钟的清洗。
3. **数据血缘（Data Lineage）**：每一份输出，你都能追溯它的"血统"——它是从哪个输入、经过哪几步变换、在什么时间生成的。

**让你的脚本变幂等——最简单的两步**

第一步：**清空输出，再写输出。**

```python
import shutil
from pathlib import Path

# 先清空输出目录
output_dir = Path('output')
if output_dir.exists():
    shutil.rmtree(output_dir)
output_dir.mkdir()

# 然后写文件
df.to_csv(output_dir / 'report.csv', index=False)
```

为什么不是直接覆盖？因为如果这次跑的结果比上次少（比如原始数据少了几天），上次留下的文件不在这次写入的名单里——它就留在那里，变成"幽灵文件"（你以为它是这次生成的，其实它是上次剩下的）。

第二步：**提取和转换分离。不要在转换过程中又去提取新数据。**

```python
# ✅ 对的：提取全部完成 → 转换全部完成 → 加载全部完成
raw = extract()
clean = transform(raw)
load(clean)

# ❌ 错的：在转换中间又去读文件，循环依赖
raw = pd.read_csv('data/orders.csv')
raw['category'] = pd.read_csv('data/categories.csv')['name']  # transform 阶段又 extract 了
```

**数据血缘——最简单的实现**

在你的输出 CSV 或报告的第一行（或 metadata 里）记录：
```
数据来源: data/orders.csv (导出时间: 2026-08-12 08:00)
处理脚本: main.py (commit: abc1234)
处理时间: 2026-08-12 14:32:05
```

等你两周后回来看这份报告，你能立刻知道它是从哪份数据、哪个版本的代码生成的。

## D3（周三 8/13）：依赖管理原理——为什么 `pip freeze` 导出的文件不能直接用

> 📓 今日主课：窗口函数——ROW_NUMBER/RANK/LAG/SUM OVER/ROWS vs RANGE

---

### 🔴 认知冲突

你执行了 `pip freeze > requirements.txt`，文件里有 87 行。push 到 GitHub。同事 clone 后执行 `pip install -r requirements.txt`——装到第 23 行时炸了，报错 `Could not find a version that satisfies the requirement`。

你打开 `requirements.txt` 一看——里面有一大堆你没听过的包名：`six`、`python-dateutil`、`pytz`、`et-xmlfile`。你没装过这些——它们是 pandas 和 openpyxl 的依赖（依赖的依赖）。

**问题**：`pip freeze` 导出的到底是什么？为什么别人用同样的文件装不上？"直接依赖"和"传递依赖"有什么区别？

---

### 📖 核心原理

**你的项目依赖的是"你 import 的包"，不是"这些包内部依赖的包"。**

当你 `pip install pandas`，pip 做了什么：
1. 下载 pandas 的安装包
2. 检查 pandas 的依赖——发现它需要 numpy、python-dateutil、pytz
3. 下载并安装这些依赖
4. 检查这些依赖的依赖——python-dateutil 需要 six
5. 下载并安装 six
6. 完成

所以你的 venv 里有 pandas（你装的），也有 six（pip 自动装的）。`pip freeze` 把它们全部列出来——不区分"你装的"和"pip 自动装的"。

**直接依赖 vs 传递依赖**

- 直接依赖（Direct Dependency）：你在 `import` 语句里写的包。你的项目依赖 `pandas`、`numpy`、`matplotlib`。如果你的代码里 `import pandas`——pandas 是直接依赖。
- 传递依赖（Transitive Dependency）：你的直接依赖所依赖的包。`six` 是被 pandas 的依赖 python-dateutil 依赖的。你的代码里没有 `import six`——它是传递依赖。

传递依赖会随着 pandas 版本更新而变化。pandas 1.5 需要 six==1.16，pandas 2.0 可能不需要 six 了。**所以不应该在你的 requirements.txt 里锁死 six 的版本**——它应该由 pandas 自己决定。

**为什么"只列直接依赖"还不够——依赖解析的问题**

假设你的 `requirements.txt` 只有：
```
pandas>=1.5
numpy>=1.23
```

pip 会做什么？它会去 PyPI 网上查——"pandas 的最新版本是什么？它需要什么版本的 numpy？"——然后下载匹配的版本。

听起来不错。但有一个问题：**两个月后，pandas 出了新版本，它的依赖也变了。** 同事 clone 后 `pip install -r requirements.txt`——装到的是两个月后的版本，可能和你的代码不兼容。

所以真正的生产级做法是：**锁定直接依赖的版本 + 让 pip 自动解析传递依赖**。

你的 `requirements.txt` 应该是：
```
pandas==2.0.3
numpy==1.24.3
matplotlib==3.7.2
seaborn==0.12.2
scipy==1.10.1
```
（只有你 import 过的包，每行锁版本，不要传递依赖。）

**手动维护 requirements.txt 的步骤**

```bash
# 1. 在 venv 里只装你需要的包
pip install pandas numpy matplotlib seaborn scipy

# 2. 导出并手动精简
pip freeze > requirements_full.txt           # 全量导出（有传递依赖）
# 然后打开 requirements_full.txt，删掉不是你主动装的包
# 只保留 pandas, numpy, matplotlib, seaborn, scipy 等

# 或者用 pipreqs（自动只列直接依赖）
pip install pipreqs
pipreqs . --force
# pipreqs 会扫描你的 import 语句，只输出你真正用了的包
```

### 🏢 鲜果多案例

鲜果多项目现在用到 `pandas`、`numpy`、`matplotlib`、`seaborn`。你的 `requirements.txt` 应该是 5 行——不是 87 行。因为别人 clone 你的代码时，pip 会根据你的 5 行需求，自动帮他们安装对应的传递依赖（匹配他们的操作系统和 Python 版本）。

## D4（周四 8/14）：字符编码深度——为什么中文 CSV 总乱码，怎么彻底解决

> 📓 今日主课：CTE + 递归 CTE + 三大模板（留存/漏斗/连续登录）

---

### 🔴 认知冲突

W1D3 你学了字符编码的基础。但今天你遇到了一个更复杂的问题：

运营同事用 Excel 编辑了 `users.csv`，保存后你的 Python 脚本报错了：`UnicodeDecodeError: 'utf-8' codec can't decode byte 0xb1 in position 15`。你试了 `encoding='gbk'`——这次没报错，但城市名"杭州"变成了"杭刿"。部分正确、部分乱码。

你用 VS Code 打开 `users.csv`——右下角显示编码是 UTF-8。但 Python 用 UTF-8 打开就报错了。

**问题**：VS Code 说它是 UTF-8，Python 用 UTF-8 打不开。为什么？"混合编码"是什么情况？同一个文件为什么有的字正常有的字乱码？

---

### 📖 核心原理

**VS Code 的编码检测是"猜测"，不一定是正确的。**

VS Code 读文件的前几百个字节，根据字节模式猜测编码。绝大多数时候是对的。但当一个文件被多次用不同编码编辑保存后——文件里可能同时存在两种编码的字符。VS Code 只能猜一种，Python 只能指定一种编码打开。

**混合编码是怎么产生的？**

1. 运营同事用 Excel（Windows 中文版，默认 GBK 保存）创建了 `users.csv`，写入了 100 个用户
2. 后来他在 Mac 上用 Numbers 打开了这个文件，编辑后保存——Numbers 用 UTF-8 保存
3. 但 Numbers 只改了前 50 行——后 50 行的中文仍然是 GBK 编码

这个文件：前 50 行是 UTF-8，后 50 行是 GBK。任何单一编码都打不开全部。

**彻底解决方案——分层处理**

```
第一层（预防）：统一编码标准。团队规定：所有 CSV 文件统一用 UTF-8（不带 BOM）。
第二层（检测）：用 chardet 或 cchardet 库自动检测文件编码，而不是硬编码。
第三层（修复）：用 errors 参数控制解码失败时的行为。
第四层（隔离）：混合编码文件单独处理——先检测编码块，分段读取。
```

在你的阶段，前两层就够了：

**第二层：自动检测编码**

```python
import chardet

def detect_encoding(filepath: str) -> str:
    """检测文件的编码。"""
    with open(filepath, 'rb') as f:
        raw = f.read(10000)  # 读前 10000 字节就够了
    result = chardet.detect(raw)
    confidence = result['confidence']
    encoding = result['encoding']
    logger.info("检测到编码: %s (置信度: %.1f%%)", encoding, confidence * 100)
    return encoding
```

然后 `pd.read_csv(filepath, encoding=detect_encoding(filepath))`。

**第三层：errors 参数**

```python
# errors='strict'（默认）：遇到非法字节直接报错
pd.read_csv(file, encoding='utf-8')  # UnicodeDecodeError

# errors='ignore'：跳过非法字节——但会丢失数据
pd.read_csv(file, encoding='utf-8', errors='ignore')

# errors='replace'：非法字节替换为 � (U+FFFD)
pd.read_csv(file, encoding='utf-8', errors='replace')
```

对于分析场景，`errors='replace'` 最安全——至少你知道哪里出了问题（出现 `�` 的地方）。

**到底应该用哪个编码？——规则速查**

| 数据来源 | 推荐编码 | 原因 |
|---------|---------|------|
| Python 生成的 CSV | `utf-8` | Python 默认 UTF-8 |
| Git Bash 生成的文件 | `utf-8` | Git Bash 默认 UTF-8 |
| Windows Excel 导出 | `gbk` 或 `utf-8-sig` | Excel 中文版默认 GBK；"导出为 CSV UTF-8" 用 utf-8-sig（带 BOM） |
| Mac Numbers 导出 | `utf-8` | Mac 默认 UTF-8 |
| 公司 ERP 系统导出 | 不一定——用 chardet 检测 | 老系统可能是 GBK 或 GB2312 |
| 不确定 | `chardet.detect()` | 自动检测，人工验证 |

---

### 🏢 鲜果多案例

鲜果多的 `orders.csv` 来源是 ERP 系统（UTF-8），`users.csv` 来源是运营同事手动维护的 Excel（GBK），`products.csv` 是另一个部门从数据库导出的（UTF-8 with BOM）。

一个项目里有三种编码。你的 `load_users()` 函数（W1D6 写的）用了 try/except 先试 UTF-8 再试 GBK——但这方法不优雅。用 chardet 自动检测更稳。

或者更彻底的做法：**在数据进入项目时就统一编码。** 在 `io.py` 里加一个函数——"把所有 CSV 统一转成 UTF-8 存到 `data/` 目录"。这样分析函数不需要知道原始编码是什么。

### ✅ 自检反馈

**✅ 参考答案**

- `chardet.detect()` 对 GBK 文件应返回 `encoding='GB2312'` 或 `'gbk'`，置信度 ≥ 90%。
- 对 UTF-8 文件应返回 `encoding='utf-8'`，置信度 ≥ 99%（UTF-8 的检测更可靠）。

**❓ 常见偏差**

| 偏差 | 原因 | 🔧 补救 |
|------|------|---------|
| "chardet 检测结果不准确" | 短文件（< 100 字节）的编码难以检测——中文文本太短，BOM 也没有，chardet 只能瞎猜 | 文件越长，检测越准。对于短文件（如只有表头），可能需要手动指定编码 |
| "觉得不如直接 try/except" | 在只有两种编码时 try/except 确实更简单。但当你有 5 种可能的编码时，try/except 就变成俄罗斯套娃了 | 当前阶段 try/except 够用。理解 chardet 的原理——以后遇到多编码场景时知道有工具可用 |
| "转码之后文件变大了" | UTF-8 对中文字符用 3 个字节，GBK 用 2 个字节。转码后中文字符变大了 50% | 对于数据分析场景（几十万行），这个差异可以忽略。对于 GB 级别的数据，考虑保留原始编码 |

## D5（周五 8/15）：知识管理方法论——错题归档不是"建个文件夹"

> 📓 今日主课：查询优化 + 反模式——EXPLAIN/索引/8 大反模式

---

### 🔴 认知冲突

学 SQL 三周了，你踩了至少 10 个坑：NOT IN + NULL、LEFT JOIN + WHERE 右表条件、GROUP BY 和 SELECT 不对齐、窗口函数忘了加 ORDER BY、隐式类型转换、通配符开头的 LIKE、回表查询、分页陷阱……

你在本地 `.md` 文件里记了一些，在 GitHub Issue 里记了一些，在代码注释里记了一些。今天面试官问"你遇到过哪些 SQL 坑？"——你脑子里知道"遇到过很多"，但嘴里只能说出 2 个。剩下的在哪？——分散在各处，临场调不出来。

**问题**：知识管理不是"记下来"。记下来只完成了 10%。剩下的 90% 是：分类、检索、模式化、在需要的时候能被调出来。

---

### 📖 核心原理

**知识管理的三级跃迁**

| 级别 | 做什么 | 典型行为 | 检索效率 |
|------|--------|---------|---------|
| **L1：记录** | 踩坑后记一句话 | 在代码注释里写 `# 注意: NOT IN + NULL 会导致空结果` | ⭐ 低——分散各处，无法检索 |
| **L2：归档** | 按类型整理到一个地方 | GitHub Issue 标签 `sql`、`bug`，统一格式（错误→正确→教训） | ⭐⭐⭐ 中——有统一入口，按标签可搜索 |
| **L3：模式化** | 把同类错误抽象成模式 | "凡是 `NOT IN` 子查询，必须先确认子查询结果无 NULL 或用 `NOT EXISTS` 替代"——这不再是一个具体的错误，而是一个可迁移的防御规则 | ⭐⭐⭐⭐⭐ 高——面试时可以脱口而出，写代码时可以预判 |

你现在的目标是：**从 L1 跳到 L2。** L3 需要积累更多案例，会在月3（W9-W12）自然达到。

**L2 的具体做法——GitHub Issue 标准化归档**

每一个错题作为一个 Issue，标签至少含：`bug` + 领域标签（`sql` / `python` / `pandas` / `git`）。

Issue 模板：
```markdown
### 错误代码
```python
# 你写的错误代码
```

### 错误现象
程序报错/结果不对/数据丢失——具体现象是什么？

### 根因
为什么错了？NOT IN 遇到 NULL / 编码不匹配 / 相对路径起点不对...

### 正确代码
```python
# 修正后的代码
```

### 防御规则（一句话）
避免再次犯同样错误的检查清单条目。

### 标签
bug, sql（或 python/pandas/git/...）
```

**为什么用 GitHub Issue 而不是本地 .md 文件？**

1. **可搜索**：GitHub Issue 有全文搜索。面试前搜 `label:bug label:sql`——你所有的 SQL 错题都在眼前。
2. **可追溯**：每个 Issue 有日期、有链接。面试时你可以说"我在 GitHub 上维护了一个错题知识库，这是链接"——比"我记了很多笔记"有说服力 100 倍。
3. **标准化**：用模板强制自己每次都写清楚"错误→根因→正确→防御规则"。没有模板你就偷懒写"NOT IN 坑"——三个字等于没记。
4. **公开的**：面试官看到你的 GitHub 上有 Issues 记录你的学习过程——这说明你不是"学过就忘"，而是在系统性地积累经验。

---

### 🏢 鲜果多案例

你在鲜果多项目中踩了 3 个工程化相关的坑，各建一个 Issue：

### ✅ 参考答案

**Q1**：①存在性（文件存在/列存在/行数>0）②数据类型（amount 是数值不是字符串）③值范围（无负值/日期在合理范围/缺失率不高）④跨表一致（join 后行数验证/外键完整性）⑤业务规则（占比和为1/转化率≤100%）。偏差：说不出第 4-5 层的具体例子——回到 D1 看代码示例。

**Q2**：幂等性 = 同样的输入，跑一次和跑十次，结果一样。不幂等的例子：脚本把中间结果写到了 `output/temp.csv`，第二次跑的时候又去读这个文件——读到的不是原始数据而是上次的结果。偏差：说"跑两次可能不一样因为数据变了"——数据变了是输入变了，不叫不幂等。不幂等是输入不变但输出变了。

**Q3**：直接依赖 = 你在 `import` 里写的包（pandas）。传递依赖 = 直接依赖所依赖的包（six，被 pandas 的依赖 python-dateutil 依赖）。requirements.txt 只列直接依赖——因为传递依赖会随版本变化，锁死它们会导致跨平台安装失败。偏差：分不清 pandas 的哪些依赖该留哪些该删。判断标准：你的代码里有没有 `import xxx`？有→保留。没有→删掉。

**Q4**：Windows 中文版 Excel 默认用 GBK 保存 CSV。Mac 默认用 UTF-8 打开文件。GBK 编码的中文在 UTF-8 下解释会乱码。根本原因是文件缺少编码声明——CSV 格式本身不标注编码。偏差：说"文件坏了"——文件没坏，编码不一致而已。

**Q5**：UTF-8 是全球统一编码，中文字符用 3 个字节。GBK 是中国国标编码，中文字符用 2 个字节。UTF-8 能表示全球所有语言字符，GBK 只能表示中文+英文。偏差：说 UTF-8 中文用 2 个字节——那是 UTF-16。UTF-8：英文 1 字节，中文 3 字节，少数罕见字 4 字节。

**Q6**：①可搜索——全文搜索+标签筛选 ②可追溯——每个 Issue 有时间戳和链接 ③标准化——用模板强制三段式 ④公开的——面试官可以看到你的学习过程。偏差：只说了"方便"——具体说方便在哪。

**Q7**：`git rm` = 删除本地文件 + 从 Git 跟踪中移除。`git rm --cached` = 只从 Git 跟踪中移除，保留本地文件。偏差：以为 `--cached` 表示"从缓存里删"——它是"从 Git 的索引（也叫 cache）里移除"，但不碰工作目录的文件。

**Q8**：①用 chardet 自动检测编码 ②或 try/except 依次试 utf-8 → gbk → utf-8-sig ③显式传 encoding 参数给 pd.read_csv。偏差：说"全转成 utf-8"——这是最终目标，但你要先读出来才能转。读的时候就需要指定编码。
