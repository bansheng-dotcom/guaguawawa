### 📖 核心原理

**pathlib 使用三原则——不是"尽量用 Path"，是"不该出现字符串路径的地方一个字都不该出现"：**

**原则 1：Python 内部——永远传 Path 对象，不要在中途转成字符串。**

```python
# ✅ 对：全程 Path 对象——从定义到使用，从不断开
from pathlib import Path
DATA_DIR = Path('data')
OUTPUT_DIR = Path('output')

filepath = DATA_DIR / 'orders.csv'           # Path 对象
df = pd.read_csv(filepath)                    # pandas 2.0+ 原生支持 Path
df.to_parquet(OUTPUT_DIR / 'clean.parquet')   # 原生支持

# ❌ 错：中途转成了字符串——Path 的优势被丢弃了
filepath = str(DATA_DIR) + '/' + 'orders.csv'   # 为什么错？
# str(DATA_DIR) 在 Windows 上返回 'data\\orders.csv'，然后你加 '/'→'data\\orders.csv'
# 在 Linux 上返回 'data/orders.csv'。两种行为不一样——你在 Windows 上测过了，
# 以为自己写对了——但 Linux 上可能因为某个边界条件出错。
df = pd.read_csv(filepath)
```

**为什么 `str(Path)` 是坏的？** 因为 Path 对象"知道"自己在什么操作系统上——`Path('data') / 'orders.csv'` 在 Windows 上自动变成 `data\orders.csv`（反斜杠），在 Linux 上自动变成 `data/orders.csv`（正斜杠）。一旦你调了 `str()`——操作系统适配能力就丢了。

**原则 2：传给不支持 Path 的第三方库——在调用处显式 `str(path)`，并加注释说明为什么。**

```python
# ⚠️ some_old_lib v0.3.1 不支持 Path 对象——已知限制
# 升级到 v0.4.0 后可以移除此 str() 转换
result = some_old_lib.process(str(DATA_DIR / 'input.csv'))
```

这个原则的价值不在"这个 `str()` 本身"——在于"注释标注了为什么"。三个月后你回来看——知道这不是随意写的——是有原因的。v0.4.0 发布后——你可以全局搜索 `# some_old_lib` 找到所有需要升级的调用点。

**原则 3：只在"给人看"的地方转字符串——日志输出、错误消息、用户展示。**

```python
logger.info('输出文件: %s', output_path)           # logging 支持 Path 对象——直接用
error_msg = f'文件不存在: {output_path.as_posix()}' # 错误消息——用 as_posix() 统一正斜杠
```

`.as_posix()` 总是返回正斜杠格式——无论在 Windows 还是 Linux 上。用于日志和错误消息时——格式统一、方便搜索。

**全项目审计——找到所有漏网之鱼的三条命令：**

```bash
# 命令1: 搜索所有还在用 os.path 的地方
grep -rn "os\.path" src/ --include="*.py"

# 命令2: 搜索所有字符串拼接路径
grep -rnE "['\"](data/|output/)" src/ --include="*.py" | grep -v "^.*#"

# 命令3: 搜索所有 open() 调用中传字符串路径的
grep -rn "open(" src/ --include="*.py" | grep -v "Path\|encoding"
```

**三条命令全部返回空（或 ≤ 2 行且有注释解释）——这才是 pathlib 终局。**

### 🔴 认知冲突

你的 `main.py` 现在是 80 行——加载→验证→清洗→分析→可视化→输出——6 个步骤。跑一次约 30 秒。某天运营总监反馈"今天的报表少了上海的数据"。

你花了 20 分钟逐行排查——从"是不是数据问题"到"是不是清洗逻辑改了"到"是不是 pandas 版本不兼容"——最后才发现是磁盘空间不足。这个排查过程本应是 20 秒——如果你在日志里能看到每一步的执行时间和状态。

**问题**：你的 `main()` 是一个扁平的大函数——步骤之间没有计时间隔、没有成功标记、没有失败恢复路径。日志只记录了"某些时刻的 INFO 消息"——但没有记录"哪些步骤成功完成了、分别花了多久"。你怎么知道"慢在哪一步"、"失败在哪一步"？

---

### 📖 核心原理

**标准化 `main()` 模板——四个要素：声明式步骤定义、每步计时、成功/失败状态、结束时汇总报告。**

这不是让你多写代码——是让你以后排查问题时少花时间。

```python
import time
from datetime import datetime
from typing import Dict, List, Tuple, Callable, Any
import logging

logger = logging.getLogger(__name__)


def main() -> Dict[str, Any]:
    """鲜果多日报分析管道——标准化执行模板。

    设计原则:
    1. 步骤是声明式的——加新步骤只需在 steps 列表加一行
    2. 每步独立计时——瓶颈一目了然
    3. 步骤失败不阻断后续（除非后续步骤依赖该步骤的数据）
    4. 结束时输出汇总报告——X步成功 / Y步失败
    """
    logger.info("=" * 60)
    logger.info("鲜果多数据分析管道启动: %s", datetime.now().isoformat())
    t_start = time.time()

    # ---- 步骤定义（声明式——加步骤只需加一行）----
    # 格式: (步骤名称, 函数, 参数字典)
    steps: List[Tuple[str, Callable, Dict]] = [
        ("1.加载数据", load_all_data, {}),
        ("2.验证数据", validate_all, {}),
        ("3.清洗数据", clean_all, {}),
        ("4.分析数据", analyze_all, {}),
        ("5.生成图表", create_charts, {'output_dir': OUTPUT_DIR}),
        ("6.导出报告", export_report, {'output_dir': OUTPUT_DIR}),
    ]

    # ---- 逐步骤执行——每一步: 计时 + 状态 + 失败不阻断 ----
    results = {}
    n_success, n_fail = 0, 0

    for name, fn, kwargs in steps:
        t_step = time.time()
        try:
            step_result = fn(**kwargs)
            results[name] = step_result
            elapsed = time.time() - t_step
            logger.info("✅ %s (%.1fs)", name, elapsed)
            n_success += 1
        except Exception as e:
            elapsed = time.time() - t_step
            logger.error("❌ %s 失败 (%.1fs): %s", name, elapsed, e)
            logger.exception(e)  # 完整 traceback 写入日志文件——后续排查的关键
            n_fail += 1
            # 不 raise——让后续步骤继续执行。如果后续步骤依赖失败步骤的数据，
            # 后续步骤会在内部检测到数据为空并 logger.warning

    # ---- 汇总报告 ----
    t_total = time.time() - t_start
    logger.info("-" * 60)
    logger.info("管道完成: %d 步成功 / %d 步失败 | 总耗时: %.1fs",
                n_success, n_fail, t_total)
    if n_fail > 0:
        logger.warning("⚠️ 有 %d 个步骤失败——请检查上述错误日志", n_fail)
    else:
        logger.info("✅ 全部步骤成功")

    _write_metadata(t_start, n_success, n_fail, steps, results)
    return results
```

**这个模板和你现在 `main()` 的核心差异：**

| 维度 | 你现在的 `main()` | 标准化模板后 |
|------|-----------------|------------|
| **查看哪步最慢** | 需要手动在日志里减时间戳 | 直接看 `✅ 3.清洗数据 (16.2s)` |
| **某步失败了** | 可能看不到——异常被掩盖 | `❌ 6.导出报告 失败 (2.0s): [Errno 28]` |
| **加新步骤** | 在 `main()` 函数体里找到插入位置 | 在 `steps` 列表里加一行 |
| **整体状态** | 没有——需要判断"是不是成功了" | 汇总报告——`5 步成功 / 1 步失败` |
| **排查时间** | 20 分钟——逐行推导"失败在哪" | 20 秒——搜索 `❌`，定位失败步骤 |

**输出效果——一条真实的日志记录：**

**✅ 参考答案**

- 终端输出每行格式统一：`✅/❌ 步骤名 (耗时s)`

**❓ 常见偏差**

| 偏差 | 原因 | 🔧 补救 |
|------|------|---------|
| "失败步骤之后的步骤也全失败了——因为数据是空的" | 步骤之间存在数据依赖——如"清洗失败"→"分析"拿到空数据也失败 | 在步骤函数内部检查前置数据是否存在。不存在→`logger.warning` 并返回 None |

| "日志输出太多——终端刷屏了" | 每步一行 + 分隔线 + 汇总——共约 10 行 | 开发环境临时把 level 设成 WARNING，生产环境切回 INFO |

## D4（周四 9/18）：Linux 数据分析师速查——不只是"会敲"，是"知道什么时候敲、敲完能看出什么"

> 📓 今日主课：数据质量+指标口径——五维度/口径三要素/监控脚本

---

### 🔴 认知冲突

你一直在 Windows Git Bash 里敲 Linux 命令。你习惯了 `ls`、`cd`、`cat`——你觉得"会用 Linux"就够了。

然后今天你 SSH 到了公司新配的纯 Linux 服务器。你拿到了一份新的 `orders.csv`——需要确认数据完整。你在 Windows 上会"双击打开 Excel——看右下角行数"。服务器没有 Excel——只有一个黑底白字的终端。

你想看看这个 CSV 有多少行——你敲了 `cat data/orders.csv | wc -l`——终端卡了 30 秒——因为这个文件有 5000 万行——`cat` 把它全部读进内存再传给 `wc`。

同事路过——看到你在等——说：`wc -l data/orders.csv`——3 秒出结果。你问为什么——他说"因为 `wc` 直接读文件——不经过 `cat`——不经过管道——不经过内存复制。"

**问题**：会敲命令和会用命令之间的差距——是在关键时刻知道"哪种方式是正确的"。数据分析师不需要知道 Linux 的 100 条命令。你需要知道 8 条——每条精确对应一个高频场景——并且理解"为什么这种写法比那种写法好"。

---

### 📖 核心原理

**8 条命令——每条不只是语法，是"什么时候用、为什么这样写、敲完能看出什么"。**

---

**命令 1：`wc -l`——统计行数。验证数据完整性的第一道检查。**

```bash
wc -l data/orders.csv
# 输出: 98523 data/orders.csv
```

**什么时候用**：每次收到新数据——第一件事确认行数。昨天是 98523 行，今天是 523 行？→ 数据导出过程中断了。今天是 98523 行，但昨天是 120000 行？→ 可能数据源换了导出逻辑——先确认再跑分析。

**为什么不用 `cat file | wc -l`**？`cat` 把文件内容读进内存→通过管道传给 `wc`→`wc` 数行数。`wc -l file` 直接从磁盘读——不经过管道——不经过额外内存复制。5000 万行的文件——`cat | wc` 可能卡 30 秒，`wc -l file` 3 秒。这是数据分析师最常用的行数检查——"3 秒还是 30 秒"决定了你"每收到一份新数据都做一次"还是"懒得做、出事了再说"。

**面试如果被问到**："你怎么验证一份新数据的完整性？"——"第一件事——`wc -l`。对比昨天的行数、上个月同一天的行数——如果偏差超过预期范围的 ±10%——数据源可能有问题，先排查再分析。"

---

**命令 2：`head`——看前几行。确认数据格式和编码，不需要打开整个文件。**

```bash
head -5 data/orders.csv
# 输出文件的前 5 行——包括表头和前 4 条数据
```

**什么时候用**：跑脚本前快速看一眼——有没有肉眼可见的乱码？列的顺序变了吗？分隔符变了吗（昨天逗号分隔、今天变成了制表符）？这些是 `pd.read_csv()` 不会告诉你的——它只会在你跑完分析后给你错误的结果——而且不报错。

**你真正在看的**：第一行是不是你预期的列名（不是，列被调换顺序了）？有没有 BOM 字符（第一列列名前有 `﻿`）？编码对不对（中文是否正常显示）？

---

**命令 3：`grep`——搜索日志中所有报错。管道失败后的第一步排查。**

```bash
grep ERROR output/run.log | tail -10
# 从日志文件中找出所有包含 ERROR 的行——只显示最后 10 条
```

**什么时候用**：管道失败后——打开日志——不是从头读 300 行——而是直接 `grep ERROR`——跳到报错处。

**进阶用法——按时间范围搜索**：
```bash
# 只看今天 8:00 到 9:00 之间的错误
grep "2026-09-18 08:" output/run.log | grep ERROR

# 统计今天出现了多少次 ERROR
grep "2026-09-18" output/run.log | grep -c ERROR

# 搜索"失败"关键词（包括中文日志）
grep -E "ERROR|失败|异常" output/run.log
```

---

**命令 4：`tail -f`——实时追踪日志。跑慢分析时不需要每隔 30 秒手动打开日志。**

```bash
tail -f output/run.log
# 终端会实时显示新增的日志行——Ctrl+C 停止追踪
```

**什么时候用**：跑一个预计 5 分钟的分析——不想每隔 30 秒手动打开日志——让终端自动刷新。你在另一个终端窗口（或 tmux session）里跑 `python main.py`——这个窗口开着 `tail -f`——可以看到管道在哪个步骤、有没有报错。

**面试场景**：你说"我的管道有完整的日志记录"——面试官问"如果管道在跑的过程中卡住了——你怎么知道卡在哪一步？"——"我开一个 `tail -f output/run.log`——看到最后一行日志是 `✅ 3.清洗数据 (16.2s)`——说明卡在步骤 4。进到步骤 4 的函数——看它在等什么。"

---

**命令 5：`df -h`——查磁盘空间。跑大查询前必看——10 秒的检查能省 2 小时的数据重建。**

```bash
df -h
# 输出每个挂载点的总空间/已用/可用/使用率
```

**什么时候用**：跑一个预估输出 2GB 的分析前——先 `df -h`。如果 `/data` 分区只有 500MB 剩余——你的输出文件写到一半——磁盘满了——`df.to_csv()` 会静默写一个大小为 0 的文件——不报错——你以为是分析结果就是 0——结论全错。

**数据分析师的血泪教训**：不是"我从来没用过 `df -h`"——是"我还没遇到过磁盘满的那一天"。那一天一定会来——你的日志文件、中间 Parquet 文件、模型 pickle 文件——它们一直在堆积。养成习惯——每天跑日报前 `df -h`——看一眼。

---

**命令 6：`du -sh`——查文件/目录大小。定位"谁吃了磁盘"。**

```bash
du -sh data/* output/* | sort -rh | head -10
# 输出 data/ 和 output/ 下各文件/目录的大小——按从大到小排——只看最大的 10 个
```

**什么时候用**：`df -h` 告诉你磁盘使用率 95%——你不知道是谁吃的。`du -sh` 告诉你——"`output/run.log` 占了 8GB"——因为日志写了 3 个月没轮转。`output/models/` 占了 15GB——因为每次实验都保存了模型快照——从来没清理过。

---

**命令 7：`crontab -l`——查定时任务。确认自动化在正常工作。**

```bash
crontab -l
# 列出当前用户的所有 cron 定时任务
```

**什么时候用**：运营说"今天的日报在哪？"——你不是先排查代码——是先确认 cron 是否配置并启用。`crontab -l` 比翻代码快 100 倍——你瞬间知道是不是 cron 的问题。

**常见的问题不是"cron 不工作"——是"cron 工作的环境和你的终端不一样"**。cron 的 PATH 可能不含你的 venv 路径、工作目录可能是 `$HOME` 而不是项目根目录。排查 cron 问题的第一步永远是 `crontab -l` 确认任务存在——第二步是检查 cron 日志。

---

**命令 8：`find`——批量查找、批量操作。强大到危险——必须先 `ls` 确认再执行。**

```bash
# 第一步：查找（只看不删）
find output/ -name "*.tmp" -type f -mtime +7
# 解释: 在 output/ 下找文件名为 *.tmp 的、普通文件（不是目录）、修改时间 > 7 天前的

# 第二步：确认——肉眼检查输出——真的是 7 天前的临时文件吗？

# 第三步：删除（确认后执行）
find output/ -name "*.tmp" -type f -mtime +7 -delete
```

**`find` 和 `rm -rf` 的区别**：`rm -rf /` 是无差别核弹。`find` 是精确制导导弹——可以有精确的条件（文件名、时间、大小、类型）——但它仍然是导弹。先用 `find ... -print`（默认行为）确认匹配了哪些文件——肉眼确认——再 `-delete`。

---

### 🏢 鲜果多案例

鲜果多的 Linux 服务器上——今早 `df -h` 显示 `/data` 分区使用率 97%。你跑了 `du -sh data/* output/* | sort -rh | head -5`——发现 `output/models/` 占了 22GB——是你过去 3 个月每次 AB 实验保存的 XGBoost 模型快照——从来没清理过。你用 `find output/models/ -name "*.pkl" -mtime +30` 找到了 30 天前保存的 20 个模型文件——确认后 `-delete`——释放了 15GB。

如果你没有这个习惯——再过两天磁盘满了——日报管道的 `df.to_csv()` 静默写空文件——你会发现不了——运营总监拿到的是"GMV=0"的报表——然后你花一下午排查。

## D5（周五 9/19）：自动化锁文件——为什么"放到 crontab 里"不是终点，而是起点

> 📓 今日主课：自动化+定时任务——crontab + smtplib + 幂等性

---

### 🔴 认知冲突

你写了一个 cron 任务：每天早上 8:00 跑 `python main.py`。你觉得"自动化完成了"。

第三天早上——cron 延迟了 20 分钟，在 8:20 启动了。然后 8:25——cron 守护进程异常重启——又触发了一次——第二个实例也启动了。两个 Python 进程同时写同一个 `output/report.csv`——一个进程写到一半，另一个进程覆盖——文件损坏了。运营总监打开报表——看到乱码——问"今天的报表呢？"

你花了 3 个小时才找到根因——不是数据分析逻辑的问题——是两个进程同时写同一个文件。

你问了两个问题——①"怎么防止两个实例同时跑？"——锁文件。②"但锁文件如果因为上次程序崩溃没删干净——下一次 crontab 永远不会启动——怎么办？"

**问题**：自动化不是"把命令放到 crontab 里就完了"。自动化脚本必须能应对它在无人值守时一定会遇到的两个问题——**并发冲突**（前一个还没跑完、下一个就启动了）和**僵尸锁**（上次崩溃了导致锁文件永久留在磁盘上）。这背后有一个共同的设计原则——**程序必须能自动恢复自己的状态**。

---

### 📖 核心原理

**场景 1：并发冲突——为什么需要锁文件？**

cron 不保证"上一次运行结束了才启动下一次"。如果你的脚本跑了 5 分钟——而 cron 表达式是 `*/3 * * * *`（每 3 分钟）——在 8:00 启动第一个实例、8:03 启动第二个——第一个还在跑——第二个又开始跑——两个实例同时操作同一个 `output/report.csv`。

**场景 2：僵尸锁——为什么 `finally` 是必须的？**

锁文件放在磁盘上——如果你的脚本在获取锁后、释放锁前——崩溃了（`raise` 了一个未被捕获的异常）——锁文件永久留在磁盘上。下一次 cron 触发——检测到锁文件——退出。下一次也是。永远退出。直到你手动登入服务器——找到那个 `.pipeline.lock` 文件——手动删除。

**`finally` 是解决僵尸锁的关键——但不是唯一的防线：**

```python
import sys
import time
from pathlib import Path
import logging

logger = logging.getLogger(__name__)

LOCK_FILE = OUTPUT_DIR / '.pipeline.lock'
ZOMBIE_THRESHOLD = 3600  # 1 小时——超过这个时间的锁文件视为僵尸锁


def acquire_lock() -> bool:
    """尝试获取排他锁。

    两个保护层:
    1. 如果锁文件不存在 → 创建 → 继续执行
    2. 如果锁文件存在 → 检查是否"过期"（上次崩了遗留的僵尸锁）
       - 过期 → 强制清除 → 创建新锁 → 继续执行
       - 未过期 → 另一个实例仍在运行 → 退出

    Returns:
        True——获取成功，可以继续执行
        (获取失败时 sys.exit——不会返回 False)
    """
    if LOCK_FILE.exists():
        lock_age = time.time() - LOCK_FILE.stat().st_mtime

        if lock_age > ZOMBIE_THRESHOLD:
            # 锁文件超过阈值——大概率是上次崩溃遗留的僵尸锁
            logger.warning(
                "检测到僵尸锁文件——已存在 %d 秒（阈值 %d 秒）。"
                "可能上次管道异常退出未清理。强制清除并重新获取锁。",
                int(lock_age), ZOMBIE_THRESHOLD
            )
            LOCK_FILE.unlink()
        else:
            # 锁文件较新——另一个实例可能仍在运行
            logger.warning(
                "锁文件已存在（%d 秒前创建）——另一个管道实例可能正在运行。"
                "当前实例将退出。如果确认没有其他实例在跑——手动删除 %s",
                int(lock_age), LOCK_FILE
            )
            sys.exit(0)

    LOCK_FILE.touch()
    logger.info("已获取锁文件")
    return True


def release_lock():
    """释放锁——写入完成标记后删除。"""
    if LOCK_FILE.exists():
        LOCK_FILE.unlink()
        logger.info("已释放锁文件")


# ---- 在 main() 中的使用 ----
def main():
    acquire_lock()
    try:
        run_pipeline()        # 你的实际管道逻辑
    except Exception as e:
        logger.exception("管道执行失败——释放锁后退出")
        raise                  # 重新抛出——让外部（CI/cron）知道失败了
    finally:
        release_lock()         # 无论如何——finally 保证锁被释放
```

**为什么 `finally` 是必须的——用三个场景对比：**

| 场景 | `release_lock()` 在哪 | 结果 |
|------|---------------------|------|
| 管道正常完成 | `main()` 末尾 | ✅ 锁释放——正常 |
| 管道中途崩溃(抛异常) | `main()` 末尾 | ❌ 锁未释放——因为 `raise` 跳过了末尾的 `release_lock()`。锁文件永久留在磁盘——cron 永远不会再启动 |
| 管道中途崩溃 | `finally` 块内 | ✅ 锁释放——因为 `finally` 在 `raise` 传递出去之前一定会执行 |

**`finally` 不是"更好的编程习惯"——它是"没有锁文件你的自动化会在第一次崩溃后就永久停止"的物理必需。**

除了锁文件——自动化脚本还需要三种保护：

**1. 幂等性（W3D2 已学）：** 同一天的输入数据跑两次，输出结果完全一致。这是自动化的安全网——即使 crontab 异常触发了两次——第二次输出覆盖第一次——数据不变。

**2. 输出时间戳：** 每次跑的输出文件名含日期——`output/report_2026-09-19.md`——而不是固定文件名 `output/report.md`。为什么？因为固定文件名意味着——今天的报表只存在于"此时此刻"——你无法回答"上周三的报表长什么样"。含日期的文件名让你可以追溯到任何历史时点。

**3. 元数据记录：** 每份输出附带一个 `output/metadata.txt`（或写在报表文件头部的注释中）——记录：数据来源 / 数据最后更新时间 / 代码版本（git commit hash） / 管道开始时间 / 管道结束时间 / 成功步骤数 / 失败步骤数 / 输入数据行数。当有人质疑"这个数是怎么来的"——这份 metadata 是自包含的答案——不需要翻日志。

### ✅ 自检反馈

**✅ 参考答案**

- 终端 2 检测到锁文件——`sys.exit(0)`——日志有 `WARNING` 记录
- 手动创建超过 1 小时的僵尸锁——管道强制清除并继续执行

**❓ 常见偏差**

| 偏差 | 原因 | 🔧 补救 |
|------|------|---------|
| "管道崩了之后锁文件没被清理——cron 永久停止" | `release_lock()` 不在 `finally` 块里——在 `main()` 末尾——异常跳过了它 | 必须用 `try...finally` 包裹——不是"在末尾调用"——是"在 finally 块里调用" |
| "正常跑完的管道——锁文件也没被清理" | `release_lock()` 里有 bug——或者 `LOCK_FILE` 路径和你创建时不一致 | 打印日志确认：`logger.info("释放锁: %s", LOCK_FILE)`。跑完检查 `ls output/.pipeline.lock` 是否还存在 |
| "僵尸锁阈值设太短——一个正常的慢查询被当成僵尸锁误杀了" | 你的周报管道跑 2 小时——但僵尸锁阈值设为 1 小时 | 阈值设为你最大期望运行时间 × 2。日报设 30 分钟、周报设 4 小时 |
| "日期戳文件名导致 output 目录堆满了几百个文件" | 每天产生一个文件——30 天后 30 个——还好。但如果 crontab 每 5 分钟跑一次——一天 288 个 | 定期清理：保留最近 N 天的文件——周末自动 `find output/ -name "*.md" -mtime +30 -delete` |
| "元数据记录里 git commit hash 是空的" | 你在本地开发——没有 push 到 GitHub——`git rev-parse HEAD` 可能失败 | 加 fallback：`commit = subprocess.getoutput('git rev-parse HEAD') or 'unknown'` |
