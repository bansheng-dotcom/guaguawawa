# 一人公司 · 协同协议（PROTOCOL.md）

> 本文档规定 20 个角色 Agent 之间**任务如何流动**：如何展开、如何下发、
> 失败如何移交、多角色如何编排、完成如何验收。
> 组织关系见 `ORG.md`；字段契约见 `core/protocol.py`；汇报格式见 `REPORT-STANDARD.md`。

---

## 〇、总原则

1. **编排器必须瘦**：R01 只做四件事——加载上下文、派发正确角色、回收结果、更新状态。
2. **上下文隔离**：Agent 之间不共享内存，只通过「子进程边界 + 共享工作区」协作。
   每角色只拿它需要的工件，不喂全历史。
3. **单一主责**：一张任务卡一个 owner，一个职能一个 owner。
4. **谁生成谁负责，谁校验谁独立**：生成者不签自己的质量结论。
5. **一切带终止条件**：每张任务卡都有成功标准与杀死标准。

---

## 一、模式 A · 单角色直接调用（用户只点一个角色）

当用户直接对某一个角色（如「R06，帮我分析这份数据」）下指令，该角色按**五步展开协议**自展开：

```
① 澄清（Clarify）  →  ② 自查（Self-check）  →  ③ 展开（Expand）
                                                →  ④ 自评（Self-assess）  →  ⑤ 汇报（Report）
```

### ① 澄清
收到模糊意图，先做**六问裁剪版**（对齐 R01 模块 A2），只问真正缺的：

| # | 问 | 判定 |
|---|---|---|
| 1 | 交付物是什么？（报告/代码/图/方案） | 缺 → 问 |
| 2 | 目标与成功标准？（指标+阈值+时限） | 缺 → 问 |
| 3 | 边界？（范围、口径、明确不做） | 缺 → 问 |
| 4 | 输入在哪？（数据/文件/上游产物路径） | 缺 → 问 |
| 5 | 验收判据？（可机器测的） | 缺 → 问 |
| 6 | 有无时限/依赖？ | 缺 → 问 |

能自行推断的**不要问**（历史案例里有口径就沿用）。澄清无果 → 进模式 B（移交 R01）。

### ② 自查
- 我的哪个**技能域**（`SKILL.md` 能力域表）能覆盖这个意图？
- 我的**契约**（`contract list`）需要哪些输入字段？上游产物齐不齐？
- 有没有**越界**？（对照 `ORG.md` 第三节边界列，命中「明确不做」→ 进模式 B）

### ③ 展开
- `run --task <task_id>` 走意图路由（`_INTENT_ROUTES`），或直接 `python agent.py <skill> <action>`。
- 拉取契约要求的输入 → 执行 → 过 `harness` 门禁。
- 结果以单行 `__AGENT_RESULT__ {json}` 输出；产物写入 `workspace/artifacts/{task_id}/`。

### ④ 自评
对照本角色交付标准（`REPORT-STANDARD.md` + 本角色 harness）：
- 门禁是否 PASS？脏数据是否被正确拦？
- 每个数字是否可复算回溯？
- 不达标 → **不许硬交**，进模式 B。

### ⑤ 汇报
按 `REPORT-STANDARD.md` 的一线执行汇报格式产出（`.md` 快读 + `.html` 正式），
不吐裸 JSON。

## 二、模式 B · 失败与越界移交（任务进行不下去时）

任务卡 `status` 无法推进到 `done` 时，**不许沉默、不许硬凑**，按分类路由移交。

### 移交分类表

| 触发条件 | 移交对象 | 事件/端口 | 载体 |
|---|---|---|---|
| 输入不足 / 口径不明 / 需求矛盾 | 回上游 或 R01 澄清 | `note` | 澄清问题清单 |
| 超出本角色边界（对照 ORG 边界列） | 边界表指定的邻角色 | `handoff` | 任务卡 + 已产出中间物 |
| 需独立质量判断 | R04 评审 | `artifact` 端口 | 成品 + 验收判据 |
| 命中 2+ 职能域（跨域） | R01 重拆 | `task_cards` | 原意图 + 已完成部分 |
| 不可逆操作 / 资金 / 合同 / 大额 | 升级创始人 | `escalate` | 决策卡 + 回滚计划 |
| 依赖的上游任务 failed | R01（重排依赖） | `note` | 阻塞说明 |

### 移交协议字段（`handoff` 事件 payload）

```json
{
  "from": "r06",
  "to": "r03",
  "reason": "boundary_exceeded",
  "task_id": "a1b2c3d4",
  "artifacts": ["workspace/artifacts/a1b2c3d4/analysis_report.md"],
  "acceptance": ["财务口径由 R03 复核并签字"],
  "context_summary": "一句话说明已做什么、缺什么、为什么移交",
  "call_chain": ["r01", "r06"]
}
```

### 移交铁律（防死循环，继承 R01 模块 B6）
- **禁止自调用**；**最大调用深度 = 2**；**禁止闭环**；每跳必带 `call_chain`。
- 移交必须给**足够上下文**（`context_summary` + `artifacts`），不让接收方重新问一遍。
- 接收方若也做不了 → 继续按表移交，但同一任务**总移交次数 > 3 次即升级 R01 重拆**。

## 三、模式 C · 多角色编排（跨域方案）

对齐 R01 的 **GSD 五相环**：`Discuss → Plan → Execute → Verify → Ship`。

### 编排流程

```
意图 → R01 拆解
  ① Discuss：澄清意图，判定是否跨域（2+ 职能域 → boardroom）
  ② Plan：拆成任务卡（单一主责 + 六段门禁 + 接口契约），建依赖图
  ③ Execute：按波次（Wave）并行执行，无依赖的进第 1 波
  ④ Verify：R04 独立复核，R01 验收（需求覆盖/决策覆盖/目标对齐三缺一即不过）
  ⑤ Ship：收口归档到 workspace/artifacts/，更新决策日志
```

### 任务卡六段（R01 模块 B2，下发的最小单元）

```
## 任务 <名>        （title + owner，单一主责）
### 目标            1-2 句要构建什么
### 拥有文件         独占文件清单（一个文件一个 owner）
### 需求            具体交付 1..n
### 接口契约        导出:<本流提供> / 导入:<从别流消费>
### 验收标准        可机器测的准则（- [ ]）
### 明确不做        非目标（空 = 门禁不通过）
```

### 依赖与波次
- 依赖图 `blockedBy / blocks`；**循环检测必须在波次划分之前**（有环时拓扑分层会死循环，
  先 DFS 三色标记截停）。
- 无依赖 → 第 1 波并行；依赖第 1 波 → 第 2 波；`max_wave_depth = 6`。
- 共享状态写用原子锁（`O_EXCL` 锁文件，陈旧锁 10s 清除），已由 `core/workspace.py` 实现。

### 典型编排 pattern（可复用）

| Pattern | 链路 | 适用 |
|---|---|---|
| 链式交付 | R05 研究 → R07 产品 → R08 实现 → R09 工程 → R04 评审 | 从想法到上线 |
| 数据驱动 | R07 出假设 → R06 验证假设 → R08 渲染报告 → R04 复核 | 营收/增长方案 |
| 内容增长 | R11 成稿 → R10 配图 → R12 投放 → R06 复盘归因 | 内容营销 |
| 合规闭环 | 任一产出 → R03 合规复核 → R04 独立评审 | 涉红线交付 |

**关键约束（TEAM.md 继承）**：谁生成谁负责——R07 出「假设」，R06 只「验证假设」不发明方案，
R08 只「渲染」不新增分析声明。跨角色失败路由：R06 验证推翻 R07 假设 → 回 R07 改假设，不硬凑结论。

## 四、验收协议（Verify）

**验收 = 已完成定义**：完成 ≠ 无报错，而 =「所建 = 所规划 = 所决定」。

| 验收方 | 验收什么 | 不通过的处理 |
|---|---|---|
| 执行角色自己的 harness | 门禁：干净数据 PASS / 脏数据 FAIL | 退回重做（模式 B） |
| 上游角色（交接验收） | 下游交付物是否满足接口契约 | 退回补字段/重算 |
| R04 独立评审 | 成品三级证据链 + 6 项对抗挑战 | `verdict=FAIL` + failure_category 回路由 |
| R01 总验收 | 需求覆盖 / 决策覆盖 / 目标对齐 | 三缺一即不过，重拆或补做 |

R04 三个回路由（对齐 R06 T7 规范）：
- `evidence_does_not_support_conclusion` → 回 **react** 重算
- `expression_title_or_line_fit` → 回 **writer** 改写
- `no_report_value` → 回 **controller** 丢弃

## 五、事件流（可追溯的审计底账）

所有协作动作写入 `workspace/events.jsonl`（只追加）：`task_created / task_assigned /
task_started / task_finished / task_failed / handoff / note / verify`。
每次运行写 `workspace/runlog.jsonl`（input_hash / 耗时 / 退出码）。
**任何移交、验收、失败都必须留事件**——没有事件等于没发生。
