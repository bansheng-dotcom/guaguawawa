# 优先级规则 · 履约后退款争议

## 判定顺序（不可跳步）

1. **额度合法性 > 一切**
   `refund.amount / refund.original_amount > 1.0` → **BLOCKER**，直接拒绝。
   拒绝话术只讲额度，不讲业务情理。超额退款不存在"特殊情况"。

2. **支付前置状态 > 履约讨论**
   `prior_status ∉ {succeeded, partially_refunded}` → **BLOCKER**。
   典型错误：对 `canceled` 的支付意图"再退一次"，此时资金未入账，退款无从谈起。
   正确处置是把支付意图重新走 `requires_payment_method`，而非发起退款。

3. **履约进度决定退款性质（争议 vs 常规）**
   | fulfillment_status | 退款性质 | R14 动作 |
   |---|---|---|
   | not_fulfilled / partially_fulfilled | 常规退款 | 产出请求工件，单级授权 |
   | shipped / partially_delivered / delivered | **争议退款** | 产出请求工件并标注 dispute=true，升级授权（业务负责人 + 交付证据） |
   | canceled | 异常态 | 先核对是否已 captured，是则先退款再取消订单 |

4. **状态迁移只走白名单**
   合法：`captured → partially_refunded → refunded`；`completed → canceled`（仅当未履约或退款完成后）。
   非法：**任何跳过 refunded 直达 completed 的路径**，以及 `refunded → captured` 这类回滚。

5. **事件必须补登**
   退款完成后必须出现 `refund.created` 事件，否则收入口径与资金流不一致，属 WARN 并要求补登。

## 冲突取舍

- **客户情绪 vs 额度门禁**：额度门禁永远优先。超额度申请一律拒绝，转人工协商。
- **"快一点处理" vs 授权链**：授权链优先。争议退款不得因催促而跳过人工授权。
- **多角色诉求**：若客户同时要求"退款 + 开发票红冲 + 退货"，R14 只处理退款工件；红冲移交 R03，退货入库移交 R15，并在结论中显式列出移交项。
- **部分退款 vs 整单退款**：优先考虑部分退款（更小额度、更少审批层级）；整单退款仅在交付完全未达成时建议。

## 授权层级建议

| 退款金额占原单比 | 建议授权层级 |
|---|---|
| ≤ 20% 且常规退款 | 执行人自审 + 记录 |
| 20%–100% 常规退款 | 业务负责人 |
| 任意比例**争议退款** | 业务负责人 + 交付/退货证据 |
| 任何**超额**申请 | 一律拒绝，不做授权讨论 |

## 常见误判清单

- 把 `partially_refunded` 当成"已关闭"而拒绝后续合法部分退款 → 错，仍可退剩余额度。
- 把 `requires_action` 的支付当成"已付款"而允许退款 → 错，资金未入账。
- 把已 `delivered` 的订单按常规退款放行 → 错，跳过争议升级等同于越权。
- 用"我们已与客户达成一致"替代授权声明 → 错，授权必须有具体角色，不能是泛指的"一致"。
