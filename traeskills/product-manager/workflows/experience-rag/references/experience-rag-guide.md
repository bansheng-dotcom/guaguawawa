# 经验 RAG 质量指南

## 1. 好经验库的定义

好的产品经验不是“我做过什么”，而是“下次遇到类似情况该怎么判断”。

它必须包含：

- 触发信号。
- 适用范围。
- 可执行规则。
- 不适用边界。
- 来源和可信度。

## 2. 经验和项目事实的区别

| 类型 | 放哪里 | 例子 |
| --- | --- | --- |
| 项目事实 | 项目正式文档 | 某功能接口、页面路由、需求状态 |
| 用户偏好 | `user/` 或项目经验 | 用户希望先看选项差异 |
| 纠错规则 | `experience/<项目>/纠错经验库.md` | 技术报告必须写后台兜底 |
| 跨项目经验 | `experience/global/` | 正式开发输入必须回链需求卡 |

## 2.1 发问前怎么用经验

发问前不是完整检索，而是先过 L1 Gate。目标是判断“这次真正缺的是什么”，不是把过去的问题再问一遍。

L1 只看：

- `EXPERIENCE_INDEX.md` 是否有命中。
- 当前项目经验索引、用户偏好、纠错摘要。
- 这个项目常见的实际使用场景、后台兜底、决策偏好。
- 哪些问题问了也不会改变方向。

默认不打开经验卡。输出时只保留 0-1 个关键问题。问题必须能改变后续方案、报告结构或决策路径；如果只是补模板字段，改成默认假设和风险标注。

## 2.2 重任务怎么用经验

重任务指正式报告、文档或需求包，不包括单纯提问和质问。

进入重任务前先过 Gate：L1 判断，必要时 L2 打开 3-5 条经验卡，用来建立 `experience_brief` 和重思考中间包：

- 这份文档服务哪个决策。
- 真实问题和实际场景是什么。
- 类似文档之前哪里容易让用户听不懂。
- 哪些数据、证据、兜底、验收或归档规则必须提前写。
- 哪些点只能推荐，不能替用户拍板。

重任务内部如果还要追问，默认复用入口 `experience_brief`。只有项目、workflow、产物或决策点变化，才回到 `pre-question` Gate。

## 3. 提炼方法

把任务结果提炼成经验时，按这个顺序写：

1. 触发：用户说了什么或任务出现什么问题。
2. 问题模式：抽象成下次可识别的模式。
3. 规则：下次应该怎么做。
4. 边界：什么时候不能套用。
5. 关键词：能被检索命中的词。

## 4. 常见反模式

- 把整份报告复制进经验库。
- 只写“要更清楚”，没有说怎么清楚。
- 没有触发条件，导致下次检索不到。
- 没有不适用边界，导致过度套用。
- 把候选经验当作已验证规则。
