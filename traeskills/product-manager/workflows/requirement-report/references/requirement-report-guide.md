# 需求分析报告质量指南

## 1. 这类报告做什么

需求分析报告位于“想法/反馈”和“PRD”之间。

它不负责写完整方案，而是判断一个诉求是否值得继续：

| 输入 | 输出 |
| --- | --- |
| 用户说想要的功能 | 真实问题、用户场景、成本和行动意愿 |
| 一批客户反馈 | 主题聚类、机会大小、优先级 |
| 一个产品想法 | 需求成立判断、核心假设、最低成本验证 |
| 老板或团队的方案 | 表层诉求与真正问题、取舍建议 |

进入完整报告前，先读取 `references/light-intake-and-data-gate.md`，判断数据状态、需求细节状态和本轮报告深度。没有数据不必阻塞所有分析，但必须决定是证据版、假设版，还是先补证据。

## 2. 轻量 intake 与数据门禁

| 方法 | 在需求报告里怎么用 |
| --- | --- |
| 轻量 react | 先用一句话复述当前理解，避免跑偏 |
| 轻量 grill | 只在缺口会改变方向时问 1 个关键问题 |
| 数据状态 | 判断 Data-ready / Data-partial / Data-missing but feasible / Data-missing and not feasible |
| 细节状态 | 检查用户、场景、行动、痛点成本、期望结果、约束、决策目标 |
| 无数据可行性 | 低风险探索可做假设版；高风险决策先补证据 |

## 3. 腾讯产品法融合规则

| 方法 | 在需求报告里怎么用 |
| --- | --- |
| 问对问题 | 先写表层诉求，再写真实问题和元问题 |
| 需求不是想要 | 判断是否同时有需要、行动、成本可承受 |
| 产品强度 | 说明体验提升、成本降低、新增成本 |
| 用户模型 | 写清 Who、Where、When、What、How |
| MVP | 下一步只验证核心假设，不把完整产品缩小一圈 |
| 产品规则 | 多方冲突时写清保护谁、鼓励什么、拒绝什么 |
| 数据纠偏 | 有数据时看基线、分布、总量、分组和场景 |
| 战略取舍 | 写清为什么做、为什么不做、为什么现在做 |

## 4. pm-skills 融合规则

| 来源方法 | 融合方式 |
| --- | --- |
| analyze-feature-requests | 批量需求先聚类 theme，再看数量、分群、情绪和战略匹配 |
| triage-requests | 需求按 Act Now / Plan Next / Collect More Signal / Decline or Defer 输出 |
| discover | 对不确定想法，走“想法 -> 假设 -> 优先假设 -> 实验” |
| identify-assumptions | 从 Value、Usability、Viability、Feasibility 四类找风险 |
| prioritize-features | 用 Impact、Effort、Risk、Strategic Alignment 排序 |
| Opportunity Score | 优先问题：Importance × (1 - Satisfaction)，不是优先用户给的功能名 |

## 5. 推荐报告结构

| 段落 | 必须回答 |
| --- | --- |
| 一句话结论 | 建议做、先验证、暂缓、拒绝，还是转 PRD |
| 轻量判断与数据门禁 | 当前理解、数据状态、细节状态、本轮路径 |
| 输入与来源 | 谁提出、原话是什么、频次/数量、证据强度 |
| 表层诉求 vs 真实问题 | 用户要的功能是什么，背后阻碍是什么 |
| 用户与场景 | 谁在什么时候、哪里、为了什么任务遇到问题 |
| 需求成立判断 | 需要、行动、成本是否成立 |
| 产品强度 | 体验提升、成本降低、新增成本、强/中/弱 |
| 机会/主题 | 单个需求写机会树；批量反馈写主题聚类 |
| 优先级建议 | Act Now / Plan Next / Collect More Signal / Decline or Defer |
| 最低成本验证 | 本周能做的访谈、数据查询、假门、原型或 concierge test |
| 下一步 | 转 PRD、继续调研、补证据、拒绝并说明原因 |

## 6. 需求强度判断

| 判断项 | 强 | 中 | 弱 |
| --- | --- | --- | --- |
| 痛点强度 | 高频、高成本、影响核心目标 | 明确但非核心 | 只是偏好或不便 |
| 行动信号 | 已付费、流失威胁、重复使用替代方案 | 多次表达兴趣 | 只口头想要 |
| 成本可承受 | 学习/迁移/信任成本低 | 需要引导 | 成本高于收益 |
| 战略匹配 | 直接服务当前目标 | 间接相关 | 偏离主线 |
| 验证成本 | 本周可低成本验证 | 需要小实验 | 需要大开发才知道 |

## 7. 输出优先级规则

| 优先级 | 含义 | 下一步 |
| --- | --- | --- |
| Act Now | 需求强、证据足、战略匹配、验证成本低 | 转 PRD 或小实验 |
| Plan Next | 需求成立，但时机或资源未到 | 进入候选池，补范围 |
| Collect More Signal | 方向可能对，但证据不足 | 访谈、数据查询、假门验证 |
| Decline or Defer | 与战略不符、成本过高、问题不成立 | 写清拒绝/暂缓理由 |

## 8. 常见反模式

- 把“用户要求暗色模式”直接写成“要做暗色模式”，没有问真实问题是不是长时间阅读疲劳。
- 把需求数量当优先级，不看用户分群和战略价值。
- 只写“优先级高”，不写为什么高、代价是什么。
- 需求还没成立就开始拆前端/后端任务。
- 没有证据却写成确定结论。
- 入口阶段一次性追问多个问题，把需求分析变成重度访谈。
- 没有数据却不判断“是否仍可分析”，直接写完整报告。
- 只说“建议调研”，不给本周能做的最低成本验证。
